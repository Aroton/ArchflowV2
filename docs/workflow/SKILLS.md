# workflow/SKILLS

**Explored:** 2026-11-11 · **Commit:** `f1fe689` · **Covers:** `skills/`, `src/init/`, `src/local/`, `assets/constitution/`, `skills/archflow-run/scripts/counter-review.sh`, `skills/archflow-run/scripts/cleanup.sh`, `skills/archflow-run/scripts/wait.sh`

ArchFlow ships four skills. Each is a short, portable instruction file (the Agent Skills format) in `skills/`, and the installer copies the same set into Claude Code, Codex and Antigravity. Skills do not carry workflow state or talk to a server: the only program behind them is `archflow-local` ([COMMANDS](../cli/COMMANDS.md)), and the only durable state is ordinary files in the repository and Git.

| Skill | Purpose |
| --- | --- |
| `archflow-init` | Scaffold the files `archflow-local review` reads and clean up registrations older versions left behind |
| `archflow-constitution` | Explain and edit the repository's constitution rules |
| `archflow-explore` | Produce or refresh the maintained `docs/` set |
| `archflow-run <name> [ask]` | Plan a large job once, then orchestrate it across fresh sessions with sub-agents, worktrees and cross-model review |

Claude Code and Antigravity invoke skills with `/` (`/archflow-init`); Codex uses `$` (`$archflow-init`). `archflow-run` is installed for every client but needs Claude Code as the orchestrator, because it generates `.claude/agents` and spawns worktree-isolated sub-agents; in another client it says so and stops.

## archflow-init

Runs `archflow-local init` from the repository root. It scaffolds `.archflow/config.yaml` (reviewer routing and approval rules), `.archflow/constitution/` (the repository's policy rules) and `.archflow/.gitignore`, removes the MCP registrations earlier versions of init wrote, and reports diagnostics: the Node version, whether the Claude and Codex CLIs are installed and logged in, and whether an ancestor Git ignore rule hides the generated files.

The skill explains the outcome in plain language. It refuses to overstate the isolation of reviewers (the diagnostics themselves say it is best-effort), never edits the project's own `.gitignore` (it asks the human to add exceptions instead), and treats a `scaffold-diverged` refusal as a question for the human: keep the repository's files, or re-run with `--force`. Invoking the skill authorizes scaffolding the shipped defaults, removing the legacy registrations init reports, and committing the resulting repository files; the skill performs that commit itself after the checks pass. When the human asks how reviewers are routed, it explains the `roles` and `producers` sections of the config and points at the commented example in the template.

## archflow-constitution

Explains and maintains the rules in `.archflow/constitution/`. The constitution is repository-owned policy for human trust boundaries and durable engineering constraints; it is not a style guide, a task checklist, or a way to compensate for a model's current weaknesses.

An explanation request edits nothing. A request to add or change a rule authorizes the scoped edit and its commit. The skill reads the existing rules first and works out the effective set after custom replacements; puts new rules and default replacements in `custom/` under an unused two-digit prefix; keeps each rule one independently reviewable policy with a stable kebab-case `id`; raises the `version` when contents change; and deprecates rather than deletes. It adds a `review_trigger` only when the repository genuinely wants a human decision whenever a condition appears, and the trigger must be something a reviewer can observe in the plan, the changed files or the repository, not a process fact such as who approved what. It names `enforced_by` only for mechanical checks that exist. It validates the whole rule set after editing and shows the diff and its practical effect on review. Refreshing shipped defaults is a separate, explicit `archflow-local init --force`; a rule edit never authorizes it.

It also says out loud, before changing them, that the rules about explicit human authority and a truthful plan, and the rule that guards the policy files, exist to keep a human in the loop. How rules are judged is on the [counter-review page](../review/COUNTER-REVIEW.md#the-constitution).

## archflow-explore

Produces or refreshes the maintained documentation set (this directory): caps-named pages, each with a stamp of date, commit and covered paths. In refresh mode it diffs each page's covered paths since its stamped commit and re-explores only the pages whose code changed, plus any focus area the user names. It may delegate large explorations to parallel sub-agents with complete briefs, reviews the pages against the code, checks links and stamps, and commits the documentation without another approval. It also makes sure the target repository's `CLAUDE.md` lists the pages and states the rule that a change altering behavior a page describes must update that page.

## archflow-run

The orchestrated workflow, for large jobs ("port this system", "build these fifty tasks") where approving each step would cost more than it is worth and one long session would run out of context. The run lives in `.archflow/runs/<name>/`: `PLAN.md` (the whole run: requirements, architecture, invariants, commands, model routing, milestones, declared STOPs), `milestones/M<n>.md` (one per milestone, and what that milestone is executed from: its design and its task table), `PROGRESS.md` (the live state: a status line, resume notes, task log), `DEFERRED.md` (the open deferred findings, each with the task that owns it), `HISTORY.md` (the record: session reports and closed findings), `DECISIONS.md`, `BRIEF.md`, `reviews/`, and a gitignored `packets/`. Git is the record of what merged, and where the ledger and git disagree, git wins. A run pays for a plan, a plan review and a milestone gate before its first task merges, so the skill says so when an ask is plainly a handful of tasks and recommends doing it directly.

```mermaid
flowchart LR
  X["Cheap explorers map the repository"] --> P["Planner on the strongest model<br/>writes the plan + run agents"]
  P --> R0["Cross-model plan review"]
  R0 --> S0{"STOP 0: human approves"}
  S0 --> B["Batch: packet, implementer in a worktree,<br/>one review: reviewer + cross-model review,<br/>decide findings, fixer, verify the fix,<br/>squash-merge, commit"]
  B -->|"context past about 300k tokens"| H["Handoff: resume notes in PROGRESS.md,<br/>session report in HISTORY.md, fresh session"]
  H --> B
  B --> G["Milestone gate lenses + whole-milestone<br/>counter-review, deferral pass"]
  G -->|declared STOP| S1{"Human STOP"}
  G --> B
```

**Why markdown instead of a server.** A strong orchestrator follows a written protocol reliably, and resuming needs only an honest ledger and the commit history. The trust boundaries a human needs are plain rules in the skill:

- a session on a model other than the run's orchestrator route does no run work until the human says to continue on it;
- the plan is approved before any code, and with it the review depth of every task;
- the plan is written by a planner sub-agent on the strongest model, never by the orchestrating session;
- declared STOPs end the session until the human answers;
- the run halts between STOPs only for a decision that is the human's: a change to what they get, reversing a decision they made, a risky change the plan does not cover, a kind of change the repository's rules ask a human to see, an unresolved critical finding, or an irreversible or outward-facing action;
- every other decision is the orchestrator's, and none is hidden: each is recorded with how to undo it and reported in the next message that ends a turn;
- commits stay local;
- the human is assumed not to be watching. Every message that ends a turn stands on its own: it opens with where the run stands, and it restates each open question in full, with the choices and a recommendation, instead of pointing back at an earlier message. A halt between STOPs is also written into `PROGRESS.md` with the status `AWAITING USER (halt)`, so a fresh session can ask again in full. Results that are not a reason to stop, such as a milestone gate verdict, ride along in the next closing message.

Everything else in the skill, its `PLANNING.md` and its `PROTOCOL.md` is a default whose numbers (batch size, fix rounds, task size) can be adapted and recorded in `DECISIONS.md`.

**Why the progress file holds only live state.** Every session reads `PROGRESS.md` whole, the orchestrator then carries it on every turn of that session, and the planner reads it again for each milestone it details. The first template kept the run's record in the same file: every session's handoff was added below the last, and a deferred finding that closed was ticked and left in place. On one run that file reached 141 KB, roughly 35 to 40 thousand tokens, after seven sessions:

| Part of the file | Size | What a later session used |
|---|---|---|
| Seven session handoffs | 72 KB | about 2 KB: the last one's in-flight work, carry-overs and next steps |
| Open deferred findings, 99 of them | 31 KB | all of it, but each entry only when the task that owns it starts |
| Task log | 28 KB | about 4 KB: the task ids and commits; the rest retold each review, which its review file already holds |
| Merge-check results, one section per session | 4 KB | nothing |
| Status, board, approvals, decisions to report, gate log | 6 KB | all of it |

About two thirds of the file was record.

So the file is split by who reads it. `PROGRESS.md` holds what the next session acts on, and its "Resume here" section is rewritten at each handoff instead of added to. `HISTORY.md` holds the record: each session's report and each closed finding, added at the end with a shell command and searched, not loaded, when a STOP report or a planner needs the past. Nothing is dropped, and no archive step exists to forget, because a record is written to its final place the first time. `DEFERRED.md` holds the open deferred findings. They are state, not record, but no turn needs all of them: the orchestrator searches the file for a task's entries when it writes that task's packet, and reads it whole at each milestone's deferral pass, which is what catches an entry its owner never picked up. Split this way, that run's `PROGRESS.md` comes to an estimated 15 KB. `DECISIONS.md` grows the same way (83 KB and 51 decisions on that run), so a session reads it as an index of titles with who made each decision, and opens a decision in full when the work touches its subject, always before deciding something a human's decision covers.

**Why each milestone's tasks are in their own file.** A plan in one file grows with every milestone that is detailed, and its most expensive reader is the planner, on the strongest model, which read all of it each time. On the same run `PLAN.md` went from 83 KB at approval to 404 KB by the third milestone: 226 KB of it task rows, more than half of them already merged, and a "detail" section added to the architecture for each milestone. The general-purpose spawns, most of them planners, were the costliest of the run per spawn, about 1.7 times an implementer. The split follows who reads what. The planner needs the whole plan, so it reads `PLAN.md` and as much of the earlier milestones' files as it judges the new milestone builds on. The agents that execute a milestone need only that milestone, so its file, `milestones/M<n>.md`, is written to be executed from: the task rows, and under "Design" everything those tasks need from the architecture and from earlier milestones. The orchestrator works from the current milestone's file and the plan's shared sections (requirements, invariants, commands, routing, milestones, task conventions, risks), and builds each packet from the row and the design entries it cites. Those sections are marked in the plan itself: each of their headings ends in `(shared)`, and an executing agent selects them with one `awk` command on that mark instead of opening the file, so what it reads of the plan is decided by the mark and not by its judgment of what looks relevant. Task agents read less still, the invariants alone, by the same kind of command. The plan-stage review of a later milestone receives `PLAN.md` and the new file, not the finished ones.

**Why a milestone is a unit of design.** The plan used to say what happens at a milestone's end, and not what a milestone is, so nothing told a planner where to draw one. A milestone is one complete set of work that has to be designed together: the first is what must be built and seen working before the rest can be designed well, and each later one is drawn the same way. That is also why its tasks and its design share a file, and why a later milestone is detailed when it starts, from the code the earlier ones merged. A boundary is not free: each later milestone spends a planner on the strongest model, a plan review and a gate. So work whose design depends on nothing unbuilt stays in one milestone however large it is, a milestone is typically tens of tasks, and a run whose design can be settled at the start is a single milestone.

**Why the handoff is set by context size.** The orchestrator's context is cached, and the cache holds: across 1,726 orchestrator requests on that run, 99.3% of the context sent was read from cache and no request missed it, including the ones that came after a wait of 15 minutes or more. What a long session costs is therefore not rewriting its context but re-reading it, on every turn, at a tenth of the input price. Sessions handed off after 8 to 10 tasks, as the first rule said, and by then held 400 to 630 thousand tokens, with a median near 300 thousand over about 215 turns. A handoff at 300 thousand would have re-read roughly two thirds as much, and one at 250 thousand a little over half, by a simple replay of the same sessions. The count of tasks was a stand-in for the thing that costs, so the rule now names it: `scripts/context.sh` prints the session's context size, read from the session's own transcript, and the orchestrator checks it as each task is committed. Past about 300 thousand tokens it starts nothing new, lets what is in flight finish and merge, and hands off. The mark is not lower because each handoff is a restart the human has to make: the same replay needed 20 sessions at 300 thousand where the run took 8. Claude Code documents neither the variable that names the session nor the transcript's format, so the script reports that it does not know instead of guessing, and the orchestrator falls back to the task count.

**Why review is the part that stays tooled.** ArchFlow's counter-review is what this workflow lacked when it was run by hand. Routing, snapshot views and structured reports are worth reusing rather than re-prompting. When an implementer returns, the orchestrator runs `archflow-local review` on its worktree through `scripts/counter-review.sh` ([COMMANDS](../cli/COMMANDS.md#how-to-treat-the-result) describes the script). For a task, it dispatches the opposite-family counter-reviewer and the test reviewer; the constitution reviewer runs on the plan and at each milestone gate (below). At the same moment the orchestrator spawns a fresh reviewer sub-agent, which does its own acceptance check without waiting for the counter-review. When both finish, another fresh reviewer, in merge mode, folds the counter-review into the same findings table: a point both reviewers made becomes one row naming both, since agreement between model families is strong evidence. A counter-review that cannot run blocks the merge; it is never replaced by self-review.

**Why the constitution is judged on the plan and at the gate, not on every task.** The constitution's rules are about what a change is and who approved it. The plan review answers that for the whole run, and a task that follows its approved row gives the constitution reviewer nothing new to judge. One measured run dispatched it on 62 task reviews: 681 of 682 rule judgments passed, and 30 of the 31 human-review reasons it raised were one database trigger the approved plan had already settled. Each of those was a reviewer dispatch, a row for the merge reviewer to write and a decision for the orchestrator to record. So a task's review names the counter-reviewer and the test reviewer, and the constitution reviewer runs in the plan review and in each whole-milestone counter-review, which is narrowed to that reviewer rather than skipped when a milestone is small and holds no change that only the orchestrator has read. What this gives up is timing: a rule's trigger is heard at the milestone gate, for work already merged on the run branch, instead of in the task. That is still before any STOP, push or pull request. Path approval rules are unaffected, because `archflow-local review` matches them on every call whatever roles it names. The human is told this at STOP 0 with the list of active triggers and can ask for a rule to be checked as each task lands.

**Why a change is reviewed once.** The first version of this loop sent a task back through every reviewer after every fix, and it did not converge. A fresh reviewer has no memory of the previous round, so it does not confirm fixes: it reviews from scratch, and on any nontrivial diff it finds something. Each re-review also received the whole task diff rather than the fix, so it re-judged code already judged, and each fix added new code for the next round to object to. The loop ended at its round cap, not at a clean review, and it spent two opposite-family dispatches per round. So the open-ended question, "what is wrong with this?", is now asked once per change, by two model families at the same time. After a fix the question is closed: is each finding fixed, and did the fix break anything?

```mermaid
flowchart TD
  I["Implement"] --> R["One review: in-model reviewer<br/>+ cross-model pass"]
  R --> D{"Anything to fix now?"}
  D -->|no| M["Merge and commit"]
  D -->|yes| F["Fresh fixer"]
  F --> V["Fix verify: closed check<br/>of the fix, in-model"]
  V --> H{"Can the fix be checked against<br/>something the fixer did not produce?"}
  H -->|"yes: a test with independent values, or the reference"| OK{"Resolved?"}
  H -->|"no: new derived logic, a rework, or a finding the in-model reviewer missed"| X["Delta review: cross-model,<br/>the fix alone"]
  X --> OK
  OK -->|yes| M
  OK -->|no| F
```

A fresh in-model reviewer does the fix verify. For each finding it says whether the fix resolves it and on what basis: a test whose expected values the fixer did not compute, a comparison with the run's reference, or reading alone. It can reopen only what it was asked to check, so fix rounds end.

**Why some fixes still get a cross-model look.** An in-model verifier is reliable on "does the code now do what the finding asked". It is unreliable on "is this new reasoning right", because it comes from the same model family as the fixer and tends to repeat the fixer's mistake. A test does not help when the fixer computed its expected values from the same reasoning. So a fix gets a cross-model delta review when it adds or replaces derived logic (a formula, a numerical method, an algorithm, an ordering or concurrency argument, a parser, a security check) that could be confirmed only by reading; when it fixes a correctness finding that only the opposite family caught, which marks a blind spot in the family doing the verifying; or when it is a rework rather than a patch. The delta review runs the counter-reviewer alone on a scratch worktree whose baseline is the task as it stood before the fixer, so the subject is the fix and nothing else. It is one small dispatch, where the old loop spent a full round on the whole task.

**Why the test reviewer runs once per task.** It judges the change's tests, and a fix to one finding rarely changes that verdict. Its findings are fixed and verified like any other. It sees the work again at the milestone, on the integrated result, which is the version that matters.

**Why structure is reviewed as well as behavior.** The first reviews judged a task against its acceptance criteria and the reference, and the cross-model rubric told reviewers that file organization alone is not a defect. One measured run fixed 211 findings that way, and nearly all were behavior and test findings; several of the serious ones had a structural cause that stayed in the code after the symptom was fixed (the same counters owned by two modules, one cleanup written in three paths). Structure matters more to agents than to people: a sub-agent starts cold, reads in bounded windows, and copies what is already there, so a unit that does two jobs is paid for by every later task. So the implementer is told what shape to leave, the in-model reviewer makes a separate structure pass with its own `structure` source, the cross-model rubric has a non-blocking structure criterion, and the architecture gate lens judges the milestone's code as a whole. A structure row names what the shape costs the next change. The orchestrator fixes it in the task when later tasks will build on it, and makes a larger or older one a task of its own, so a reorganization is reviewed on its own instead of inside a behavior change.

**Why the plan says where code goes.** Reviewing structure catches a poor shape after it is written, and an agent copies the shape it finds, so a shape nobody chose is still decided, by whichever task got there first. The plan's architecture section therefore carries a short code shape: the units the run adds and the one job of each, and any existing pattern in the touched code that new work must not copy. Packets carry the entries for a task's files, implementers follow existing patterns except the ones named there, and the structure pass and the architecture lens judge against it. An implementer that finds a mess it should not fix records it under `## Already there` in its notes file, and the architecture lens reads those sections, so the note reaches someone who can turn it into a cleanup task. The reviewer and the fixer are handed that notes file too; before, it was written and nobody was told to read it.

**Why a findings table holds only what needs a decision.** The orchestrator decides every row and re-reads the table on every later turn. In the measured run 549 of 760 rows were notes. Of 203 rows for work a task row had not asked for, 191 recommended keeping it and none led to a revert; another 103 said a carried finding was fixed. So sound unplanned work shares one row, fixed carried findings share one row, and an item gets a row of its own only when there is something to decide: a trim or a revert, a plan detail to correct, a finding still open. The `source` column is a fixed vocabulary, because free text there made it impossible to count afterwards what each reviewer had found.

**Why review depth is set in the plan.** A documentation update does not carry the risk of a concurrency change, and reviewing both the same way spent most of a run's opposite-family budget on work where a mistake is cheap and visible. Each task row carries a depth. `full`, the default for anything that changes behavior, gets the in-model review and the cross-model counter-review. `light`, for documentation, comments, formatting, regenerated files and renames the typecheck proves, gets the in-model review alone. The human approves the depths with the plan, the orchestrator may raise one but may not lower a behavior-changing task without a waiver, and a `light` task whose diff turns out to change behavior is raised. The whole-milestone counter-review, now the default at each gate, is the cross-model coverage for `light` tasks, for fixes that were only verified, and for how the tasks fit together. What this gives up is stated plainly in the skill's plan presentation: a patch-sized fix is not reviewed across model families on its own, so a subtle defect in one can surface at the milestone instead of in the task.

**Why the orchestrator decides most things.** The human approved a plan so the run could proceed without them, and a stop for something they would wave through costs the time the run was meant to save. Asking about everything the plan or the decision log does not explicitly cover produces questions about bug fixes already made and obvious follow-on work. So the skill draws the line by what kind of decision it is, not by whether it was written down. Plan approval makes the requirements and the declared STOPs the human's. The architecture, task rows and acceptance criteria are the approved means, which the orchestrator keeps working: it keeps or reverts work a sub-agent did beyond its task row, fixes defects found along the way, corrects a row or criterion the code has shown to be wrong, and revises its own earlier decisions. Sub-agents do necessary extra work and report it instead of stopping to ask; reviewers list it as an `unplanned` row for the orchestrator to decide, and judge work by what it does rather than by whether the plan mentioned it.

A human-review reason from the counter-review is treated the same way: as evidence the orchestrator triages, not a verdict. The constitution reviewer cannot see what the human delegated, so a reason that says only "no human approved this" about a decision that belongs to the orchestrator is decided by the orchestrator. A reason that names a decision the human kept, or a kind of change the repository's rules single out for a human (database behavior, a path under an approval rule), still stops the run. Control is kept by visibility rather than by stops: every orchestrator decision is marked as such in `DECISIONS.md` with how to undo it, and is reported in the next closing message, where the human can overturn it.

The run also reads the repository's review policy during planning and tells the human at STOP 0 which triggers will stop the run. A repository that still carries constitution rules from before the default/custom split has triggers written for an earlier, gated workflow, which match on almost every orchestrated task; the skill points that out and recommends refreshing the rules with `/archflow-init`, which is the human's decision.

**Why findings are decided, not sorted.** Severity says how bad a finding is, not whether to fix it now. The orchestrator always fixes criticals. It also fixes a major or minor when leaving it would cost more later: the finding has knock-on effects on tasks that build on it, it is a real bug rather than a style point, or no later task would own it. It defers what does not matter yet, with a reason and an owning task. A deferral is a decision to revisit, so after each milestone gate a deferral pass re-decides every open entry: fix it, carry it, or close it. Nothing stays open past the final STOP, whose report lists each won't-fix so the human can overturn it. Fix rounds stop at a default of three, and because each round after the first only checks a fix, the limit is rarely reached.

**Why "done" is accounted for requirement by requirement.** The human approves requirements and comes back to a report. Task reviews judge one diff against one row, and the orchestrator may drop or reshape tasks, so nothing in the loop itself shows that every requirement is still met. The plan numbers its requirements, the fidelity lens names the evidence for each one a milestone was to meet, and every STOP report carries that account; the final report covers all of them and says what was never run end to end. The plan chooses each gate's lenses except at the last milestone, which always runs fidelity and runtime, so a run cannot report done for something nobody ran and checked against what was asked.

**Why the orchestrator writes only rows the run has shown to be needed.** The planner's rows carry the strongest model's understanding to the cheaper agents through their invariants and checks. A row the orchestrator adds has no such author, so it is limited to work that brings its own oracle: a finding, a failed check, a deferred finding, a cleanup, a split. The failure scenario or the failing test becomes its acceptance test. Work that adds behavior or an interface the plan does not hold goes to a planner.

**Why no sub-agent waits on a review or is resumed.** A sub-agent's prompt cache lasts about five minutes. An agent that idles while a review runs, or is resumed for a fix, re-reads its whole context uncached. So the orchestrator, whose own cache lasts longer, does all the waiting on reviews, and every fix, check of a fix or answered question goes to a fresh agent that reads one packet and one review file. A check can still be slow on a busy machine, and an agent sometimes needs a result that takes longer than five minutes, so agents run their commands through the skill's `scripts/wait.sh`. It runs the command in the background and hands control back every 100 seconds while it runs; each return is a cheap turn that keeps the cache warm, where a single long blocking call would let it expire. Its `stop` command ends a stuck command together with everything that command started, so an agent never returns with a build still running.

**Why tests run in three places, and only one of them per task.** An earlier loop ran the same tests over and over: the implementer ran its check, the reviewer ran it again on the same bytes, the fixer and the fix verifier did the same, and all of it happened in several worktrees at once. Tasks took a long time and the host stalled. The same tests on the same bytes say the same thing however often they run, so each run now has one owner and one reason:

| Tier | Who | What | When |
|---|---|---|---|
| Task check | implementer or fixer | the task's own test files, by name, plus typecheck and lint | while it works, in its worktree |
| Merge check | orchestrator | the same check, once, over the test files of the tasks just merged | after the tasks in flight together have merged |
| Full validation | orchestrator | full build, full suite, slow test groups | at the session handoff and the milestone gate |

A reviewer reads the tests and the reported result instead of repeating the check: what a review adds is a judgment of what the tests prove, which a second run does not show. It runs a single test only to demonstrate a finding. The run that does not rely on an agent's report is the orchestrator's merge check, and it is a stronger one than the reviewer's was, because it covers the combination of tasks that each passed only on their own base. The task check names test files rather than selecting tests by what imports the changed code, since that selection runs most of a suite when a core file changes. A full-suite failure is attributed by reading it, and bisected only with the failing tests.

A failure in the merge check or in full validation is a fix task that goes through the per-task loop. By then the code is on the run branch and its worktree is gone, and this is the first test run that does not rely on an agent's report, so it is also where an orchestrator is most tempted to repair something in its own checkout. Anything beyond a trivial fixup that it repaired there would be code only its author had read. For the same reason a fixup made after a task's review, or a conflict resolved by hand, is listed in the review file, and a milestone that holds one runs its counter-review with every role.

**Why `wait.sh` limits how many commands run at once.** Asking agents to mind the machine's load does not hold when each one sees only its own worktree. Every sub-agent already runs its installs and checks through `wait.sh`, so the script is where the limit lives: its runner takes one of a few machine-wide slots (two unless `ARCHFLOW_WAIT_SLOTS` says otherwise) before starting the command, and a command with no free slot waits, showing a `queued` line. A slot is a `flock` on a file in a directory only that user can write, held by the runner alone, so the kernel releases it when the runner ends, however it ends, and nothing is left to clean up. Where `flock` is missing the script runs commands without a limit.

**Why a test's cost is reviewed with its coverage.** Every rule about tests used to push one way: a test per criterion, a test per fix, and a test reviewer that looks for missing coverage. Nobody saw how long a test took, so suites gained slow tests task after task, and every later task paid for them. "What tests to write" in `PLANNING.md` gives the planner the defaults for the run's test policy: a test earns its place by a failure no other test catches; test at the lowest layer where the failure can happen, with a few real tests per boundary rather than one per case; a criterion can be covered by extending a test; a fix's regression test is the cheapest one that fails without it; a slow test says what it proves that a fast one cannot; a test that is replaced is removed. Implementers report how long their check took, that figure reaches the cross-model test reviewer in the verification evidence, and both the in-model reviewer and the shipped `test-quality` criterion treat a needlessly slow or repeated test as a finding whose fix is the cheaper equivalent. The handoff records how long the full suite took, so growth is visible at the milestone gate.

**Why the wait is 100 seconds and not close to five minutes.** Fewer, longer waits would cost fewer turns, but Claude Code does not let a foreground command run that long. It moves one to the background after three minutes, or at the call's timeout when that is shorter, which is two minutes unless the call sets one. The agent then gets a notice that it will be told when the command completes, not the line to run next, and agents handled that in different ways: a second wait beside the first, reading the handle's files by hand, or polling. With the wait at four minutes, about one call in six ended this way. A wait of 100 seconds ends before either limit, so every call returns with the result or the line to run next and needs no timeout of its own.

**Why the helper scripts run inside one function.** Bash reads a script as it runs it. An install copies the skills over the installed files in place, so a script still waiting on a command would continue at its old position in the new bytes and fail with a syntax error partway through a line. `wait.sh` sits in a sleep loop and `counter-review.sh` in one review for many minutes, so each of the three scripts puts its body in `main` and calls it on the last line, which makes bash read the whole file before it runs anything.

**Why the orchestrator is not the strongest model.** An orchestrator's context is re-read on every turn of a long session, so its model sets a large part of what a run costs; a run orchestrated on Fable spent more than its judgment calls were worth. The run is designed for an Opus orchestrator at high effort, which keeps the judgment that needs the whole run in view: the requirements, the decision on each finding, the merges, the conversation with the human. A session on another model does no run work until the human says to continue on it: it stops with one message naming the model it is on, the model the run expects and how to switch. The earlier rule, to say so once and carry on, let three sessions of one run orchestrate on Fable unnoticed, because the note was one line in a message nobody was watching. A stronger model counts as a mismatch for the same reason a weaker one does: the human pays the difference on every turn, and on a subscription the strongest model's allowance is the first to run out. Planning is split by what each part needs:

- cheap explorers (Haiku at xhigh effort by default: it is cheap, and it keeps gaining past high) locate code and write what they find, with file and line pointers, into the run's `research/` folder;
- the orchestrator writes a planning brief: the ask, the settled requirements, the human's decisions and an index of that research;
- a fresh planner sub-agent on the strongest model (Fable at high effort today) reads the brief and the research, looks up whatever else it needs in the code, and writes `PLAN.md`, the decision records, the run's agents and `BRIEF.md`. What it needs to do that is in `PLANNING.md`, apart from the execution procedure, so each planner spawn reads about half of what it would otherwise, on the model whose allowance is scarcest.

The plan is always written this way, and that is one of the skill's hard rules: an error in the plan is repeated in every task built on it, while writing it is one bounded spawn rather than a session. The same planner route details a later milestone and applies any revision that changes scope, architecture or agents, or adds work the plan does not hold. Small corrections during the run, such as a task row the code has shown to be wrong or a row for a fix, stay with the orchestrator.

A question that is the human's does not stop the planner. It writes the plan on the answer it would assume and returns the question with it, the orchestrator asks at STOP 0, and only an answer that differs leads to a revision. Stopping first cost a second full planning pass for every question, on the strongest model. The planner still returns without a plan when the whole plan turns on the answer.

**Why Sonnet writes and Opus reviews.** The goal is the best automated code for the least compute, and a measured run showed where the compute goes. On the same model, writing a task cost about twice what reviewing it did ($4.30 against $2.00 on Opus), because an implementer builds, runs its check, waits and iterates while a reviewer reads and returns; writing and fixing together were the largest line of the run. Ten tasks written on Sonnet cost about a tenth of an Opus one and drew findings at a similar rate. Every task is already reviewed by a reviewer that did not write it, and every behavior change by another model family too, so the protocol spends the cheaper model on writing and the stronger one on the net: implementers and fixers run on Sonnet at high, every task review and fix verify on Opus at high, and only the mechanical steps (merging a finished counter-review, checking a rename) on Sonnet at medium. What this accepts is more first-pass mistakes from the writer, on the bet that two reviews catch them and a fix round on Sonnet is cheap. The structure review exists partly for this: a weaker writer's first cost is the shape of the code, not its behavior.

**Why a task leaves the defaults only through a hatch.** There are two different reasons to want a stronger model, and they send it to different places. A task that is hard to write gets an Opus implementer: review would catch the cheaper model's mistakes, so the cost being avoided is rework. A task that is hard to check, where an error would pass its tests and both reviewers and fail silently (concurrency, an access boundary, money, deleting data), gets a Fable reviewer with an Opus implementer: that risk is caught in review, and reviewing on Fable costs about half of implementing on it. The planner assigns these, because it sees the whole design before any code exists, but it first writes the check into the row (the invariant and the oracle that proves it) and splits or sharpens a row that seems to need a stronger writer. That is also how the strongest model's understanding reaches a cheap implementer. Each hatch carries its reason on the task row and the human approves the list at STOP 0, so the spend above the defaults is known before the run starts. Other hatches open at run time on evidence: a critical in the first review or a failed fix moves the next fixer up a model, to Opus at most, and only a critical that survives two Opus fix rounds reaches a Fable fixer. A Fable implementer happens only when the human names the task. In the measured run Fable was 46% of the Claude spend, and on a subscription its allowance ran out first while the other models had room; under these rules it is spent on the plan, the fidelity and architecture lenses, and the named reviews.

**Why routing names a model and an effort.** Effort is always named, because the models' own defaults differ, and a struggling task moves up a model before it moves up an effort level. Only a task that has shown it is hard moves up: an agent that died on a usage limit, a rate limit or a tooling error has shown nothing about the task, so it runs again on the same model when the limit allows, and the run hands off when it will not clear soon. Fixes and their checks are routed by the finding instead of the task: most findings on a hard task are small, a fix verify is a closed question with a stated basis, and a fix whose reasoning needs a second opinion gets the cross-model review of the fix, not a stronger verifier from the same family. Each handoff reports what the routing bought (tasks, findings and fix rounds per writing model, and every run-time hatch), so the human and the next milestone's planner can tell whether the cheaper writer is holding up. The table is a default the plan adapts and the human approves at STOP 0.

**Why agents are generated per kind of work.** A physics engine, a UI and database integrations need very different guidance: what correct is checked against, how the work is validated, and how it usually goes wrong. An agent specialized to its work does it better than a general one handed the same task. So the planner writes the run's agents into `.claude/agents/` from two role scaffolds, an implementer and a reviewer, and fills each with the standing guidance of one kind of work, called a domain. Guidance sits at the scope it applies to:

| It applies to | It lives in |
| --- | --- |
| every task in the run | the plan's invariants |
| every task of one kind | that kind's agents |
| one task | its packet |

A kind of work becomes a domain when its guidance really differs from the rest of the run and serves several tasks, typically three or more. Each domain gets an implementer and a reviewer, because both need the same reference and the same way of validating against it. A general pair takes everything else: glue, configuration, a kind with only a task or two (whose guidance rides in the packet), and the reviews that span the run, such as the deferral pass and the gate lenses. A run that is all one kind of work has only the general pair. The split stops where the guidance stops changing: "physics" is a domain, "collision detection" is a task. Directory, layer and model tier are not domains, since model and effort are chosen per spawn by how hard a task is.

There is no separate fixer agent. A fix needs the same guidance as the work it corrects, so a fixer is a fresh spawn of the task's implementer agent in fix mode; it has none of the implementer's context because it is a new agent. Explorers, the planner and the cross-model reviewers stay general and get what they need in a brief. The roster can change during a run: when the same finding keeps returning in one domain, the orchestrator adds the lesson to that domain's agents, and a planner adds a domain when a later milestone opens one. Prompts stay short, and the human approves the agents together with the plan. A gate teaches the agents as repeated findings do: a critical or major confirmed at a gate is something a task review let through, so the orchestrator adds what a task reviewer would have had to look for to that reviewer's lenses.

**Why a script removes the run.** The run's files and generated agents are working files: tracked on the run branch so a fresh session can resume, and out of place in a pull request. Removing them by hand meant an agent deleting files one by one and guessing which agent definitions were the run's. `scripts/cleanup.sh` does it in one step, and only when the human says to, because they may still want to read the plan, the decisions or the reviews. It is built so that it cannot lose anything:

- It removes the run directory and the agent files that are provably this run's: named for the run, with a matching frontmatter name and the description sentence "Spawned only by the <name> orchestrator". That sentence separates run `foo` with a domain `bar` from a run called `foo-bar`. Anything else under the same name, a person's own agent or a symbolic link, is kept and reported.
- It refuses while any of those files has uncommitted changes. Everything it deletes is therefore in git history, and it commits the deletion on its own, so one `git revert` brings the run back.
- It never touches a branch or a sub-agent's worktree. It lists the worktrees that remain so the orchestrator or the human can deal with them deliberately.

**Why the run cleans up worktrees and temp directories as it goes.** Claude Code keeps a sub-agent's worktree and branch whenever the agent changed anything, so every task leaves one, and the reviews build scratch worktrees under the temp directory. Nobody can tell later which of these are safe to delete. The orchestrator therefore removes a task's worktree and branch right after the task's commit, sweeps `git worktree list` at each handoff and at completion, and deletes a scratch worktree with its directory when the review returns. Scratch directories are named for the run so the cleanup script can remove any that a dead session left. `scripts/wait.sh` looks after its own handles: each time a command starts, it deletes the handles last touched over a day ago whose command has finished or whose runner is gone. Unmerged work is never swept away: a leftover worktree with changes goes to a reviewer first, then is merged or discarded on purpose.

**Requirements and design.** Requirements are sized to the work rather than a separate document stage. Milestones replace per-phase design: a milestone is detailed during planning or "detailed at start", in which case a fresh planner writes its task rows from what the run learned and they are reviewed once without a human gate unless scope or an accepted decision changes: by the plan-stage counter-review, counter-reviewer alone. Another model family reading rows the strongest model wrote adds more than a second pass on that model would, and spends none of its allowance.

## Conventions shared by the skills

- **Human gates are conversations.** Skills explain what needs attention, why it matters and the choices, in plain language, and keep digests, JSON and internal paths out unless the user asks for diagnostics.
- **A skill authorizes only what it says.** An explanation request edits nothing; an edit request authorizes the scoped change and its commit; machine-global installs are never authorized by a skill.
- **Skills state intent and trust boundaries, not workarounds.** A rule gets "never" or "must" language only when a human needs it; numbers in the skills are defaults.
- **Payloads.** Small generated JSON can be piped to a payload command on stdin; anything with authored prose or quotes goes in a file passed with `--input`, because shell quoting silently corrupts prose. A command's `{"ok": false}` result also exits nonzero, and the JSON body is the authority for the details.
- **Needs the CLI.** If `archflow-local` is missing or lacks `review`, the installed ArchFlow predates the skill; the skill tells the human to reinstall rather than installing anything itself.
