# Phase Implementation

Treat the arguments as `<task> <phase-number>`. On entry call `archflow_status` with exactly `{"schema_version":"1","task_id":"<task>","invocation":{"skill":"archflow-phase-impl","phase":<phase-number>,"intent":"resume"}}`. Every `archflow_apply` call uses that exact task and invocation plus `"action":{"offer":<next_action.offer>}` and only the submission that `next_action.expected_submission` requests; omit `submission` for `none`. This skill has no reopen: an explicit request to reopen an earlier planning boundary belongs to that boundary's skill, and the server targets only a strictly earlier PRD, task design, or phase design.

This session is the producer and orchestrator. Use only returned `resources` shaped `{role,path,access}`; select `current-artifact`, `phase-design`, `task-design`, `prd`, any `prior-implementation-notes`, and `verification-transcript` by role, use returned paths, respect access, and never read another task's files. Shared `docs/`, ordinary repository exploration, and the implementation paths the approved phase design names remain available. After every `archflow_apply`, trust its returned fresh view. If an offer is lost, stale, or refused, call `archflow_status` again. Perform one offered action per call and never start successor work in this invocation.

The server identifies the producer family from the initialize handshake of the connected client and dispatches the configured counter-review (opposite-family by default), plus the constitution review when the repository has active constitution rules; you never perform, spawn, or simulate either. The orchestrator's context is the workflow's scarcest resource: conversation with the user, human gates, triage, and synthesis stay here. Implementation chunks are sub-agent work by default: brief each chunk sub-agent completely (goal, files, pinned cross-chunk interfaces, the phase-design excerpts it needs — a sub-agent sees nothing of this conversation), run independent chunks in parallel, and integrate the results here; do inline only what is too small to justify a hand-off. Run every verification command yourself, or through a verifying sub-agent whose raw transcript you capture. Review the change through a fresh review sub-agent before submitting (below), and run independent review work in parallel: the counter-review dispatch runs in the background while any same-side review sub-agents run. Then triage, resolve, and re-enter review as needed, bounded by the attempt budget.

## Degraded operation

If either semantic workflow tool is unavailable, run read-only `archflow-local manual-status --task <task>`, report its position, and stop. Create no commit, stage nothing, edit no workflow artifact, record nothing offline, and infer no authorization. Never stage or commit while the server is unavailable; wait for restoration, then resume through the normal loop. An offer refusal is ordinary semantic recovery, not tool unavailability.

## Production and verification

If entry status returns `start-next-skill` with `next_action.offer`, apply that no-submission offer with this exact invocation before writing; it completes the hand-off from the phase design that just finished. If it names a successor without an offer, report the returned successor command and stop; this completed invocation does not own the hand-off. Otherwise require the position to be `phase-impl` with the requested phase and report a different phase or an inspection result rather than bypassing it. Never write code before the phase design is durably approved — a design file on disk or an approval in conversation is not authority.

Read the returned phase design, task design, PRD, prior implementation notes whose interfaces matter, and pinned policy from the view. Implement only the approved scope. Name every file, test, script, and identifier you create for the behavior it covers, never for the phase that produced it. Update the returned writable `task-design` and `prd` resources whenever implementation changes reality. Keep the `current-artifact` (`impl-notes.md`) current: its implementation log has `## Implementation Log: Phase <phase-number> - <name>` followed by `### Decisions Made`, `### Deviations from Plan`, `### Patterns Established`, `### Gotchas`, `### Key Interfaces`, and `### Verification Evidence`; fill each with exact paths, signatures, commands, and observed facts useful to the next phase. After all implementation and parent changes are final, propose every task-independent convention for the target project's `CLAUDE.md`; keep task-specific facts in the notes.

Run all executable verification from the phase design and exercise the changed behavior; fix failures before review. Write each verification command and its raw, unedited output to the `verification-transcript` resource; it is ignored and never enters the change set. The server digests those exact bytes into the implementation's verification evidence before the raw cache is removed at the phase boundary — the dispatched counter-review judges verification only from that digest-checked transcript, so a claim without one reads as unverified. When a counter-review fails with ENVELOPE_OVERFLOW, diagnose compact output declarations and mandatory pinned evidence; do not infer from source-file size that the approved phase must be split, and never trim authenticated evidence to evade the cap.

Submit the finished work through the current offer with `{"kind":"work-result","outcome":"succeeded","implementation":{...}}` carrying only the facts you genuinely own: the `base_commit` you started from, sorted repository-relative `outputs`, `restore_targets`, and `declared_inputs` as `{input_id,path}` entries — or the offered failed form with a concrete reason. The server derives every manifest, blob identity, digest, secret scan, accounting entry, and the verification evidence from the transcript bytes, and binds any changed governing document as a co-produced output; never author those values.

## Review and triage

Apply the offered `review`. The server derives the subject from durable authority, pins the transcript, and dispatches the configured rubric review plus the constitution review when active rules exist; never perform, spawn, simulate, or replace it. A dispatch may legitimately run many minutes, so run the call in the background rather than assuming a hang. If you run any same-side review, use `review_context.rubric` verbatim and the returned active rules; never author durable review policy.

When both workflow tools answer but a counter-review dispatch fails because the configured reviewer route itself is unavailable, ask the human for a substitute route (`model`, `effort`, optionally `provider`) and a reason. The reason is required, carries the human's words, and is recorded on the review evidence. Apply the `review` offer with `{"kind":"review-dispatch","route_override":{"reason":<the human's reason>,"counter-reviewer":{"model":<model>,"effort":<effort>}}}`, naming whichever role's route failed (`counter-reviewer` or `adjudicator`). This reviewer substitution parameterizes that one automatic counter-review and never skips or replaces it; it is the single human-authorized exception to never supplying routing, and it is not degraded operation — that stop path still governs when the workflow tools themselves are unreachable.

When `triage` is offered, submit exactly one disposition per returned finding. Accept only material defects whose resolution is reasonably likely to change required behavior, verification, an approved boundary, or important risk; use `accepted-editorial` only for non-blocking wording or formatting with no meaning change. Reject optional cleanup, stylistic preferences, and alleged blockers without a concrete consequence. Reject every `unverifiable-` evidence gap with evidence beginning `envelope-gap: ` and never accept it. The approval conversation is not a backlog-triage meeting; omit rejected non-material observations. On a remediation round, verify prior accepted revision intents first and accept a newly discovered issue only when it independently clears the same materiality bar. The constitution verdict is never triaged; triggered outcomes become human gates.

Accepted findings authorize no immediate edit. Apply the separate no-submission `revise` offer first; then fix code or parent documents as stated, rerun verification with a fresh transcript, and submit a new `work-result`. A human request for changes follows the same boundary: submit the selected opaque decision token and reason, then apply the returned `revise` offer before touching bytes.

Declare the actual revision on the next `work-result`. A **simple** revision is limited to typo, formatting, comment, or wording-only changes that alter no meaning, behavior, scope, interface, trust boundary, input, verification claim, or parent document; it keeps the current attempt count, may reuse the prior review for one hop, and always returns to the human for approval of the final bytes. A **significant** revision is anything else; uncertainty defaults to significant. It resets the attempt count to 1 and automatically runs a fresh counter-review plus constitution review. State the classification and reason in ordinary language; record a human override in either direction in `human_revision.user_override`.

## Commit authorization and the commit itself

When the current offer expects `gate-summary`, author a concise, self-contained human summary and submit `{"kind":"gate-summary","summary":<summary>}`. This opens the mandatory nonblocking `commit-authorization` presentation even when no trigger gate opened. Explain conversationally the final behavior, the verification outcome, every material finding or risk, every returned `presentation.details` entry, and each option with its consequence; ask one direct question. Keep opaque tokens, JSON, digests, internal paths, and protocol details internal unless the user asks for diagnostic or audit detail. The independent review already ran; there is no optional review at the end. (A `baseline-adoption` presentation is the exception: it resolves drift on already-reviewed bytes — typically from later commits or a merge — and is decided directly; there is no review to run, and adopting records which bytes are the baseline rather than approving new work.) At an `attempts-exhausted` presentation, explain the unresolved material defect and whether another revision appears worthwhile before asking.

Stop for explicit human judgment, then submit only `{"kind":"decision","choice":<selected presentation option token>,"reason":<human reason>}`. Never choose, infer, or record a decision for the human. A `waiver-requested` choice is not approval: apply the separate no-submission `open-waiver` offer, present the returned waiver choices in the same way, stop again, and later submit the waiver's opaque token and human reason. Denial or cancellation grants nothing.

After an explicit `authorize-commit` decision, fresh status returns `next_action.kind:"commit"` with the exact authorized commit facts and `requires_human_confirmation: true`. That flag keeps the two human moments distinct: the durable authorization is recorded, while the commit confirmation is conversational and client-held. Confirm HEAD matches `baseline` and `target_ref`, stage exactly every authorized path — run `git add -A -- :(top,literal)<path>` once per entry in `commit.paths` — show the human the staged diff and the exact `commit.message`, and obtain their explicit confirmation; no prior conversation substitutes for it. Then create the commit yourself with `commit.message` and the same top-anchored literal pathspecs, preserving unrelated index and worktree changes; on Git failure, report it and retry safely. Never edit the authorized path set or message. Call read-only `archflow_status` with the same invocation so the server observes the commit proof.

## Completion and hand-off

After the observed proof, fresh status returns the successor boundary. At the planned final phase this invocation owns its `finish-task` offer: apply it with the same invocation, then report terminal task completion without inventing another command — completion means the final planned implementation phase is committed, not that QA, staging, release, deployment, or publication occurred. At a non-final phase the successor arrives as `start-next-skill` with no offer to this invocation; never apply a `start-next-skill` offer and never start successor work. Report the server-derived successor and stop:

`Claude: /<next_action.skill> <task> <next_action.skill_args...>`

`Codex: $<next_action.skill> <task> <next_action.skill_args...>`
