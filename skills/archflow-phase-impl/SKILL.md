# Phase Implementation

Treat the arguments as `<task> <phase-number> [--counter-reviewer <model>:<effort>[@<provider>]] [--test-reviewer <model>:<effort>[@<provider>]] [--adjudicator <model>:<effort>[@<provider>]]`. The three optional trailing flags are order-independent and each may appear at most once. Parse both required positionals first; reject a route flag before them, an unknown trailing flag, a duplicate, a missing flag value, or an empty model, effort, or explicitly present provider. Each route value is one shell argument: split once at the first `:`, then split the remainder once at the first `@`, preserving shell-quoted provider whitespace. Normalize supplied roles once into `invocation.review_routes` under `counter-reviewer`, `test-reviewer`, and/or `adjudicator`; omit `review_routes` when no flag was supplied. An omitted role independently uses its live phase/base configured route; for phase implementation, an omitted and unconfigured test reviewer uses the shipped `gpt-5.6-luna` / `xhigh` default.

Construct one route-bearing invocation and repeat it identically on every status/apply call in this run, including retries, significant-revision reviews, review continuation, and final observation. On entry call `archflow_status` with `{"schema_version":"1","task_id":"<task>","invocation":{"skill":"archflow-phase-impl","phase":<phase-number>,"intent":"resume",<optional review_routes>}}`. Every `archflow_apply` call uses that exact task and invocation plus `"action":{"offer":<next_action.offer>}` and only the submission that `next_action.expected_submission` requests; omit `submission` for `none`. Never add, drop, or change normalized routes between status and apply. This skill has no reopen: an explicit request to reopen an earlier planning boundary belongs to that boundary's skill, and the server targets only a strictly earlier PRD, task design, or phase design.

This session is the producer and orchestrator. Use only returned `resources` shaped `{role,path,access}`; select `current-artifact`, `phase-design`, `task-design`, `prd`, any `prior-implementation-notes`, and `verification-transcript` by role, use returned paths, respect access, and never read another task's files. Shared `docs/`, ordinary repository exploration, and the implementation paths the approved phase design names remain available. Explore every member of the returned `repositories` list at its returned location, in reported primary-first, ordinal-secondary order, for implementation context; never read task artifacts or policy from a secondary repository, because task resources remain exclusively server-returned. A `context-only` secondary remains read-only context. A `writable` secondary becomes an implementation participant only when the work result declares its exact repository-qualified outputs and the server returns authority for those bytes. Dispatched reviewers receive named pinned repository views and, for every changed writable repository, its exact proposed tree; do not claim review coverage beyond those authenticated views. After every `archflow_apply`, trust its returned fresh view. If an offer is lost, stale, or refused, call `archflow_status` again. Perform one offered action per call and never start successor work in this invocation.

When the server returns the no-submission `refresh-stale-baseline` action, apply only that offer and use the fresh view: it retires a stale disposable baseline interface without recording a human choice. When it returns `recover-milestone-authority`, explain that the old milestone can no longer authorize continuation, apply only that no-submission offer, and continue from the fresh production boundary. Recovery preserves repository bytes but starts a significant production/review cycle; it is not approval, adoption, review, verification, or commit authority. Never infer either action from Git history or choose a baseline decision for the human.

Repository-aware drift and restore guidance names the affected member. For primary, keep the existing `archflow-local restore --task <task>` form. For a secondary, use `archflow-local restore --task <task> --repository <name>` exactly as returned; never substitute a filesystem path or attempt to restore a context-only member. One adoption choice may cover primary and secondary targets, but every adopted or restored path remains bound to its repository/path tuple. To explicitly re-anchor milestone and policy authority after an external commit, merge, or rebase, use `echo '{"target_commit":"HEAD","reason":"<reason>"}' | archflow-local set-commit-authority --task <task>`.

The server identifies the producer family from the connected client and dispatches the configured counter-review (opposite-family by default), plus constitution review when active rules exist; never perform, spawn, or simulate either. Keep conversation, human gates, triage, and synthesis here. Delegate substantial independent implementation chunks with complete briefs and integrate them here. Match each assignment to its remaining reasoning difficulty and the user's enabled models and cost preferences; routine instruction-following and copying volume do not justify stronger models. Respect the actual model controls and user choices; advice does not switch this session. Verify and integrate delegated work before submitting; use inline work for small pieces. Run every verification command yourself, or through a verifying sub-agent whose results you capture. Triage material defects and re-enter review only as the server directs.

## Degraded operation

If either semantic workflow tool is unavailable, run read-only `archflow-local manual-status --task <task>`, report its position, and stop. Create no commit, stage nothing, edit no workflow artifact, record nothing offline, and infer no authorization. Never stage or commit while the server is unavailable; wait for restoration, then resume through the normal loop. An offer refusal is ordinary semantic recovery, not tool unavailability.

## Production and verification

If entry status returns `start-next-skill` with `next_action.offer`, apply that no-submission offer with this exact invocation before writing; it completes the hand-off from the phase design that just finished. If it names a successor without an offer, report the returned successor command and stop; this completed invocation does not own the hand-off. Otherwise require the position to be `phase-impl` with the requested phase and report a different phase or an inspection result rather than bypassing it. Never write code before the phase design is durably approved — a design file on disk or an approval in conversation is not authority.

Immediately after the entry status—or after applying that hand-off, from its fresh returned view—and before reading implementation inputs or writing code, render the returned `implementation_recommendation`. For `ready`, state the exact implementation model and effort when supplied (do not invent an omitted effort), and summarize its optional `rationale` as advisory feedback, never as instructions or authority. For `unavailable`, explain the returned reason without guessing or treating missing advice as revoked authority. The recommendation is advice only: never copy it into invocation routing, claim it is the actual producer route, alter an offer, synthesize authority, or change the exact returned `next_action`.

Read the returned phase design, task design, PRD, prior implementation notes whose interfaces matter, and pinned policy from the view. Implement only the approved scope. The primary repository owns every workflow resource and `.archflow/**` path. A configured writable secondary may contain repository-source work only; a context-only secondary must not be edited. Name every file, test, script, and identifier you create for the behavior it covers, never for the phase that produced it. Update the returned writable `phase-design`, `task-design`, and `prd` resources whenever implementation changes reality, in the same work result: a changed phase design is reviewed with the implementation and needs no separate approval, while a changed task design or PRD meets the project's approval rules: shipped policy independently compares it with its human-approved baseline and requires approval for material changes, while meaning-preserving updates can advance automatically. SQL/database changes and custom repository triggers retain their own approval rules. Earlier phases' designs and notes are the record of completed work and are never edited; record a deviation from them in this phase's notes and, if the architecture changed, in the task design. Keep the `current-artifact` (`impl-notes.md`) current: its implementation log has `## Implementation Log: Phase <phase-number> - <name>` followed by `### Decisions Made`, `### Deviations from Plan`, `### Patterns Established`, `### Gotchas`, `### Key Interfaces`, and `### Verification Evidence`; fill each with exact paths, signatures, commands, and observed facts useful to the next phase. After all implementation and parent changes are final, propose every task-independent convention for the target project's `CLAUDE.md`; keep task-specific facts in the notes.

Run all executable verification from the phase design and exercise the changed behavior; fix failures before review. Record commands, exit statuses, outcomes, relevant failure details and subsequent reruns, and any unverified coverage in the implementation notes. Raw output may be saved to the optional `verification-transcript` resource; it is ignored and never enters the change set. The server pins the current log as supporting review evidence, independently of the implementation result. Large logs carry bounded beginning/end excerpts with a full-log digest, byte count, and explicit omissions; an omitted section is not evidence of success.

When review is still pending, you may compact or replace that optional log and apply the offered `review` again to repin it. Preserve commands, exit statuses, final results, relevant failures and reruns, and label omitted repetitive output. This works for previously produced results too; never rewrite archived manifests or hashes. A retry binds replacement evidence into a fresh envelope and cannot reuse child output bound to different evidence. Editing a log does not change prior reviews or approve new verification claims. Changes to code or the verification record in implementation notes use the normal revision workflow. Do not edit evidence while a dispatch is running; let it finish or cancel before replacing it. For ENVELOPE_OVERFLOW, inspect the named mandatory context and compact output declarations; raw log size alone does not require splitting the approved phase.

Before submitting, perform one bounded author check using `review_context.rubric` as guidance and the returned active rules. Do not spawn an extra generative reviewer or author durable review policy; the server-dispatched review is the only independent review. Submit the finished work through the current offer with `{"kind":"work-result","outcome":"succeeded","implementation":{...}}` carrying only the facts you genuinely own. The top-level `base_commit`, sorted repository-relative `outputs`, `restore_targets`, and `declared_inputs` are the primary section. Add `repositories`, sorted by configured ordinal name, with exactly one `{name,base_commit,outputs,restore_targets,declared_inputs}` section for every writable secondary; include an output-empty scan-only section, omit every context-only member, and keep `input_id` unique across all sections. Secondary paths are relative to that member and may never name `.archflow/**`. The server derives every manifest, blob identity, digest, secret scan, and accounting entry, and binds any changed governing document as a co-produced primary output; never author those values.

## Review and triage

Apply the offered `review`. Its subject is the declared add, modify, delete, and rename outputs, co-produced documents, and their current post-change behavior. Unchanged repository snapshots, upstream documents, and declared inputs are evidence for dependencies and interfaces, not additional review subjects. The server pins any current verification log and dispatches the configured rubric and constitution review; never perform, spawn, simulate, or replace it. A dispatch may legitimately run many minutes, so run the call in the background rather than assuming a hang.

When both workflow tools answer but `dispatch_failure` reports that the selected counter-reviewer or adjudicator route failed, or reports that the test-reviewer route failed, explain the safe message, failed role, and declared/configured route facts it returns, and name the repository when the failure names one. An invalid or unavailable invocation route never falls back to configuration, and the skill never drops or changes its normalized route. The server retries positively classified transient failures twice on that same route. While returned `dispatch_failure.recovery.status` is `retrying`, keep observing the existing review operation; do not request human intervention or launch a second review. Only an exhausted or repair-required failure needs the conversation below. Offer the exact safe choices: repair the declared or configured route and resume with one identically normalized invocation, or ask the human for a one-dispatch retry on the repaired route or substitute route (`model`, `effort`, optionally `provider`) and a reason. The reason is required, carries the human's words, and is recorded on the review evidence. Apply the still-current `review` offer with `{"kind":"review-dispatch","route_override":{"reason":<the human's reason>,"<failed-role>":{"model":<model>,"effort":<effort>}}}` using exactly the returned failed role (`counter-reviewer`, `test-reviewer`, or `adjudicator`). A supplied `route_override` wins only for that dispatch, never becomes invocation routing or config, and remains distinctly human-authorized; invocation-declared routing is normal run input and is never described as human- or controller-authenticated. This substitution parameterizes that one automatic review child and never skips or replaces it; it is not degraded operation — that stop path still governs when the workflow tools themselves are unreachable.

If `partial_review_reports` is returned, read the available feedback while following the retry action. The server reuses successful siblings; incomplete coverage does not authorize completion.

When `triage` is offered with `review_reports`, assess each concern on its evidence and concrete consequence. Check the relevant code and tests before accepting a claim that behavior or verification is missing. Treat the PRD and design as context for intent and constraints: plan discrepancies need a concrete consequence, and a real defect matters even when the plan never mentioned it. Submit `{"kind":"triage","response":{"decision":"finish","rationale":"..."}}` to finish, or use `decision:"revise"` with a rationale and `reviewers:[{"reviewer_id":"...","request":"..."}]` naming the previous reviewers needed to verify the changes. Use `decision:"escalate"` with the question and rationale when human judgment is needed. Reports are information: their formatting, categories, and recommendations do not dictate your decision. Resolve supported material concerns and dismiss disproved, speculative, or non-material suggestions. Finish when no supported material issue remains; agreement on every suggestion is unnecessary. Seek human judgment through the offered escalation path when an important unresolved decision needs it. Do not add another AI call just to interpret the reports. For an archived review that still returns structured `findings`, use its existing disposition submission until the next fresh review.

For a localized correction, use `{"kind":"triage","response":{"decision":"revise-minor","rationale":"<why the intended corrections are minor>"}}` without reviewer selection. This option is available by default: typos, formatting, comments, or a short clarification of established intent can qualify. A paragraph gaining a little explanatory detail is fine; coordinated rewrites across sections, new requirements, behavior changes, or changed verification commitments need ordinary review. Judge consequence and breadth from the actual diff, without paragraph-count rules or another classification call. Batch the corrections, apply the returned no-submission `revise` offer before editing, and run applicable automated checks. Submit `review_revision:{"classification":"minor","rationale":"<what actually changed>"}` alongside the succeeded `work-result` facts. If the change grew, declare `classification:"significant"` to trigger fresh review. Minor revisions reuse the original review group once, including constitution and phase-design effort evidence; they cannot clear unresolved policy requirements or bypass returned human approvals. Disclose the unreviewed correction in the final summary. Omit `review_revision` outside this pending revision.

A revision response authorizes no immediate edit. Apply the separate no-submission `revise` offer first, update the work and any parent documents made inaccurate, run appropriate verification, and submit a fresh `work-result`. The selected reviewers receive their previous feedback and your verification requests. Ask them to verify the changes and consequential regressions, not perform another comprehensive review. Constitution review remains separate; its failures and configured human approvals still follow the returned actions.

Declare the actual revision on the next `work-result`. A **simple** revision is limited to typo, formatting, comment, or wording-only changes that alter no meaning, behavior, scope, interface, trust boundary, input, verification claim, or parent document; it keeps the current attempt count, may reuse the prior review for one hop, and always returns to the human for approval of the final bytes. A **significant** revision is anything else; uncertainty defaults to significant. It resets the attempt count to 1 and automatically runs a fresh counter-review plus constitution review. State the classification and reason in ordinary language; record a human override in either direction in `human_revision.user_override`. On a successful human-revision submission, include `human_revision` alongside the other work-result facts, for example `"human_revision":{"classification":"significant","rationale":"Added validation rules and test cases, changing verification commitments."}`. This declaration describes your judgment; it is distinct from server-owned revision counters. Omit it for work that does not complete a pending human-requested revision.

## Commit authorization and the commit itself

Only when the current offer expects `gate-summary`, author a concise, self-contained human summary and submit `{"kind":"gate-summary","summary":<summary>}`. This opens the returned nonblocking human presentation. Explain conversationally the final behavior across every changed repository, the verification outcome, every material finding or risk, every returned `presentation.details` entry, and each option with its consequence. Present every returned `presentation.reasons` entry and make `presentation.class:"exception"` conspicuous; the authenticated archived request—not the gate summary or current config—is the reason source. Summarize which reviewers ran, what changed in response, and any consequential residual concerns. Use the report metadata; do not invent finding counts or reviewer agreement. Ask one direct question. Every returned `presentation` requires explicit human judgment. Keep opaque tokens, JSON, digests, internal paths, and protocol details internal unless the user asks for diagnostic or audit detail. The independent review already ran; there is no optional review at the end. Never synthesize a commit-authorization gate when the server returns direct commit facts. (A `baseline-adoption` presentation is the exception: it resolves drift on already-reviewed bytes — typically from later commits or a merge — and is decided directly; there is no review to run, and adopting records which bytes are the baseline rather than approving new work.) At an `attempts-exhausted` presentation, explain the unresolved material defect and whether another revision appears worthwhile before asking.

When a `presentation` is returned, stop for explicit human judgment, then submit only `{"kind":"decision","choice":<selected presentation option token>,"reason":<human reason>}`. Never choose, infer, or record a decision for the human. A `waiver-requested` choice is not approval: apply the separate no-submission `open-waiver` offer, present the returned waiver choices in the same way, stop again, and later submit the waiver's opaque token and human reason. Denial or cancellation grants nothing. If no presentation is returned, do not stop for a human decision; follow the fresh server-returned action directly.

When fresh status returns `next_action.kind:"commit"`, execute only its authenticated commit facts. The optional `commit.repository` names the repository and its freshly resolved location; omission means primary. Run every Git command with `git -C <repository.location>` for a secondary, confirm that member's identity, symbolic target, HEAD, target OID, and baseline, then stage exactly every authorized path — run `git -C <location> add -A -- :(top,literal)<path>` once per entry in `commit.paths` — inspect that repository's staged diff and exact `commit.message`, preserve unrelated index and worktree changes, and create the commit there with that message and the same top-anchored literal pathspecs. Never roll back or repeat an earlier repository commit when a later one fails; status preserves proved milestones and returns the first remaining repository. Never edit the returned path set or message, and never invent or request a second human confirmation: the returned facts already derive from either the matching ordinary approval or authenticated no-wait rule authority. The authenticated action expects you to create the commit yourself rather than through an inferred or unauthenticated operation, and the read-only `archflow_status` you call afterwards with the same invocation is what observes the commit proof for each repository before the server returns another commit.

## Completion and hand-off

After the observed proof, fresh status returns the successor boundary. At the planned final phase this invocation owns its `finish-task` offer: apply it with the same invocation, then report terminal task completion without inventing another command — completion means the final planned implementation phase is committed, not that QA, staging, release, deployment, or publication occurred. At a non-final phase the successor arrives as `start-next-skill` with no offer to this invocation; never apply a `start-next-skill` offer and never start successor work. Report the server-derived successor and stop:

## Automation responsibility

Continue the current skill through production, required review, material remediation, verification, and every authenticated commit. Use further review only when its expected value justifies the cost. The default limit remains five completed rounds; retries do not consume rounds. Finish at any round, including the limit, when no supported material issue remains; repeated reviewer disagreement alone is not a reason for more work. More review beyond the limit requires the returned human intervention. Use returned `progress` to explain the pipeline step, review budget, retry state, and boundary without inferring authority from counters. The shipped defaults require human review for the initial PRD and overall design, material amendments to their approved decisions, and SQL/database changes, including embedded queries, ORM operations, and schema/data migrations. Access-control, public-contract, cryptography, and control-plane changes within the approved plan receive automatic review and remediation; their category alone does not require a human. Repository-configured triggers still apply. Resolve routine findings and supported retries autonomously; escalate an unresolved consequential decision, exhausted remediation, unavailable required review or verification, or uncertain authority through the returned action. Do not invent an approval or bypass a returned gate. After an autonomous commit, report completion, verification, the commit, and the next skill without an authorization menu.

At `start-next-skill`, the completed invocation reports the exact successor and stops. The user's launch of that successor is the transition decision; it is not another approval of the completed result. An external controller sees this as `awaiting-transition` in automation status v3. Never treat `awaiting-client`, automatic recovery, or a pending transient retry as a request for human judgment.
