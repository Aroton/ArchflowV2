# Phase Implementation

Treat the arguments as `<task> <phase-number> [--counter-reviewer <model>:<effort>[@<provider>]] [--adjudicator <model>:<effort>[@<provider>]]`. The two optional trailing flags are order-independent and each may appear at most once. Parse both required positionals first; reject a route flag before them, an unknown trailing flag, a duplicate, a missing flag value, or an empty model, effort, or explicitly present provider. Each route value is one shell argument: split once at the first `:`, then split the remainder once at the first `@`, preserving shell-quoted provider whitespace. Normalize supplied roles once into `invocation.review_routes` under `counter-reviewer` and/or `adjudicator`; omit `review_routes` when neither flag was supplied. An omitted role independently uses its live phase/base configured route.

Construct one route-bearing invocation and repeat it identically on every status/apply call in this run, including retries, significant-revision reviews, review continuation, and final observation. On entry call `archflow_status` with `{"schema_version":"1","task_id":"<task>","invocation":{"skill":"archflow-phase-impl","phase":<phase-number>,"intent":"resume",<optional review_routes>}}`. Every `archflow_apply` call uses that exact task and invocation plus `"action":{"offer":<next_action.offer>}` and only the submission that `next_action.expected_submission` requests; omit `submission` for `none`. Never add, drop, or change normalized routes between status and apply. This skill has no reopen: an explicit request to reopen an earlier planning boundary belongs to that boundary's skill, and the server targets only a strictly earlier PRD, task design, or phase design.

This session is the producer and orchestrator. Use only returned `resources` shaped `{role,path,access}`; select `current-artifact`, `phase-design`, `task-design`, `prd`, any `prior-implementation-notes`, and `verification-transcript` by role, use returned paths, respect access, and never read another task's files. Shared `docs/`, ordinary repository exploration, and the implementation paths the approved phase design names remain available. Explore every member of the returned `repositories` list at its returned location, in reported primary-first, ordinal-secondary order, for implementation context; never read task artifacts or policy from a secondary repository, because task resources remain exclusively server-returned. A `context-only` secondary remains read-only context. A `writable` secondary becomes an implementation participant only when the work result declares its exact repository-qualified outputs and the server returns authority for those bytes. Dispatched reviewers receive named pinned repository views and, for every changed writable repository, its exact proposed tree; do not claim review coverage beyond those authenticated views. After every `archflow_apply`, trust its returned fresh view. If an offer is lost, stale, or refused, call `archflow_status` again. Perform one offered action per call and never start successor work in this invocation.

When the server returns the no-submission `refresh-stale-baseline` action, apply only that offer and use the fresh view: it retires a stale disposable baseline interface without recording a human choice. When it returns `recover-milestone-authority`, explain that the old milestone can no longer authorize continuation, apply only that no-submission offer, and continue from the fresh production boundary. Recovery preserves repository bytes but starts a significant production/review cycle; it is not approval, adoption, review, verification, or commit authority. Never infer either action from Git history or choose a baseline decision for the human.

Repository-aware drift and restore guidance names the affected member. For primary, keep the existing `archflow-local restore --task <task>` form. For a secondary, use `archflow-local restore --task <task> --repository <name>` exactly as returned; never substitute a filesystem path or attempt to restore a context-only member. One adoption choice may cover primary and secondary targets, but every adopted or restored path remains bound to its repository/path tuple.

The server identifies the producer family from the initialize handshake of the connected client and dispatches the configured counter-review (opposite-family by default), plus the constitution review when the repository has active constitution rules; you never perform, spawn, or simulate either. The orchestrator's context is the workflow's scarcest resource: conversation with the user, human gates, triage, and synthesis stay here. Implementation chunks are sub-agent work by default: brief each chunk sub-agent completely (goal, files, pinned cross-chunk interfaces, the phase-design excerpts it needs — a sub-agent sees nothing of this conversation), run independent chunks in parallel, and integrate the results here; do inline only what is too small to justify a hand-off. Run every verification command yourself, or through a verifying sub-agent whose raw transcript you capture. Review the change through a fresh review sub-agent before submitting (below), and run independent review work in parallel: the counter-review dispatch runs in the background while any same-side review sub-agents run. Then triage, resolve, and re-enter review as needed, bounded by the attempt budget.

## Degraded operation

If either semantic workflow tool is unavailable, run read-only `archflow-local manual-status --task <task>`, report its position, and stop. Create no commit, stage nothing, edit no workflow artifact, record nothing offline, and infer no authorization. Never stage or commit while the server is unavailable; wait for restoration, then resume through the normal loop. An offer refusal is ordinary semantic recovery, not tool unavailability.

## Production and verification

If entry status returns `start-next-skill` with `next_action.offer`, apply that no-submission offer with this exact invocation before writing; it completes the hand-off from the phase design that just finished. If it names a successor without an offer, report the returned successor command and stop; this completed invocation does not own the hand-off. Otherwise require the position to be `phase-impl` with the requested phase and report a different phase or an inspection result rather than bypassing it. Never write code before the phase design is durably approved — a design file on disk or an approval in conversation is not authority.

Read the returned phase design, task design, PRD, prior implementation notes whose interfaces matter, and pinned policy from the view. Implement only the approved scope. The primary repository owns every workflow resource and `.archflow/**` path. A configured writable secondary may contain repository-source work only; a context-only secondary must not be edited. Name every file, test, script, and identifier you create for the behavior it covers, never for the phase that produced it. Update the returned writable `phase-design`, `task-design`, and `prd` resources whenever implementation changes reality, in the same work result: a changed phase design is reviewed with the implementation and needs no separate approval, while a changed task design or PRD meets the project's approval rules (human approval by default). Earlier phases' designs and notes are the record of completed work and are never edited; record a deviation from them in this phase's notes and, if the architecture changed, in the task design. Keep the `current-artifact` (`impl-notes.md`) current: its implementation log has `## Implementation Log: Phase <phase-number> - <name>` followed by `### Decisions Made`, `### Deviations from Plan`, `### Patterns Established`, `### Gotchas`, `### Key Interfaces`, and `### Verification Evidence`; fill each with exact paths, signatures, commands, and observed facts useful to the next phase. After all implementation and parent changes are final, propose every task-independent convention for the target project's `CLAUDE.md`; keep task-specific facts in the notes.

Run all executable verification from the phase design and exercise the changed behavior; fix failures before review. Write each verification command and its raw, unedited output to the `verification-transcript` resource; it is ignored and never enters the change set. The server digests those exact bytes into the implementation's verification evidence before the raw cache is removed at the phase boundary — the dispatched counter-review judges verification only from that digest-checked transcript, so a claim without one reads as unverified. When a counter-review fails with ENVELOPE_OVERFLOW, diagnose compact output declarations and mandatory pinned evidence; do not infer from source-file size that the approved phase must be split, and never trim authenticated evidence to evade the cap.

Submit the finished work through the current offer with `{"kind":"work-result","outcome":"succeeded","implementation":{...}}` carrying only the facts you genuinely own. The top-level `base_commit`, sorted repository-relative `outputs`, `restore_targets`, and `declared_inputs` are the primary section. Add `repositories`, sorted by configured ordinal name, with exactly one `{name,base_commit,outputs,restore_targets,declared_inputs}` section for every writable secondary; include an output-empty scan-only section, omit every context-only member, and keep `input_id` unique across all sections. Secondary paths are relative to that member and may never name `.archflow/**`. The server derives every manifest, blob identity, digest, secret scan, accounting entry, and verification evidence from the transcript bytes, and binds any changed governing document as a co-produced primary output; never author those values.

## Review and triage

Apply the offered `review`. The server derives the subject from durable authority, pins the transcript, and dispatches the configured rubric review plus the constitution review when active rules exist; never perform, spawn, simulate, or replace it. A dispatch may legitimately run many minutes, so run the call in the background rather than assuming a hang. If you run any same-side review, use `review_context.rubric` verbatim and the returned active rules; never author durable review policy.

When both workflow tools answer but `dispatch_failure` reports that the selected counter-reviewer or adjudicator route failed, explain the safe message, failed role, and declared/configured route facts it returns, and name the repository when the failure names one (a read-only repository view that could not be materialized). An invalid or unavailable invocation route never falls back to configuration, and the skill never silently retries, drops, or changes its normalized route. Offer the exact safe choices: repair the declared or configured route and resume with one identically normalized invocation, or ask the human for a one-dispatch substitute route (`model`, `effort`, optionally `provider`) and a reason. The reason is required, carries the human's words, and is recorded on the review evidence. Apply the still-current `review` offer with `{"kind":"review-dispatch","route_override":{"reason":<the human's reason>,"counter-reviewer":{"model":<model>,"effort":<effort>}}}`, naming whichever role failed (`counter-reviewer` or `adjudicator`). A supplied `route_override` wins only for that dispatch, never becomes invocation routing or config, and remains distinctly human-authorized; invocation-declared routing is normal run input and is never described as human- or controller-authenticated. This substitution parameterizes that one automatic counter-review and never skips or replaces it; it is not degraded operation — that stop path still governs when the workflow tools themselves are unreachable.

When `triage` is offered, submit exactly one disposition per returned finding. Apply the Consequential Stopping Rule: accept only material defects whose resolution is reasonably likely to change required behavior, verification, an approved boundary, or important risk; use `accepted-editorial` only for non-blocking wording or formatting with no meaning change. Reject true observations that would not change required behavior or break verification with a concrete rationale (`non-material: does not change implementation or verification`). Reject optional cleanup, stylistic preferences, and alleged blockers without a concrete consequence. Reject every `unverifiable-` evidence gap with evidence beginning `envelope-gap: ` and never accept it. The approval conversation is not a backlog-triage meeting: present blocking and accepted findings in full, and give each rejected non-material finding a single line — finding and one-phrase reason — rather than a paragraph or a debate. When all consequential issues are resolved, reject remaining notes and advance. An `escalate-` finding is the exception: it names a material judgment the reviewer could not make with confidence, so it is never silently dropped — disposition it with a rationale, present it in full at the next human boundary this phase reaches, and name it in your report even when the phase advances without one. On a remediation round, verify prior accepted revision intents first and accept a newly discovered issue only when it independently clears the same materiality bar. The constitution verdict is never triaged. A rule the work does not meet, or a material departure from its plan, comes back as a `revise` offer whose detail names the rule or document and the reason; resolve it exactly like an accepted finding — fix the work or update the governing document this phase owns — and resubmit. Only a rule whose own `review_trigger` matched, or an exhausted attempt budget, reaches a human.

Accepted findings authorize no immediate edit. Apply the separate no-submission `revise` offer first; then fix code or parent documents as stated, rerun verification with a fresh transcript, and submit a new `work-result`. A human request for changes follows the same boundary: submit the selected opaque decision token and reason, then apply the returned `revise` offer before touching bytes.

Declare the actual revision on the next `work-result`. A **simple** revision is limited to typo, formatting, comment, or wording-only changes that alter no meaning, behavior, scope, interface, trust boundary, input, verification claim, or parent document; it keeps the current attempt count, may reuse the prior review for one hop, and always returns to the human for approval of the final bytes. A **significant** revision is anything else; uncertainty defaults to significant. It resets the attempt count to 1 and automatically runs a fresh counter-review plus constitution review. State the classification and reason in ordinary language; record a human override in either direction in `human_revision.user_override`.

## Commit authorization and the commit itself

Only when the current offer expects `gate-summary`, author a concise, self-contained human summary and submit `{"kind":"gate-summary","summary":<summary>}`. This opens the returned nonblocking human presentation. Explain conversationally the final behavior across every changed repository, the verification outcome, every material finding or risk, every returned `presentation.details` entry, and each option with its consequence. Present every returned `presentation.reasons` entry and make `presentation.class:"exception"` conspicuous; the authenticated archived request—not the gate summary or current config—is the reason source. Also state, in plain words, how strong the review evidence is from the returned `review_strength`: which model reviewed at what effort, whether it is the same model family as this producing session, and how many findings each round raised; treat a same-family reviewer, an effort below `high`, or a pass that came from a remediation round as something the human should hear as conspicuously as an exception, because they are approving on the strength of that evidence. Ask one direct question. Every returned `presentation` requires explicit human judgment. Keep opaque tokens, JSON, digests, internal paths, and protocol details internal unless the user asks for diagnostic or audit detail. The independent review already ran; there is no optional review at the end. Never synthesize a commit-authorization gate when the server returns direct commit facts. (A `baseline-adoption` presentation is the exception: it resolves drift on already-reviewed bytes — typically from later commits or a merge — and is decided directly; there is no review to run, and adopting records which bytes are the baseline rather than approving new work.) At an `attempts-exhausted` presentation, explain the unresolved material defect and whether another revision appears worthwhile before asking.

When a `presentation` is returned, stop for explicit human judgment, then submit only `{"kind":"decision","choice":<selected presentation option token>,"reason":<human reason>}`. Never choose, infer, or record a decision for the human. A `waiver-requested` choice is not approval: apply the separate no-submission `open-waiver` offer, present the returned waiver choices in the same way, stop again, and later submit the waiver's opaque token and human reason. Denial or cancellation grants nothing. If no presentation is returned, do not stop for a human decision; follow the fresh server-returned action directly.

When fresh status returns `next_action.kind:"commit"`, execute only its authenticated commit facts. The optional `commit.repository` names the repository and its freshly resolved location; omission means primary. Run every Git command with `git -C <repository.location>` for a secondary, confirm that member's identity, symbolic target, HEAD, target OID, and baseline, then stage exactly every authorized path — run `git -C <location> add -A -- :(top,literal)<path>` once per entry in `commit.paths` — inspect that repository's staged diff and exact `commit.message`, preserve unrelated index and worktree changes, and create the commit there with that message and the same top-anchored literal pathspecs. Never roll back or repeat an earlier repository commit when a later one fails; status preserves proved milestones and returns the first remaining repository. Never edit the returned path set or message, and never invent or request a second human confirmation: the returned facts already derive from either the matching ordinary approval or authenticated no-wait rule authority. The authenticated action expects you to create the commit yourself rather than through an inferred or unauthenticated operation, and the read-only `archflow_status` you call afterwards with the same invocation is what observes the commit proof for each repository before the server returns another commit.

## Completion and hand-off

After the observed proof, fresh status returns the successor boundary. At the planned final phase this invocation owns its `finish-task` offer: apply it with the same invocation, then report terminal task completion without inventing another command — completion means the final planned implementation phase is committed, not that QA, staging, release, deployment, or publication occurred. At a non-final phase the successor arrives as `start-next-skill` with no offer to this invocation; never apply a `start-next-skill` offer and never start successor work. Report the server-derived successor and stop:
