# Initialize ArchFlow

Run `archflow-local init` from the repository root. Translate its result into a short, conversational summary: what was initialized, anything the human must approve or trust, and the next action. Explain failures in plain language with the safe recovery action. When it refuses because a scaffold file diverged from the shipped template, name the file and offer the two choices: keep the human's version (review or delete it, then re-run) or replace every diverged scaffold file with the template via `archflow-local init --force`; run the forced form only when the human chooses it, since it also resets `.archflow/config.yaml`. Do not relay raw output or expose IDs, digests, JSON, internal managed-policy paths, or protocol codes unless the user explicitly asks for diagnostics or audit detail.

If the MCP server is unavailable after initialization, run read-only `archflow-local manual-status --task <task>`, report its position, and create no task milestone — there is no offline recording path; the server records all progress once restored. If `archflow-local` is also unavailable, reinstall with `./install.sh`, then rerun `archflow-local init` and `manual-status`. Do not infer initialization or recovery authority from files while the executables are unavailable.

Do not claim that initialization passed a host's human approval/trust boundary. Do not describe ArchFlow's best-effort dispatch context hygiene as an enforced isolation boundary.

Initialization creates no task state and no commit. It scaffolds `.archflow/.gitignore` with the single rule `/runtime/`, reports whether that nested ignore file was created or already present, and diagnoses both whether `.archflow/runtime/` is ignored and whether any path below it is already tracked. It also reports generated ArchFlow policy or MCP registration files hidden by an ancestor ignore rule. It never edits the project root `.gitignore`; ask the human to review that rule and explicitly add only the intended generated files. Ask the human conversationally to review and commit the scaffolded policy and host-registration files before starting a task; summarize their purpose instead of dumping an internal path inventory, while retaining that inventory for an explicitly requested diagnostic report.

Initialization also scaffolds the repository-level `.archflow/config.yaml` from the asset template. Explain its optional `repositories` map when relevant: `primary` is reserved for the implicit writable repository containing `.archflow/`; secondary names use task-slug syntax; paths may be absolute or relative to the primary worktree root; and an omitted mode means `context-only`. `writable` allows a phase implementation to declare changes in that repository, but grants no authority by itself: the server requires a section for every writable member, reviews every changed member's exact proposed tree, and returns authenticated commits one repository at a time. Context-only members remain read-only review context. The primary task remains the only source of task resources, policy, and workflow authority, so a secondary repository's `.archflow/` is never consulted or writable through ArchFlow. Repository declaration edits are ordinary informational config changes and status reports members primary-first followed by secondary names in ordinal order. Repository views are best-effort context hygiene, not OS isolation; multi-root projection and restore rollback are coordinated, not atomic.

The optional `overrides` section tunes reviewer routing per phase kind (`explore`, `prd`, `design`, `phase-design`, `phase-impl`): a kind may substitute the route (`model`, `effort`, optionally `provider`) of a dispatched review role (`counter-reviewer` or `adjudicator`) on top of the default `roles`. When the human asks about reviewer routing, explain that section conversationally and point at the commented example in `assets/config.template.yaml` as the reference shape.
