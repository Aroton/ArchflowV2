# Product Requirements Document

Treat the argument as `<task>`. This is a normal-mode phase skill: durable state and every server-checked value come from the local helper and the four workflow tools. Work only in `.archflow/tasks/<task>/` plus the shared documentation set under `docs/`; never read another task's files.

This session is the **producer** and workflow orchestrator — the server identifies the producer family from the initialize handshake of the connected client. The server dispatches the opposite-family counter-review, and the constitution review with it when the repository has active constitution rules; you never perform, spawn, or simulate either. The orchestrator's context is the workflow's scarcest resource: conversation with the user, human gates, triage, and synthesis stay here. Run research through sub-agents in parallel, each spawned with a complete brief — a sub-agent sees nothing of this conversation — writing bulk output to disk and returning only the conclusions the PRD needs. Plan the work, then delegate the parallelizable pieces to sub-agents; do inline only what is too small to justify a hand-off. Perform one bounded author check before recording produce, then let the server-dispatched counter-review be the independent generative review. Triage and resolve material defects; do not iterate on polish.

## Degraded operation

If any workflow tool is unavailable, run read-only `archflow-local manual-status --task <task>`, report its position, and stop — create no PRD milestone and record nothing offline, because no offline recording path exists; the MCP server records all progress. Wait for the server to be restored (reinstall with `./install.sh` if needed), then resume through the normal loop below; never create a purported PRD milestone from conversation or filenames.

## Stable rubric

Use this exact JSON object, without editing or reordering it, in the two places that carry it: the payload for the server-dispatched counter-review (never yours to perform) and the brief handed to each non-durable self-review sub-agent you spawn:

```json
{"schema_version":"1","kind":"artifact","mode":"adversarial","criteria":[{"id":"substantive-correctness","text":"Report a finding only for a material defect: leaving the artifact unchanged is reasonably likely to change a downstream design, implementation, verification, or approval decision, or create an important product, reliability, security, or workflow risk. A blocking finding must cite the exact artifact, pinned, or repository evidence; name the concrete downstream consequence; and explain why it survives the stated non-goals and priority order. Wording is blocking only when it permits materially different reasonable interpretations. If prior-triage is present, make verification of the accepted revision intents the primary task; report a previously undiscovered issue only when it clears the same materiality bar. A challenge to a prior disposition is blocking only when its revision intent was not carried out or the change introduced a material defect. Do not report optional polish, harmless wording refinements, stylistic preferences, or other observations that would not materially change an outcome.","blocking":true},{"id":"ask-fidelity","text":"Compare the PRD against the pinned verbatim user ask. Report only an omitted need, unexplained exclusion, or contradiction reasonably likely to materially change what is designed, implemented, or accepted. If the ask is not pinned, do not infer it; use unverifiable-claims only when the gap prevents a material judgment.","blocking":true},{"id":"proportionality","text":"Report only substantial scope, machinery, or process that the pinned ask does not justify and that would materially change cost, architecture, delivery, or user outcome. Do not report minor simplifications or preferred alternatives.","blocking":true},{"id":"testable-requirements","text":"Report a defect only when a requirement permits materially different reasonable interpretations or prevents meaningful verification of an important outcome. Do not request extra specificity when a reasonable implementer and verifier would reach the same result.","blocking":true},{"id":"stated-assumptions","text":"Report only an unstated assumption or unresolved human choice that could materially change scope, behavior, acceptance, or risk; harmless implementation latitude is not a finding.","blocking":true},{"id":"unverifiable-claims","text":"When missing envelope or read-only repository evidence prevents a material judgment, record one non-blocking finding naming the claim and missing evidence, with a finding_id beginning unverifiable-. Never guess. An explicit assumption is handled under stated-assumptions. Omit gaps that cannot materially affect the review, report each material gap once, and do not re-report one already named in prior-triage.","blocking":false},{"id":"advisory-observations","text":"Do not report non-material observations, optional improvements, completeness suggestions, stylistic preferences, or harmless prose refinements. A sound, decision-ready artifact should return no findings rather than a list of possible enhancements.","blocking":false}]}
```

Review against the pinned active rules status reports; the request composer derives `rubric_digest`, provenance, and every routing identity from durable authority, so never self-declare routing, model family, model, or effort and never substitute mutable worktree policy.

## Durable loop

Run `archflow-local status --task <task>`, perform exactly its `next_action`, then run status again; a failing command exits nonzero and prints a JSON error body, and the JSON `ok` field remains the authority for structured details. Use `--brief` for these routine loop iterations — it projects position, blockers, open-gate and reconciliation summaries, and the one `next_action` from the same computed status without rendered rule text, prompts, or template bodies; run full status when opening or resolving a gate or repairing. Continue until status requests human judgment or reports that the phase advanced. Do not infer state, approval, or evidence currency from Markdown, filenames, conversation, or an absent gate. When `next_action` carries a prefilled `request`, it is the preview of the call `archflow-local build-request --task <task>` composes: prefer piping the matching kind's facts to build-request, and complete a prefill by hand through `archflow-local envelope --task <task>` only when no kind composes that request — either way the resolved output, not the prefill, is the digest authority.

If `next_action` is `initialize-repository`, stop and direct the user to `archflow-init`. If it is `create-task`, pipe `{"intent_id":"initialize-task","kind":"initialize"}` to `archflow-local build-request --task <task>` and call `archflow_state` with the returned `request.input` verbatim as typed JSON — `artifact` is a JSON object and `expected_revision` is the number `0`, never strings. Initialize is the one build-request kind whose output carries no `staged` reference, because no durable task directory exists yet to hold one; the server accepts no entry point other than `prd`/`produce`/`running` at `expected_revision: 0`. For reconciliation, configuration, or inspection actions, report the helper's one safe action. Never improvise repair; use only the degraded-operation path above when a capability is actually unavailable.

Enter each pipeline step by piping `{"kind":"running","step":"<step>"}` to `archflow-local build-request --task <task>` and calling `archflow_state` with the returned `staged.reference`; the composer refuses an illegal entry with the server's own answer. `archflow_counter_review` records its own successful exit and covers both the rubric review and the constitution review; the skill records the terminal `succeeded` or `failed` state only for `produce` and `triage`. Do not send a second successful state transition after the tool returns. When material new information invalidates the current PRD mid-loop — an upstream change, the user restating the ask — do not park it for the gate or smuggle it into a triage finding: record a fresh produce running entry through build-request (`kind: "running"`, `step: "produce"`, legal from any succeeded step) and only then revise `prd.md`; downstream evidence goes stale and the loop re-runs from produce.

Pipe small generated JSON payloads to `archflow-local` commands directly on stdin (for example `printf '%s' '<json>' | archflow-local build-request --task <task>`); write any payload carrying authored prose or quotes — findings, dispositions, rubric-bearing requests, gate summaries — to a file and pass it with `--input <json-file>`, because shell quoting silently corrupts such payloads. Every tool request is resolved exactly once before the call: `archflow-local build-request --task <task>` composes and resolves each request kind named below, and `archflow-local envelope --task <task>` resolves a complete proposed request as `{"tool":…,"input":…}`, such as a status prefill — in both cases the helper resolves the `input_fingerprint` internally and returns the resolved request with its true `request_digest`, so never hand-copy a fingerprint or digest between commands, and a further `envelope` pass over build-request output is a no-op fixed point, harmless but never required. Omit `intent_id` from every build-request payload: the composer generates a fresh one and echoes it in the request and in `staged.reference`; supply an explicit `intent_id` only to replay or resume an interrupted call by reusing the id a previous envelope echoed. The MCP call sends the three-field staged reference from that output: build-request stages the resolved request at `staged.path` and echoes `staged.reference` — `schema_version`, `task_id`, `intent_id`, `request_digest` — which is the entire tool input to pass; the server loads the staged request and refuses on any digest mismatch, so the multi-kilobyte `request.input` is never transcribed. If the staged reference is unavailable, fall back to passing `request.tool` and `request.input` verbatim. Each workflow tool's success result echoes the `request_digest` it recorded: a match proves the operation's semantic fields — repository and task identity, the operation, its request fields, and the resolved input fingerprint — arrived verbatim, while `intent_id` and `expected_revision` sit outside the digest and are checked separately by intent correlation and the revision check. If the echo differs from the helper's, stop and re-run status.

To record the terminal produce result: draft `.archflow/tasks/<task>/prd.md` (with `ask.md` already written, below), then pipe `{}` to `archflow-local build-request --task <task>`. It builds the document artifact with the canonical PRD defaults — `document_path: "prd.md"` and declared input `user-ask` for `ask.md`, whose digest the helper records itself; a missing `ask.md` fails the build rather than producing an undeclared PRD — assembles the complete `archflow_state` request, and returns it already resolved and staged. Call `archflow_state` with its `staged.reference`.

If a tool reports a fingerprint mismatch, discard the pending intent, take the expected digest and safe next action from the result, rebuild the request with a fresh intent, and re-run status. This is recovery, not the normal recipe.

## Phase work

Before any clarifying conversation or research, write the user's original request verbatim to `.archflow/tasks/<task>/ask.md` — the exact words the user gave, unedited. Never summarize, paraphrase, or fold later clarifying answers into it; clarifications belong in the PRD's stated assumptions. The dispatched counter-review judges ask fidelity against exactly these bytes, so an edited ask defeats the review. If `ask.md` already exists from an earlier produce round, leave it unchanged unless the user restates the ask itself.

When status selects `produce`, research only as much as the brief needs and write `.archflow/tasks/<task>/prd.md`. Capture the problem, users, goals and non-goals, testable requirements, assumptions, risks, and success criteria. Keep the artifact useful for architecture decisions rather than prescribing implementation prematurely. The dispatched counter-review reads the repository at the pinned commit (excluding task workflow files), so repository claims are verifiable — write the PRD so each claim about existing code or context can be checked against those bytes.

Before recording the terminal produce result, perform one bounded author check: map each material ask clause to a requirement or explicit non-goal; confirm each important requirement has one reasonable interpretation and an observable success condition; surface assumptions that materially change scope, behavior, acceptance, or risk; and remove substantial scope the ask does not justify. Fix material defects found by this check. Do not spawn an additional generative reviewer or iterate on optional prose improvements here; the counter-review is the independent, server-attested review.

When status selects `counter_review`, write `{"kind":"counter-review","rubric":<the stable rubric object>}` to a file, pass it with `--input` to `archflow-local build-request --task <task>`, and call `archflow_counter_review` with the returned `staged.reference`; the artifact path is derived. The one call covers two reviews: the server dispatches the other-family rubric reviewer, which explores a read-only checkout of the repository at the pinned commit, and then — only when the pinned constitution has active rules, a decision the server makes alone — a second other-family child that performs the constitution and drift review against a sealed envelope with no checkout. Each dispatch may legitimately run many minutes — the server allows up to fifteen per dispatch — so run the call in the background rather than assuming a hang. The result reports both: the rubric verdict and a `constitution` block, where `{status:"not-run", reason:"no-active-constitution-rules"}` is normal and simply means the repository pins no active rules. Do not manufacture, summarize into authority, or edit the server-attested result.

When status selects `triage`, author exactly one disposition per rubric finding — `{"finding_id":…,"disposition":"accepted"|"accepted-editorial"|"rejected","rationale":…}` plus `revision_intent` for either acceptance and `evidence` for rejection. `accepted` is only for a material defect whose resolution is reasonably likely to change downstream design, implementation, verification, approval, or important risk. `accepted-editorial` is only for a non-blocking wording or formatting correction that changes no meaning and touches nothing cited by a blocker; the composer and server refuse it for blocking findings. Reject optional polish, harmless specificity requests, preferred phrasing, and any alleged blocker that cannot name a material consequence. On a remediation round, verify the prior accepted revision intents first; accept a newly discovered issue only when it independently clears the same materiality bar. Findings beginning `unverifiable-` are evidence gaps, not producer defects: reject them with evidence beginning `envelope-gap: ` and never accept them.

Write `{"kind":"triage","dispositions":[…]}` to a file, pass it with `--input` to `archflow-local build-request --task <task>`, and record it through `archflow_state` with the staged reference. The composer binds the current evidence set and requires exactly one disposition per finding. Any plain acceptance revises `prd.md` and re-enters fresh production and remediation review. When every acceptance is editorial, apply exactly those revision intents and record produce through the status-prefilled entry; the one-hop editorial predecessor keeps the retained reviews and constitution verdict current, and the eventual gate discloses that they evaluated the predecessor bytes. The constitution verdict is never triaged; any failing or triggering outcome becomes a human gate after rubric triage.

## Human gates

The PRD always requires an `artifact-approval` gate after the fixed point closes. Write `{"kind":"gate","summary":<text for the human>}` to a file and pass it with `--input` to `archflow-local build-request --task <task>`: the composer derives the gate kind, subject, evidence, revision, and fingerprint from durable state with `context: {"artifact_kind":"prd"}`, and you author only the summary. Present `ask.md` alongside the PRD at the gate so the user can catch a mistranscribed ask before approving against it. When status carries an `editorial_revision` block, the approved artifact is an editorial revision: present the diff against the predecessor alongside the applied revision intents, and include in the gate summary the disclosure that the retained reviews and the constitution verdict evaluated the predecessor bytes. Present the returned gate ID and optional counter-review prompt to the user, then make the blocking call to `archflow_gate` with the returned `staged.reference`.

The constitution gates (`constitution-review`, `material-drift`) are derived by the server after triage: status names the pending gate and, when a review demands more than one, reports every gate still pending; `archflow-local build-request` (kind `"gate"`) derives kind, subject, and context from retained adjudication evidence, so you author only the summary. For every open gate, re-run status and present its decision templates, paths, and complete optional counter-review prompt. Ordinary artifact approval is not a backlog-triage meeting: do not add rejected non-material review observations to its agenda. Keep durable review and triage evidence auditable, and disclose an envelope gap only when it prevented a material judgment. If status opens an `attempts-exhausted` gate, present the unresolved material defect and say plainly whether another revision is warranted. The user alone chooses whether to run the optional gate review and which decision to authorize. Ingest an elected review with `archflow-local gate-counter --task <task>`; accept any material artifact-changing result by revising the PRD and re-entering the fixed point, and reject non-material output. Record the chosen template with `archflow-local decide --task <task>` using `kind: "interface"`, then let the blocked call resume.

Keep the original `archflow_gate` input and `intent_id` for every supplemental retry; a retry adds `supplemental_outcome`, which the staged file does not carry, so pass the full `request.input` plus that field rather than the staged reference. Decline by retrying with status's exact `decline` outcome and create no review. If review is elected, record it, let the blocked call return `SUPPLEMENTAL_REVIEW_REQUIRED`, then retry with status's exact `ingest` outcome. Re-run status after ingest and retry with its exact `triage-no-change` outcome, or, for an accepted change, revise and rebuild the artifact, take the exact new subject digest from `envelope`, retry with the authenticated supersede facts plus that digest, and expect `GATE_SUPERSEDED`. A superseded gate approves nothing: re-enter produce, review, and triage to a fixed point before opening a fresh gate. Never fabricate review, triage, subject, or human-decision facts.

If the explicit decision is `waiver-requested`, it is not approval. Re-run status, construct the `archflow_waiver` origin only from the server's archived request and decision plus helper-derived digests, run `envelope` before the blocking waiver call, and handle the waiver gate through the same status/templates/prompt procedure. A denied or cancelled waiver grants nothing.

Never claim approval, select a decision, or pass the gate for the user. Stop until the user's explicit decision. After the approved gate resolves, re-run status and report the durable next action; approval in conversation alone is not authority.
