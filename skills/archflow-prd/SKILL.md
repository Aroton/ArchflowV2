# Product Requirements Document

Treat the argument as `<task>`. This is a normal-mode phase skill: durable state and every server-checked value come from the local helper and the four workflow tools. Full status returns task-scoped `resources` entries shaped `{role,path,access}`; select workflow artifacts by role and use the returned paths instead of reconstructing task paths. Never read another task's files. Shared documentation under `docs/` and ordinary repository exploration remain available when the work needs them.

This session is the **producer** and workflow orchestrator — the server identifies the producer family from the initialize handshake of the connected client. The server dispatches the opposite-family counter-review, and the constitution review with it when the repository has active constitution rules; you never perform, spawn, or simulate either. The orchestrator's context is the workflow's scarcest resource: conversation with the user, human gates, triage, and synthesis stay here. Run research through sub-agents in parallel, each spawned with a complete brief — a sub-agent sees nothing of this conversation — writing bulk output to disk and returning only the conclusions the PRD needs. Plan the work, then delegate the parallelizable pieces to sub-agents; do inline only what is too small to justify a hand-off. Perform one bounded author check before recording produce, then let the server-dispatched counter-review be the independent generative review. Triage and resolve material defects; do not iterate on polish.

## Degraded operation

If any workflow tool is unavailable, run read-only `archflow-local manual-status --task <task>`, report its position, and stop — create no PRD milestone and record nothing offline, because no offline recording path exists; the MCP server records all progress. Wait for the server to be restored (reinstall with `./install.sh` if needed), then resume through the normal loop below; never create a purported PRD milestone from conversation or filenames.

## Review policy

Run full status before review work and use its canonical `review_policy`. Use `review_policy.rubric` verbatim in any non-durable same-side review brief; never copy a rubric from skill text or author one. The server selects that same policy for the durable counter-review. Review against the pinned active rules status reports; the request composer derives `rubric_digest`, provenance, and every routing identity from durable authority, so never self-declare routing, model family, model, or effort and never substitute mutable worktree policy.

## Durable loop

Run `archflow-local status --task <task>`, perform exactly its `next_action`, then run status again; a failing command exits nonzero and prints a JSON error body, and the JSON `ok` field remains the authority for structured details. Use `--brief` for these routine loop iterations — it projects position, blockers, open-gate and reconciliation summaries, and the one `next_action` from the same computed status without rendered rule text, prompts, or template bodies; run full status when opening or resolving a gate or repairing. Continue until status requests human judgment or reports that the phase advanced. Do not infer state, approval, or evidence currency from Markdown, filenames, conversation, or an absent gate. When `next_action` carries a prefilled `request`, it is the preview of the call `archflow-local build-request --task <task>` composes: prefer piping the matching kind's facts to build-request, and complete a prefill by hand through `archflow-local envelope --task <task>` only when no kind composes that request — either way the resolved output, not the prefill, is the digest authority.

When status returns `next_action.code: "advance-phase"` or `"complete-task"` from this PRD session, pipe the small payload `{"kind":"advance"}` to `archflow-local build-request --task <task>` and call `archflow_state` with the returned `staged.reference`. Approval and hand-off are distinct durable transitions: a resolved gate does not move the phase by itself, and the advance composer succeeds only for the exact server-derived successor after rechecking the current authenticated approval. Re-run status after the call and do not return until durable status shows the phase changed to `next_action.target_phase_instance` or the task became terminal. If status no longer offers that exact action, follow its newly derived safe action instead of replaying the old request.

If `next_action` is `initialize-repository`, stop and direct the user to `archflow-init`. If it is `create-task`, pipe `{"intent_id":"initialize-task","kind":"initialize"}` to `archflow-local build-request --task <task>` and call `archflow_state` with the returned `request.input` verbatim as typed JSON — `artifact` is a JSON object and `expected_revision` is the number `0`, never strings. Initialize is the one build-request kind whose output carries no `staged` reference, because no durable task directory exists yet to hold one; the server accepts no entry point other than `prd`/`produce`/`running` at `expected_revision: 0`. For reconciliation, configuration, or inspection actions, report the helper's one safe action. Never improvise repair; use only the degraded-operation path above when a capability is actually unavailable.

Enter each pipeline step by piping `{"kind":"running","step":"<step>"}` to `archflow-local build-request --task <task>` and calling `archflow_state` with the returned `staged.reference`; the composer refuses an illegal entry with the server's own answer. `archflow_counter_review` records its own successful exit and covers both the rubric review and the constitution review; the skill records the terminal `succeeded` or `failed` state only for `produce` and `triage`. Do not send a second successful state transition after the tool returns. When material new information invalidates the current PRD mid-loop — an upstream change, the user restating the ask, or a later clarification — do not park it for the gate or smuggle it into a triage finding: record a fresh produce running entry through build-request (`kind: "running"`, `step: "produce"`, legal from any succeeded step) before changing the `user-ask` or `current-artifact` resource; downstream evidence goes stale and the loop re-runs from produce.

Pipe small generated JSON payloads to `archflow-local` commands directly on stdin (for example `printf '%s' '<json>' | archflow-local build-request --task <task>`); write any payload carrying authored prose or quotes — findings, dispositions, and gate summaries — to a file and pass it with `--input <json-file>`, because shell quoting silently corrupts such payloads. Every tool request is resolved exactly once before the call: `archflow-local build-request --task <task>` composes and resolves each request kind named below, and `archflow-local envelope --task <task>` resolves a complete proposed request as `{"tool":…,"input":…}`, such as a status prefill — in both cases the helper resolves the `input_fingerprint` internally and returns the resolved request with its true `request_digest`, so never hand-copy a fingerprint or digest between commands, and a further `envelope` pass over build-request output is a no-op fixed point, harmless but never required. Omit `intent_id` from every build-request payload: the composer generates a fresh one and echoes it in the request and in `staged.reference`; supply an explicit `intent_id` only to replay or resume an interrupted call by reusing the id a previous envelope echoed. The MCP call sends the three-field staged reference from that output: build-request stages the resolved request at `staged.path` and echoes `staged.reference` — `schema_version`, `task_id`, `intent_id`, `request_digest` — which is the entire tool input to pass; the server loads the staged request and refuses on any digest mismatch, so the multi-kilobyte `request.input` is never transcribed. If the staged reference is unavailable, fall back to passing `request.tool` and `request.input` verbatim. Each workflow tool's success result echoes the `request_digest` it recorded: a match proves the operation's semantic fields — repository and task identity, the operation, its request fields, and the resolved input fingerprint — arrived verbatim, while `intent_id` and `expected_revision` sit outside the digest and are checked separately by intent correlation and the revision check. If the echo differs from the helper's, stop and re-run status.

To record the terminal produce result, write the full-status `current-artifact` resource (with the `user-ask` resource already written, below), then pipe `{}` to `archflow-local build-request --task <task>`. The helper uses those canonical resource paths, assembles the complete `archflow_state` request, and returns it already resolved and staged. Call `archflow_state` with its `staged.reference`.

If a tool reports a fingerprint mismatch, discard the pending intent, take the expected digest and safe next action from the result, rebuild the request with a fresh intent, and re-run status. This is recovery, not the normal recipe.

## Phase work

Before any clarifying conversation or research, write the user's original request verbatim to the full-status `user-ask` resource — the exact words the user gave, unedited. Keep that original request unchanged as the beginning of the file. If clarification is needed, append this section after the original request, creating the heading only once:

```markdown
## Clarifications

### Question 1

<the producer's exact question>

### Answer 1

<the user's exact reply>
```

Append each numbered `### Question N` with the producer's exact words **before presenting it to the user**, then append the matching `### Answer N` with the user's exact reply as soon as it arrives. Do not summarize, paraphrase, silently resolve, or move clarification dialogue only into session context or PRD assumptions. An unanswered question remains in the resource without an invented answer, making the interrupted conversation resumable. When one reply answers several questions asked together, preserve that exchange as one question-and-answer entry rather than rewriting it. The dispatched counter-review judges ask fidelity against this entire pinned record. If the `user-ask` resource already has content, preserve its original request and prior clarification entries; if a clarification becomes necessary after a terminal produce result was recorded, re-enter `produce` before appending so no current evidence remains bound to older ask bytes.

When status selects `produce`, research only as much as the brief needs and write the full-status `current-artifact` resource. Capture the problem, users, goals and non-goals, testable requirements, assumptions, risks, and success criteria. Keep the artifact useful for architecture decisions rather than prescribing implementation prematurely. The dispatched counter-review reads the repository at the pinned commit (excluding task workflow files), so repository claims are verifiable — write the PRD so each claim about existing code or context can be checked against those bytes.

Before recording the terminal produce result, perform one bounded author check: map each material ask clause to a requirement or explicit non-goal; confirm each important requirement has one reasonable interpretation and an observable success condition; surface assumptions that materially change scope, behavior, acceptance, or risk; and remove substantial scope the ask does not justify. Fix material defects found by this check. Do not spawn an additional generative reviewer or iterate on optional prose improvements here; the counter-review is the independent, server-attested review.

When status selects `counter_review`, pipe `{"kind":"counter-review"}` to `archflow-local build-request --task <task>` and call `archflow_counter_review` with the returned `staged.reference`; the server derives the artifact path and canonical review policy. The one call covers two reviews: the server dispatches the other-family rubric reviewer, which explores a read-only checkout of the repository at the pinned commit, and then — only when the pinned constitution has active rules, a decision the server makes alone — a second other-family child that performs the constitution and drift review against a sealed envelope with no checkout. Each dispatch may legitimately run many minutes — the server allows up to fifteen per dispatch — so run the call in the background rather than assuming a hang. The result reports both: the rubric verdict and a `constitution` block, where `{status:"not-run", reason:"no-active-constitution-rules"}` is normal and simply means the repository pins no active rules. Do not manufacture, summarize into authority, or edit the server-attested result.

When status selects `triage`, author exactly one disposition per rubric finding — `{"finding_id":…,"disposition":"accepted"|"accepted-editorial"|"rejected","rationale":…}` plus `revision_intent` for either acceptance and `evidence` for rejection. `accepted` is only for a material defect whose resolution is reasonably likely to change downstream design, implementation, verification, approval, or important risk. `accepted-editorial` is only for a non-blocking wording or formatting correction that changes no meaning and touches nothing cited by a blocker; the composer and server refuse it for blocking findings. Reject optional polish, harmless specificity requests, preferred phrasing, and any alleged blocker that cannot name a material consequence. On a remediation round, verify the prior accepted revision intents first; accept a newly discovered issue only when it independently clears the same materiality bar. Findings beginning `unverifiable-` are evidence gaps, not producer defects: reject them with evidence beginning `envelope-gap: ` and never accept them.

Write `{"kind":"triage","dispositions":[…]}` to a file, pass it with `--input` to `archflow-local build-request --task <task>`, and record it through `archflow_state` with the staged reference. The composer binds the current evidence set and requires exactly one disposition per finding. Any plain acceptance revises the `current-artifact` resource and re-enters fresh production and remediation review. When every acceptance is editorial, apply exactly those revision intents and record produce through the status-prefilled entry; the one-hop editorial predecessor keeps the retained reviews and constitution verdict current, and the eventual gate discloses that they evaluated the predecessor bytes. The constitution verdict is never triaged; any failing or triggering outcome becomes a human gate after rubric triage.

## Human gates

The PRD always requires an `artifact-approval` gate after the fixed point closes. Write `{"kind":"gate","summary":<text for the human>}` to a file and pass it with `--input` to `archflow-local build-request --task <task>`: the composer derives the gate kind, subject, evidence, revision, and fingerprint from durable state with `context: {"artifact_kind":"prd"}`, and you author only the summary. Present the user's ask and the PRD together in ordinary language so the user can catch a mistranscribed ask. When status carries an `editorial_revision` block, show the small diff and explain that the retained reviews evaluated its predecessor. Make the blocking `archflow_gate` call with the returned `staged.reference`, keeping the bindings internal.

The constitution gates (`constitution-review`, `material-drift`) are derived by the server after triage. For every open gate, re-run status and use its human-facing presentation. Explain conversationally what is ready, material findings or risks, why the decision matters, and each available choice with its consequence, then ask one direct question. Never dump gate IDs, digests, JSON, decision templates, internal paths, or protocol codes unless the user explicitly asks for diagnostics or audit detail. The normal opposite-client counter-review already ran automatically before the gate; there is no optional gate review. Ordinary artifact approval is not a backlog-triage meeting: do not add rejected non-material review observations to its agenda. At an `attempts-exhausted` gate, explain the unresolved material defect and whether another revision appears worthwhile. Record the user's chosen server-issued option and reason through `archflow-local decide --task <task>`; the helper supplies all live bindings.

If the human requests changes, apply them and classify the actual diff. A **simple** revision is limited to typo, formatting, comment, or wording-only changes that alter no meaning, behavior, scope, interface, trust boundary, input, verification claim, or parent document. It keeps the current attempt count, may reuse the prior review and constitution evidence for one hop, shows the exact small diff, and always returns to the human for approval of the final bytes. A **significant** revision is anything else; uncertainty defaults to significant. It archives the prior evidence as history, resets the attempt count to 1, and automatically runs a fresh opposite-client counter-review plus constitution review before a new gate. State the classification and reason in ordinary language. The human may override it in either direction, and the durable record must reflect that override. The `attempts-exhausted` gate counts only attempts since the latest significant human revision.

If the explicit decision is `waiver-requested`, it is not approval. Re-run status, construct the `archflow_waiver` origin only from the server's archived request and decision plus helper-derived digests, run `envelope` before the blocking waiver call, and present the waiver gate through the same conversational procedure. A denied or cancelled waiver grants nothing.

Never claim approval, select a decision, or pass the gate for the user. Stop until the user's explicit decision. After the approved gate resolves, re-run status and perform the server-derived hand-off described above; approval in conversation alone is not authority. Report the next skill only after fresh status proves the durable phase changed.
