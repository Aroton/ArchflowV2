# Product Requirements Document

Treat the arguments as `<task> [--counter-reviewer <model>:<effort>[@<provider>]] [--adjudicator <model>:<effort>[@<provider>]]`. The two optional trailing flags are order-independent and each may appear at most once. Parse required positionals first; reject a route flag before them, an unknown trailing flag, a duplicate, a missing flag value, or an empty model, effort, or explicitly present provider. Each route value is one shell argument: split once at the first `:`, then split the remainder once at the first `@`, preserving shell-quoted provider whitespace. Normalize supplied roles once into `invocation.review_routes` under `counter-reviewer` and/or `adjudicator`; omit `review_routes` when neither flag was supplied. An omitted role independently uses its live phase/base configured route.

This session is the producer and workflow orchestrator. Durable truth comes from the two semantic workflow tools. Construct one route-bearing invocation and repeat it identically on every status/apply call in this run, including reopen/resume, retries, significant-revision reviews, review continuation, and final observation. On entry call `archflow_status` with `{"schema_version":"1","task_id":"<task>","invocation":{"skill":"archflow-prd","intent":"resume",<optional review_routes>}}`. Every `archflow_apply` call uses that exact task and invocation plus `"action":{"offer":<next_action.offer>}` and only the submission that `next_action.expected_submission` requests; omit `submission` for `none`. Use `intent:"reopen"` only when the human explicitly asked to reopen the PRD; after status explains the impact, apply the offered action with the same normalized routes and `{"kind":"reopening-request","request":<the human's exact request>}`. After that succeeds, call `archflow_status` again with the exact `intent:"resume"` invocation above; the one-shot reopen invocation does not own production. Never add, drop, or change normalized routes between status and apply, turn an ordinary correction, review finding, or resumed session into a reopen.

Use only the returned `resources` entries shaped `{role,path,access}`: select workflow artifacts by role, use their returned paths, respect their access, and never read another task's files. Shared `docs/` and ordinary repository exploration remain available. The returned `repositories` list names every repository the task spans with its resolved location, mode, and current commit; use every member at its returned location for repository research and context, in the reported primary-first, ordinal-secondary order, and do not discover task artifacts or policy from a secondary repository, because task resources remain exclusively server-returned. Every dispatched reviewer sees the same repositories as read-only pinned snapshots and cites files as `<name>/<path>`. Context-only repositories are never written or committed; a `writable` secondary can receive declared implementation changes later, which are reviewed and committed per repository, but PRD work writes nothing outside the returned resources. After every `archflow_apply`, use its returned fresh view as authority; if a response is lost or an offer is refused, call `archflow_status` again and follow the newly offered action. Never consume a successor offer in this invocation.

The server identifies the producer family from the connected client and dispatches the configured counter-review (opposite-family by default), plus constitution review when active rules exist; never perform, spawn, or simulate either. Keep conversation, human gates, triage, and synthesis here. Delegate substantial parallel research with complete briefs and use inline work for small pieces. Triage material defects; do not iterate on polish.

Review feedback is a small per-round response: `outcome:"issues_found"` with actionable `feedback`, or `outcome:"no_issues_found"` with an explicit short signoff. Read and reason as deeply as needed; mostly reading is an efficiency goal, not a quota. Do not author a separate review document, quote whole source files, narrate the investigation, or recap resolved findings. On re-review, use the revision diff and previous feedback to verify the fixes and their consequential regressions. A missing, failed, or interrupted reviewer is never signoff. The calling agent owns triage and follows the returned workflow action; a reviewer outcome does not grant approval. Historical reports without an outcome keep their original meaning.

## Degraded operation

If either semantic workflow tool is unavailable, run read-only `archflow-local manual-status --task <task>`, report its position, and stop. Create no milestone, edit no workflow artifact, record nothing offline, and never infer authorization. A stale or rejected offer is normal semantic recovery, not tool unavailability.

## Production and review

For a new task, the first offered action expects `task-ask`. Before research or clarification, apply it with `{"kind":"task-ask","text":<the user's exact original ask>}`. Do not paraphrase. The server owns initialization and the ask-history record. On an explicit reopen, send the exact human correction only as `reopening-request`; the server derives the target and appends PRD ask history.

When the offered action opens production, apply its no-submission offer before editing. Read the returned `user-ask` and other relevant resources, then research only as much as the brief needs. Run research through parallel sub-agents with complete briefs when it is substantial; keep conversation, clarification, synthesis, and decisions here. Record clarification questions and exact answers in the writable ask resource when returned, preserving this form:

```markdown
## Clarifications

### Question 1

<exact question>

### Answer 1

<exact reply>
```

Write each question before presenting it. An unanswered question remains without an invented answer. Write the `current-artifact` as a PRD covering the problem, users, goals and non-goals, testable requirements, assumptions, risks, and observable success criteria. Keep it useful for design rather than prescribing implementation. Before submitting, perform one bounded author check using `review_context.rubric` as guidance and the returned active rules, focusing on ask fidelity, ambiguity, observable acceptance, material assumptions, and unjustified scope. Do not spawn an extra generative reviewer or author durable review policy; the server-dispatched review is the only independent review.

Submit the finished bytes through the current offer with `{"kind":"work-result","outcome":"succeeded"}` (or the offered failed form with a concrete reason). Do not supply paths, policy, routing, digests, server-owned revision counters, or other server-owned facts. Apply the next `review` offer. The server selects the configured rubric and constitution review (opposite-family by default) from the returned `review_context`; never perform, spawn, simulate, or replace it.

When both workflow tools answer but `dispatch_failure` reports that the selected counter-reviewer or adjudicator route failed, explain the safe message, failed role, and declared/configured route facts it returns, and name the repository when the failure names one (a read-only repository view that could not be materialized). An invalid or unavailable invocation route never falls back to configuration, and the skill never drops or changes its normalized route. The server retries positively classified transient failures twice on that same route. While returned `dispatch_failure.recovery.status` is `retrying`, keep observing the existing review operation; do not request human intervention or launch a second review. Only an exhausted or repair-required failure needs the conversation below. Offer the exact safe choices: repair the declared or configured route and resume with one identically normalized invocation, or ask the human for a one-dispatch retry on the repaired route or substitute route (`model`, `effort`, optionally `provider`) and a reason. The reason is required, carries the human's words, and is recorded on the review evidence. Apply the still-current `review` offer with `{"kind":"review-dispatch","route_override":{"reason":<the human's reason>,"counter-reviewer":{"model":<model>,"effort":<effort>}}}`, naming whichever role failed (`counter-reviewer` or `adjudicator`). A supplied `route_override` wins only for that dispatch, never becomes invocation routing or config, and remains distinctly human-authorized; invocation-declared routing is normal run input and is never described as human- or controller-authenticated. This substitution parameterizes that one automatic counter-review and never skips or replaces it; it is not degraded operation — that stop path still governs when the workflow tools themselves are unreachable.

## Triage and revision

If `partial_review_reports` is returned, read the available feedback while following the retry action. The server reuses successful siblings; incomplete coverage does not authorize completion.

When `triage` is offered with `review_reports`, assess each concern on its evidence and concrete consequence. Check the relevant code and tests before accepting a claim that behavior or verification is missing. Treat the PRD and design as context for intent and constraints: plan discrepancies need a concrete consequence, and a real defect matters even when the plan never mentioned it. Submit `{"kind":"triage","response":{"decision":"finish","rationale":"..."}}` to finish, or use `decision:"revise"` with a rationale and `reviewers:[{"reviewer_id":"...","request":"..."}]` naming the previous reviewers needed to verify the changes. Use `decision:"escalate"` with the question and rationale when human judgment is needed. Reports are information: their formatting, categories, and recommendations do not dictate your decision. Resolve supported material concerns and dismiss disproved, speculative, or non-material suggestions. Finish when no supported material issue remains; agreement on every suggestion is unnecessary. Seek human judgment through the offered escalation path when an important unresolved decision needs it. Do not add another AI call just to interpret the reports. For an archived review that still returns structured `findings`, use its existing disposition submission until the next fresh review.

For a localized correction, use `{"kind":"triage","response":{"decision":"revise-minor","rationale":"<why the intended corrections are minor>"}}` without reviewer selection. This option is available by default: typos, formatting, comments, or a short clarification of established intent can qualify. A paragraph gaining a little explanatory detail is fine; coordinated rewrites across sections, new requirements, behavior changes, or changed verification commitments need ordinary review. Judge consequence and breadth from the actual diff, without paragraph-count rules or another classification call. Batch the corrections, apply the returned no-submission `revise` offer before editing, and run applicable automated checks. Submit `review_revision:{"classification":"minor","rationale":"<what actually changed>"}` alongside the succeeded `work-result` facts. If the change grew, declare `classification:"significant"` to trigger fresh review. Minor revisions reuse the original review group once, including constitution and phase-design effort evidence; they cannot clear unresolved policy requirements or bypass returned human approvals. Disclose the unreviewed correction in the final summary. Omit `review_revision` outside this pending revision.

A revision response authorizes no immediate edit. Apply the separate no-submission `revise` offer first, update the work and any parent documents made inaccurate, run appropriate verification, and submit a fresh `work-result`. The selected reviewers receive their previous feedback and your verification requests. Ask them to verify the changes and consequential regressions, not perform another comprehensive review. Constitution review remains separate; its failures and configured human approvals still follow the returned actions.

## Returned gate or autonomous hand-off

Classify human-requested revisions on the next work result. A **simple** revision changes only wording or formatting without changing meaning, scope, interfaces, verification commitments, or parent documents; it may reuse review once and requires human approval of the final bytes. A **significant** revision is anything else, resets the attempt count to 1, and automatically runs a fresh counter-review plus constitution review. Explain the classification and record a human override in either direction in `human_revision.user_override`. On a successful human-revision submission, include `human_revision` alongside the other work-result facts, for example `"human_revision":{"classification":"significant","rationale":"Added validation rules and test cases, changing verification commitments."}`. This declaration describes your judgment; it is distinct from server-owned revision counters. Omit it for work that does not complete a pending human-requested revision.

Only when `next_action.expected_submission` is `gate-summary`, author a concise, self-contained human summary and submit `{"kind":"gate-summary","summary":<summary>}`. This only opens the nonblocking presentation. Explain conversationally what is ready, the ask and PRD outcome, each material finding or risk, every returned `presentation.details` entry, and every option with its consequence. Present every returned `presentation.reasons` entry and make `presentation.class:"exception"` conspicuous; the reason envelope comes from authenticated archived request bindings, not from your gate summary or live config. Summarize which reviewers ran, what changed in response, and any consequential residual concerns. Use the report metadata; do not invent finding counts or reviewer agreement. Ask one direct question. Every returned `presentation` requires explicit human judgment. Keep opaque tokens, JSON, digests, internal paths, and protocol details internal unless the user asks for diagnostic or audit detail. There is no optional review at the end. Never synthesize a gate when the server instead returns a direct successor. (A `baseline-adoption` presentation is the exception: it resolves drift on already-reviewed bytes — typically from later commits or a merge — and is decided directly; there is no review to run, and adopting records which bytes are the baseline rather than approving new work.) At an `attempts-exhausted` presentation, explain the unresolved material defect and whether another revision appears worthwhile before asking.

When a `presentation` is returned, stop for explicit human judgment. Later submit only `{"kind":"decision","choice":<the selected presentation option token>,"reason":<the human's reason>}` through the current offer. Never choose, infer, or record a decision for the human. If the choice is `waiver-requested`, it is not approval: apply the separate no-submission `open-waiver` offer, present the returned waiver choices in the same way, stop again, and submit the later opaque token and human reason. A denial or cancellation grants nothing. If no presentation is returned, do not stop for a human decision; follow the fresh server-returned action directly.

When fresh status returns `next_action.kind:"commit"`, execute its exact task-local commit facts: verify the target and baseline, stage only the returned paths, inspect the staged changes, and commit with the returned message. The PRD approval already authorizes this commit; do not ask again. Call `archflow_status` with the same invocation so the server verifies the commit before hand-off. Do not report PRD completion or advance to design while a commit remains pending.

After a returned gate decision, or immediately after clean review when no gate is returned, use fresh `archflow_status` with the same invocation and follow only its action. Apply an offered no-submission `start-next-skill` only when it belongs to this exact invocation. Once fresh status names the successor, report it without starting it:

`Claude: /<next_action.skill> <task> <next_action.skill_args...>`

`Codex: $<next_action.skill> <task> <next_action.skill_args...>`


## Automation responsibility

Continue the current skill through production, required review, material remediation, verification, and every authenticated commit. Use further review only when its expected value justifies the cost. The default limit remains five completed rounds; retries do not consume rounds. Finish at any round, including the limit, when no supported material issue remains; repeated reviewer disagreement alone is not a reason for more work. More review beyond the limit requires the returned human intervention. Use returned `progress` to explain the pipeline step, review budget, retry state, and boundary without inferring authority from counters. The shipped defaults require human review for the initial PRD and overall design, material amendments to their approved decisions, and SQL/database changes, including embedded queries, ORM operations, and schema/data migrations. Access-control, public-contract, cryptography, and control-plane changes within the approved plan receive automatic review and remediation; their category alone does not require a human. Repository-configured triggers still apply. Resolve routine findings and supported retries autonomously; escalate an unresolved consequential decision, exhausted remediation, unavailable required review or verification, or uncertain authority through the returned action. Do not invent an approval or bypass a returned gate. After an autonomous commit, report completion, verification, the commit, and the next skill without an authorization menu.

At `start-next-skill`, the completed invocation reports the exact successor and stops. The user's launch of that successor is the transition decision; it is not another approval of the completed result. An external controller sees this as `awaiting-transition` in automation status v3. Never treat `awaiting-client`, automatic recovery, or a pending transient retry as a request for human judgment.
