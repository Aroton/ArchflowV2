# Product Requirements Document

Treat the arguments as `<task> [--counter-reviewer <model>:<effort>[@<provider>]] [--adjudicator <model>:<effort>[@<provider>]]`. The two optional trailing flags are order-independent and each may appear at most once. Parse required positionals first; reject a route flag before them, an unknown trailing flag, a duplicate, a missing flag value, or an empty model, effort, or explicitly present provider. Each route value is one shell argument: split once at the first `:`, then split the remainder once at the first `@`, preserving shell-quoted provider whitespace. Normalize supplied roles once into `invocation.review_routes` under `counter-reviewer` and/or `adjudicator`; omit `review_routes` when neither flag was supplied. An omitted role independently uses its live phase/base configured route.

This session is the producer and workflow orchestrator. Durable truth comes from the two semantic workflow tools. Construct one route-bearing invocation and repeat it identically on every status/apply call in this run, including reopen/resume, retries, significant-revision reviews, review continuation, and final observation. On entry call `archflow_status` with `{"schema_version":"1","task_id":"<task>","invocation":{"skill":"archflow-prd","intent":"resume",<optional review_routes>}}`. Every `archflow_apply` call uses that exact task and invocation plus `"action":{"offer":<next_action.offer>}` and only the submission that `next_action.expected_submission` requests; omit `submission` for `none`. Use `intent:"reopen"` only when the human explicitly asked to reopen the PRD; after status explains the impact, apply the offered action with the same normalized routes and `{"kind":"reopening-request","request":<the human's exact request>}`. After that succeeds, call `archflow_status` again with the exact `intent:"resume"` invocation above; the one-shot reopen invocation does not own production. Never add, drop, or change normalized routes between status and apply, turn an ordinary correction, review finding, or resumed session into a reopen.

Use only the returned `resources` entries shaped `{role,path,access}`: select workflow artifacts by role, use their returned paths, respect their access, and never read another task's files. Shared `docs/` and ordinary repository exploration remain available. The returned `repositories` list names every repository the task spans with its resolved location, mode, and current commit; use every member at its returned location for repository research and context, in the reported primary-first, ordinal-secondary order, and do not discover task artifacts or policy from a secondary repository, because task resources remain exclusively server-returned. Every dispatched reviewer sees the same repositories as read-only pinned snapshots and cites files as `<name>/<path>`. Context-only repositories are never written or committed; a `writable` secondary can receive declared implementation changes later, which are reviewed and committed per repository, but PRD work writes nothing outside the returned resources. After every `archflow_apply`, use its returned fresh view as authority; if a response is lost or an offer is refused, call `archflow_status` again and follow the newly offered action. Never consume a successor offer in this invocation.

The server identifies the producer family from the initialize handshake of the connected client and dispatches the configured counter-review (opposite-family by default), plus the constitution review when the repository has active constitution rules; you never perform, spawn, or simulate either. The orchestrator's context is the workflow's scarcest resource: conversation with the user, human gates, triage, and synthesis stay here. Run research through sub-agents in parallel, each spawned with a complete brief — a sub-agent sees nothing of this conversation — writing bulk output to disk and returning only the conclusions the PRD needs. Plan the work, then delegate the parallelizable pieces to sub-agents; do inline only what is too small to justify a hand-off. Perform one bounded author check before recording produce, then let the server-dispatched counter-review be the independent generative review. Triage and resolve material defects; do not iterate on polish.

## Degraded operation

If either semantic workflow tool is unavailable, run read-only `archflow-local manual-status --task <task>`, report its position, and stop. Create no milestone, edit no workflow artifact, record nothing offline, and never infer authorization. A stale or rejected offer is normal semantic recovery, not tool unavailability.

## Production and review

For a new task, the first offered action expects `task-ask`. Before research or clarification, apply it with `{"kind":"task-ask","text":<the user's exact original ask>}`. Do not paraphrase. The server owns initialization and the ask-history record. On an explicit reopen, send the exact human correction only as `reopening-request`; the server derives the target and appends PRD ask history.

When the offered action opens production, apply its no-submission offer before editing. Read the returned `user-ask` and other relevant resources, then research only as much as the brief needs. Run research through parallel sub-agents with complete briefs when it is substantial; keep conversation, clarification, synthesis, and decisions here. Record clarification questions and exact answers in the writable ask resource when returned, preserving this form:

```markdown
## Clarifications

### Question 1

<exact question>

### Answer 1

<exact reply>
```

Write each question before presenting it. An unanswered question remains without an invented answer. Write the `current-artifact` as a PRD covering the problem, users, goals and non-goals, testable requirements, assumptions, risks, and observable success criteria. Keep it useful for design rather than prescribing implementation. Perform one bounded author check for ask fidelity, ambiguity, observable acceptance, material assumptions, and unjustified scope. Do not spawn an extra generative reviewer or iterate on polish.

Submit the finished bytes through the current offer with `{"kind":"work-result","outcome":"succeeded"}` (or the offered failed form with a concrete reason). Do not supply paths, policy, routing, digests, revisions, or other server-owned facts. Apply the next `review` offer. The server selects the independent configured rubric and constitution review (opposite-family by default) from the returned `review_context`; never perform, spawn, simulate, or replace that review. If you run any same-side author review, use `review_context.rubric` verbatim and the returned active rules, never an authored rubric.

When both workflow tools answer but `dispatch_failure` reports that the selected counter-reviewer or adjudicator route failed, explain the safe message, failed role, and declared/configured route facts it returns, and name the repository when the failure names one (a read-only repository view that could not be materialized). An invalid or unavailable invocation route never falls back to configuration, and the skill never silently retries, drops, or changes its normalized route. Offer the exact safe choices: repair the declared or configured route and resume with one identically normalized invocation, or ask the human for a one-dispatch substitute route (`model`, `effort`, optionally `provider`) and a reason. The reason is required, carries the human's words, and is recorded on the review evidence. Apply the still-current `review` offer with `{"kind":"review-dispatch","route_override":{"reason":<the human's reason>,"counter-reviewer":{"model":<model>,"effort":<effort>}}}`, naming whichever role failed (`counter-reviewer` or `adjudicator`). A supplied `route_override` wins only for that dispatch, never becomes invocation routing or config, and remains distinctly human-authorized; invocation-declared routing is normal run input and is never described as human- or controller-authenticated. This substitution parameterizes that one automatic counter-review and never skips or replaces it; it is not degraded operation — that stop path still governs when the workflow tools themselves are unreachable.

## Triage and revision

When offered `triage`, submit exactly one disposition for every returned finding. Apply the Consequential Stopping Rule: accept a finding only when fixing it is reasonably likely to change requirements, downstream design, verification, approval, or important risk; use `accepted-editorial` only for non-blocking wording or formatting with no meaning change. Reject true observations that would not change downstream design, implementation, or verification with a concrete rationale (`non-material: does not change downstream design or verification`). Reject optional polish and preferences with concrete evidence. Reject every `unverifiable-` evidence gap with evidence beginning `envelope-gap: ` and never accept it. The approval conversation is not a backlog-triage meeting; omit rejected non-material observations. When all consequential issues are resolved, reject remaining notes and advance. An `escalate-` finding is the exception: it names a material judgment the reviewer could not make with confidence, so it is never silently dropped — disposition it with a rationale, present it in full at the next human boundary this phase reaches, and name it in your report even when the phase advances without one.

After any accepted finding, apply the separate no-submission `revise` offer before editing. Then make only the stated changes and submit a new `work-result`; significant changes receive fresh independent review. For a human request for changes, first submit the selected opaque decision token and reason, then apply the returned `revise` offer before touching bytes. Declare the actual revision on the next `work-result`: a **simple** revision is limited to typo, formatting, comment, or wording-only changes with no change to meaning, behavior, scope, interface, trust boundary, input, verification claim, or parent document; it may reuse review for one hop but still requires approval of the final bytes. A **significant** revision is anything else, resets the attempt count to 1, and automatically runs a fresh opposite-client counter-review plus constitution review. Uncertainty defaults to significant. State the classification and rationale to the human, and encode a human override in `human_revision.user_override` when they override it in either direction.

## Returned gate or autonomous hand-off

Only when `next_action.expected_submission` is `gate-summary`, author a concise, self-contained human summary and submit `{"kind":"gate-summary","summary":<summary>}`. This only opens the nonblocking presentation. Explain conversationally what is ready, the ask and PRD outcome, each material finding or risk, every returned `presentation.details` entry, and every option with its consequence. Present every returned `presentation.reasons` entry and make `presentation.class:"exception"` conspicuous; the reason envelope comes from authenticated archived request bindings, not from your gate summary or live config. Also state, in plain words, how strong the review evidence is from the returned `review_strength`: which model reviewed at what effort, whether it is the same model family as this producing session, and how many findings each round raised; treat a same-family reviewer or a pass that came from a remediation round as something the human should hear as conspicuously as an exception, because they are approving on the strength of that evidence. Ask one direct question. Every returned `presentation` requires explicit human judgment. Keep opaque tokens, JSON, digests, internal paths, and protocol details internal unless the user asks for diagnostic or audit detail. There is no optional review at the end. Never synthesize a gate when the server instead returns a direct successor. (A `baseline-adoption` presentation is the exception: it resolves drift on already-reviewed bytes — typically from later commits or a merge — and is decided directly; there is no review to run, and adopting records which bytes are the baseline rather than approving new work.) At an `attempts-exhausted` presentation, explain the unresolved material defect and whether another revision appears worthwhile before asking.

When a `presentation` is returned, stop for explicit human judgment. Later submit only `{"kind":"decision","choice":<the selected presentation option token>,"reason":<the human's reason>}` through the current offer. Never choose, infer, or record a decision for the human. If the choice is `waiver-requested`, it is not approval: apply the separate no-submission `open-waiver` offer, present the returned waiver choices in the same way, stop again, and submit the later opaque token and human reason. A denial or cancellation grants nothing. If no presentation is returned, do not stop for a human decision; follow the fresh server-returned action directly.

After a returned gate decision, or immediately after clean review when no gate is returned, use fresh `archflow_status` with the same invocation and follow only its action. Apply an offered no-submission `start-next-skill` only when it belongs to this exact invocation. Once fresh status names the successor, report it without starting it:

`Claude: /<next_action.skill> <task> <next_action.skill_args...>`

`Codex: $<next_action.skill> <task> <next_action.skill_args...>`
