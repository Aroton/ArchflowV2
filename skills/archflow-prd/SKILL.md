# Product Requirements Document

Treat the argument as `<task>`. This is a normal-mode phase skill: durable state and every server-checked value come from the local helper and the five workflow tools. Work only in `.archflow/tasks/<task>/` plus the shared documentation set under `docs/`; never read another task's files.

This session is the workflow orchestrator, and its context is the workflow's scarcest resource: conversation with the user, human gates, triage, and synthesis stay here. Run research through sub-agents in parallel, each spawned with a complete brief — a sub-agent sees nothing of this conversation — writing bulk output to disk and returning only the conclusions the PRD needs. Plan the work, then delegate the parallelizable pieces to sub-agents; do inline only what is too small to justify a hand-off. Review the draft through a fresh review sub-agent before recording produce (below), and run independent review work in parallel: the counter-review dispatch runs in the background while any same-side review sub-agents run. Then triage, resolve, and re-enter review as needed, bounded by the attempt budget.

## Degraded operation

If any workflow tool is unavailable, do not substitute an informal file edit or infer progress. Run input-free `archflow-local manual-status --task <task>`, report its `normal`, `degraded`, or `repair-required` mode, and perform exactly its single `next_action`. For an unavailable `archflow_state`, `archflow_counter_review`, `archflow_adjudicate`, `archflow_gate`, or `archflow_waiver`, pass only the complete plain-JSON selector and source artifact requested by status to `archflow-local manual-next --task <task>`; use the returned fallback artifact, prompt, decision templates, checkpoint result, and resume action verbatim. The helper derives every digest, anchor, result reference, evidence binding, and gate fact, retains outputs before checkpointing them, and stops for schema-valid review or an explicit human decision where required. Re-run `manual-status` after every manual milestone. If both server and helper are unavailable, stop non-advancing, reinstall with `./install.sh`, and rerun `manual-status`; never create a purported PRD milestone from conversation or filenames.

## Stable rubric

Use this exact JSON object, without editing or reordering it, in the two places that carry it: the counter-review payload and the brief handed to each review sub-agent:

```json
{"schema_version":"1","kind":"artifact","mode":"adversarial","criteria":[{"id":"substantive-correctness","text":"Report a blocking defect only when it requires producer action, and cite the specific artifact statement it contradicts or stated requirement it leaves unmet; citation is necessary but not sufficient. The violation must follow from the artifact's own text, pinned envelope evidence, or repository evidence at the pinned commit, without assuming behavior the artifact does not specify. A sound artifact is expected to yield zero blocking findings; that is successful review, not under-performance.","blocking":true},{"id":"ask-fidelity","text":"Compare the PRD against the pinned verbatim user ask. Every stated user need is addressed or explicitly excluded with rationale, and no requirement contradicts the ask. If the ask is not pinned in the envelope, do not infer it; report the gap under unverifiable-claims.","blocking":true},{"id":"proportionality","text":"Scope, machinery, and success measures are proportionate to the pinned ask. Flag requirements that exist for hypothetical futures, generality the ask does not need, or process the ask does not justify.","blocking":true},{"id":"testable-requirements","text":"Each requirement is specific and observable enough to verify without guessing intent.","blocking":true},{"id":"stated-assumptions","text":"Material assumptions and unresolved human choices are explicit and do not masquerade as requirements.","blocking":true},{"id":"unverifiable-claims","text":"For each claim you cannot verify because neither the envelope nor the read-only repository checkout contains the evidence (the user ask, a referenced document, a constraint), record one non-blocking finding naming the claim and the missing evidence. Never resolve an unverifiable claim as either satisfied or violated. Give each such finding a finding_id beginning unverifiable-.","blocking":false},{"id":"advisory-observations","text":"Use non-blocking findings for completeness suggestions, debatable readings, and observations. Do not inflate them into blockers merely to report them.","blocking":false}]}
```

Review against the pinned active rules status reports; the request composer derives `rubric_digest`, provenance, and every routing identity from durable authority, so never self-declare routing, model family, model, or effort and never substitute mutable worktree policy.

## Durable loop

Run `archflow-local status --task <task>`, inspect the JSON result's `ok` field rather than relying on the process exit code, perform exactly its `next_action`, then run status again. Use `--brief` for these routine loop iterations — it projects position, blockers, open-gate and reconciliation summaries, and the one `next_action` from the same computed status without rendered rule text, prompts, or template bodies; run full status when opening or resolving a gate or repairing. Continue until status requests human judgment or reports that the phase advanced. Do not infer state, approval, or evidence currency from Markdown, filenames, conversation, or an absent gate. When `next_action` carries a prefilled `request`, it is the preview of the call `archflow-local build-request --task <task>` composes: prefer piping the matching kind's facts to build-request, and complete a prefill by hand through `archflow-local envelope --task <task>` only when no kind composes that request — either way the resolved output, not the prefill, is the digest authority.

If `next_action` is `initialize-repository`, stop and direct the user to `archflow-init`. If it is `create-task`, pipe `{"intent_id":"initialize-task","kind":"initialize"}` to `archflow-local build-request --task <task>` and call `archflow_state` with the returned `request.input` verbatim as typed JSON — `artifact` is a JSON object and `expected_revision` is the number `0`, never strings. Initialize is the one build-request kind whose output carries no `staged` reference, because no durable task directory exists yet to hold one; the server accepts no entry point other than `prd`/`produce`/`running` at `expected_revision: 0`. For reconciliation, configuration, checkpoint, or inspection actions, report the helper's one safe action. Never improvise repair; use only the degraded-operation path above when a capability is actually unavailable.

Enter each pipeline step by piping `{"kind":"running","step":"<step>"}` to `archflow-local build-request --task <task>` and calling `archflow_state` with the returned `staged.reference`; the composer refuses an illegal entry with the server's own answer. The skill records the terminal `succeeded` or `failed` state for `produce` and `triage`. `archflow_counter_review` and `archflow_adjudicate` record their own successful terminal state; do not send a second successful state transition after either tool returns. When material new information invalidates the current PRD mid-loop — an upstream change, the user restating the ask — do not park it for the gate or smuggle it into a triage finding: record a fresh produce running entry through build-request (`kind: "running"`, `step: "produce"`, legal from any succeeded step) and only then revise `prd.md`; downstream evidence goes stale and the loop re-runs from produce.

Pipe small generated JSON payloads to `archflow-local` commands directly on stdin (for example `printf '%s' '<json>' | archflow-local build-request --task <task>`); write any payload carrying authored prose or quotes — findings, dispositions, rubric-bearing requests, gate summaries — to a file and pass it with `--input <json-file>`, because shell quoting silently corrupts such payloads. Every tool request is resolved exactly once before the call: `archflow-local build-request --task <task>` composes and resolves each request kind named below, and `archflow-local envelope --task <task>` resolves a complete proposed request as `{"tool":…,"input":…}`, such as a status prefill — in both cases the helper resolves the `input_fingerprint` internally and returns the resolved request with its true `request_digest`, so never hand-copy a fingerprint or digest between commands, and a further `envelope` pass over build-request output is a no-op fixed point, harmless but never required. Omit `intent_id` from every build-request payload: the composer generates a fresh one and echoes it in the request and in `staged.reference`; supply an explicit `intent_id` only to replay or resume an interrupted call by reusing the id a previous envelope echoed. The MCP call sends the three-field staged reference from that output: build-request stages the resolved request at `staged.path` and echoes `staged.reference` — `schema_version`, `task_id`, `intent_id`, `request_digest` — which is the entire tool input to pass; the server loads the staged request and refuses on any digest mismatch, so the multi-kilobyte `request.input` is never transcribed. If the staged reference is unavailable, fall back to passing `request.tool` and `request.input` verbatim. Each workflow tool's success result echoes the `request_digest` it recorded: a match proves the operation's semantic fields — repository and task identity, the operation, its request fields, and the resolved input fingerprint — arrived verbatim, while `intent_id` and `expected_revision` sit outside the digest and are checked separately by intent correlation and the revision check. If the echo differs from the helper's, stop and re-run status.

To record the terminal produce result: draft `.archflow/tasks/<task>/prd.md` (with `ask.md` already written, below), then pipe `{}` to `archflow-local build-request --task <task>`. It builds the document artifact with the canonical PRD defaults — `document_path: "prd.md"` and declared input `user-ask` for `ask.md`, whose digest the helper records itself; a missing `ask.md` fails the build rather than producing an undeclared PRD — assembles the complete `archflow_state` request, and returns it already resolved and staged. Call `archflow_state` with its `staged.reference`.

If a tool reports a fingerprint mismatch, discard the pending intent, take the expected digest and safe next action from the result, rebuild the request with a fresh intent, and re-run status. This is recovery, not the normal recipe.

## Phase work

Before any clarifying conversation or research, write the user's original request verbatim to `.archflow/tasks/<task>/ask.md` — the exact words the user gave, unedited. Never summarize, paraphrase, or fold later clarifying answers into it; clarifications belong in the PRD's stated assumptions. The dispatched counter-review judges ask fidelity against exactly these bytes, so an edited ask defeats the review. If `ask.md` already exists from an earlier produce round, leave it unchanged unless the user restates the ask itself.

When status selects `produce`, research only as much as the brief needs and write `.archflow/tasks/<task>/prd.md`. Capture the problem, users, goals and non-goals, testable requirements, assumptions, risks, and success criteria. Keep the artifact useful for architecture decisions rather than prescribing implementation prematurely. The dispatched counter-review reads the repository at the pinned commit (excluding task workflow files), so repository claims are verifiable — write the PRD so each claim about existing code or context can be checked against those bytes.

Before recording the terminal produce result, spawn a fresh review sub-agent with a complete brief: the drafted PRD, `ask.md`, the stable rubric, and the pinned active rules from status — nothing of this conversation. Have it return findings only. Fix what it finds or consciously dismiss it, revising the PRD until you are satisfied; spawn a second reviewer sub-agent when the first pass found substantive problems — typically one pass suffices. Nothing from this review is recorded durably; the counter-review remains the independent, server-attested check.

When status selects `counter_review`, write `{"kind":"counter-review","rubric":<the stable rubric object>}` to a file, pass it with `--input` to `archflow-local build-request --task <task>`, and call `archflow_counter_review` with the returned `staged.reference`; the artifact path is derived. The call dispatches the other-family reviewer, which explores a read-only checkout of the repository at the pinned commit and may legitimately run many minutes — the server allows up to fifteen — so run the call in the background rather than assuming a hang. Do not manufacture, summarize into authority, or edit the server-attested result.

When status selects `triage`, author exactly one disposition per finding in the current counter-review — `{"finding_id":…,"disposition":"accepted"|"accepted-editorial"|"rejected","rationale":…}` plus `revision_intent` for either acceptance and `evidence` for rejected. `accepted` marks a real defect and includes a concrete revision intent; `accepted-editorial` is only for a non-blocking finding whose fix changes wording or formatting but no meaning, and whose edit touches nothing a blocking finding's evidence cited — the composer and server both refuse it on a blocking finding; rejected findings cite artifact evidence. Write `{"kind":"triage","dispositions":[…]}` to a file, pass it with `--input` to `archflow-local build-request --task <task>`, and record triage by calling `archflow_state` with the returned `staged.reference`; the composer binds the current evidence set, canonical source digest order, counts, and every finding's resolution, and refuses at compose time when a disposition names an unknown finding or misses one. Findings whose finding_id begins `unverifiable-` report gaps in evidence genuinely outside both the sealed envelope and the repository checkout, not producer defects: reject each with rationale and evidence beginning `envelope-gap: ` naming the missing evidence, and never accept one — acceptance forces produce re-entry for a non-defect. If any finding is plain `accepted`, revise `prd.md` and follow status back through fresh production and review: the post-acceptance edit to `prd.md` is the expected next act, reported under `reconciliation.expected_reentry_edits` while status derives the normal prefilled produce running entry; drift on any other recorded file still requires the restore flow. If instead every accepted finding is `accepted-editorial`, the next status-driven act is applying exactly those revision intents to `prd.md` — nothing else — and recording produce through the same prefilled entry; build-request attaches the editorial predecessor link from durable authority, the retained reviews stay current for that one hop, and only adjudication is re-run before the gate. An editorial round still consumes one durable attempt slot — the shared produce re-entry rule increments the attempt — so a later substantive re-entry may reach the attempts-exhausted gate one round early; that gate's human retry decision is the intended recovery.

When status selects `adjudicate`, pipe `{"kind":"adjudicate"}` to `archflow-local build-request --task <task>` and call `archflow_adjudicate` with the returned `staged.reference`; the artifact and upstream paths are derived. Let the server evaluate the pinned constitution and open any required gate.

## Human gates

The PRD always requires an `artifact-approval` gate after the fixed point closes. Write `{"kind":"gate","summary":<text for the human>}` to a file and pass it with `--input` to `archflow-local build-request --task <task>`: the composer derives the gate kind, subject, evidence, revision, and fingerprint from durable state with `context: {"artifact_kind":"prd"}`, and you author only the summary. Present `ask.md` alongside the PRD at the gate so the user can catch a mistranscribed ask before approving against it. When status carries an `editorial_revision` block, the approved artifact is an editorial revision: present the diff against the predecessor alongside the applied revision intents, and include in the gate summary the disclosure that the reviews evaluated the predecessor bytes and only adjudication saw the final ones. Present the returned gate ID and optional counter-review prompt to the user, then make the blocking call to `archflow_gate` with the returned `staged.reference`.

For every open gate, including one opened inside adjudication, re-run status and present its ready-to-write decision templates, paths, and complete optional counter-review prompt. Alongside the templates, list any `unverifiable-`-prefixed findings from the current reviews as a distinct Envelope gaps section, so the user sees exactly what the review could not verify; with the reviewer reading the repository checkout, such findings name only evidence genuinely outside both the envelope and the checkout. The user alone chooses whether to run that review and which decision template to authorize. If they run it, follow the generated recipe and `archflow-local gate-counter --task <task>`; if status then requests supplemental triage, disposition every returned finding and accept any artifact-changing result only by revising the PRD and re-entering the fixed point. If they decline, record no review. Record the chosen template with `archflow-local decide --task <task>` using `kind: "interface"`, then let the blocked call resume.

Keep the original `archflow_gate` input and `intent_id` for every supplemental retry; a retry adds `supplemental_outcome`, which the staged file does not carry, so pass the full `request.input` plus that field rather than the staged reference. Decline by retrying with status's exact `decline` outcome and create no review. If review is elected, record it, let the blocked call return `SUPPLEMENTAL_REVIEW_REQUIRED`, then retry with status's exact `ingest` outcome. Re-run status after ingest and retry with its exact `triage-no-change` outcome, or, for an accepted change, revise and rebuild the artifact, take the exact new subject digest from `envelope`, retry with the authenticated supersede facts plus that digest, and expect `GATE_SUPERSEDED`. A superseded gate approves nothing: re-enter produce, review, triage, and adjudication to a fixed point before opening a fresh gate. Never fabricate review, triage, subject, or human-decision facts.

If the explicit decision is `waiver-requested`, it is not approval. Re-run status, construct the `archflow_waiver` origin only from the server's archived request and decision plus helper-derived digests, run `envelope` before the blocking waiver call, and handle the waiver gate through the same status/templates/prompt procedure. A denied or cancelled waiver grants nothing.

Never claim approval, select a decision, or pass the gate for the user. Stop until the user's explicit decision. After the approved gate resolves, re-run status and report the durable next action; approval in conversation alone is not authority.
