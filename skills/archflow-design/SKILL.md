# Task Design

Treat the arguments as `<task> [--counter-reviewer <model>:<effort>[@<provider>]] [--adjudicator <model>:<effort>[@<provider>]]`. The two optional trailing flags are order-independent and each may appear at most once. Parse required positionals first; reject a route flag before them, an unknown trailing flag, a duplicate, a missing flag value, or an empty model, effort, or explicitly present provider. Each route value is one shell argument: split once at the first `:`, then split the remainder once at the first `@`, preserving shell-quoted provider whitespace. Normalize supplied roles once into `invocation.review_routes` under `counter-reviewer` and/or `adjudicator`; omit `review_routes` when neither flag was supplied. An omitted role independently uses its live phase/base configured route.

Construct one route-bearing invocation and repeat it identically on every status/apply call in this run, including reopen/resume, retries, significant-revision reviews, review continuation, and final observation. On entry call `archflow_status` with `{"schema_version":"1","task_id":"<task>","invocation":{"skill":"archflow-design","intent":"resume",<optional review_routes>}}`. Every `archflow_apply` call uses that exact task and invocation plus `"action":{"offer":<next_action.offer>}` and only the submission that `next_action.expected_submission` requests; omit `submission` for `none`. Use `intent:"reopen"` only when the human explicitly asked to reopen task design, and submit the human's exact request as `{"kind":"reopening-request","request":<exact request>}` through the returned offer using the same normalized routes. After it succeeds, call `archflow_status` again with the exact `intent:"resume"` invocation above; the one-shot reopen invocation does not own production. Never add, drop, or change routes between status and apply. The server derives the reopened boundary and invalidation impact. Never reinterpret ordinary feedback as reopen.

This session is the producer and orchestrator. Use only returned `resources` shaped `{role,path,access}`; select `prd` and `current-artifact` by role, use returned paths, respect access, and never read another task's files. Shared `docs/` and ordinary repository exploration remain available. The returned `repositories` list names every repository the task spans with its resolved location, mode, and current commit; explore and design across every member at its returned location, in reported primary-first, ordinal-secondary order, and never use a secondary repository's `.archflow/` as task input, because task resources and policy remain exclusively server-returned. Every dispatched reviewer sees the same repositories as read-only pinned snapshots and cites files as `<name>/<path>`. Context-only repositories are never written or committed; a `writable` secondary can receive declared implementation changes that are reviewed and committed per repository, so plan which repository each piece of work lands in, but design work itself writes only the returned resources. After each `archflow_apply`, use its returned fresh view. On a lost, stale, or rejected offer, call `archflow_status` again. Perform exactly one offered semantic action per apply call and never start successor work in this invocation.

When the server returns the no-submission `refresh-stale-baseline` action, apply only that offer and use the fresh view: it retires a stale disposable baseline interface without recording a human choice. When it returns `recover-milestone-authority`, explain that the old milestone can no longer authorize continuation, apply only that no-submission offer, and continue from the fresh production boundary. Recovery preserves repository bytes but starts a significant production/review cycle; it is not approval, adoption, review, or commit authority. Never infer either action from Git history or choose a baseline decision for the human.

The server identifies the producer family from the initialize handshake of the connected client and dispatches the configured counter-review (opposite-family by default), plus the constitution review when the repository has active constitution rules; you never perform, spawn, or simulate either. The orchestrator's context is the workflow's scarcest resource: conversation with the user, human gates, triage, and synthesis stay here. Run codebase exploration and research through sub-agents in parallel, each spawned with a complete brief — a sub-agent sees nothing of this conversation — writing bulk output to disk and returning only the conclusions the design needs. On the initial design pass, spawn a dedicated **Library & Ecosystem Research** sub-agent for any new capability to survey package registries for mature, widely-adopted, and actively-maintained libraries (verifying recent activity within 12 months, strong adoption/download volume, responsive maintainers, and permissive licenses, while filtering out unmaintained or obscure single-user packages) before planning custom machinery. Plan the work, then delegate the parallelizable pieces to sub-agents; do inline only what is too small to justify a hand-off. Review the draft through a fresh review sub-agent before recording produce (below), and run independent review work in parallel: the counter-review dispatch runs in the background while any same-side review sub-agents run. Then triage, resolve, and re-enter review as needed, bounded by the attempt budget.

## Degraded operation

If either semantic workflow tool is unavailable, run read-only `archflow-local manual-status --task <task>`, report its position, and stop. Create no milestone, edit no workflow document, record nothing offline, and infer no approval. An offer refusal is not degraded operation.

## Production and independent review

If entry status returns `start-next-skill` with `next_action.offer`, apply that no-submission offer with the same exact invocation before writing. If it names a successor without an offer, report the returned successor command and stop; this completed invocation does not own the hand-off. If it selects another phase or an inspection action, report that safe result and stop. When production is open, read the returned PRD and relevant repository context. Use parallel sub-agents with complete briefs for substantial exploration, ecosystem library research, and a fresh same-side draft review; keep conversation, triage, and synthesis here. Write the `current-artifact` with system boundaries, data and control flow, key interfaces and decisions, requirement mapping, dependency and library evaluation, risks, verification strategy, and the implementation phase plan. Update a returned writable PRD in the same production result if design makes it inaccurate. If the requirements instead need a fundamentally new pass, an explicit user reopen request (above) durably restarts at the PRD without discarding the worktree; superseded authority stays archived for audit.

For a finite plan, make the sizing attempt observable in the artifact. The default phase is one coherent repository-ready increment: it has one primary behavioral or enabling outcome, leaves the repository in a valid completion state, consumes named approved predecessors or stable inputs, and has one understandable verification story. Repository-ready does not require separate deployment or user visibility, and a phase may cross technical layers when they jointly deliver that outcome.

Apply both directions of boundary judgment before finalizing the plan. The **split check** asks whether a candidate bundles outcomes, integration stories, or risk boundaries that can be implemented, verified, reviewed, and committed meaningfully on their own. The **merge check** asks whether adjacent candidates are merely scaffolding, isolated technical layers or files, separated tests, or transitional steps without a stable capability or concrete risk-reduction value of their own. Work chunks may divide or parallelize implementation inside one governed phase without becoming phase authority. Retain an unusually broad phase only with a concrete atomicity, repository-validity, or inseparable-verification rationale; retain an unusually small phase only when its stable interface, capability, or risk reduction justifies another full phase lifecycle. Phase count, layer count, file count, diff size, and numeric thresholds are not sizing evidence; prefer the fewest phases that preserve coherent outcomes and useful completion states.

Make quantitative and safety commitments auditable in the same way the sizing attempt is. Every constant a stated bound or budget depends on appears in the constants table with a value or a named measurement that precedes the phase relying on it, and a derived figure shows its arithmetic; every isolation, safety, ordering, or recovery property names the mechanism it rests on and the test that asserts that mechanism directly. A reviewer, and later a human, must be able to recompute the design rather than take it on trust.

When a plan is genuinely open-ended, explain why responsible phase boundaries cannot yet be named and what information will make decomposition possible. Do not use the open-ended form merely to avoid the sizing attempt.

Every finite phase plan uses consecutive headings beginning at 1 in the exact form `### Phase N: Name`; alternate dashes, tables, skipped numbers, and other headings are not phase authority. An intentionally open-ended plan contains exactly `<!-- archflow:phase-plan:open-ended -->` and no `### Phase` headings. Design artifact approval fails closed when neither form is valid.

For a same-side review, use the returned `review_context.rubric` verbatim and its active rules; never author durable review policy. Then submit the completed bytes with `{"kind":"work-result","outcome":"succeeded"}`. Do not submit paths, routing, policy, fingerprints, digests, or revisions. Apply the offered `review` action. The server derives and runs the configured rubric and constitution review (opposite-family by default); never perform, spawn, simulate, or replace it.

When both workflow tools answer but `dispatch_failure` reports that the selected counter-reviewer or adjudicator route failed, explain the safe message, failed role, and declared/configured route facts it returns, and name the repository when the failure names one (a read-only repository view that could not be materialized). An invalid or unavailable invocation route never falls back to configuration, and the skill never silently retries, drops, or changes its normalized route. Offer the exact safe choices: repair the declared or configured route and resume with one identically normalized invocation, or ask the human for a one-dispatch substitute route (`model`, `effort`, optionally `provider`) and a reason. The reason is required, carries the human's words, and is recorded on the review evidence. Apply the still-current `review` offer with `{"kind":"review-dispatch","route_override":{"reason":<the human's reason>,"counter-reviewer":{"model":<model>,"effort":<effort>}}}`, naming whichever role failed (`counter-reviewer` or `adjudicator`). A supplied `route_override` wins only for that dispatch, never becomes invocation routing or config, and remains distinctly human-authorized; invocation-declared routing is normal run input and is never described as human- or controller-authenticated. This substitution parameterizes that one automatic counter-review and never skips or replaces it; it is not degraded operation — that stop path still governs when the workflow tools themselves are unreachable.

## Triage and revision

For an offered `triage`, submit exactly one disposition per returned finding. Apply the Consequential Stopping Rule: accept only defects with a material consequence for requirements, architecture, implementation, verification, approval, or important risk. `accepted-editorial` is only non-blocking wording or formatting with no meaning change. Reject true observations that would not change downstream implementation or verification with a concrete rationale (`non-material: does not change implementation or verification`). Reject optional cleanup or preferred alternatives with concrete evidence. Reject `unverifiable-` gaps with evidence beginning `envelope-gap: `. Design approval is not a backlog-triage meeting; rejected non-material observations stay out of it. When all consequential issues are resolved, reject remaining notes and advance. An `escalate-` finding is the exception: it names a material judgment the reviewer could not make with confidence, so it is never silently dropped — disposition it with a rationale, present it in full at the next human boundary this phase reaches, and name it in your report even when the phase advances without one.

Accepted findings do not authorize edits. Apply the separate no-submission `revise` offer first, then edit the design and any returned writable parent made inaccurate, submit another `work-result`, and allow fresh review when required. A human request for changes follows the same boundary: submit the selected opaque token and reason, apply `revise`, then edit.

Classify the actual human-requested change on the next work result. A **simple** revision is only typo, formatting, comment, or wording work that changes no meaning, behavior, scope, interface, trust boundary, input, verification claim, or parent document; it may reuse review once but always returns for approval of the final bytes. A **significant** revision is anything else, resets the attempt count to 1, and automatically runs a fresh opposite-client counter-review plus constitution review. Default uncertainty to significant, explain the rationale, and preserve a human override in either direction in `human_revision.user_override`.

## Returned decision, Git, and successor

Only when the current offer expects `gate-summary`, submit a concise self-contained `{"kind":"gate-summary","summary":<summary>}`. The result opens a nonblocking presentation. Explain conversationally the design and phase-plan outcome, every material risk and returned detail, and all choices with their consequences. Present every returned `presentation.reasons` entry and make `presentation.class:"exception"` conspicuous; those reasons are authenticated archived facts and must not be replaced by the gate summary or current config. Also state, in plain words, how strong the review evidence is from the returned `review_strength`: which model reviewed at what effort, whether it is the same model family as this producing session, and how many findings each round raised; treat a same-family reviewer or a pass that came from a remediation round as something the human should hear as conspicuously as an exception, because they are approving on the strength of that evidence. Ask one direct question. Every returned `presentation` requires explicit human judgment. Do not expose opaque tokens or mechanical bindings unless the user requests diagnostics or audit detail. The independent review already ran; there is no optional review at the end. Never synthesize a gate when the server returns an autonomous commit or successor. (A `baseline-adoption` presentation is the exception: it resolves drift on already-reviewed bytes — typically from later commits or a merge — and is decided directly; there is no review to run, and adopting records which bytes are the baseline rather than approving new work.)

When a `presentation` is returned, stop for explicit judgment, then submit only `{"kind":"decision","choice":<selected presentation option token>,"reason":<human reason>}`. Never select a decision yourself. `waiver-requested` is not approval: apply the separate no-submission `open-waiver`, present the waiver gate, stop again, and later submit its opaque token and reason. Denial and cancellation authorize nothing. If no presentation is returned, do not stop for a human decision; follow the fresh server-returned action directly.

When fresh status returns `next_action.kind:"commit"`, use only its returned `commit` facts, regardless of whether they follow a human gate or authenticated no-wait rule authority. Confirm HEAD matches `baseline` and `target_ref`, stage exactly every authorized path — run `git add -A -- :(top,literal)<path>` once per entry in `commit.paths` — inspect the staged task-local diff, and commit with `commit.message` and the same top-anchored literal pathspecs. These authenticated facts are the complete commit authority; do not invent or request a second confirmation. Preserve unrelated index and worktree changes. On Git failure, report it and retry safely. Then call read-only `archflow_status` with the same invocation so the server observes commit proof.

If fresh status instead blocks with a design-milestone inspection, the milestone cannot succeed as things stand and retrying the commit only loops. Explain in plain language which file or fact is in the way and what would resolve it: a stray task document nobody approved is removed, while a milestone commit that already exists and cannot be recognized needs the user's decision about the branch. Never edit the archived approval or the commit history to make the check pass.

Apply an offered no-submission `start-next-skill` only for this exact invocation. After fresh status names the successor, report it and stop:
