# Task Design

Recommended producing model: GPT-6 Astra at high effort. This is advisory; it does not switch the current session or alter server authority. Never use Astra max.

Treat the arguments as `<task> [--counter-reviewer <model>:<effort>[@<provider>]] [--adjudicator <model>:<effort>[@<provider>]]`. The two optional trailing flags are order-independent and each may appear at most once. Parse required positionals first; reject a route flag before them, an unknown trailing flag, a duplicate, a missing flag value, or an empty model, effort, or explicitly present provider. Each route value is one shell argument: split once at the first `:`, then split the remainder once at the first `@`, preserving shell-quoted provider whitespace. Normalize supplied roles once into `invocation.review_routes` under `counter-reviewer` and/or `adjudicator`; omit `review_routes` when neither flag was supplied. An omitted role independently uses its live phase/base configured route.

Construct one route-bearing invocation and repeat it identically on every status/apply call in this run, including reopen/resume, retries, significant-revision reviews, review continuation, and final observation. On entry call `archflow_status` with `{"schema_version":"1","task_id":"<task>","invocation":{"skill":"archflow-design","intent":"resume",<optional review_routes>}}`. Every `archflow_apply` call uses that exact task and invocation plus `"action":{"offer":<next_action.offer>}` and only the submission that `next_action.expected_submission` requests; omit `submission` for `none`. Use `intent:"reopen"` only when the human explicitly asked to reopen task design, and submit the human's exact request as `{"kind":"reopening-request","request":<exact request>}` through the returned offer using the same normalized routes. After it succeeds, call `archflow_status` again with the exact `intent:"resume"` invocation above; the one-shot reopen invocation does not own production. Never add, drop, or change routes between status and apply. The server derives the reopened boundary and invalidation impact. Never reinterpret ordinary feedback as reopen.

This session is the producer and orchestrator. Use only returned `resources` shaped `{role,path,access}`; select `prd` and `current-artifact` by role, use returned paths, respect access, and never read another task's files. Shared `docs/` and ordinary repository exploration remain available. The returned `repositories` list names every repository the task spans with its resolved location, mode, and current commit; explore and design across every member at its returned location, in reported primary-first, ordinal-secondary order, and never use a secondary repository's `.archflow/` as task input, because task resources and policy remain exclusively server-returned. Every dispatched reviewer sees the same repositories as read-only pinned snapshots and cites files as `<name>/<path>`. Context-only repositories are never written or committed; a `writable` secondary can receive declared implementation changes that are reviewed and committed per repository, so plan which repository each piece of work lands in, but design work itself writes only the returned resources. After each `archflow_apply`, use its returned fresh view. On a lost, stale, or rejected offer, call `archflow_status` again. Perform exactly one offered semantic action per apply call and never start successor work in this invocation.

When the server returns the no-submission `refresh-stale-baseline` action, apply only that offer and use the fresh view: it retires a stale disposable baseline interface without recording a human choice. When it returns `recover-milestone-authority`, explain that the old milestone can no longer authorize continuation, apply only that no-submission offer, and continue from the fresh production boundary. Recovery preserves repository bytes but starts a significant production/review cycle; it is not approval, adoption, review, or commit authority. Never infer either action from Git history or choose a baseline decision for the human.

The server identifies the producer family from the connected client and dispatches the configured counter-review (opposite-family by default), plus constitution review when active rules exist; never perform, spawn, or simulate either. Keep conversation, human gates, triage, and synthesis here. Delegate substantial parallel exploration or research with complete briefs and use inline work for small pieces. For a new capability, research suitable maintained libraries before planning custom machinery. Triage material defects and re-enter review only as the server directs.

Review feedback is a small per-round response: `outcome:"issues_found"` with actionable `feedback`, or `outcome:"no_issues_found"` with an explicit short signoff. Read and reason as deeply as needed; mostly reading is an efficiency goal, not a quota. Do not author a separate review document, quote whole source files, narrate the investigation, or recap resolved findings. On re-review, use the revision diff and previous feedback to verify the fixes and their consequential regressions. A missing, failed, or interrupted reviewer is never signoff. The calling agent owns triage and follows the returned workflow action; a reviewer outcome does not grant approval. Historical reports without an outcome keep their original meaning.


Responses are scoped to the current action. `state` names the current boundary and `next_action.actor` identifies who acts; gate preparation, waiting for a human, and settling an already-recorded choice are different states. Use the returned action and its expected submission. Resources, review policy, feedback, and implementation advice appear when relevant; an omitted optional field is not a failure or permission to infer its value. On failure, follow `error.recovery`: correcting inputs, refreshing status, and replaying an identical interrupted call are different remedies. Request `archflow_status` with `detail:"diagnostic"` only when the task needs policy/history or operator diagnostics; this changes neither the offer nor authority. For returned `restore_targets`, follow the exact retrieval instructions; the helper returns content and does not write files, and existing destinations must not be overwritten.

## Degraded operation

If either semantic workflow tool is unavailable, run read-only `archflow-local manual-status --task <task>`, report its position, and stop. Create no milestone, edit no workflow document, record nothing offline, and infer no approval. An offer refusal is not degraded operation.

## Production and independent review

If entry status returns `start-next-skill` with `next_action.offer`, apply that no-submission offer with the same exact invocation before writing. If it names a successor without an offer, report the returned successor command and stop; this completed invocation does not own the hand-off. If it selects another phase or an inspection action, report that safe result and stop. When production is open, read the returned PRD and relevant repository context. Use parallel sub-agents with complete briefs for substantial exploration or ecosystem research; keep conversation, triage, and synthesis here. Write the `current-artifact` to settle architecture, ownership, shared contracts, and phase dependencies. Explain how the chosen components and data/control flow meet the PRD, why consequential tradeoffs were chosen, and which existing APIs or maintained libraries supply the foundations. Give shared mechanisms one clear home here; reference PRD intent rather than restating it, and leave local changes and implementation sequencing to each phase design. For interacting state, ordering, or recovery behavior, a compact transition table, algorithm sketch, or worked example can establish the contract more clearly than repeated prose. Use whichever representation resolves the real ambiguity; routine wiring needs less detail. Update a returned writable PRD in the same production result if design makes it inaccurate. If the requirements instead need a fundamentally new pass, an explicit user reopen request (above) durably restarts at the PRD without discarding the worktree; superseded authority stays archived for audit.

### Phase sizing

For a finite plan, make phase outcomes, boundaries, dependencies, and verification observable in the artifact. Name the tested interfaces or guarantees each phase will supply to its consumers, so later phase designs can distinguish available foundations from work still to invent. The default phase is one coherent repository-ready increment: it has one primary behavioral or enabling outcome, leaves the repository in a valid completion state, consumes named approved predecessors or stable inputs, and has one understandable verification story. Repository-ready does not require separate deployment or user visibility, and a phase may cross technical layers when they jointly deliver that outcome. Work chunks may divide or parallelize implementation inside one governed phase without becoming phase authority.

Design for economical implementation after strong architecture and phase design: most phases should leave routine or bounded reasoning for the configured economical implementation models. This is a planning objective, not a model quota or authority condition. Reserve stronger implementation effort for identifiable reasoning that remains difficult after design.

Assess the work remaining, rather than adding file/test counts or targeting a token budget:

| Parameter | Normal target | When to reconsider |
|---|---|---|
| Material decisions | Approach, important semantics, and interfaces settled; ordinary local choices remain with implementation | Resolve unanswered architectural decisions during design |
| New mechanisms | Typically one coherent mechanism plus routine wiring | Separate independently testable mechanisms when doing so reduces implementation and rework cost |
| Existing foundations | Named APIs, guarantees, and relevant working examples | Investigate missing foundations before downstream work depends on them |
| Verification | A credible way to expose important failures, reusing existing checks | Establish a useful oracle; long-running tests alone do not require stronger reasoning |
| Coupling | Explicit interfaces make changes understandable together | Improve boundaries or explain the concrete reason work is inseparable |

A large mechanical edit can suit an economical agent; a small synchronization algorithm can require deeper reasoning. Distinguish implementing an ownership mechanism from calling its tested API. Security labels, timers, shared state, document length, and tool duration alone do not establish implementation difficulty.

Prefer a tested internal prerequisite followed by its consumers when that removes substantial reasoning from later implementation. For example, bounded record decoding can be verified before its transactional importer is wired. An intermediate phase need not complete the whole user capability; “the feature would remain unfinished” is not a reason to reject a useful split. Preserve compiling, testable completion states and keep required safety behavior with the capability it protects.

Avoid fragmenting routine work into many design/review cycles. Compare total design, implementation, verification, and likely rework cost. A small hard component can be isolated in a useful phase or a bounded implementation assignment with an explicit integration/checking responsibility; do not assume unspecified delegation makes a difficult phase cheap. Keep inseparable hard work together when splitting would add more cost or weaken its verification.

#### Automation

Plan every phase before the last with fully machine-verifiable exit criteria: compiler, tests, lints, or simulation. If an intermediate criterion says only “verify visually” or “confirm behavior,” revise the design to name a machine-checkable criterion. If the validation is genuinely manual, batch it into the final phase. Add a separate final validation phase only when needed.

A cut that depends on human inspection to establish that the intermediate state works is a poor cut. Where a verifier needs to be built, prefer harness-first sequencing so subsequent phases have automated checks. This guidance concerns validation of behavior; all server-returned human approval gates still require explicit judgment, including before the final phase.

#### Calibration

Treat model choices as provisional engineering judgments. Use a small sample of real implementations to compare actual model/effort, total work including design/review and rework, and consequential defects. Existing notes and usage evidence are enough; no scoring worksheet, token-tracking subsystem, or extra model call is required. Reconsider repeated expensive recommendations by identifying the remaining hard problem, rather than forcing a cheaper label or a preferred phase count.

### Finalize and submit

Explain quantitative and safety commitments where they affect a concrete behavior or constraint. Show load-bearing assumptions, calculations, or measurements needed before implementation relies on them. For important isolation, safety, ordering, or recovery properties, describe the mechanism and meaningful verification; reuse existing or equivalent behavioral checks where they provide credible evidence. A missing table or direct mechanism test alone is not a design defect.

When acceptance depends on costly empirical evaluation, identify a small feasibility probe before substantial work relies on unconfirmed capabilities. Account for total work across participating roles, comparison pairs, and retries; start with a bounded comparison that can answer the consequential question. Explain what evidence would justify more runs and when the result remains inconclusive. Preserve required acceptance evidence and human decision boundaries; a cheaper pilot cannot establish a stronger claim. Use existing execution and usage evidence rather than introducing a budget or telemetry subsystem.

When a plan is genuinely open-ended, explain why responsible phase boundaries cannot yet be named and what information will make decomposition possible. Do not use the open-ended form merely to avoid the sizing attempt.

Every finite phase plan uses consecutive headings beginning at 1 in the exact form `### Phase N: Name`; alternate dashes, tables, skipped numbers, and other headings are not phase authority. An intentionally open-ended plan contains exactly `<!-- archflow:phase-plan:open-ended -->` and no `### Phase` headings. Design artifact approval fails closed when neither form is valid.

Before submitting, perform one bounded author check using the authoring view’s `review_context.rubric` as guidance and its returned active rules. Do not spawn an extra generative reviewer or author durable review policy; the server-dispatched review is the only independent review. Then submit the completed bytes with `{"kind":"work-result","outcome":"succeeded"}`. Do not submit paths, routing, policy, fingerprints, digests, or server-owned revision counters. Apply the offered `review` action; never perform, spawn, simulate, or replace the configured rubric and constitution review.

When both workflow tools answer but `dispatch_failure` reports that the selected counter-reviewer or adjudicator route failed, explain the safe message, failed role, and declared/configured route facts it returns, and name the repository when the failure names one (a read-only repository view that could not be materialized). An invalid or unavailable invocation route never falls back to configuration, and the skill never drops or changes its normalized route. The server retries positively classified transient failures twice on that same route. While returned `dispatch_failure.recovery.status` is `retrying`, keep observing the existing review operation; do not request human intervention or launch a second review. Only an exhausted or repair-required failure needs the conversation below. Offer the exact safe choices: repair the declared or configured route and resume with one identically normalized invocation, or ask the human for a one-dispatch retry on the repaired route or substitute route (`model`, `effort`, optionally `provider`) and a reason. The reason is required, carries the human's words, and is recorded on the review evidence. Apply the still-current `review` offer with `{"kind":"review-dispatch","route_override":{"reason":<the human's reason>,"counter-reviewer":{"model":<model>,"effort":<effort>}}}`, naming whichever role failed (`counter-reviewer` or `adjudicator`). A supplied `route_override` wins only for that dispatch, never becomes invocation routing or config, and remains distinctly human-authorized; invocation-declared routing is normal run input and is never described as human- or controller-authenticated. This substitution parameterizes that one automatic counter-review and never skips or replaces it; it is not degraded operation — that stop path still governs when the workflow tools themselves are unreachable.

## Triage and revision

If `partial_review_reports` is returned, read the available feedback while following the retry action. The server reuses successful siblings; incomplete coverage does not authorize completion.

When `triage` is offered with `review_reports`, assess each concern on its evidence and concrete consequence. Check the relevant code and tests before accepting a claim that behavior or verification is missing. Treat the PRD and design as context for intent and constraints: plan discrepancies need a concrete consequence, and a real defect matters even when the plan never mentioned it. Submit `{"kind":"triage","response":{"decision":"finish","rationale":"..."}}` to finish, or use `decision:"revise"` with a rationale and `reviewers:[{"reviewer_id":"...","request":"..."}]` naming the previous reviewers needed to verify the changes. Use `decision:"escalate"` with the question and rationale when human judgment is needed. Reports are information: their formatting, categories, and recommendations do not dictate your decision. Resolve supported material concerns and dismiss disproved, speculative, or non-material suggestions. Finish when no supported material issue remains; agreement on every suggestion is unnecessary. Seek human judgment through the offered escalation path when an important unresolved decision needs it. Do not add another AI call just to interpret the reports. For an archived review that still returns structured `findings`, use its existing disposition submission until the next fresh review.

For a localized correction, use `{"kind":"triage","response":{"decision":"revise-minor","rationale":"<why the intended corrections are minor>"}}` without reviewer selection. This option is available by default: typos, formatting, comments, or a short clarification of established intent can qualify. A paragraph gaining a little explanatory detail is fine; coordinated rewrites across sections, new requirements, behavior changes, or changed verification commitments need ordinary review. Judge consequence and breadth from the actual diff, without paragraph-count rules or another classification call. Batch the corrections, apply the returned no-submission `revise` offer before editing, and run applicable automated checks. Submit `review_revision:{"classification":"minor","rationale":"<what actually changed>"}` alongside the succeeded `work-result` facts. If the change grew, declare `classification:"significant"` to trigger fresh review. Minor revisions reuse the original review group once, including constitution and phase-design effort evidence; they cannot clear unresolved policy requirements or bypass returned human approvals. Disclose the unreviewed correction in the final summary. Omit `review_revision` outside this pending revision.

A revision response authorizes no immediate edit. Apply the separate no-submission `revise` offer first, update the work and any parent documents made inaccurate, run appropriate verification, and submit a fresh `work-result`. The selected reviewers receive their previous feedback and your verification requests. Ask them to verify the changes and consequential regressions, not perform another comprehensive review. Constitution review remains separate; its failures and configured human approvals still follow the returned actions.

Classify the actual human-requested change on the next work result. A **simple** revision is only typo, formatting, comment, or wording work that changes no meaning, behavior, scope, interface, trust boundary, input, verification claim, or parent document; it may reuse review once but always returns for approval of the final bytes. A **significant** revision is anything else, resets the attempt count to 1, and automatically runs a fresh opposite-client counter-review plus constitution review. Default uncertainty to significant, explain the rationale, and preserve a human override in either direction in `human_revision.user_override`. On a successful human-revision submission, include `human_revision` alongside the other work-result facts, for example `"human_revision":{"classification":"significant","rationale":"Added validation rules and test cases, changing verification commitments."}`. This declaration describes your judgment; it is distinct from server-owned revision counters. Omit it for work that does not complete a pending human-requested revision.

## Returned decision, Git, and successor

Only when the current offer expects `gate-summary`, submit a concise self-contained `{"kind":"gate-summary","summary":<summary>}`. The result opens a nonblocking presentation. Explain conversationally the design and phase-plan outcome, every material risk and returned detail, and all choices with their consequences. Present every returned `presentation.reasons` entry and make `presentation.class:"exception"` conspicuous; those reasons are authenticated archived facts and must not be replaced by the gate summary or current config. Summarize which reviewers ran, what changed in response, and any consequential residual concerns. Use the report metadata; do not invent finding counts or reviewer agreement. Ask one direct question. Every returned `presentation` requires explicit human judgment. Do not expose opaque tokens or mechanical bindings unless the user requests diagnostics or audit detail. The independent review already ran; there is no optional review at the end. Never synthesize a gate when the server returns an autonomous commit or successor. (A `baseline-adoption` presentation is the exception: it resolves drift on already-reviewed bytes — typically from later commits or a merge — and is decided directly; there is no review to run, and adopting records which bytes are the baseline rather than approving new work.)

When a `presentation` is returned, stop for explicit judgment, then submit only `{"kind":"decision","choice":<selected presentation option token>,"reason":<human reason>}`. Never select a decision yourself. `waiver-requested` is not approval: apply the separate no-submission `open-waiver`, present the waiver gate, stop again, and later submit its opaque token and reason. Denial and cancellation authorize nothing. If no presentation is returned, do not stop for a human decision; follow the fresh server-returned action directly.

When fresh status returns `next_action.kind:"commit"`, use only its returned `commit` facts, regardless of whether they follow a human gate or authenticated no-wait rule authority. Confirm HEAD matches `baseline` and `target_ref`, stage exactly every authorized path — run `git add -A -- :(top,literal)<path>` once per entry in `commit.paths` — inspect the staged task-local diff, and commit with `commit.message` and the same top-anchored literal pathspecs. These authenticated facts are the complete commit authority; do not invent or request a second confirmation. Preserve unrelated index and worktree changes. On Git failure, report it and retry safely. Then call read-only `archflow_status` with the same invocation so the server observes commit proof.

If fresh status instead blocks with a design-milestone inspection, the milestone cannot succeed as things stand and retrying the commit only loops. Explain in plain language which file or fact is in the way and what would resolve it: a stray task document nobody approved is removed, while a milestone commit that already exists and cannot be recognized needs the user's decision about the branch. Never edit the archived approval or the commit history to make the check pass.

Apply an offered no-submission `start-next-skill` only for this exact invocation. After fresh status names the successor, report it and stop:

`Claude: /<next_action.skill> <task> <next_action.skill_args...>`

`Codex: $<next_action.skill> <task> <next_action.skill_args...>`


## Automation responsibility

Continue the current skill through production, required review, material remediation, verification, and every authenticated commit. Use further review only when its expected value justifies the cost. The default limit remains five completed rounds; retries do not consume rounds. Finish at any round, including the limit, when no supported material issue remains; repeated reviewer disagreement alone is not a reason for more work. More review beyond the limit requires the returned human intervention. Use returned `progress` to explain the pipeline step, review budget, retry state, and boundary without inferring authority from counters. The shipped defaults require human review for the initial PRD and overall design, material amendments to their approved decisions, and SQL/database changes, including embedded queries, ORM operations, and schema/data migrations. Access-control, public-contract, cryptography, and control-plane changes within the approved plan receive automatic review and remediation; their category alone does not require a human. Repository-configured triggers still apply. Resolve routine findings and supported retries autonomously; escalate an unresolved consequential decision, exhausted remediation, unavailable required review or verification, or uncertain authority through the returned action. Do not invent an approval or bypass a returned gate. After an autonomous commit, report completion, verification, the commit, and the next skill without an authorization menu.

At `start-next-skill`, the completed invocation reports the exact successor and stops. The user's launch of that successor is the transition decision; it is not another approval of the completed result. An external controller sees this as `awaiting-transition` in automation status v3. Never treat `awaiting-client`, automatic recovery, or a pending transient retry as a request for human judgment.
