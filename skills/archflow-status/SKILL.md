# Workflow Status

Accept an optional `<task>`. This skill is read-only: it does not edit artifacts, resolve gates, repair authority, stage files, or commit, and it never calls `archflow_apply`.

This skill is the interactive, human-facing status surface. External controllers instead poll input-free `archflow-local automation-status --task <task>` and follow its versioned actor/skill descriptor; that command is an observational integration contract, not a substitute source of semantic authority for this conversation. Do not use automation status to bypass `archflow_status`, render a human gate, or reconstruct an offer or decision.

If `.archflow/` is absent, report that repository initialization is required. If no task is supplied, list directory names directly under `.archflow/tasks/`; do not ask the helper to enumerate tasks.

For each selected task, call read-only `archflow_status` with exactly `{"schema_version":"1","task_id":"<task>"}` and no invocation — the reconciled view with no mutation offer. It is the only task-state authority. Report its `condition`, `headline`, and `detail` conversationally, including position, review state, material blockers, and whether human judgment is needed. List every returned repository in server order with its name, location, mode, and current commit; show a last-reviewed commit only when returned. Primary is writable, an omitted secondary mode is `context-only`, and only `writable` secondaries can receive reviewed and committed outputs. Reviewers receive pinned read-only views of all configured repositories and cite `<name>/<path>`; context-only repositories are never changed. Do not infer progress from documents, filenames, Git, conversation, or missing files.

When the view carries a `presentation`, explain the decision, why it matters, every `presentation.reasons` entry, material evidence, and each choice with its consequence. Make `presentation.class:"exception"` conspicuous; any exceptional reason dominates the aggregate class. If `review_strength` is returned, state the reviewer model and effort, family relation to the producer, and per-round finding counts; give same-family review and remediation-round passes exception-level prominence. Ask one direct question. The counter-review already ran, so offer no optional review. Keep gate IDs, digests, decision paths, JSON, internal paths, raw fields, and protocol codes diagnostic-only. Never decide or resolve the gate; the producing session records the human's choice.

Present exactly one recommended action from `next_action`. For workflow skills, render both exact server-derived destination commands from `next_action.skill` and `next_action.skill_args`: `Claude: /<skill> <task> <args...>` and `Codex: $<skill> <task> <args...>`. Never substitute the current phase's skill, infer arguments, or reconstruct a command from prose. Print no command at terminal completion and keep mechanical bindings diagnostic-only. In particular:

- `initialize-task`, `begin-work`, `submit-work`, `review`, `triage`, `revise`, `refresh-stale-baseline`, `recover-milestone-authority`, `start-next-skill`, and `finish-task` identify workflow work owned by the named producing skill, not inferred permission to skip that skill; the destination invocation the server returns can complete the one pending hand-off. A stale-baseline refresh only replaces an obsolete disposable decision interface, while milestone recovery preserves repository bytes and starts fresh significant production/review; neither is a human decision, approval, review, or commit authority. When Git baseline commits diverge or authority must be re-anchored after external commits, branch merges, or rebases, `echo '{"target_commit":"HEAD","reason":"<reason>"}' | archflow-local set-commit-authority --task <task>` explicitly re-anchors milestone and policy authority.
- When `next_action` carries commit facts, report that the producing skill must execute those authenticated facts directly after the existing baseline, target, path, staged-diff, and exact-message checks; no second human confirmation remains. Git has not yet proved the exact commit on the returned target. This read-only skill reports pending work and never stages or commits it.
- An open-gate `presentation` and a pending waiver request are human trust boundaries and remain pending until durable authority proves resolution.
- A `blocked` condition whose next action asks for inspection is reported as blocking recovery work exactly as returned; do not invent a repair.
- A `complete` condition means the final planned implementation phase is committed. It does not imply QA, staging, release, deployment, or publication.

## Degraded and fallback operation

If the MCP server is unavailable, run input-free `archflow-local manual-status --task <task>` once for that task; the helper-classified result is then the only authority for task state, as described below. Separately from availability: a semantic read that projects no durable task state for a named task — the initialization-ready projection whose next action is `initialize-task` — may be hiding a staged, not-yet-adopted legacy import, because the import's ignored runtime stage is not durable task state and only the helper can classify it. Before reporting that projection, run the same input-free `archflow-local manual-status --task <task>` check once: when it classifies `upgrade-staged` or `upgrade-restart-required`, that classification is the authority and the account below replaces the initialization recommendation; when the helper finds no staged import, the initialization-ready projection stands and the task is simply new. A failing command exits nonzero and prints a JSON error body, and the JSON `ok` field remains the authority for structured details.

The helper-classified result is then the only authority for task state. Translate it into a concise, conversational account of where the task stands, what—if anything—is blocking it, and exactly one recommended next action. Preserve the classification as `normal`, `degraded`, `repair-required`, `upgrade-staged`, or `upgrade-restart-required`, but do not print the complete machine-shaped `task_status`. In normal mode, mention the current phase and review state, material blockers, whether human judgment is needed, and cleanup only when it is pending, and render any open gate from its human-facing presentation exactly as above. In degraded mode, explain that no durable state exists, there is no offline recording, and the workflow must wait for the server. In `upgrade-staged` mode, explain that a current-format ignored import stage is reusable but is not durable task authority and must resume through the upgrade skill in an MCP-enabled session. In `upgrade-restart-required` mode, explain that old or ambiguous staging cannot be adopted and report only the helper's exact safe discard-and-restart action. In repair-required mode, explain that state exists but cannot currently be trusted and give only the safe recovery action.

When configuration is not verified, explain the returned issue and safe action without inventing recovery guidance or mutation authority. When the next action is `upgrade-tooling`, nothing changed — the pinned bytes are exact but this installed ArchFlow cannot parse their schema, so say the task needs tooling that accepts its pinned configuration (or a restart under the current schema), never a config edit or restore. Keep the expected and observed digests available for diagnostics, but do not show them unless the user asks.

When the result is not `ok`, explain the problem and safe next action conversationally without promoting partial information to state. Keep the structured error, identifiers, and protocol code internal unless diagnostics are requested. For `repair-required`, recommend only the returned action; unreadable, corrupt, or contradictory authority never becomes progress. If the helper itself is unavailable, report only this static non-advancing action: reinstall with `./install.sh`, then rerun `archflow-local manual-status --task <task>`. Do not reconstruct a status while both server and helper are unavailable.
