# Phase Design

Recommended producing model: GPT-6 Astra at high effort. This is advisory; it does not switch the current session or alter server authority. Never use Astra max.

Treat the arguments as `<task> <phase-number> [--counter-reviewer <model>:<effort>[@<provider>]] [--test-reviewer <model>:<effort>[@<provider>]] [--effort-reviewer <model>:<effort>[@<provider>]] [--adjudicator <model>:<effort>[@<provider>]]`. The four optional trailing flags are order-independent and each may appear at most once. Parse both required positionals first; reject a route flag before them, an unknown trailing flag, a duplicate, a missing flag value, or an empty model, effort, or explicitly present provider. Each route value is one shell argument: split once at the first `:`, then split the remainder once at the first `@`, preserving shell-quoted provider whitespace. Normalize supplied roles once into `invocation.review_routes` under `counter-reviewer`, `test-reviewer`, `effort-reviewer`, and/or `adjudicator`; omit `review_routes` when no flag was supplied. An omitted role independently uses its live phase/base configured route; for phase design, an omitted and unconfigured test reviewer uses the shipped `gpt-5.6-luna` / `xhigh` default.

Construct one route-bearing invocation and repeat it identically on every status/apply call in this run, including reopen/resume, retries, significant-revision reviews, review continuation, and final observation. On entry call `archflow_status` with `{"schema_version":"1","task_id":"<task>","invocation":{"skill":"archflow-phase-design","phase":<phase-number>,"intent":"resume",<optional review_routes>}}`. Every `archflow_apply` call uses that exact task and invocation plus `"action":{"offer":<next_action.offer>}` and only the submission that `next_action.expected_submission` requests; omit `submission` for `none`. Use `intent:"reopen"` only when the human explicitly asked to reopen this planning boundary; submit their exact request as `{"kind":"reopening-request","request":<exact request>}` through the returned offer using the same normalized routes. After it succeeds, call `archflow_status` again with the exact `intent:"resume"` invocation above; the one-shot reopen invocation does not own production. Never add, drop, or change routes between status and apply. Let the server derive the affected phases and authority changes.

This session is the producer and orchestrator. Use only returned `resources` shaped `{role,path,access}`; select `current-artifact`, `task-design`, `prd`, and any `prior-implementation-notes` by role, use returned paths, respect access, and never read another task's files. Shared `docs/` and ordinary repository exploration remain available. The returned `repositories` list names every repository the task spans with its resolved location, mode, and current commit; explore and design the phase across every member at its returned location, in reported primary-first, ordinal-secondary order, and never read task artifacts or policy from a secondary repository, because task resources remain exclusively server-returned. Every dispatched reviewer sees the same repositories as read-only pinned snapshots and cites files as `<name>/<path>`. Context-only repositories are never written or committed; a `writable` secondary can receive the implementation changes this phase declares for it, which are reviewed and committed per repository, so name the repository for every planned change while the phase design itself writes only the returned resources. After every `archflow_apply`, trust its returned fresh view. If an offer is lost, stale, or refused, call `archflow_status` again. Perform one offered action per call and never start implementation in this invocation.

When the server returns the no-submission `refresh-stale-baseline` action, apply only that offer and use the fresh view: it retires a stale disposable baseline interface without recording a human choice. When it returns `recover-milestone-authority`, explain that the old milestone can no longer authorize continuation, apply only that no-submission offer, and continue from the fresh production boundary. Recovery preserves repository bytes but starts a significant production/review cycle; it is not approval, adoption, review, or commit authority. Never infer either action from Git history or choose a baseline decision for the human.

The server identifies the producer family from the connected client and dispatches the configured counter-review (opposite-family by default), plus constitution review when active rules exist; never perform, spawn, or simulate either. Keep conversation, human gates, triage, and synthesis here. Delegate substantial parallel exploration or research with complete briefs and use inline work for small pieces. Research libraries or integrations when a concrete dependency or implementation uncertainty warrants it. Triage material defects and re-enter review only as the server directs.

## Degraded operation

If either semantic workflow tool is unavailable, run read-only `archflow-local manual-status --task <task>`, report its position, and stop. Create no milestone, edit no workflow document, write no code, record nothing offline, and infer no approval. An offer refusal is ordinary recovery, not degraded operation.

## Production and independent review

If entry status returns `start-next-skill` with `next_action.offer`, apply its no-submission offer with this exact invocation before writing. If it names a successor without an offer, report the returned successor command and stop; this completed invocation does not own the hand-off. Otherwise require position `phase-design` with the requested phase; report a different phase or inspection result rather than bypassing it. Read the returned task design, PRD, relevant context, and prior implementation notes whose interfaces matter. Delegate substantial exploration or ecosystem research with complete briefs while keeping conversation, triage, and synthesis here.

Before detailing work chunks, perform one bounded fit check: can an economical implementation agent execute this phase using settled decisions, explicit interfaces, and meaningful verification? Aim for Sol medium or Astra low for most phases. Identify the mechanisms implementation must still derive, distinguish them from tested predecessor APIs it only calls, and settle material design questions here. Typically retain one coherent mechanism plus routine wiring. A single-component phase needs no special atomicity justification when it has a useful tested outcome. Preserve sound boundaries; reconsider a split or a bounded implementation assignment when an independent hard component would otherwise raise the cost of the whole phase. A tested internal prerequisite is a valid increment even when the complete feature comes later. Compare the extra design/review cost before splitting, and keep safety behavior with the capability it protects. Work chunks divide implementation inside this governed phase; they do not create separate authority.

If the fit check finds a material split or merge needed for coherent implementation, verification, or review, correct it only through a returned writable task-design or PRD parent, record the deviation, and include those bytes in the existing compound production result so normal server-returned review and authority govern them before implementation. Do not invent a gate, renumber beyond what the returned resources can represent, or treat edited parent bytes as authority. If the needed correction belongs to an earlier boundary or cannot be represented safely here, stop and follow the existing server-returned reopen or restart path. In particular, when a revised final bound would be below the current phase, do not edit toward an impossible cursor: explain that an explicit human request to reopen task design is required, stop, and let that skill follow the server-returned authority.

Write the `current-artifact` with the phase goal, requirements, context, files, implementation approach, work chunks, pinned cross-chunk interfaces, success criteria, and executable verification. Where the phase fixes constants, budgets, or bounds, give each its value or the measurement that settles it and show derived arithmetic; where the phase carries an important isolation, safety, ordering, or recovery property, describe the mechanism and meaningful verification, reusing existing or equivalent behavioral checks where they provide credible evidence. Do not write implementation code; document bytes alone grant no authority. Plan only this phase. Change a returned writable task-design or PRD parent, including future-phase boundaries, only as much as required to keep the approved plan accurate; record the deviation in the same compound production result. Earlier phase designs remain immutable records. A changed parent follows the project's approval rules. Shipped policy independently compares changed PRD and architecture documents to their human-approved baselines: material changes require approval; meaning-preserving updates can advance automatically. SQL and truly public contract changes still require approval.

Before submitting, perform one bounded author check using `review_context.rubric` as guidance and the returned active rules. Do not spawn an extra generative reviewer or author durable review policy; the server-dispatched review is the only independent review. Submit the completed current artifact and any parent updates with `{"kind":"work-result","outcome":"succeeded"}`. Do not name paths or author routing, policy, fingerprint, digest, or server-owned revision counters. Apply the offered `review`; never perform, spawn, simulate, or replace the configured rubric and constitution review.

Every changed phase-design subject requires fresh effort selection; predecessor evidence never supplies the implementation agent for changed bytes. Render the returned `implementation_recommendation`: for `ready`, state its exact model and effort and summarize its optional `rationale`; for `unavailable`, explain the returned reason without guessing. The rationale is advisory feedback about remaining difficulty and opportunities to settle or isolate expensive work, not an instruction or authority. Assess a material concern on its merits through the existing review/triage or server-returned reopen path; do not launch another review merely to obtain agreement with a recommendation. A selector failure defaults to GPT-5.6 Sol medium without retry or a human boundary. Follow the exact returned `next_action`; advice neither switches the session nor authorizes edits or delegation.

When both workflow tools answer but `dispatch_failure` reports that the selected counter-reviewer, test-reviewer, or adjudicator route failed, explain the safe message, exact failed role, and returned declared/configured route facts, and name the repository when the failure names one. An invalid or unavailable invocation route never falls back to configuration, and the skill never drops or changes its normalized route. The server retries positively classified transient failures twice on that same route. While returned `dispatch_failure.recovery.status` is `retrying`, keep observing the existing review operation; do not request human intervention or launch a second review. Only an exhausted or repair-required failure needs the conversation below. Offer the exact safe choices: repair the declared or configured route and resume with one identically normalized invocation, or ask the human for a one-dispatch retry on the repaired route or substitute route (`model`, `effort`, optionally `provider`) and a reason. The reason is required, carries the human's words, and is recorded on the review evidence. Apply the still-current `review` offer with `{"kind":"review-dispatch","route_override":{"reason":<the human's reason>,"<failed-role>":{"model":<model>,"effort":<effort>}}}` using exactly the returned failed role. This substitution parameterizes the automatic review child and never skips or replaces it; invocation-declared routing is normal run input and is never described as human- or controller-authenticated; it is not degraded operation. Effort-selector failures never enter this path; they use the fixed Sol-medium default.

The ordinary route-only outage case remains: both workflow tools answer but `dispatch_failure` reports that the selected counter-reviewer or adjudicator route failed. The same path applies when `dispatch_failure` reports that the test-reviewer route failed, using exactly the returned failed role (`counter-reviewer`, `test-reviewer`, or `adjudicator`).

## Triage and revision

If `partial_review_reports` is returned, read the available feedback while following the retry action. The server reuses successful siblings; incomplete coverage does not authorize completion.

When `triage` is offered with `review_reports`, assess each concern on its evidence and concrete consequence. Check the relevant code and tests before accepting a claim that behavior or verification is missing. Treat the PRD and design as context for intent and constraints: plan discrepancies need a concrete consequence, and a real defect matters even when the plan never mentioned it. Submit `{"kind":"triage","response":{"decision":"finish","rationale":"..."}}` to finish, or use `decision:"revise"` with a rationale and `reviewers:[{"reviewer_id":"...","request":"..."}]` naming the previous reviewers needed to verify the changes. Use `decision:"escalate"` with the question and rationale when human judgment is needed. Reports are information: their formatting, categories, and recommendations do not dictate your decision. Resolve supported material concerns and dismiss disproved, speculative, or non-material suggestions. Finish when no supported material issue remains; agreement on every suggestion is unnecessary. Seek human judgment through the offered escalation path when an important unresolved decision needs it. Do not add another AI call just to interpret the reports. For an archived review that still returns structured `findings`, use its existing disposition submission until the next fresh review.

A revision response authorizes no immediate edit. Apply the separate no-submission `revise` offer first, update the work and any parent documents made inaccurate, run appropriate verification, and submit a fresh `work-result`. The selected reviewers receive their previous feedback and your verification requests. Ask them to verify the changes and consequential regressions, not perform another comprehensive review. Constitution review remains separate; its failures and configured human approvals still follow the returned actions.

Declare the actual human revision on the next work result. A **simple** revision is only typo, formatting, comment, or wording work that changes no meaning, behavior, scope, interface, trust boundary, input, verification claim, or parent document; it can reuse review once but always returns for approval of the final bytes. A **significant** revision is anything else, resets the attempt count to 1, and automatically runs a fresh opposite-client counter-review plus constitution review. Uncertainty defaults to significant. Explain the classification, and record a human override in either direction in `human_revision.user_override`. On a successful human-revision submission, include `human_revision` alongside the other work-result facts, for example `"human_revision":{"classification":"significant","rationale":"Added validation rules and test cases, changing verification commitments."}`. This declaration describes your judgment; it is distinct from server-owned revision counters. Omit it for work that does not complete a pending human-requested revision.

## Returned decision, Git, and hand-off

Only when an offer expects `gate-summary`, submit a concise self-contained `{"kind":"gate-summary","summary":<summary>}`. It opens a nonblocking presentation. Explain conversationally the phase-design outcome, all material risks, every returned detail, and each choice with its consequence. Present every returned `presentation.reasons` entry and make `presentation.class:"exception"` conspicuous; those reasons derive from authenticated archived request bindings rather than your summary or mutable config. Summarize which reviewers ran, what changed in response, and any consequential residual concerns. Use the report metadata; do not invent finding counts or reviewer agreement. Ask one direct question. Every returned `presentation` requires explicit human judgment. Keep opaque tokens and mechanical bindings internal unless the user requests diagnostics or audit detail. The independent review already ran and there is no optional review at the end. Never synthesize a gate when the server returns an autonomous commit or successor. (A `baseline-adoption` presentation is the exception: it resolves drift on already-reviewed bytes — typically from later commits or a merge — and is decided directly; there is no review to run, and adopting records which bytes are the reviewed baseline rather than approving new work.)

When a `presentation` is returned, stop for explicit human judgment. Later submit only `{"kind":"decision","choice":<selected presentation option token>,"reason":<human reason>}`. Never choose or infer it. A `waiver-requested` choice is not approval: apply the separate no-submission `open-waiver` offer, present its choices, stop again, and later submit the waiver's opaque token and reason. Denial or cancellation grants nothing. If no presentation is returned, do not stop for a human decision; follow the fresh server-returned action directly.

When fresh status returns `next_action.kind:"commit"`, use only returned `commit` facts, regardless of whether they follow a human gate or authenticated no-wait rule authority. Confirm HEAD matches `baseline` and `target_ref`, stage exactly every authorized path — run `git add -A -- :(top,literal)<path>` once per entry in `commit.paths` — inspect the staged task-local diff, and commit with `commit.message` and the same top-anchored literal pathspecs. Authenticated commit facts require direct execution after these checks; do not invent or request another confirmation. Preserve unrelated staged or worktree changes. After any Git failure, report it and retry safely. Call read-only `archflow_status` with the same invocation so the server observes the commit proof.

If fresh status instead blocks with a design-milestone inspection, the milestone cannot succeed as things stand and retrying the commit only loops. Explain in plain language which file or fact is in the way and what would resolve it: a stray task document nobody approved is removed, while a milestone commit that already exists and cannot be recognized needs the user's decision about the branch (or explicit re-anchoring via `echo '{"target_commit":"HEAD","reason":"<reason>"}' | archflow-local set-commit-authority --task <task>`). Never edit the archived approval or the commit history to make the check pass.

Apply an offered no-submission `start-next-skill` only for this exact invocation. Report `DESIGNED` only after fresh status proves the hand-off and names the successor; do not start implementation here:

`Claude: /<next_action.skill> <task> <next_action.skill_args...>`

`Codex: $<next_action.skill> <task> <next_action.skill_args...>`


## Automation responsibility

Continue the current skill through production, required review, material remediation, verification, and every authenticated commit. Use further review only when its expected value justifies the cost. The default limit remains five completed rounds; retries do not consume rounds. Finish at any round, including the limit, when no supported material issue remains; repeated reviewer disagreement alone is not a reason for more work. More review beyond the limit requires the returned human intervention. Use returned `progress` to explain the pipeline step, review budget, retry state, and boundary without inferring authority from counters. The shipped defaults require human review for the initial PRD and overall design, material amendments to their approved decisions, and SQL/database changes, including embedded queries, ORM operations, and schema/data migrations. Access-control, public-contract, cryptography, and control-plane changes within the approved plan receive automatic review and remediation; their category alone does not require a human. Repository-configured triggers still apply. Resolve routine findings and supported retries autonomously; escalate an unresolved consequential decision, exhausted remediation, unavailable required review or verification, or uncertain authority through the returned action. Do not invent an approval or bypass a returned gate. After an autonomous commit, report completion, verification, the commit, and the next skill without an authorization menu.

At `start-next-skill`, the completed invocation reports the exact successor and stops. The user's launch of that successor is the transition decision; it is not another approval of the completed result. An external controller sees this as `awaiting-transition` in automation status v3. Never treat `awaiting-client`, automatic recovery, or a pending transient retry as a request for human judgment.
