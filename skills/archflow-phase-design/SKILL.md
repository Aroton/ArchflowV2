# Phase Design

Treat the arguments as `<task> <phase-number> [--counter-reviewer <model>:<effort>[@<provider>]] [--test-reviewer <model>:<effort>[@<provider>]] [--adjudicator <model>:<effort>[@<provider>]]`. The three optional trailing flags are order-independent and each may appear at most once. Parse both required positionals first; reject a route flag before them, an unknown trailing flag, a duplicate, a missing flag value, or an empty model, effort, or explicitly present provider. Each route value is one shell argument: split once at the first `:`, then split the remainder once at the first `@`, preserving shell-quoted provider whitespace. Normalize supplied roles once into `invocation.review_routes` under `counter-reviewer`, `test-reviewer`, and/or `adjudicator`; omit `review_routes` when no flag was supplied. An omitted role independently uses its live phase/base configured route; an omitted and unconfigured test reviewer does not run.

Construct one route-bearing invocation and repeat it identically on every status/apply call in this run, including reopen/resume, retries, significant-revision reviews, review continuation, and final observation. On entry call `archflow_status` with `{"schema_version":"1","task_id":"<task>","invocation":{"skill":"archflow-phase-design","phase":<phase-number>,"intent":"resume",<optional review_routes>}}`. Every `archflow_apply` call uses that exact task and invocation plus `"action":{"offer":<next_action.offer>}` and only the submission that `next_action.expected_submission` requests; omit `submission` for `none`. Use `intent:"reopen"` only when the human explicitly asked to reopen this planning boundary; submit their exact request as `{"kind":"reopening-request","request":<exact request>}` through the returned offer using the same normalized routes. After it succeeds, call `archflow_status` again with the exact `intent:"resume"` invocation above; the one-shot reopen invocation does not own production. Never add, drop, or change routes between status and apply. Let the server derive the affected phases and authority changes.

This session is the producer and orchestrator. Use only returned `resources` shaped `{role,path,access}`; select `current-artifact`, `task-design`, `prd`, and any `prior-implementation-notes` by role, use returned paths, respect access, and never read another task's files. Shared `docs/` and ordinary repository exploration remain available. The returned `repositories` list names every repository the task spans with its resolved location, mode, and current commit; explore and design the phase across every member at its returned location, in reported primary-first, ordinal-secondary order, and never read task artifacts or policy from a secondary repository, because task resources remain exclusively server-returned. Every dispatched reviewer sees the same repositories as read-only pinned snapshots and cites files as `<name>/<path>`. Context-only repositories are never written or committed; a `writable` secondary can receive the implementation changes this phase declares for it, which are reviewed and committed per repository, so name the repository for every planned change while the phase design itself writes only the returned resources. After every `archflow_apply`, trust its returned fresh view. If an offer is lost, stale, or refused, call `archflow_status` again. Perform one offered action per call and never start implementation in this invocation.

When the server returns the no-submission `refresh-stale-baseline` action, apply only that offer and use the fresh view: it retires a stale disposable baseline interface without recording a human choice. When it returns `recover-milestone-authority`, explain that the old milestone can no longer authorize continuation, apply only that no-submission offer, and continue from the fresh production boundary. Recovery preserves repository bytes but starts a significant production/review cycle; it is not approval, adoption, review, or commit authority. Never infer either action from Git history or choose a baseline decision for the human.

The server identifies the producer family from the connected client and dispatches the configured counter-review (opposite-family by default), plus constitution review when active rules exist; never perform, spawn, or simulate either. Keep conversation, human gates, triage, and synthesis here. Delegate substantial parallel exploration or research with complete briefs and use inline work for small pieces. For a new capability or integration, research suitable maintained libraries before inventing bespoke routines. Triage material defects and re-enter review only as the server directs.

## Degraded operation

If either semantic workflow tool is unavailable, run read-only `archflow-local manual-status --task <task>`, report its position, and stop. Create no milestone, edit no workflow document, write no code, record nothing offline, and infer no approval. An offer refusal is ordinary recovery, not degraded operation.

## Production and independent review

If entry status returns `start-next-skill` with `next_action.offer`, apply its no-submission offer with this exact invocation before writing. If it names a successor without an offer, report the returned successor command and stop; this completed invocation does not own the hand-off. Otherwise require position `phase-design` with the requested phase; report a different phase or inspection result rather than bypassing it. Read the returned task design, PRD, relevant context, and prior implementation notes whose interfaces matter. Delegate substantial exploration or ecosystem research with complete briefs while keeping conversation, triage, and synthesis here.

Before detailing work chunks, perform one bounded fit check against the concrete repository, interface, dependency, risk, and verification evidence now available. Preserve a sound approved boundary rather than reopening settled decomposition for minor preferences. Distinguish a work chunk, which divides or parallelizes work inside the governed phase, from a phase-worthy increment with its own valid repository-ready outcome and verification story. A difference from the decomposition you would prefer is not by itself a defect.

If the fit check finds a material split or merge needed for coherent implementation, verification, or review, correct it only through a returned writable task-design or PRD parent, record the deviation, and include those bytes in the existing compound production result so normal server-returned review and authority govern them before implementation. Do not invent a gate, renumber beyond what the returned resources can represent, or treat edited parent bytes as authority. If the needed correction belongs to an earlier boundary or cannot be represented safely here, stop and follow the existing server-returned reopen or restart path. In particular, when a revised final bound would be below the current phase, do not edit toward an impossible cursor: explain that an explicit human request to reopen task design is required, stop, and let that skill follow the server-returned authority.

Write the `current-artifact` with the phase goal, requirements, context, files, work chunks, pinned cross-chunk interfaces, success criteria, and executable verification. Keep it within the approved phase scope. Where the phase fixes constants, budgets, or bounds, give each its value or the measurement that settles it and show derived arithmetic; where the phase carries an isolation, safety, ordering, or recovery property, name the mechanism and the executable verification that asserts it directly. Do not write implementation code; document bytes alone grant no authority. Plan only this phase. Change a returned writable task-design or PRD parent, including future-phase boundaries, only as much as required to keep the approved plan accurate; record the deviation in the same compound production result. Earlier phase designs remain immutable records. A changed parent follows the project's approval rules (human approval by default), while a phase design that changes only itself advances on its own.

Before submitting, perform one bounded author check using `review_context.rubric` verbatim and the returned active rules. Do not spawn an extra generative reviewer or author durable review policy; the server-dispatched review is the only independent review. Submit the completed current artifact and any parent updates with `{"kind":"work-result","outcome":"succeeded"}`. Do not name paths or author routing, policy, fingerprint, digest, or revision fields. Apply the offered `review`; never perform, spawn, simulate, or replace the configured rubric and constitution review.

When both workflow tools answer but `dispatch_failure` reports that the selected counter-reviewer or adjudicator route failed, or reports that the test-reviewer route failed, explain the safe message, failed role, and declared/configured route facts it returns, and name the repository when the failure names one. An invalid or unavailable invocation route never falls back to configuration, and the skill never silently retries, drops, or changes its normalized route. Offer the exact safe choices: repair the declared or configured route and resume with one identically normalized invocation, or ask the human for a one-dispatch substitute route (`model`, `effort`, optionally `provider`) and a reason. The reason is required, carries the human's words, and is recorded on the review evidence. Apply the still-current `review` offer with `{"kind":"review-dispatch","route_override":{"reason":<the human's reason>,"<failed-role>":{"model":<model>,"effort":<effort>}}}` using exactly the returned failed role (`counter-reviewer`, `test-reviewer`, or `adjudicator`). A supplied `route_override` wins only for that dispatch, never becomes invocation routing or config, and remains distinctly human-authorized; invocation-declared routing is normal run input and is never described as human- or controller-authenticated. This substitution parameterizes that one automatic review child and never skips or replaces it; it is not degraded operation — that stop path still governs when the workflow tools themselves are unreachable.

## Triage and revision

When `triage` is offered, submit exactly one disposition per returned finding. This phase design and its minimal co-produced parent corrections are the review subject; repository snapshots, prior phases, and upstream documents are evidence only. Reject unrelated or pre-existing defects unless this submission introduced, exposed, or materially worsened them, or they directly block evaluating this phase. Apply the Consequential Stopping Rule: accept only a defect with a material consequence for scope, interfaces, implementation, verification, approval, or important risk. Use `accepted-editorial` only for wording or formatting with no meaning change. Reject true but non-material observations with `non-material: does not change implementation or verification`; reject optional cleanup and preferred alternatives with evidence. Reject every `unverifiable-` gap with evidence beginning `envelope-gap: `. Phase-design approval is not a backlog-triage meeting: present blocking and accepted findings in full and summarize each rejected non-material finding in one line. When consequential issues are resolved, reject remaining notes and advance. An `escalate-` finding names a material judgment the reviewer could not make confidently: disposition it with a rationale, present it at the next human boundary, and include it in the report even if the phase advances.

Accepted findings authorize no immediate edit. Apply the separate no-submission `revise` offer first; only then edit the phase design and any returned writable PRD or task-design parent, submit a new `work-result`, and allow required review. A `revise` offer may also come from the constitution review: its detail names a rule the document does not meet or a material departure from an approved parent; resolve it the same way. Only a rule whose own `review_trigger` matched, or an exhausted attempt budget, reaches a human. A human request for changes uses the same close-then-revise sequence: record their selected opaque decision token and reason, apply `revise`, then edit.

Declare the actual human revision on the next work result. A **simple** revision is only typo, formatting, comment, or wording work that changes no meaning, behavior, scope, interface, trust boundary, input, verification claim, or parent document; it can reuse review once but always returns for approval of the final bytes. A **significant** revision is anything else, resets the attempt count to 1, and automatically runs a fresh opposite-client counter-review plus constitution review. Uncertainty defaults to significant. Explain the classification, and record a human override in either direction in `human_revision.user_override`.

## Returned decision, Git, and hand-off

Only when an offer expects `gate-summary`, submit a concise self-contained `{"kind":"gate-summary","summary":<summary>}`. It opens a nonblocking presentation. Explain conversationally the phase-design outcome, all material risks, every returned detail, and each choice with its consequence. Present every returned `presentation.reasons` entry and make `presentation.class:"exception"` conspicuous; those reasons derive from authenticated archived request bindings rather than your summary or mutable config. Also state, in plain words, how strong the review evidence is from the returned `review_strength`: which model reviewed at what effort, whether it is the same model family as this producing session, and how many findings each round raised; treat a same-family reviewer or a pass that came from a remediation round as something the human should hear as conspicuously as an exception, because they are approving on the strength of that evidence. Ask one direct question. Every returned `presentation` requires explicit human judgment. Keep opaque tokens and mechanical bindings internal unless the user requests diagnostics or audit detail. The independent review already ran and there is no optional review at the end. Never synthesize a gate when the server returns an autonomous commit or successor. (A `baseline-adoption` presentation is the exception: it resolves drift on already-reviewed bytes — typically from later commits or a merge — and is decided directly; there is no review to run, and adopting records which bytes are the reviewed baseline rather than approving new work.)

When a `presentation` is returned, stop for explicit human judgment. Later submit only `{"kind":"decision","choice":<selected presentation option token>,"reason":<human reason>}`. Never choose or infer it. A `waiver-requested` choice is not approval: apply the separate no-submission `open-waiver` offer, present its choices, stop again, and later submit the waiver's opaque token and reason. Denial or cancellation grants nothing. If no presentation is returned, do not stop for a human decision; follow the fresh server-returned action directly.

When fresh status returns `next_action.kind:"commit"`, use only returned `commit` facts, regardless of whether they follow a human gate or authenticated no-wait rule authority. Confirm HEAD matches `baseline` and `target_ref`, stage exactly every authorized path — run `git add -A -- :(top,literal)<path>` once per entry in `commit.paths` — inspect the staged task-local diff, and commit with `commit.message` and the same top-anchored literal pathspecs. Authenticated commit facts require direct execution after these checks; do not invent or request another confirmation. Preserve unrelated staged or worktree changes. After any Git failure, report it and retry safely. Call read-only `archflow_status` with the same invocation so the server observes the commit proof.

If fresh status instead blocks with a design-milestone inspection, the milestone cannot succeed as things stand and retrying the commit only loops. Explain in plain language which file or fact is in the way and what would resolve it: a stray task document nobody approved is removed, while a milestone commit that already exists and cannot be recognized needs the user's decision about the branch (or explicit re-anchoring via `echo '{"target_commit":"HEAD","reason":"<reason>"}' | archflow-local set-commit-authority --task <task>`). Never edit the archived approval or the commit history to make the check pass.

Apply an offered no-submission `start-next-skill` only for this exact invocation. Report `DESIGNED` only after fresh status proves the hand-off and names the successor; do not start implementation here:

`Claude: /<next_action.skill> <task> <next_action.skill_args...>`

`Codex: $<next_action.skill> <task> <next_action.skill_args...>`
