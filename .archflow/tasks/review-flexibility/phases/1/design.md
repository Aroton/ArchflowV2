# Phase 1 Design — Config as an editable input

**Task:** review-flexibility
**Phase:** 1 of 6
**Date:** 2026-08-19
**Scope:** task design D1–D3 only (byte-pin removal, fingerprint legacy fallback, change reporting). `approval_rules`, the template's active ruleset, gate conditionality, skill prose, and docs refresh belong to Phases 2–6.
**Fact basis:** verified against the current tree (branch `feature/review-override-flexibility`, `dd32d66`); all file:line references below were re-checked during this phase design. Deltas found versus the task design's citations are listed in "Deviations from the task design" — none change its decisions.

## Phase goal

Turn `.archflow/tasks/<task>/config.yaml` from a byte-pinned constant into an ordinary editable input:

1. No comparison of live config bytes against the recorded creation-time digest ever fails a workflow step (D1). The digest survives only in creation-time provenance roles.
2. `config_digest` leaves the `InputFingerprintSubject` composition; a bounded legacy-composition fallback in the single internal resolver keeps in-flight tasks (including this one) valid across the cutover (D2).
3. A `last_seen_config` snapshot in task state drives a field-level change notice in the status value; unparseable config stays fail-closed (D3).

This delivers PRD observable criteria 1 and 6.

## Requirements mapped to this phase

| Source | Requirement |
|--------|-------------|
| PRD R1 | Editing config at any point never produces a workflow error attributable to the edit; config content leaves the input fingerprint; existing evidence and open gates stay valid. |
| PRD R2 (status half) | Field-level change notice (old → new) in the status view when config differs from last-seen. Informational only; nothing blocks. (The gate-presentation half of R2 lands with the triggered-gate presentation work in Phase 4, per the task design's phase file allocation.) |
| Task design D1 | Delete the six live-byte `PINNED_CONFIG_MISMATCH` comparisons and the status-side pin verification; keep `CONFIG_INVALID` fail-closed; remove the `pinned-config-schema-unsupported` branch, the `restore-pinned-config`/`upgrade-tooling` next actions, and the `PINNED_CONFIG_MISMATCH` error vocabulary. |
| Task design D2 | Subject drops `config_digest`; resolver returns the accepted fingerprint value; bounded legacy fallback keyed on the recorded creation-time `state.config_digest`; never rewrites recorded values. |
| Task design D3 | `last_seen_config` in `TaskStateV1`, recorded by the transaction kernel; leaf diff in status; retired-`producer` normalization before diffing. |

### Chunk B — Resolver accepted-value contract and legacy fallback

- `src/state/read.ts`: `FingerprintReadContext` gains `expected_input_fingerprint?: Sha256Digest`, supplied per call site.
- `src/state/fingerprint.ts`: delete the pin check (:79-88). The resolver returns a result carrying **both** the subject (new composition) and the **accepted fingerprint digest**:
  - Compute the new-composition digest. If no `expected_input_fingerprint` is supplied, or it matches, that is the accepted value.
  - On mismatch, recompute **once** under the legacy composition — the pre-change field set, with `config_digest` taken from the recorded creation-time `state.config_digest`, never from live bytes. Accept on match. If neither matches, the resolver returns the new-composition value; the caller's existing mismatch error fires unchanged (fail-closed preserved).
  - The fallback never rewrites any recorded value. **Composition convergence model:** comparing sites — the kernel, the local envelope, and the gate-reentry *replay validations* — require the accepted value to equal the recorded/claimed fingerprint (`buildPlan` enforces `plan.next_state.input_fingerprint === identified.input_fingerprint`, `src/state/transaction.ts:801-803`), so a legacy-state task keeps its legacy composition on the ordinary path. The composition flips to the new one only at the **no-expected write sites**: revision zero, the planning-restart landing recomputes (`gates.ts:683`, `state.ts:200`), and the gate-reentry *landing* computations (`gates.ts:591`, `:1402`), which write the freshly recomputed fingerprint by construction. This is the corrected form of the task design's "converge as they transact" wording (see Deviations).
- Update all six callers to the new return shape:
  - `src/state/transaction.ts:418` (`liveIdentification`): pass `expected_input_fingerprint = request.call.input.input_fingerprint`; compare the returned accepted value at the existing :429 check.
  - `src/state/initialization.ts:264` (revision zero): no expected value; record the new-composition fingerprint in the identification.
  - `src/state/gates.ts:683` and `src/mcp/handlers/state.ts:200` (planning-restart recomputes): no expected value; the landing state records the new-composition fingerprint.
  - `src/local/call-envelope.ts:94` (`fingerprintFor`): pass `expected_input_fingerprint = services.state.value.input_fingerprint`; return the accepted value (legacy composition when that is what the recorded fingerprint was computed over). The existing gate/waiver short-circuit (:81-83) is unchanged.
  - `src/state/production.ts:378-400` (`resolve_gate_reentry_fingerprint`): digest the resolver's returned accepted value instead of recomputing over the subject (:399), and split the seam by use — the **replay-validation** calls (`gates.ts:860-868`, `:895-904`) pass `expected_input_fingerprint = current.value.input_fingerprint`, so the legacy fallback keeps a pre-cutover landing replayable after the cutover; the **landing** calls (`gates.ts:591-611`, `:1402-1416`) omit the expected value and write the new composition. Evidence continuity across a reentry does not ride the landing fingerprint at all: it rides the recorded `pending_human_revision.predecessor_input_fingerprint` pair (`gates.ts:620-630`), which `boundToDeclaredPredecessor` (`src/review/fixed-point.ts:114-122`) compares against the evidence's own recorded fingerprint — untouched by this phase.

## Pinned cross-chunk interfaces

1. **Resolver return:** `ProjectResult<{ subject: InputFingerprintSubject; fingerprint: Sha256Digest }>` — `fingerprint` is the *accepted* value (new composition, or legacy when legacy matched the expected digest). Comparison sites compare `fingerprint`, never recompute.
2. **Expected-digest seam:** `FingerprintReadContext.expected_input_fingerprint?: Sha256Digest` — supplied only where the recomputation is *compared* to a value the same call shape produced: the kernel (request's claim), the local envelope (state's record), and the gate-reentry replay validations (state's record). Absent at revision zero, both planning-restart recomputes, and the gate-reentry landing computations.
3. **Legacy composition:** exactly the pre-change subject field set with `config_digest = state.config_digest` (creation-time record, never live bytes). Retry-once-and-accept; no recorded value is ever rewritten. Comparing sites keep recording the accepted (possibly legacy) value — the composition flips to the new one only at no-expected write sites (revision zero, planning-restart landings, gate-reentry landings).
4. **`TaskStateV1.last_seen_config?: TaskConfigSnapshot`** — plain-JSON parsed config, `type` alias graph, zod-optional, written only by the kernel's commit-time normalization and revision-zero seeding.
5. **`computeConfigChange(before, after) → readonly ConfigChangeEntry[]`** and **`normalizeForChangeDetection`** — pure functions in `src/state/config-change.ts`; status and (in Phase 4) gate presentations both consume this one module.
6. **`TaskStatusV1.config_change?: readonly ConfigChangeEntry[]`** — informational; never a blocker, never an action-kind change.

## Success criteria

- PRD criterion 1 (status half): a mid-task config edit (routing, `max_attempts`, any field) produces no error anywhere in the apply/status path; the next transaction accepts, uses the new values, and status reports the field-level change.
- PRD criterion 6: a config edit made while a gate is open and after counter-review evidence exists invalidates neither — the gate remains resolvable against the same evidence (fingerprint stable: live config no longer composed into it), and status adds only the change notice.
- This task's own recorded evidence (config in the legacy subject composition) still validates after the Phase 1 cutover — including after this task later edits its own config (Phase 3 switchover) — via the recorded-digest fallback.
- Unparseable config still fails closed (`CONFIG_INVALID` in the kernel; `config-invalid` blocker + `inspect-state` next action in status).

## Deviations from the task design (facts, not decisions)

The task design's D1–D3 decisions all hold; these are citation-level corrections and one seam clarification discovered during verification:

1. `TaskStateV1` is declared in `src/contracts/durable-state.ts:251`, not `durable.ts`; `durable.ts:713` is the (correctly cited) agreement check. `last_seen_config` therefore lands in `durable-state.ts`.
2. A seventh `PINNED_CONFIG_MISMATCH` producer exists: `verifyPinnedConfig` (`src/contracts/fingerprints.ts:397-405`), called only from status (`src/state/status.ts:760`). D1's six-site list becomes seven enforcement deletions (six comparisons + one factory).
3. Two resolver callers exist beyond D2's list: `src/mcp/handlers/state.ts:200-207` (PRD planning-restart recompute; recorded-not-compared, takes the new composition) and `src/state/production.ts:378-400` (`resolve_gate_reentry_fingerprint`; a comparing site that must pass the recorded fingerprint as expected so reentry preserves composition continuity). D2's caller list is extended accordingly.
4. D3's implication that the transaction kernel is the only state writer is wrong: the gate lifecycle and revision-zero initialization also write state.json. `last_seen_config` recording is therefore a shared helper applied on every config-reading commit path, and settlement commits that never read config intentionally leave the baseline unchanged (the notice persists to the next config-observing commit).
5. D2's claim that "new writes always use the new composition, so tasks naturally converge as they transact" is contradicted by the machinery it relies on: comparing sites must record the accepted (legacy) value (`buildPlan` equality at `src/state/transaction.ts:801-803`), so convergence happens only at no-expected write sites — revision zero, planning-restart landings, and gate-reentry landings (whose recomputation can never equal the pre-reentry recorded value in any composition, since the synthetic call's step differs and so does its rubric digest). The task design's D2 wording is corrected in the same production result.
6. There is no notice surface in the status/semantic-view values today, so D3's "`config_change` notice in the status value" is a new optional field on `TaskStatusV1` (not a new value of an existing notice kind). No parent change required — D3 did not assert an existing surface.
7. Seam clarifications for D2/D3, within their contracts: the expected digest enters through `FingerprintReadContext.expected_input_fingerprint` (per-caller), because the same resolver serves comparing and recording call sites; and the `last_seen_config` injection happens inside draft finalization (`buildPlan`, before `prepared_state` derivation), because the committed bytes must equal the intent receipt's prepared state (rank 8b, `src/contracts/durable.ts:805-830`).
8. The task design's D3 gate-presentation bullet is allocated to Phase 4 by the phase plan's file list (`gate-decision-interface.ts`); this phase delivers the status-side notice only. Recorded here so the phase boundary is explicit.

One task-design correction is recorded with this phase (item 5); no other parent change is required.
