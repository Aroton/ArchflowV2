# Phase 15 Design Counter-Review

1. **Blocker — the gate-owned supplemental route has neither an admissible storage key nor a producer before its first read.** The design says to retain a payload and manifest under a gate-scoped `decision` key and then have `resolve_supplemental_review` load it (`phase-15-five-tool-mcp-assembly-and-offline-local-cli.md:96-100`), but the `decision` path class admits only `decisions/<gate-id>/{request,decision}.json` (`src/repository/paths.ts:62-68,117-120,148-152`); `ensureDecisionDirectory` only creates directories (`src/state/layout.ts:87-98`). More importantly, the first supplemental wake invokes the resolver with only `{authority, request}` (`src/state/gates.ts:1038-1045`), while the proposed `archflow-local gate-counter` writes only the Markdown wake-up projection and that projection is explicitly non-authoritative. “Write when the gate service accepts” is circular because acceptance already needs the resolver (`src/state/gates.ts:596-605`). **Suggested resolution:** pin one concrete immutable gate-owned record, such as `decisions/<gate-id>/supplemental-review.json`, with a schema embedding the validated `ReviewEvidence`, gate/request bindings, evidence digest, and projection digest. Admit that exact path to the immutable writer, have `archflow-local gate-counter` create/reuse-identically that record first and atomically publish the Markdown projection last, and make the resolver read only the retained record. The gate ID is then the real non-colliding key and the record never enters `state.authoritative_results` or the `PipelineStep` map.

2. **Blocker — the proposed resolver cannot authenticate the assurance and family bindings it claims.** `parseReviewEvidence` accepts a structurally valid `server-attested` object (`src/contracts/review.ts:150-179`), but genuine server attestation is minted only from an invocation-scoped observation capability (`src/contracts/trust.ts:88-105`). The second-terminal helper observes no dispatch capability, and the existing supplemental check only compares the evidence to a caller-authored slot (`src/state/gates.ts:489-500`), so a forged slot and forged evidence can agree. `ReviewEvidence` also carries no `gate_id`; only a surrounding authority record can bind it. **Suggested resolution:** constrain this manual route to `assurance: "degraded"`, bind `gate_id` in the new retained record, derive the producer family from the archived gate request's authenticated current-evidence slots, require the reviewer family to be the exact opposite, and reject `server-attested` unless a separate real dispatch/observation-capability path produced and retained it.

3. **Blocker — supplemental triage remains unauthenticated, so a fabricated digest can resolve or supersede a gate.** `SupplementalReviewOutcome` carries bare `triage_digest` and `accepted_triage_digest` strings (`src/contracts/supplemental.ts:10-14,24-30`). `authenticSupplementalReview` authenticates only review evidence (`src/state/gates.ts:472-500`), and the supersession path copies `accepted_triage_digest` directly into the archived decision without reading a triage artifact (`src/state/gates.ts:607-617`). This misses REQ-41's requirement that the supplemental result be triaged before resolution and that only an accepted change re-enter the fixed point. **Suggested resolution:** add gate-scoped retained supplemental-triage authority (or a single gate-owned compound review-plus-exact-cover-triage record) and authenticate its digest, complete finding dispositions, and no-change/accepted outcome before admitting `triage-no-change` or `supersede`. Include it in the same archive and maintenance walk; decline remains the only resolver-free branch.

4. **Blocker — an explicit decline loops back into `SUPPLEMENTAL_REVIEW_REQUIRED` when the projection exists.** `currentSupplementalLedger` accepts an exact decline (`src/state/gates.ts:444-469`), but `runDurableGate` sets `already_recorded` only when a non-decline ledger entry exists (`src/state/gates.ts:1029-1035`). The persistent projection therefore wakes the waiter again, invokes the resolver, and returns `SUPPLEMENTAL_REVIEW_REQUIRED`, contradicting both the design's resolver-free decline and REQ-41's requirement that declining not prevent an otherwise valid decision. **Suggested resolution:** treat any exact authenticated caller supplemental outcome, including decline, as having handled that projection (or remove/retire the projection on decline), modify `src/state/gates.ts`, and add an end-to-end `runDurableGate` decline-then-decision test rather than testing only the lower-level resolver.

5. **Blocker — the `archflow_state` prepare callback cannot be implemented as the design specifies.** Chunk 4 says to dispatch the seven artifact variants only between `planCheckpointAdoption` and `planStateTransition` (`phase-15-five-tool-mcp-assembly-and-offline-local-cli.md:163`). `planStateTransition` returns only `ProjectResult<NextStateDraft>` (`src/state/transitions.ts:179-205`), while `runStateTransaction` requires a complete `PreparedTransaction` with a correlated expectation and result (`src/state/transaction.ts:88-92,1016-1023`), and a succeeded artifact also needs an authenticated result reference and installation (`src/state/transaction.ts:580-631`). Documents, implementation outputs, self-review, and triage require different existing verification/snapshot/evidence preparation paths; checkpoint adoption is the only listed planner that supplies more than a pure transition. **Suggested resolution:** pin the per-artifact preparation table: initialization through `runStateInitialization`; document snapshot preparation; implementation-manifest verification plus snapshot preparation; self-review/triage through `prepareEvidenceResult`; manual checkpoint adoption through `planCheckpointAdoption`; and artifact-free transitions through `planStateTransition`. Each succeeded arm must build the exact expectation/result/reference/installation tuple before entering the kernel.

6. **Blocker — exact replay still launches another model before the transaction kernel can recognize it.** `runCounterReview` resolves and dispatches before `runStateTransaction` (`src/review/counter-review.ts:85-119`), and `runAdjudication` does the same (`src/review/adjudication.ts:374-428`). Replay detection is inside `runStateTransaction`, after those calls. Wiring handlers directly to these services therefore violates REQ-23/REQ-25 by consuming a second model attempt for the same committed intent, even if the kernel later returns the retained result. **Suggested resolution:** add an authenticated pre-dispatch intent/replay operation that returns the committed tool outcome or resumes an immediate prepared receipt without dispatch, and call the service only for a genuinely new intent; alternatively refactor both services so dispatch occurs inside a kernel-owned prepare path that is never invoked for replay. Add call-count tests for exact replay and receipt-only recovery.

7. **Blocker — expected routing and child failures cross the pinned callback seam as exceptions and become `INTERNAL_ERROR`.** `resolveDispatchRoute` throws `DispatchRoutingError` (`src/dispatch/routing.ts:19-28`), adapter/preflight/output failures throw `CliAdapterError` (`src/dispatch/cli.ts:125-149`), and `runDispatchChild` throws `DispatchProcessError` for cancellation, timeout, overflow, and I/O (`src/dispatch/process.ts:40-49,218-234`). The coordinator's pinned callback type returns only success bytes, while `runCounterReview` does not catch any of these and `runAdjudication` catches only post-dispatch observation validation. At the MCP boundary an uncaught handler error is deliberately flattened to `INTERNAL_ERROR`, missing REQ-29/31/35 and the phase success criterion for distinguishable host/family/child errors. **Suggested resolution:** make the dispatch/service seam return `ProjectResult<DispatchResult>`, or explicitly catch all typed routing/adapter/process errors in both services and return their `project_error`; reserve thrown errors for defects. Test every stable failure class through the live handler boundary.

8. **Blocker — cancellation and attempt telemetry cannot satisfy the design's own verification case.** `CliAdapter.preflight(workspace)` has no signal, and both preflight children receive a fresh never-aborted `AbortController().signal` (`src/dispatch/cli.ts:74-83,183-196`), so MCP cancellation during version/auth preflight does not terminate active descendants. After preflight, `runDispatchChild` throws on cancellation/timeout (`src/dispatch/process.ts:218-234`), but the design writes the attempt record only after failure classification/output parsing (`phase-15-five-tool-mcp-assembly-and-offline-local-cli.md:127-131`); that code is unreachable for a cancelled child, contradicting the required cancellation test. **Suggested resolution:** thread the invocation signal and cancellation source through adapter preflight, and define attempt-record finalization around the whole selected-adapter operation so preflight/launch failures and cancellation record available managed-policy/version facts before rethrow/return. Publish the diagnostic record in a `finally`-style path without allowing its failure to mask the primary classified error.

9. **Blocker — the single adjudication `open_gate` derivation is false for the constitution-edit arm.** The design assumes “by the time it fires the result has committed” and derives gate inputs from committed adjudication evidence (`phase-15-five-tool-mcp-assembly-and-offline-local-cli.md:170-173`), but `runAdjudication` calls `open_gate` for a detected constitution edit before dispatch or result commit (`src/review/adjudication.ts:332-342`). No committed adjudication evidence or post-commit revision exists in that arm, and the service can return only `{gate}` while the wire `archflow_adjudicate` success requires `path`, `constitution`, `drift`, `triggers`, and `revision` (`src/contracts/mcp-tools.ts:46-47,128-141`). **Suggested resolution:** define a distinct pre-dispatch constitution-edit gate adapter derived from current canonical state and the original call, with a classified non-success/retry contract for `archflow_adjudicate`; keep the post-commit deterministic gate adapter only for adjudication-result obligations. Specify how crash-window replay reconstructs the retained adjudication wire result without redispatch after synthetic gate state has removed the original committed-intent head.

10. **Blocker — the live production graph is rejected by the release builtin-import policy before staging.** `RELEASE_BUILD_PROFILE.allowedImports` and the launch-profile schema permit only buffer/crypto/module/process/util (`scripts/release-support.mjs:67-73`; `src/contracts/schemas/v1/release-manifest.schema.json:312-314`), and both build and payload validation enforce the list (`scripts/release-support.mjs:938-939,1180-1182`). The newly reachable state/repository/dispatch graph imports additional builtins including `node:async_hooks`, `node:child_process`, `node:fs`, `node:fs/promises`, `node:os`, `node:path`, `node:perf_hooks`, `node:stream`, and `node:timers/promises`; chunk 6 never widens or re-derives the allowlist. **Suggested resolution:** pin the exact union required by the two real entry outputs, update the manifest schema/derivation/validator and contract tests, and validate imports per output. This is independent of the owner-approved loader-policy deletion.

11. **Blocker — the fixed “five new installed dependencies” legal inventory is not the graph live handlers create.** Legal validation derives every contributing installed package with `bytes_in_output > 0` and requires exact equality with `current_components` (`scripts/release-support.mjs:712-746`). Beyond the named Ajv closure, production wiring reaches at least `yaml` (`src/contracts/yaml.ts:1`), `write-file-atomic` and `signal-exit` (`src/state/atomic.ts:5`), and the contributing Secretlint closure (`src/state/secret-scan.ts:3-5`). A probe over the actual modules also reports contributing `@secretlint/core`, `@secretlint/profiler`, `@secretlint/secretlint-rule-preset-recommend`, `boundary`, `debug`, `ms`, and `structured-source`. The prescribed five LICENSE files and fixed `dist/` count therefore cannot pass legal correlation. **Suggested resolution:** remove the fixed five/count assumption, derive the installed contributor closure across both staged outputs, retain one exact installed-copy legal source for every resulting component (disambiguating same-version embedded copies), and update the file plan and tests from that derived closure.

12. **Blocker — the proposed legal staging/promotion sequence cannot produce its first valid stage and uses an intermediate commit to bypass a known contradictory invariant.** `buildReleasePayload` materializes a stage and immediately validates it (`scripts/release-support.mjs:1237-1239`), while every existing decision must already bind the new bundle/inventory/entry/handler tuple. Thus the design's first `release:stage` with stale legal evidence exits unsuccessfully; after authoring evidence it omits the required second stage. Promotion then forbids changing any HEAD decision bytes (`scripts/release-support.mjs:1361-1380`), the exact contradiction already recorded in `architecture.md:514`; committing the changed decision first merely moves it into HEAD to evade that check and temporarily commits an inconsistent legal/release set. **Suggested resolution:** add an explicit preview/two-pass operation that computes candidate bundle, dependency, entry, and handler bindings without claiming finalized legal acceptance; obtain the human decision from that preview; then run one normal validated stage. Revise the HEAD immutability/supersession model so an explicitly re-authorized decision can be promoted atomically without a commit-around.

13. **Blocker — keeping provenance MCP-only leaves the helper entry unbound despite the architecture requiring a complete server/helper manifest.** Current validation requires the global metafile input set to equal top-level `bundle_inputs` and treats one output as authoritative (`scripts/release-support.mjs:930-950`). The design keeps `bundle_inputs`, `contributing_inputs`, dependency inventory, and launch profile bound only to MCP while placing the helper only in `build_entries`/`artifacts`. Local-only source and dependency changes therefore lack source/dependency provenance, and the current global input equality fails as soon as the second entry is present. **Suggested resolution:** model the minimal per-entry provenance needed for both outputs (entry/output digest plus exact source/dependency input set is sufficient; per-input byte contribution need not be generalized), derive the installed legal closure across both outputs, validate each output against its entry, and mutation-test local-only source drift.

14. **Blocker — adjudication crash/restart assembly omits the authority and result-recovery seams needed to resume without redispatch.** `assessCurrentEvidence` treats a prior gate as satisfied only through `AuthenticatedGateApproval` capabilities (`src/review/fixed-point.ts:150-201`), which must be minted by rereading canonical state plus the archived request/decision through `loadAuthenticatedGateApproval` (`src/state/gates.ts:296-370`). The design says only to call `assessCurrentEvidence`; without loading every approval capability, it can select an already-resolved first obligation again. After a synthetic gate advances, the original adjudication receipt is no longer the current `committed_intent`, yet the handler must return the retained `AdjudicateSuccess` without calling `runAdjudication`, which redispatches. **Suggested resolution:** pin crash-entry subject assembly (authentic constitution, retained evidence set, every authenticated approval, live waivers, and max attempts), deterministic next-unsatisfied-gate derivation, and an authenticated loader that reconstructs the retired adjudication tool outcome from its retained result/receipt for the wire response.

15. **Major — `archflow-local maintain` lacks the candidate and immutable-record assembly required by the existing maintenance API.** The new helpers enumerate only `MaintenanceRoots` and manifests, but `computeMaintenanceProof` also requires fully resolved and digested `MaintenanceCandidate[]` (`src/state/maintenance.ts:54-68`), and `performMaintenance` requires a complete human-authored, proof-bound `MaintenanceRecordV1` plus its resolved target (`src/state/maintenance.ts:151-189`). No chunk discovers bounded unreferenced-attempt/superseded-payload candidates or binds the helper's human reason and maintenance ID into the immutable record, so this is not a thin adapter over existing exports. **Suggested resolution:** add a bounded candidate enumerator and specify how `maintain` accepts the explicit human reason/ID, constructs and validates the exact proof-bound record, resolves its create-exclusive target, and only then deletes admitted candidates.

16. **Major — one supported producer direction remains disabled because the production `allow_claude_dispatch` decision is not made.** `selectCliAdapter("codex")` returns `CONFIG_FAMILY_UNSUPPORTED` unless `{allow_claude_dispatch: true}` is passed (`src/dispatch/cli.ts:468-478`). The coordinator input leaves this optional and the handler/session chunks never state what production supplies, so a Codex producer cannot launch the required Claude-family counter-review/adjudication path. **Suggested resolution:** explicitly separate implementation enablement from release authorization: wire the reviewed production/fixture policy deliberately (including the still-blocking VAL-14 legal gate), and test both producer directions rather than relying on the option's default.
