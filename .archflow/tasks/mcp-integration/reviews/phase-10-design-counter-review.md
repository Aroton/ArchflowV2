## Finding 1 — BLOCKER: Request/receipt identity for artifact-carrying operations is undefined, and the modules that must change are absent from Files

The revision-0 initialization and the checkpoint-adoption transactions both "use Phase 9's receipt-first/state-last protocol." A Phase 9 receipt binds `tool`, `operation`, and `request_digest` (`src/contracts/durable-intent.ts`, `intent-receipt.schema.json`), and `INTENT_MISMATCH` classification is request-digest comparison (transaction truth table). But the shipped request identity for `archflow_state` is closed to exactly one operation, `record-state-boundary`, with exactly `phase_instance`, `step`, `status` (`src/contracts/fingerprints.ts:46-48`, enforced by the compile-time `ExactSelectorCoverage` at `fingerprints.ts:67-86`; selector at `src/state/request.ts:19-20`). `StateInput` has no `artifact` member at all and its Zod contract is strict (`src/contracts/mcp-tools.ts:33`).

Consequence if implemented as written: nothing binds the initialization manifest or the supplied checkpoint chain into the request digest. After a committed import, re-delivering the same `intent_id` with refreshed CAS and a **different** chain (or a different initialization manifest) computes the same request digest and the same caller-asserted fingerprint path, so the kernel's replay row returns the earlier success instead of `INTENT_MISMATCH`. That violates REQ-23 ("reusing an identity with different inputs is rejected as `INTENT_MISMATCH`") and the architecture's pinned closed digest field list, which explicitly includes "that operation's request-specific semantic fields from the five-tool table **and closed artifact union**" (architecture, Request and Mutation Flow). The design's own Verification Steps demand "exact and mismatched initialization retries," which is unimplementable without this.

The design is silent on all of it, and the Files table touches neither `src/contracts/fingerprints.ts`, `src/state/request.ts`, `src/contracts/mcp-tools.ts` (or wherever the transport-neutral artifact-carrying call shape will live), nor their tests (`test/unit/fingerprints.test.ts`, `test/unit/state-request.test.ts`, `test/unit/mcp-tools.test.ts`). Note the compile-time exhaustiveness guard means the implementer *cannot* extend the input shape without editing `fingerprints.ts` — the omission will be discovered mid-implementation as a build break, forcing unplanned contract decisions at the worst time.

**Suggested resolution**: Pin in the design (a) how the artifact reaches the transaction — enabling the relevant `archflow_state.artifact` union members on a transport-neutral parsed-call shape, or an equivalent internal request form; (b) distinct operation literals for the artifact-driven operations (direct initialization, legacy initialization, checkpoint adoption) versus the plain state boundary; (c) the exact semantic fields each operation binds into the request digest (the artifact value or its canonical digest satisfies the architecture's closed-list requirement); and (d) add the affected modules and tests to Files/Work Breakdown. This decision also resolves Finding 2.

## Finding 2 — MAJOR: The narrow adoption seam has no durable discriminant, so rank 8a cannot be relaxed without weakening the invariant Phase 9 forbids weakening

`src/contracts/durable.ts:764` (`intent-receipt-adopted-checkpoint-mismatch`, rank 8a) hard-fails any prepared relation whose prepared state changes `adopted_checkpoint`, and the kernel both validates that relation before installing a receipt (`src/state/transaction.ts:369`) and independently enforces preservation in `assertPreserved` (`transaction.ts:170-183`). An adoption transaction legitimately changes exactly that field. The design says to extend `durable.ts` "for … whole-chain adoption" and `transaction.ts` with a "narrow internally authenticated checkpoint-adoption mode," but never says how the **consolidated validator** — which also runs over retained receipts outside the live transaction (replay/ambiguity paths at `transaction.ts:433`/`464`, plus this phase's own audit/repair classification) — distinguishes an adoption receipt from an ordinary one from durable facts alone.

If adoption receipts reuse the `record-state-boundary` operation literal, there are only two outcomes: rank 8a is relaxed for *all* prepared relations (exactly the "silently weaken this kernel's preservation invariant" the approved Phase 9 design prohibits), or legitimately committed adoption receipts fail semantic validation whenever they are re-examined. Either way the code differs from what a correct design would produce.

**Suggested resolution**: Record the adoption (and initialization) transactions under distinct receipt `operation` literals (Finding 1), and pin the adoption-aware prepared relation as a separate subject mode selected on that durable evidence, so ordinary receipts keep the exact preservation check. Also pin how the kernel's adoption authorization is authenticated — a non-exported planner-minted capability following the existing `TransactionAuthority`/WeakSet pattern — so no ordinary caller can flip the kernel into adoption mode via a plain flag.

## Finding 3 — MAJOR: Explicit abandoned-lock repair is assigned to this phase and is absent from its scope

The approved Phase 9 design assigns to Phase 10, verbatim: "explicit repair for abandoned locks or foreign/superseded receipts," and its recorded crash story depends on it — "A `SIGKILL` receipt-only crash resumes only after that explicit lock repair" (Phase 9 Non-Goals; Phase 9 log Gotchas: an abandoned `.transaction-lock` blocks until out-of-band removal of the exact verified directory; architecture: "an abandoned lock stops for explicit repair"). The Phase 10 design's `repair.ts` scope covers only caller-bounded retained-history *documents*; the word "lock" appears in the design only as chunk 6's never-do ("never … removes an abandoned task lock" on the handoff path). No success criterion, verification step, or chunk classifies an abandoned lock or produces its repair action, and no later phase owns it (Phase 15 wires handlers, 17 owns status, 18 owns manual/degraded flows).

As designed, the headline REQ-22 recovery path this phase claims in success criterion 2 — receipt-only crash resume — is unreachable after the very `SIGKILL` case Phase 9's crash suite pins, because the resume is gated behind a repair operation that will not exist.

**Suggested resolution**: Extend `repair.ts` scope to classify the exact verified abandoned lock and return a precise, explicitly human-confirmed repair action that removes only that verified lock directory (never age/staleness-inferred, per Phase 9's decisions); cover it in success criteria and the crash-suite verification. Alternatively, explicitly reassign ownership with the user and record the new owner in the architecture — silence is the only wrong option.

## Checked and found sound (no finding)

- **Revision independence after multi-checkpoint adoption** — the specific attention item. Verified at the validator level: today rank 5m (`durable.ts:530-536`) forces `expected_state_revision === predecessor.revision` and rank 5p forces `state.revision === expected_state_revision`, which is unsatisfiable after any multi-checkpoint adoption (state advances once, the head advances by chain length). The design's chunk 1 change — delete that equality, keep 5p/5q authenticating current state and 5s (`durable.ts:562-571`) authenticating `state.adopted_checkpoint` against the wrapper predecessor — is necessary and sufficient at this layer, and the success criteria pin the right observable (state advances once per transaction while checkpoint revision follows the adopted head).
- **State-anchored first checkpoint** fits the shipped contract: the current Zod refinement admits only revision-1-with-initialization or revision≥2-with-predecessor (`durable-checkpoint.ts:217-231`), so the anchored branch ("immediate successor" of the anchored state revision, retaining the initialization digest, only when no checkpoint is adopted) is a clean third discriminant, and `ChainAnchor` (`durable-checkpoint.ts:294-310`) extends naturally.
- **Reuse claims are real**: `readHistoryStatus` (`src/repository/history.ts:296`) and `classifyMutationReadiness` (`:385`) exist; `GIT_CONFLICT`, `GIT_DIVERGED`, `HANDOFF_REQUIRED`, `STATE_MISSING`, `RECONCILIATION_REQUIRED`, `TRANSITION_INVALID` already exist in the closed error registry, so the design correctly needs no `errors.ts` change for its classifications. All named test files exist. The receipt contract already provisions `prior_revision: 0` for the initialization sibling.
- **Over-engineering**: none found that meets the bar. Bounded reconciliation vs. explicit audit/repair separation, the immutable handoff record, and preserve-both-heads semantics are each explicitly established by the architecture's request-flow and one-writer-handoff sections, not invented here; the design also correctly claims no new dependency and defers directory enumeration to Phase 15 and payload restore to Phase 11.

Findings: 1 blocker, 2 major. Nothing else met the materiality bar.

## Triage

### Finding 1 — Accepted

The design now enables the closed optional `archflow_state.artifact` union and pins an exhaustive operation map: no artifact uses `record-state-boundary`; the five artifact kinds use `adopt-task-initialization`, `adopt-legacy-import-initialization`, `record-document-artifact`, `record-implementation-output`, or `adopt-manual-checkpoint-import`. Every artifact operation binds the phase/step/status, artifact kind, and recomputed canonical artifact digest into the request digest. The Files, work breakdown, success criteria, and verification sections now include `mcp-tools.ts`, the MCP JSON Schema, `fingerprints.ts`, `state/request.ts`, and their tests, including changed-manifest and changed-chain `INTENT_MISMATCH` cases.

### Finding 2 — Accepted

The design now gives checkpoint adoption both required discriminants. The retained receipt carries durable operation `adopt-manual-checkpoint-import`, which the consolidated semantic validator uses to permit the exact adoption relation while leaving rank 8a unchanged for ordinary receipts. The live adoption planner separately mints a non-exported WeakSet-authenticated capability consumed by the transaction kernel, so a caller cannot enable adoption through a plain flag. Verification now covers retained-receipt validation, operation/capability mismatch, ordinary receipt preservation, and rejection of any other pin change.

### Finding 3 — Accepted

The explicit repair chunk now owns abandoned task-lock recovery. Repair requires separate human confirmation that no writer is live, re-resolves only the fixed `.transaction-lock` direct child beneath authenticated task authority, rejects symlinks, non-directories, unexpected contents, missing/replaced targets, and removes only the exact empty directory. It never infers abandonment from age or metadata and never performs automatic takeover. Success criteria and real-process verification now require a SIGKILL lock-plus-receipt crash, blocked ordinary acquisition, negative repair cases, exact repair, and same-intent resumption with refreshed CAS.
