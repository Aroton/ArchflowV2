# Phase 19 Design Counter-Review

- **blocker — A destination initialized after `prd` cannot run the current pipeline from that cursor.** Revision 1 deliberately starts with empty `authoritative_results` and `approvals` (`src/state/initialization.ts:156-174`), while the design materializes imported documents only as files. Current production/status requires retained upstream produce results for every non-PRD phase (`src/state/produce-subject.ts:31-80`) and requires an `artifact-approval` bound to every upstream digest (`src/review/fixed-point.ts:350-366`). Consequently `design` has no authoritative approved PRD, `phase-design-<n>` has no authoritative approved PRD/design, and `phase-impl-<n>` has no authoritative approved design/current phase design; status falls to `fixed-point-disagreement` before the resume phase can produce. This contradicts the design's claim that cursors past `design` are limited only in terminal completion. **Suggested resolution:** preserve the settled direct-cursor decision but add an explicit pre-resume bootstrap for every prerequisite document: create retained current-version produce/review/triage/adjudication evidence and obtain fresh explicit approvals without treating imported evidence as authority, then make revision 1 authenticate those results/approvals while its active cursor remains caller-declared. Add end-to-end cases for `design`, `phase-design-<n>`, and `phase-impl-<n>` that reach the resume phase's produce step through real status/handler code.

- **blocker — The advertised cross-repository source path cannot initialize.** The design explicitly expects a separate source repository to work and tests for a differing `source_identity_digest`, but the shipped `validateLiveInitialization` resolves `import_baseline_commit`, `code_baseline_commit`, and `policy_base_commit` through the destination runner (`src/state/initialization.ts:102-118`). A source repository's import baseline will normally be absent from the destination object database, so the real handler rejects the emitted manifest before revision 1. **Suggested resolution:** validate `import_baseline_commit` against the authenticated source runner in the offline stager, and change destination initialization to require only the destination-owned code and policy commits there. Add an end-to-end two-repository case that reaches committed revision 1, not only a staging identity assertion.

- **blocker — Initialization trusts the claimed import digest and staged references without authenticating the staged import.** The ordered pass computes a digest, but the design's only server-side addition is `mapping[].destination_path` classification. Current initialization does not recompute `import_digest`, require every mapped `legacy_path` to name a staged ref, or read `imports/<import-digest>/payload/...` to verify its digest and byte count. A caller—or the explicitly supported hand-authored manual route—can therefore alter the mapping, claim an arbitrary import digest, omit/corrupt payloads, and still commit state and later open an audit over that unauthenticated digest. The design also never materializes the architecture's required `imports/<import-digest>/manifest.json`; it emits the initialization manifest only on stdout while `state.initialization_digest` purports to name an adopted document. **Suggested resolution:** persist one canonical import manifest at the declared import path, make its digest subject exactly specified and shared by stager/server, and have `runStateInitialization` reload it plus every staged ref, verify mapping membership, byte counts and content digests, and require byte-equivalence with the submitted initialization artifact before committing revision 1. Exercise missing, changed, and mismatched staged material through both direct and initial-checkpoint adoption.

- **blocker — The migration audit is neither a durable prerequisite for advancement nor placed after evidence reaches a fixed point.** As designed, only the skill promises to open it. Current `deriveNextAction` requires only `artifact-approval` for PRD/design/phase-design and `commit-authorization` for phase implementation (`src/state/next-action.ts:88-115`); once any gate resolves, `nextStateForRecord` merely clears `open_gate` and appends a generic approval (`src/state/gates.ts:922-945`). Nothing recognizes a legacy-initialized task and requires a current-subject `migration-audit` approval before leaving the resume phase. Gate opening also special-authenticates commit/restore contexts but otherwise archives the caller-supplied migration context, subject, and evidence without correlating them to the adopted import or retained current evidence (`src/state/gates.ts:843-890`). Moreover, the prescribed integration sequence opens the audit immediately after self/counter review (`phase-19-legacy-upgrade-workflow.md:98`), before triage/adjudication; an accepted finding can then replace the produce subject while the old import-audit approval remains archived. Implementing this literally permits advance with no audit, or with an audit bound to fabricated or stale evidence, missing REQ-50 and the phase success criterion. **Suggested resolution:** retain a minimal durable legacy-import obligation derivable from authenticated initialization authority, add migration-specific gate-open validation for the resume phase, current retained produce/evidence, and all five imported context digests, surface the audit only after the resume phase's fixed point closes, and make advancement/status require its current-subject acceptance. Any re-entry that changes the subject must require a fresh audit. Test bypass and forged-context attempts through the real state/status handlers, not only that an already-open gate temporarily blocks movement.

- **blocker — Staging can overwrite the declared source or an existing destination before the state transaction gets a chance to reject it.** The input contract accepts an arbitrary `source_root`, but the design does not prove that the destination task root is outside it. If the source is the repository root (or another ancestor of `.archflow/tasks/<destination>`), creating config/import/draft files mutates the source during the walk and can make the walk ingest its own output. Independently, `createTaskConfig` is create-or-read and draft/import writes use `replaceRegular`, while no preflight establishes that the destination is unused; a mistyped existing task ID can overwrite canonical PRD/design/phase files even though the architecture requires a distinct unused destination and collision-without-overwrite behavior. **Suggested resolution:** before the first write, reject overlapping source/destination roots, existing `state.json`, existing canonical destination artifacts, and unexpected destination contents. Use no-clobber-or-byte-identical installation for staged payloads and draft projections so an exact interrupted rerun is allowed but an occupied disagreeing target stops without overwrite. Cover a repository-root source, an existing live task ID, a partial identical rerun, and a disagreeing partial destination.

- **blocker — The ordered staging pass cannot create its first parent in a truly unused destination.** The design stages imports in work-breakdown item 2 and creates/reads `config.yaml` only in item 3. Although `TransactionAuthority` can resolve a missing task root, `ensureTaskProjectionParent` starts at that missing root and calls non-recursive `mkdir` only for descendants (`src/state/layout.ts:171-183`); the first `imports` directory creation therefore fails with `ENOENT`. **Suggested resolution:** establish and validate the destination task root by creating the config through the existing safe initialization helper before minting/using staging authority, or add one narrowly scoped task-root creation primitive. Test staging from a destination for which `.archflow/tasks/<task>` does not exist at all.

## Triage

- **Finding 1 (destination past `prd` cannot run the current pipeline) — accepted; the design was restructured around it.** Verified directly: `expectedProduceUpstreamBindings` (`src/state/produce-subject.ts:31-49`) names `prd.md` and `design.md` as the upstreams of every `phase-design-<n>`, `loadProduceUpstreamSubject` fails `current-upstream-produce-result-missing` without a matching retained reference, and `requireApprovedUpstreamDigests` (`src/review/fixed-point.ts:350-366`) throws without a bound `artifact-approval`. A destination initialized at a late cursor deadlocks before it can produce. The user was consulted, since this falsified the premise of the earlier settled decision. The resolution taken is not the suggested pre-resume evidence bootstrap — minting retained results and approvals without a gate opening would fabricate the human decisions REQ-50 forbids. Instead the destination initializes at `prd` and walks `prd` and `design` for real, with the imported documents as `draft` produce artifacts and genuine human approvals, which creates the required upstream results, approvals, and `planned_final_phase`; an accepted `migration-audit` gate then enacts one guarded transition to the derived resume phase design. Verification covers the full journey through the real handlers and asserts upstream resolution after the jump.

- **Finding 2 (cross-repository source cannot initialize) — accepted, resolved by scoping rather than by changing server validation.** `validateLiveInitialization` (`src/state/initialization.ts:102-118`) does resolve all three commit baselines through the destination runner, so a foreign import baseline is absent from its object database. Splitting baseline validation across two runners is machinery bought only by a speculative use case; the realistic case is upgrading a task inside one's own repository. V1 therefore requires source and destination to share a repository, the stager rejects otherwise, and the cross-repository staging assertion was removed rather than promoted to an end-to-end case.

- **Finding 3 (initialization trusts the claimed import digest and staged refs) — partially accepted.** The real gap is accepted: nothing wrote `imports/<import-digest>/manifest.json`, which the architecture layout requires and which — now that the guarded jump derives the resume phase from it — is also the transition's authority source. The stager persists it, and the transition authenticates it by canonical-digesting against `state.initialization_digest`. Two cheap server-side checks were added: every `mapping[].destination_path` must classify, and every `mapping[].legacy_path` must name a staged ref. Rejected: reloading and re-verifying every staged payload's bytes, digest, and byte count on the server. The PRD places malicious-local-user protection explicitly out of scope, the source is the user's own repository, and the two added checks catch the authoring mistakes that are actually reachable. Full re-verification is integrity machinery the operating envelope does not pay for.

- **Finding 4 (audit neither durable nor placed after the fixed point) — accepted in substance, rejected in mechanism.** Both defects were real. The audit now opens at `design` only after its fixed point and `artifact-approval` close, so an accepted triage finding cannot leave a stale approval behind. And it is durably load-bearing by construction rather than skill-promised: accepting it is the only thing that enacts the cursor jump, guarded in `legalMovement` by `assertAuthenticatedGateApproval` — the same unforgeable WeakSet membership that already guards the `phase-impl` exit — so a forged or absent approval cannot advance. Rejected: a new durable legacy-import obligation field in state. It is made redundant by the guard, and adding a durable schema field is exactly the machinery this phase set out not to add.

- **Finding 5 (staging can overwrite the source or an existing destination) — accepted, minus one part.** The overlap hazard is real and cheap to close, as is the unused-destination requirement the architecture already states. The design now rejects overlapping source and destination roots, a cross-repository source, and a destination holding `state.json` or any canonical artifact, all before the first write, with unit coverage for each. Rejected: the no-clobber-or-byte-identical installation matrix for staged payloads. Import payload paths are content-addressed, so a disagreeing target at the same path is not reachable — an identical digest implies identical bytes. The concern applies only to the two `draft` projections, which the unused-destination preflight already covers.

- **Finding 6 (staging cannot create its first parent in an unused destination) — accepted.** Confirmed: `ensureRealDirectory` (`src/state/layout.ts:122-127`) calls non-recursive `mkdir`, so `ensureTaskProjectionParent` fails when `authority.task_root` itself is absent. Resolved by ordering rather than a new primitive — the destination task root and `config.yaml` are now created and validated through the existing task-initialization config helper before the staging authority is minted, and a destination whose task directory does not exist at all is a named unit case.
