# Phase 8 Design Counter-Review

- **blocker — A revision-1 checkpoint can prove possession of another task's initialization and still validate.** `TaskInitializationV1` and `LegacyImportInitializationV1` both carry `task_id` and `repository_identity_digest`, but 5c/5d compare only each checkpoint to the wrapper and 5i compares only `initialization_digest` to the embedded artifact's canonical digest. Rank 7 is deliberately left unchanged, and `isInitialization(wrapper)` is false. A schema-valid initial import can therefore use task/repository A on the wrapper and every checkpoint, embed a valid initialization for task/repository B, recompute `initialization_digest`, and pass 5c–5j with no state slot. This violates REQ-26 and means the first success criterion proves only that the chain supplies *an* initialization, not its own initialization. **Suggested resolution:** add explicit consolidated-validator invariants binding the embedded initialization's task and repository identity to the revision-1 checkpoint/wrapper, pin their position in the total order, and add normal- and legacy-initialization witnesses for both cross-task and cross-repository substitution.

- **blocker — Existing state is not correlated to the exact predecessor checkpoint digest.** Architecture lines 554 and 559 require digest correlation to the exact predecessor checkpoint, never revision alone. The proposed 5h proves only that `chain[0]` repeats the wrapper's untrusted predecessor claim; 5k/5n compare revisions; and 5o proves that `expected_state_digest` describes the supplied state bytes. None proves that this state adopted `predecessor.checkpoint_digest`. Concrete witness: state at revision R actually resulted from checkpoint D2; submit a continuation wrapper naming `{revision: R, checkpoint_digest: D1}`, use the correct canonical digest of that state as `expected_state_digest`, and link `chain[0]` to D1. All proposed comparisons pass. Phase 9 resolving D1 to a retained file proves D1 exists, not that the current state came from D1. Deferring the state provenance decision to Phase 9 therefore leaves a Phase 8 success criterion unsatisfied. **Suggested resolution:** add a verifiable durable state-to-checkpoint binding in this phase—most directly an optional/manual checkpoint-head digest in state, or an equally strong deterministic checkpoint-to-state relation—and test D1 versus D2 at the same revision. If changing the shipped state shape is intentionally deferred, revise the architecture and success criterion at the human gate rather than claiming it here.

- **blocker — `greatestValidChain` cannot identify the greatest valid checkpoint chain described by the architecture.** D-H redefines the operation as truncating `wrapper.chain`, which is already a caller-selected linear sequence. It accepts no candidate set and deliberately ignores identity and initialization validity, so it cannot detect a fork, collision, or ambiguity. Given A@1 and two checkpoints B@2 and C@2 that both validly link to A, separate calls over `[A,B]` and `[A,C]` each return a full "greatest" chain. No call identifies that authority is ambiguous, even though architecture lines 261, 284, and 320 require the greatest valid chain and require collision/ambiguity to stop without consulting server state. Deferring filesystem enumeration to Phase 14 is reasonable; deferring the pure selection semantics is not completion of Phase 8 criterion 4. **Suggested resolution:** define and implement a pure candidate-set selector in Phase 8 (anchor plus unordered checkpoints to either one unique greatest chain or an explicit gap/fork/ambiguity result), reusing the linkage predicates. Leave reading checkpoint files to Phase 14.

- **major — The specified adversarial cases do not prove the claimed evaluation order across all five chain-walking sub-ranks.** Lines 483/649 claim three witness pairs prove that 5c, 5d, 5e, 5f, and 5j are separate passes, but the cases cover c↔d, e↔f, and c↔j only. An implementation can fuse 5d+5e or 5f+5j and pass every prescribed one-error test and fusion witness while returning a non-minimum error. For 5d/5e, make checkpoint 0 structurally valid but fail 5e (`revision: 3`, predecessor revision 1), then make checkpoint 1 self/link-valid but give it the wrong repository identity. The pinned order requires 5d; a per-index 5d→5e loop returns 5e at index 0. For 5f/5j, use revisions 1, 2, 4 with checkpoint 2's predecessor revision 3 (5e passes, 5f fails at index 2), while checkpoint 1 has a different `initialization_digest` (5j fails at index 1); the pinned order requires 5f, while a fused per-index loop returns 5j. **Suggested resolution:** add at least these missing 5d-versus-5e and 5f-versus-5j witnesses, or mechanically assert the implementation consists of one complete pass per sub-rank; remove the claim that the current three pairs establish every seam.

- **major — Two chunks own integration assertions whose dependencies do not yet exist, allowing incompatible implementations to pass local tests.** Chunk 6 is declared schema-only, depends only on chunk 3, and runs beside chunks 4/5, yet its pinned shuffled-chain case must call `validateDurableSemantics` and observe 5f, which chunk 5 has not implemented; the shipped Phase 7 structural corpus also has no validator dependency. Separately, chunk 4 is assigned the combined proof that identity failures are whole-wrapper rejections and verification step 10 explicitly requires validator rejection, but chunk 5 depends on chunk 4. A fresh chunk-6 agent can preserve the schema-only boundary and omit the semantic half, and a chunk-4 agent can test only derivation behavior; both pass their own available tests while the promised integration proof is absent. **Suggested resolution:** keep schema acceptance/duplicate rejection in chunk 6 and derivation-only behavior in chunk 4, then move both validator halves and the combined assertions to chunk 7 after chunk 5. Pin that ownership in the Files table, work breakdown, and verification steps.

## Audited areas with no additional finding

- No new throw route was found under `validateDurableSemantics`' documented precondition that every supplied document has passed its normative schema. Rank 4a uses the catching `decodable` predicate and `CONTRACT_INVALID`; 5c–5q use `TASK_INVALID` with a schema-valid task slug; hashing consumes rank 1's materialized plain-JSON clone; and rank 2 continues to protect every later `STATE_INVALID` construction.
- The estimated 3,100–3,700 lines across eight delegated chunks is large for the prototype but plausible within the stated ~200k implementation context. Phase 7 completed roughly 6,250 lines in thirteen delegated chunks; the serial chain affects elapsed time more than orchestrator context. The correctness and ownership findings above should be fixed without adding a new generalized framework.
- REQ-38 is not assigned to Phase 8 by the architecture; its exact fallback prompts and runtime flows belong to later phases. Phase 8 should describe only its schema slice and should not imply that the complete fallback/manual-authority workflow is already delivered.

## Triage

Triaged 2026-07-28 against shipped source at `3891341`. **All five findings accepted**; every premise was independently verified before acceptance. Blocker 2's resolution was a scope decision taken by the human at the review gate. The design document is revised to 838 lines.

**Blocker 1 — embedded initialization can belong to another task — ACCEPTED.** Verified: `TaskInitializationV1` carries `task_id`/`repository_identity_digest` at `durable-task-initialization.ts:33-34` and `LegacyImportInitializationV1` at `durable-legacy-import.ts:66-67`, and nothing bound either to the wrapper. The finding is correct and is the same class of REQ-26 isolation defect that the Phase 7 counter-review raised and that this phase exists to close. Added sub-ranks **5j** (`chain[0].initialization.task_id === wrapper.task_id`) and **5k** (repository identity), placed after 5i — which establishes that the embedded artifact is the one `initialization_digest` names — and before the chain-wide walk. Both report `TASK_INVALID` through the existing `artifactInvalid`, so no new error code and no throw route. Four witnesses added (normal × legacy initialization, cross-task × cross-repository) plus a drop-probe. Success criterion 1 now claims the chain supplies *its own* initialization.

**Blocker 2 — state not correlated to the exact predecessor checkpoint — ACCEPTED; resolved by human decision.** Verified: `TaskStateV1` (`durable-state.ts:107-145`) has twenty fields and none records checkpoint provenance, so the D1-versus-D2-at-the-same-revision witness is real and the criterion was unsatisfiable as designed. The first draft had already identified this and deferred it to Phase 9, citing Phase 7's D13; the counter-review is right that deferring leaves a *Phase 8* criterion unmet, and that the honest choices were to add the binding or to amend the architecture at the gate. **The human chose to add the binding.** `TaskStateV1` and `task-state.schema.json` gain an optional `adopted_checkpoint {revision, checkpoint_digest}`, declared as a `$def` following the shipped `open_gate`/`prepared_intent` idiom (the file's eighth `$def`). New sub-rank **5s** checks presence, then revision, then digest, in that fixed order; **absence fails with its own literal** rather than silently skipping, which is what keeps the hole closed. D-M is rewritten as an acknowledged reversal — the prior verdict is quoted, this witness reproduced, and the D13 ground refuted on the merits, since an adopted-checkpoint digest is not derivable from anything else in state. The bootstrap question the change raises — how a task that has only ever run in normal mode acquires its first `adopted_checkpoint` — is recorded as an open question owned by Phase 9, which owns adoption and writes the field.

**Blocker 3 — `greatestValidChain` cannot identify the greatest chain — ACCEPTED.** The finding is correct: truncating an already-ordered `wrapper.chain` cannot detect a fork, and the A@1 / B@2 / C@2 construction shows two separate calls each returning a full "greatest" chain with nothing reporting ambiguity, against `architecture.md:261`, `:284`, and `:320`. Distinguishing pure selection semantics (Phase 8's) from filesystem enumeration (Phase 14's) is the right line. D-H is rewritten: `greatestValidChain(wrapper)` is **removed** and replaced by `selectGreatestValidChain(anchor, candidates)` over an unordered candidate set, returning one chain or an explicit `gap` / `fork` / `no-valid-successor` / `foreign-candidate` outcome. `chainHeadBreak` now takes a `ChainAnchor` so the validator and the selector share one head rule. Fork, gap, and no-silent-preference witnesses added.

**Major 4 — fusion witnesses miss two adjacent pairs — ACCEPTED.** Correct: the three prescribed pairs covered only c↔d, e↔f and c↔j, so a 5d+5e or 5f+5j fusion passed everything. Both supplied constructions were adopted verbatim (renumbered for the new ladder). There are now five witnesses covering every adjacent pair among the chain-walking sub-ranks, and the unproven "these establish every seam" claim is replaced by an argued one: any non-adjacent fusion necessarily also fuses an adjacent pair.

**Major 5 — chunks assert against authorities that do not exist yet — ACCEPTED.** Verified against the shipped file: `durable-structural-corpus.test.ts:34-35` states it imports no `durable.ts` and calls no validator, yet chunk 6's pinned shuffled-chain case required exactly that — from a chunk running *beside* chunk 5, which writes it. Chunk 4's no-silent-salvage proof had the mirror-image problem, since chunk 5 depends on chunk 4. Both validator halves moved to chunk 7, which runs after chunk 5 and already owns the validator's rejection matrix; chunk 6 keeps schema acceptance and duplicate rejection, chunk 4 keeps derivation-only behaviour. The general rule is now stated — *a chunk may only assert against an authority that exists at its point in the serialisation* — and every other chunk was re-checked against it, which surfaced one further correction: chunk 6 now also depends on chunk 1.

**Audited-areas notes.** The throw-route audit and the sizing assessment are consistent with our own review rounds and required no change. On REQ-38: the design does not assign itself REQ-38 — its requirement line is REQ-11, REQ-21, REQ-26, REQ-39, REQ-50, matching `architecture.md:552` — and it already states that it completes no requirement and names Phases 9, 14, and 17 as the owners of the adopting, driving, and verifying behaviour. No change made.

**Consequential updates.** The ladder is now 18 sub-ranks (5c–5t) carrying 22 literals; `DURABLE_ISSUE_CODES` goes 22 → 44. Files go 8 new / 10 modified → 8 new / 14 modified, and the line estimate 3,100–3,700 → 3,450–4,100. Every claim that `task-state.schema.json` is byte-unchanged was located and corrected. Two stale assertions in shipped comments were found while applying this and are now assigned: `task-state.schema.json:80`'s `$comment` asserts "exactly seven `$def`s for this file", and `durable-structural-corpus.test.ts:449`'s says "Nine fields do".

### Post-triage verification round

Because these revisions were substantial — a shipped Phase 7 root edited, the sub-rank ladder renumbered, and one exported function replaced — a further fresh-context round was run against the revised document. It found **no blockers**, two majors and five minors, all accepted and applied. The design document is now 886 lines.

The consequential one was a side effect of blocker 2's resolution that neither the counter-review nor our own triage anticipated: because 5s makes an absent `adopted_checkpoint` a failure, and because the checkpoint shape independently requires every `revision >= 2` checkpoint to name a predecessor, **a task that ran on the server and then lost it can begin no manual chain at all** — it has neither field, and the mutation flow (`architecture.md:63-71`) never writes a checkpoint, so `architecture.md:79`'s direct-adoption path can reach revision 7 with no checkpoint file ever having existed. That makes the headline REQ-39 scenario — server dies mid-task, work continues manually, chain imported on recovery — unrepresentable in the two formats this phase fixes. **The human chose at the gate to record it as a known unsupported path** rather than take the shape change (a head checkpoint with no predecessor) into Phase 8. It is now recorded in four places in the design, owned jointly by Phase 9 and Phase 17, and flagged as must-resolve-before-Phase-17. `architecture.md`'s Phase 8 entry is to be annotated with the same limitation on approval, so the parent document reflects it.

The remaining six: `POSITIVE_FIELDS` was miscounted (nine → fourteen, not ten) and two of its new rows could not execute against the pinned fixtures; the new fusion-completeness argument was invalid as written and is replaced by a transitivity argument; a chunk-7 instruction pointed at a test title that carries no count; the chain selector silently dropped a colliding candidate at or below the tail and now keys on the anchor's expected head revision; the embedded initialization's `canonical_paths` surface is bound by nothing and is recorded as inherited with Phase 10 as owner, with criterion 1 qualified accordingly; and the selector's outcome vocabulary was trimmed from four to three, dropping `no-valid-successor` because no requirement names it and "nothing advances the anchor" is the absence of news rather than a stop.
