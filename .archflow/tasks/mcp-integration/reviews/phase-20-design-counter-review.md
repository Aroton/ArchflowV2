# Phase 20 Design Counter-Review

- **blocker — Secret-rejection replay contradicts the approved transaction contract.** Chunk 7 and its success criterion require replaying the same rejected `intent_id` to return a “recorded failure.” That cannot happen in the current contract: `runStateTransaction` returns a failed preparation directly at `src/state/transaction.ts:1041-1042`, before a plan, intent receipt, or state write exists, and the architecture explicitly says failed preparation writes no receipt. Implementing the test as written either fails or forces a new failure-receipt authority that the architecture does not permit and the design otherwise says it will not add. **Suggested resolution:** assert that retrying the same intent reruns preparation, returns `SECRET_DETECTED` again, and leaves state, receipt, retained result, and projections unchanged; use a scanner call count if the test needs to distinguish rerun from replay.

- **blocker — The descendant matrix does not exercise the descendant-escape cell and overclaims termination.** Phase 20's architecture scope explicitly includes “descendant escape,” while the architecture already records that a descendant calling `setsid()` escapes the adopted process-group kill and that escaped-descendant death is not proven (`architecture.md:17`, `:363`, `:392`, `:823`). Chunk 3 instead adds an ordinary heartbeat grandchild to prove group reaping, treats any survivor as an unexpected follow-up, and the phase success criterion claims shutdown/cancellation terminate the child “and its descendants.” Implemented as written, that can pass without evaluating the known escape case and leaves a Phase 20 scope item neither proven nor marked unsupported. **Suggested resolution:** retain the ordinary descendant cancellation/shutdown proof, add a bounded `setsid()`/new-process-group observation for the escape case, and record that cell as unsupported in the limitations document and implementation log without absorbing OS containment or pinning a permanent test to the weakness. Narrow the success criterion to the descendants the process group actually contains.

- **major — The host-registration atomic-write fix is outside the Phase 20 contract.** The design adds a new host-configuration persistence mechanism and fault test to satisfy REQ-01, but REQ-01 is absent from Phase 20's requirements and host registration appears in neither its enumerated scope nor its seven success criteria. Phase 16's design and log did not defer registration crash testing here. The factual reuse claim is correct: `AtomicWriter.replace` accepts only `task-state` and `gate-interface`, and `ProjectionWriter` accepts only projectable path classes (`src/state/atomic.ts:102-107`, `:131-162`), so this work would require a distinct mechanism. That does not make the extra mechanism part of this phase. **Suggested resolution:** remove `src/init/registration.ts`, `test/unit/init-registration-phase20.test.ts`, and the associated source-fix verification from Phase 20, and record the discovered issue as a focused follow-up for the initialization/registration owner.

- **major — `crash-cut-points.ts` is framework ahead of need and cannot provide its claimed completeness guarantee.** The proposed helper is a hand-maintained TypeScript list consumed by a negative bundle scan, while actual cuts remain independent string literals in multiple JavaScript child fixtures (`test/fixtures/state-transaction-child.mjs:158-178` and `test/fixtures/state-phase10-child.mjs:59-67`). A future fixture cut can therefore omit the helper and still pass, so the helper does not make cut declaration and exercise a single source of truth and cannot guarantee that every new cut is guarded. This phase's few disjoint crash vocabularies do not buy a registry that is not authoritative. **Suggested resolution:** keep explicit cut unions/lists local to each owning crash suite and a local bundle-exclusion assertion, or mechanically derive and validate the inventory from the fixture sources; do not add the proposed nominal global list as written.

## Triage

Triaged 2026-08-04. All four findings verified against the source before disposition.

- **Secret-rejection replay contradicts the transaction contract — accepted.** Confirmed at `src/state/transaction.ts:1041`: a failed `prepare` returns before `buildPlan`, so no plan, receipt, or state write exists and there is no recorded failure to replay. Chunk 7 and its success criterion now assert that retrying the same intent reruns preparation, returns `SECRET_DETECTED` again, and leaves state, receipt, retained result, and projections unchanged, distinguishing rerun from replay by scanner call count. The design states explicitly that this phase adds no failure-receipt authority.

- **Descendant matrix does not exercise the escape cell — accepted.** Confirmed that `architecture.md:392` already records escaped-descendant containment as unproven while Phase 20's scope names descendant escape. Chunk 3 now separates the two: the heartbeat grandchild proves reaping of descendants that remain in the process group, and a bounded one-time `setsid()` observation closes the escape cell, recorded as unsupported in the limitations document and the implementation log. Per the finding's own caution, and consistent with this design's refusal to ship inverted canary tests, the escape observation is made during implementation and not pinned as a permanent test — it would assert an operating-system fact no ArchFlow change can alter. The success criterion is narrowed to the descendants the process group actually contains.

- **Host-registration fix is outside the Phase 20 contract — accepted as correct, resolved the other way by user decision.** The contract analysis is right: REQ-01 appears in none of Phase 20's requirements, scope items, or success criteria, and Phase 16 did not defer it. Presented as a scope decision at the design gate; the user chose to fix it here rather than defer, on the grounds that it is a small fix for a real data-loss bug in a file the user owns and no later phase obviously picks it up. REQ-01 was therefore added to the phase and to the architecture's Phase 20 entry, with the reason recorded in both, so the contract stays truthful rather than silently exceeded. The finding's factual point about write mechanisms is retained in the design: host-config writes use a helper local to `src/init/` precisely because widening the branded writers' path-class allowlists would be the wrong trade.

- **`crash-cut-points.ts` is not authoritative — accepted, resolved differently from both suggestions.** The completeness objection is correct: a hand-maintained list consumed by a negative scan cannot guarantee a future fixture cut is guarded. Neither offered resolution was taken. Keeping lists local to each suite leaves declaration and guard in different places, and scraping fixture sources is fragile. Instead each crash child now exports the cut list it already declares and validates its own requested cut against it, making declaration and exercise one source of truth; the bundle scan imports the three children and scans the union, and covers both shipped bundles. This also removes the phase-12 child's substring fall-through, where an unrecognized action silently did nothing. The separate helper file is dropped.
