# Phase 4 Design Counter-Review

Reviewed against the PRD, architecture, all current context references, the Phase 3 design and implementation log, the Phase 3 implementation/tests, the installed beta.5 declarations/runtime, and live official dependency guidance on 2026-07-27.

## Findings

1. **Severity: blocker — The required malformed-known-call result is impossible through the frozen Phase 3 boundary.** Phase 4 says a known tool with missing, non-object, or semantically invalid arguments reaches `createToolBoundary` and receives the boundary's `CONTRACT_*` classification. In the actual Phase 3 implementation, however, `src/mcp/server.ts` checks whether a handler exists before it calls `classifyVersionedArgs`; the inert empty registry therefore returns `TOOL_DISABLED` for every known tool regardless of its arguments. This directly contradicts the architecture's requirement that known malformed arguments reach `CONTRACT_*`, while Phase 4 explicitly excludes Phase 3 changes. The pre-SDK “semantically invalid” surrogate also has no legitimate oracle: the complete semantic classifier belongs to the frozen boundary, and the advertised schema intentionally omits runtime-only `x-archflow-*` rules. Duplicating that classifier in the adapter would create two authorities and weaken the Phase 3 seam.

   **Suggested resolution:** Reopen the Phase 3 seam and move known-tool argument classification ahead of handler availability, or explicitly revise the architecture to disabled-first precedence. In Phase 4, use the surrogate only for shapes the SDK itself would reject before the handler (for example, non-object arguments); forward object arguments unchanged and let the boundary remain the sole semantic classifier. Add inert/enabled fixtures for portable-schema-accepted but runtime-rejected objects.

2. **Severity: blocker — The design permits terminal request-ID reuse, which protocol `2025-11-25` forbids for the full session.** The record rules release an external-ID collision guard after response write acceptance or cancellation, and the success criteria explicitly require “terminal ID reuse.” MCP instead says a request ID “MUST NOT have been previously used by the requestor within the same session”; cancellation does not make the ID reusable. See the official [2025-11-25 base protocol](https://modelcontextprotocol.io/specification/2025-11-25/basic). This is not just an active-request race: a completed, cancelled, failed, or directly rejected valid request ID must remain spent for the connection.

   **Suggested resolution:** Separate active request records from a connection-lifetime seen-ID ledger, reject every reuse after normalization (including `-0`/`0`) with the pinned direct error, and define a fail-closed connection/request-count bound plus internal-ID exhaustion behavior so the ledger and allocator cannot grow or wrap indefinitely. Revise the architecture's ambiguous “reuse fixtures” language and test reuse after success, project/protocol error, cancellation, direct rejection, and output failure.

3. **Severity: blocker — Required SDK construction and capability registration are absent.** The design configures supported protocol versions and handlers but never pins the exact `Server` implementation identity `{ name, version }`, capabilities, or construction order. In beta.5, registering `tools/list` or `tools/call` on a low-level `Server` before `registerCapabilities({ tools: {} })` fails because the server does not support that capability. The omitted identity and capability object also make the claimed byte-pinned initialize response undefined.

   **Suggested resolution:** Specify and probe the exact order: construct `Server` with a fixed implementation identity/options, register the exact tools capability, register the two tool routes (and any other approved pass-through route), then connect the facade. Pin the resulting initialize `serverInfo` and capabilities bytes in fixtures.

4. **Severity: blocker — Initialization error and rollback transitions are missing.** `PRE_INIT` refers to a “valid” initialize without defining whether the raw guard or SDK establishes validity, while `INITIALIZING` advances on interception of “the initialize response” without distinguishing success from error. The error table has no malformed-initialize row. Beta.5 can answer malformed initialize input with an SDK error and then accept a later valid initialize, so advancing on any response would strand or falsely initialize the adapter; releasing the record after an initialize projection failure similarly leaves `INITIALIZING` without recoverable state. Raw SDK validation errors can also contain validator prose, contrary to the bounded-wire-error policy.

   **Suggested resolution:** Define the exact public validation seam and canonical error for malformed initialize, success-versus-error interception, candidate cleanup, record release, and retry transition back to `PRE_INIT`. Treat projection/write failure after SDK initialization mutation as terminal close unless a public, probed reset exists. Add malformed-then-valid, error projection, backpressured error, and same-ID overlap fixtures.

5. **Severity: major — The method-aware route contract is not closed, and `sdk-pass-through` has no defined members.** The design defines that route kind but only specifies initialize, `tools/list`, `tools/call`, initialized, and cancellation. It does not say whether `ping` passes through even though the 2025-11-25 ping receiver [MUST respond promptly](https://modelcontextprotocol.io/specification/2025-11-25/basic/utilities/ping) and beta.5 registers a ping handler. It also does not define how syntactically valid inbound JSON-RPC responses are handled; stdio explicitly carries requests, notifications, *and responses*, and replying to a response as though it were an invalid request risks a response loop. Malformed initialize and the sources of `UNSUPPORTED_PROTOCOL` and `INITIALIZATION_REPEATED` projection are likewise not assigned to exact routes.

   **Suggested resolution:** Add a closed request/notification/response routing table covering initialize, ping, list, call, initialized, cancelled, unexpected responses, and all unknown/malformed cases. For each row pin lifecycle states, outer validation, allocation/tombstoning, SDK forwarding, exact response/no-response, and cleanup. Either provide a real route for each claimed protocol mapping or narrow the success criterion.

6. **Severity: major — Beta.5 rewrites `TOOL_DISABLED`, but the request record does not retain the authenticated value needed to restore it.** ArchFlow assigns `TOOL_DISABLED` JSON-RPC code `-32002`. The exact beta.5 2025 codec unconditionally maps a handler-thrown `-32002` to `-32602` (`node_modules/@modelcontextprotocol/server/dist/src-D86MbS1I.mjs`, `encodeErrorCode`) because that number is legacy resource-not-found territory. The facade therefore cannot reconstruct the original authenticated Phase 3 outcome from the outbound SDK message alone, yet the listed request-record fields retain neither that outcome nor an expected projection. Structurally reparsing `data` after the WeakSet-authenticated wrapper is lost would not preserve provenance.

   **Suggested resolution:** Before throwing `ProtocolError`, bind the authentic boundary outcome (or an adapter-derived frozen expected projection) to the request record. Require the outbound facade to match the record and canonicalize from that retained value, not from the SDK-mutated error. The compatibility gate should assert both the observed SDK `-32602` and the restored ArchFlow `-32002`. Alternatively, revise the ArchFlow numeric allocation in the parent contracts.

7. **Severity: major — Cancellation release occurs before the public SDK surface can prove cancellation ran.** The public `Transport.onmessage` returns `void`, and beta.5 defers notification handlers with `Promise.resolve().then(...)`. Returning from the facade call proves handoff only, not that the SDK abort controller has fired. For a request and cancellation in the same input chunk, releasing the record immediately can make the later-scheduled tool handler fail record recovery; recycling an internal ID could let the delayed cancellation target a newer request. “Fresh positive nonzero” does not explicitly prohibit recycling.

   **Suggested resolution:** Define an adapter-owned `cancelling`/tombstone state and keep the record until an observable handler/signal settlement, while using connection-lifetime monotonic non-recycled internal IDs with fail-closed exhaustion. Pin same-chunk request→cancel ordering, cancellation before the handler begins, late handler start, immediate later request admission, and close during cancellation. Do not call synchronous facade return “SDK cancellation admission.”

8. **Severity: major — Queue ownership covers record-indexed responses but not direct frames or fallback frames.** Direct parse/lifecycle/method/shape errors intentionally allocate no request mapping, while close only rejects “record-indexed” queued/pending sends. A direct `-32600/-32601/-32602` arriving behind a `write(false)` therefore has no defined FIFO owner, close settlement, or listener cleanup. Projection failure has the inverse problem: the design releases the affected record before attempting `-32603`, allowing its fallback to be queued without the collision/send state that normal responses retain. The statement that the losing event in a `drain`/callback-error race is ignored also conflicts with the later rule that every callback error is fatal; Node documents the callback as the chunk's eventual success/failure signal and `drain` only as permission to resume writing. See [Node Writable semantics](https://nodejs.org/api/stream.html).

   **Suggested resolution:** Model `SendEntry` independently from semantic request records, with an optional record association, and put every direct, SDK, and fallback frame through the same FIFO. Pin acceptance, backpressure clearance, late callback error, close rejection, and record release separately. A callback error that arrives after `drain` may not retroactively un-accept bytes, but it must still trigger the single fatal-output path.

9. **Severity: major — Raw ingress and backpressure have no bounded byte/flow contract.** Once output returns false, the design keeps accepting input and accumulating later frames/handler results; it pauses ingress only during `CLOSING`. A client can therefore drive unbounded request maps and output queues under permanent backpressure, including many complete lines already present in one chunk. The replacement raw framer also omits a maximum incomplete-line/buffer size, fragmented multibyte UTF-8 behavior, invalid UTF-8 behavior, CRLF, empty lines, and partial EOF. The official stdio transport requires newline-delimited UTF-8 messages, and the bypassed SDK framer itself uses a 10 MiB buffer limit. See [MCP stdio transport](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports).

   **Suggested resolution:** Pin a byte-oriented bounded framer and exact malformed/EOF behavior. Pause ingress at the first `write(false)`, define how the unconsumed remainder of the current chunk is retained within a bound, resume only after `drain` while still open, and close/fail safely on overflow. Test split Unicode code points, invalid UTF-8, over-limit unterminated lines, CRLF/empty/partial-final lines, a many-line chunk, flood under permanent false, and close while paused.

10. **Severity: major — The runtime handle cannot report the fatal lifecycle that `src/main.ts` must arbitrate.** `McpRuntimeHandle` exposes only `close()`, but main must distinguish unsolicited input/output transport failure, startup failure, explicit close, EOF, and signals, preserve the first termination reason, classify close failure, emit one diagnostic, and choose an exit code. With no `closed`/fatal result or callback, the adapter must either mutate process state/duplicate diagnostic ownership or leave main unaware. The same omission makes deterministic spawned tests for startup, unsolicited transport, and close-failure overlaps infeasible through the declared interface.

   **Suggested resolution:** Add one SDK-free termination/fatal settlement to the handle (or a single callback with a closed result), give diagnostics to exactly one layer, and pin reason arbitration through that seam. Add an injectable process-runner/stdio/signal seam for unit tests; keep actual-process tests for real transcripts, EOF, and signals.

11. **Severity: major — The phase design weakens an impossible parent success criterion without reconciling the architecture.** Architecture line 473 promises that late or never-settling handlers produce no post-close “business side effect.” The phase correctly admits that an injected handler ignoring `AbortSignal` can still perform private effects and narrows the guarantee to adapter-owned effects/output. The original unqualified promise cannot be enforced by this runtime, and ArchFlow requires parent plans to reflect implementation reality.

   **Suggested resolution:** Before approval, revise the architecture criterion to prohibit adapter-owned state/output effects after `CLOSING`, quarantine late results, and require injected handlers to cooperate with `AbortSignal`; if arbitrary handler side effects truly must be prevented, add an authority/commit barrier in the owning later phase instead of claiming cancellation can revoke them.

12. **Severity: major — The dependency currency gate has a date-boundary race.** Live checks on 2026-07-27 confirm `@modelcontextprotocol/server@2.0.0-beta.5` is still the npm `latest`/`beta` tag and that the cited public APIs exist; `Server` alone is explicitly deprecated but documented for advanced use. However, upstream schedules stable v2 for 2026-07-28, while the design rechecks only if implementation *starts* on or after that date. A run begun on July 27 may finish after stable supersedes beta.5 without triggering the intended stop. See the [current npm package](https://www.npmjs.com/package/@modelcontextprotocol/server), the upstream [v2 status](https://github.com/modelcontextprotocol/typescript-sdk), and the official [2026-07-28 release-candidate notice](https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/).

   **Suggested resolution:** Run the live dist-tag/guidance check both before any implementation and immediately before final verification/review, and repeat it whenever the UTC date or tag changes during the phase. Stop for architecture/design review if stable appears at either point.

13. **Severity: major — The phase is not divided into implementable chunks at its actual complexity.** Work chunks 2–4 all own the same `src/mcp/sdk-adapter.ts` and overlapping unit matrix without pinned internal interfaces. Chunk 2 alone includes byte framing, lifecycle, session-ID ledger, internal-ID allocation, direct errors, record/send queues, serialization, backpressure, and close. Chunk 5 combines process control, a build refactor, and the integration harness, while chunk 6 is a large combinatorial race matrix. That prevents useful parallel delegation and makes one highly coupled implementation/review session the integration point for nearly every risk above.

   **Suggested resolution:** Split the architecture phase after the compatibility gate, or define SDK-free internal modules/interfaces with non-overlapping file ownership (for example framing/admission, send queue/lifecycle, SDK facade/projection, and process runner) while keeping SDK imports confined to the adapter. Re-size only after the corrected transition and route tables make the real work visible.

14. **Severity: minor — The normative repository map assigns lifecycle ownership to the wrong existing file.** `architecture.md` describes `src/mcp/server.ts` as the “MCP v2 lifecycle and connection context” owner, but Phase 3 implemented it as the SDK-free authenticated tool boundary and Phase 4 assigns lifecycle to `sdk-adapter.ts`. Leaving both descriptions encourages a later implementation to blur the frozen boundary.

   **Suggested resolution:** Update the architecture tree comment during design triage so `server.ts` remains the SDK-free tool boundary and `sdk-adapter.ts` owns transport/lifecycle.

15. **Severity: minor — REQ-33 completion is overstated for an inert runtime.** The phase header claims REQ-33 (“Validated model results”), but Phase 4 has no model dispatch or server-attested model-result validation; those arrive in later phases. Phase 4 contributes only transport projection of already authenticated project/protocol outcomes.

   **Suggested resolution:** State the narrow REQ-33 slice Phase 4 proves, or remove it from this phase's direct requirements and leave full satisfaction to the model-dispatch/assembly phases. Do not let Phase 4 completion imply the whole requirement is met.

Both follow-up corrections were accepted: missing `tools/call.arguments` now follows the SDK-valid unchanged route and only a present non-object value uses the surrogate; exact top-level/list/call member allowlists now reject unknown keys before SDK stripping while `_meta` and legacy `task` remain SDK-only inputs.
