# Phase 18 Design Counter-Review

1. **Blocker — The proposed gate and terminal checkpoints cannot be imported through the existing checkpoint-adoption reducer.** The design makes `gate-open`, `gate-resolved`, and `terminal` first-class manual milestones and then routes the selected chain through `buildCheckpointImportStateCall` and ordinary `archflow_state` adoption. Current `planCheckpointAdoption` replays every checkpoint only through `planStateTransition` (`src/state/checkpoints.ts:111`), but that reducer rejects every movement while `current.open_gate` exists (`src/state/transitions.ts:88`) and permits phase-implementation completion only with an authenticated commit-authorization capability plus observed committed output (`src/state/transitions.ts:186`), neither of which the adoption planner supplies. A checkpoint-head `open_gate` is then copied into the successor (`src/state/checkpoints.ts:145`), while its `frozen_state_digest` must hash the eventual state shell (`src/contracts/durable.ts:96`, `src/contracts/durable.ts:469`); the import transaction changes the state revision and adds `committed_intent`, so a manual pre-import digest cannot validate that committed import state. As written, a chain containing an open/resolved gate or terminal implementation milestone will fail adoption, missing REQ-39's recovery path. **Suggested resolution:** Design an explicit archive-authenticated manual-import reducer for gate opening/closure and implementation completion, including the exact gate-decision, commit-authorization, and committed-tree observations it consumes and the state it constructs. Do not replay those milestones through the ordinary step-transition loop. Require integration proofs for open-gate recovery, gate resolution, non-final implementation advancement, and final completion import.

2. **Blocker — The proposed pure-manual handoff cannot produce the existing handoff record.** The design changes only `CleanHandoffPosition` and adds `resolveManualHandoff(ManualAuthority)`, but `HandoffRecordV1` is a divergence-repair record that still requires exactly two `preserved_heads`, a `common_authoritative_checkpoint`, and a `selected_successor_head` (`src/contracts/durable-handoff.ts:19`; `src/contracts/schemas/v1/handoff-record.schema.json:7`). Its current creation path also requires a `DivergencePreservation` capability minted from two actually divergent Git heads (`src/repository/handoff.ts:97`, `src/repository/handoff.ts:148`). A routine clean checkpoint commit/push/pull handoff has none of those facts, so the proposed function cannot install a valid record without fabricating divergence evidence. **Suggested resolution:** Keep ordinary one-writer handoff as the architecture's documented checkpoint commit/push/clean-pull protocol and reserve `HandoffRecordV1` for actual divergence repair. If a durable record for every clean manual handoff is truly required, redesign the root contract as a discriminated record union and define its separate creation and validation inputs; discriminating only the nested clean position is insufficient.

3. **Blocker — Rebuilding the MCP bundle requires a fresh human risk decision, not a mechanical evidence rebind.** The design modifies shared runtime inputs and `dist/archflow-mcp.mjs`, lists `release/evidence/user-risk-acceptance.json` for modification, and says to retain the existing dependency/legal decisions rather than reopen them. The current acceptance explicitly lists `bundle-change` as an invalidator (`release/evidence/user-risk-acceptance.json:17`), and the Phase 17 log records that the previous bundle rebuild required explicit user re-acceptance (`phase-17-normal-mode-thin-phase-skills-and-truthful-status-log.md:36`). Rebinding the old words to a new digest would invent human approval and cannot satisfy the release checks or ArchFlow's trust boundary. **Suggested resolution:** Put a mandatory explicit user gate after the final MCP bundle digest is known and before updating the acceptance/legal evidence. If the user does not re-accept the unchanged exposure for that exact bundle, leave release staging/reproduction blocked and report it rather than rewriting the acceptance.

4. **Major — Pure-manual retained-result accounting has no authoritative byte source.** The design says normal and manual preparation share accounting and task caps, but the existing `read_retained_task_bytes` derives its total only from `state.authoritative_results` and returns zero when state is absent (`src/state/production.ts:257`). In a server-absent task, successive results are reachable from the selected checkpoint head instead, and neither `ManualAuthority` nor `installManualRetainedResult` is specified to compute and supply that total. Reusing the current service would therefore account each pure-manual result as though no prior retained results existed, allowing the task cap to be exceeded and producing manifests that disagree with eventual normal recovery. **Suggested resolution:** Add a loader-derived retained-byte total (or narrow accounting capability) to the common preparation seam, computed from unique result manifests reachable from the authenticated checkpoint head and excluding only the exact reused result. Test multiple pure-manual results approaching the task cap and recovery when stale normal state exists behind the selected checkpoint.

## Triage

1. **Accepted — checkpoint adoption reducer.** The current generic replay cannot authenticate gate effects or implementation completion, and copying an unresolved `open_gate` into a receipt-committed state cannot preserve its frozen-state digest. The design now requires one archive-authenticated manual-import evidence loader and reducer for both missing-state initialization and mature-state adoption; the MCP state handler supplies the capability to either entry path. Ordinary step movement may reuse `planStateTransition`, while resolved gate effects and commit completion require their existing authenticated capabilities. A focused follow-up review also proved that an archived pending gate cannot be reopened after checkpoint compression because its revision, request, ID, and frozen-state bindings are immutable. Import therefore remains blocked while a gate is open; manual mode must checkpoint an explicit decision, cancellation, or supersession before the closed chain can import. Verification covers both entry paths, unresolved/resolved gates, retry effects, non-final advancement, and final completion.

2. **Accepted — routine handoff is not divergence repair.** The proposed nested handoff variant was removed. `HandoffRecordV1` remains unchanged and reserved for actual two-head divergence repair. Routine normal and pure-manual handoff is the architecture's human checkpoint commit/push/clean-pull protocol, with helper readiness checks but no fabricated record. A pure-manual divergence record is finalized only after server recovery adopts the selected checkpoint into state.

3. **Accepted — bundle-bound risk decision.** The design now stops after staging the final MCP bundle and requires explicit user re-acceptance for that exact digest before modifying `user-risk-acceptance.json`, writing the tracked release, or claiming release reproduction. A refusal or absent decision leaves release work blocked; the old acceptance is never mechanically rebound.

4. **Accepted — manual retained-byte accounting.** `ManualAuthority` now privately carries accounting derived from each unique head-reachable result manifest, ignoring stale normal state and excluding only an exact reused result. The common preparation seam consumes an opaque accounting capability. Verification covers multiple manual results near the task cap, reuse, and stale-state recovery.
