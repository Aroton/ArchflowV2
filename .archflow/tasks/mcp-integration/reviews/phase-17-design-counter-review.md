# Phase 17 Design Counter-Review

1. **Blocker — the uniform fingerprint removes the only post-dispatch artifact-freshness check, and the promised regression test cannot pass as described.** `handleCounterReview` reads and hashes the artifact before dispatch (`src/mcp/handlers/counter-review.ts:61-64,104-114`), while `runCounterReview` does not enter `runStateTransaction` until the child returns (`src/review/counter-review.ts:92-119`). Today the transaction-time fingerprint resolver re-reads `artifact_path`, so an edit during dispatch changes the fingerprint and rejects installation. With `artifactPaths()` forced to `[]`, stale counter evidence can commit. Contrary to the design at lines 27 and 130, `deriveCurrentEvidenceSet` never reads the artifact; it only compares the two reviews' stored subject, fingerprint, rubric, and family fields (`src/state/evidence-results.ts:500-514`). If both reviews name the pre-edit subject, derivation succeeds. **Suggested resolution:** keep the generation fingerprint uniform only if the counter-review path re-observes the artifact after dispatch and before installation, and define a legal stale-subject re-entry if status discovers drift after commit. Replace the proposed test with a mutation during the child dispatch and remove the prohibition on compensating freshness checks.

2. **Blocker — upstream freshness is not relocated by `requireApprovedUpstreamDigests`, so the amendment misses REQ-13's upstream-invalidation requirement.** Adjudication reads approved upstream bytes before dispatch (`src/review/adjudication.ts:345-372`), dispatches at `:374-385`, and installs after return without re-reading them (`:414-430`). Removing `upstreamPaths()` from the transaction fingerprint eliminates the only post-dispatch observation. `requireApprovedUpstreamDigests` receives already-derived digest strings and approvals; it cannot observe a later path change (`src/review/fixed-point.ts:346-361`). Later fixed-point currency checks compare adjudication subject/fingerprint/source-review-set only (`src/review/fixed-point.ts:82-129`), not its approved upstream digests against current approved upstreams. A changed upstream can therefore leave stale drift evidence current and advancing. **Suggested resolution:** retain an equivalent upstream-bound generation check, or re-observe upstreams immediately before adjudication installation and again when status/gate advancement evaluates retained adjudication. Test both mutation during dispatch and an approved upstream changing after adjudication but before advancement.

3. **Blocker — the four gates opened inside `archflow_adjudicate` have no REQ-41 prompt surface.** The design puts `counter_review_prompt` only in `computeCallEnvelope`'s `archflow_gate`/`archflow_waiver` result (lines 35 and 93), while `TaskStatusV1.open_gate` is specified to carry kind and decision templates only (lines 36 and 85). `review-trigger`, `material-drift`, `adjudication-failure`, and `constitution-edit` are created inside the already-blocking adjudication call (`src/mcp/handlers/adjudicate.ts:148-185`), so no pre-call gate envelope exists for them. This directly misses REQ-41's prompt at every human gate, and makes line 97's claim that every gate goes through `envelope` before blocking impossible. **Suggested resolution:** make the open-gate status block generate and return the complete prompt and paths from the actual `GateRequestV1` in `gate.json`/its archive plus the current fingerprint, reusing `renderGateCounterPrompt`. Have skills direct the human to that second-terminal surface, and integration-test a server-opened gate rather than only `envelope -> archflow_gate`.

4. **Blocker — the closed next-action contract cannot represent creation of mandatory approval gates.** `NextActionCode` has resolution of an already-open gate but no action for opening one. The precedence ladder maps the fixed point directly toward advancement, even though PRD/design require `artifact-approval` and every phase implementation requires a distinct final-digest `commit-authorization` under REQ-09/REQ-20. `assessCurrentEvidence.next === "advance"` proves neither approval. The per-skill table mentions these gates, but the pinned skill loop says to follow the single status `next_action`; those contracts disagree and permit `advance-phase` to be recommended before required authority exists. **Suggested resolution:** add an explicit gate-opening next action carrying the required gate kind (and the references needed to assemble its context), and have status authenticate a current matching approval before it returns `advance-phase`. Cover PRD, design, and clean phase-implementation paths.

5. **Blocker — normal mode has no durable way to complete the final implementation phase or task.** `nextPhase()` maps every `phase-impl-N` success to `phase-design-(N+1)` unless `N` is `Number.MAX_SAFE_INTEGER` (`src/state/transitions.ts:65-74`). `planStateTransition` only preserves an existing `terminal` field and no live normal handler sets one (`:192-200`); the fixed workflow also carries no phase-count boundary. Consequently the proposed `task-complete` status action can only report terminal authority imported from a checkpoint, not create normal-mode completion, and a normal skill cannot know or record that the final planned implementation is complete. **Suggested resolution:** define the durable source of the final phase number and add a five-tool-compatible transition that sets `terminal: "complete"` only after the final implementation's current commit authorization. Test a task with at least two phases through final completion.

6. **Blocker — reconciliation discovery will treat ordinary historical receipts as a current corrupt orphan.** Chunk 2 selects an `intents/*.json` receipt merely because its digest differs from `state.committed_intent?.receipt_digest`. After more than one successful transaction, every older committed receipt satisfies that predicate. Passing one to `createPreparedIntentSubject` against current state fails its prior-revision relation, so `reconcileCurrentAuthority` emits `receipt-invalid` (`src/state/reconciliation.ts:117-153`) and the precedence ladder blocks otherwise healthy status. **Suggested resolution:** ignore historical receipts and consider only candidates that can be a prepared successor of the current revision (including matching prior/result revisions and prepared-state relation). Define a conservative ambiguity result if more than one current-revision candidate validates; test a normal multi-transition task as well as the crash orphan.

7. **Major — `computeTaskStatus` cannot produce the pinned self-review provenance contract.** Status is input-free, but lines 37-38/85 require it to return a complete self-review provenance block including `rubric_digest`, while that digest is produced by a separate `archflow-local hash` over a rubric literal that exists only in the invoking skill. The function has no rubric input or skill-reading dependency. The design also names `config.roles["self-reviewer"]` directly, which ignores supported per-phase overrides that `resolveDispatchRoute` applies (`src/dispatch/routing.ts:52-77`); wrong route/family data makes `deriveCurrentEvidenceSet` reject the pair (`src/state/evidence-results.ts:500-514`). **Suggested resolution:** have status expose the effective, override-aware producer and self-review routes for the current phase, validate their same-family relationship, and leave `rubric_digest` for the skill to add from the exact literal it hashes and later sends to counter-review.

8. **Major — `computeCallEnvelope` has no specified no-state path for the first `archflow_state` initialization call.** The server computes that fingerprint only after deriving a synthetic prepared initial state from the initialization artifact (`src/state/initialization.ts:300-346`). `ProductionServices.state` is absent before initialization, and the proposed envelope chunk says only to call the ordinary resolver; it neither exposes nor shares the private initialization-state derivation. Thus the status-driven `create-task` path cannot obtain the promised true first-call fingerprint/request digest without deliberately making a mismatching tool call and retrying, which the design says is fallback rather than the plan. **Suggested resolution:** extract a shared, non-mutating initialization identification helper used by both `runStateInitialization` and `computeCallEnvelope`, or explicitly pin another first-call envelope contract that derives the same prepared state and proves byte-equal fingerprint/request digests in a no-state integration test.

9. **Major — the decision-interface writer must hold the task lock across read/classify/replace.** The proposed standalone writer checks whether `gate.decision` currently binds and otherwise replaces it, but the cited precedent at `src/state/gates.ts:700-711` performs that sequence inside `lock.runExclusive`. Without the same lock, the helper can classify a stale/invalid file, race with another human writer or the resolver, and overwrite a newly valid decision. Same-task cross-process serialization is an explicit product requirement, not adversarial hardening. **Suggested resolution:** under the task lock, re-read state/open gate, `gate.json` and the existing `gate.decision`, then refuse or replace atomically. Add one representative writer-versus-writer/resolver race test.

10. **Major — the rewritten production and self-review skills have no source for the immutable policy constraints required by REQ-17.** The planned status/helper surfaces expose config, evidence, gates, and next action, but not the active rule text/version set resolved from `state.policy_base_commit`. A skill that reads the worktree constitution can consume a later or task-local edit instead of the frozen basis that adjudication checks. **Suggested resolution:** expose the resolved active pinned rules through status or a small read-only helper backed by the policy-base commit, and make production/self-review consume that output rather than mutable worktree files.

## Triage

All ten findings accepted. Three were verified at source before triage because they change the design's shape; the other seven were accepted as written. No finding was rejected.

| # | Disposition | What changed |
|---|---|---|
| 1 | **Accepted, narrower** | The claim that `deriveCurrentEvidenceSet` catches a mid-dispatch artifact edit is wrong and was removed — it never reads the artifact. But the consequence is overstated: `handleAdjudicate` re-reads the artifact and rejects `STATE_INVALID/adjudication-subject-not-current` (`src/mcp/handlers/adjudicate.ts:93-98`), so stale counter evidence commits but cannot advance. Design now states the real catch site and the real cost (the loop blocks late, at adjudicate, costing a counter-review re-run), and restores the lost check narrowly by re-observing the artifact in the counter-review installation path after the child returns. The "add no compensating machinery" prohibition was dropped — it was written against a mistaken belief that nothing was lost. The regression test is now a mutation *during* child dispatch. |
| 2 | **Accepted** | Verified: `currentFor`'s adjudicate branch compares only `subject_digest`, `input_fingerprint`, and `source_evidence_set_digest` (`src/review/fixed-point.ts:82-129`) — nothing compares upstream digests, so the uniform fingerprint genuinely drops REQ-13's upstream invalidation. Restored as an explicit comparison of the retained adjudication's recorded upstream digests against the currently approved ones, rather than by reintroducing fingerprint variance, which would break `runAdjudication` (`src/review/adjudication.ts:293`) again. |
| 3 | **Accepted** | Prompt generation moved to `status`'s open-gate block, built from the `GateRequestV1` in `gate.json` — the same place the decision templates already moved for the same reason. `envelope` keeps its prompt for the four skill-opened kinds. | 5 | **Accepted, narrower** | Verified: `nextPhase` walks `phase-impl-N → phase-design-(N+1)` and stops only at `Number.MAX_SAFE_INTEGER` (`src/state/transitions.ts:65-74`); no live normal handler sets `terminal` (only the checkpoint and initialization import paths).
