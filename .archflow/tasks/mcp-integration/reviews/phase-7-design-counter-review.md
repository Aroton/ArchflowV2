# Phase 7 Design Counter-Review

The design has materially improved over its earlier draft: the nine registry rows are arithmetically consistent, the pinned JSON `$def` inventory resolves against the shipped schemas, the seven-shape Ajv/Zod closure matches the architecture's `archflow_state.artifact` union, and the proposed architecture amendment for `snapshot-accounting` is correct and minimal. The findings below are defects that remain after those corrections.

1. **blocker — The manual-import model cannot prove either initialization from no state or exact continuation from existing state.** `ManualCheckpointV1` carries only an `initialization_digest`, `ManualCheckpointImportV1` carries only the chain/head and an optional revision, and `DurableSemanticSubject` permits only one artifact document (`phase-7…md:507-566`). A `manual-checkpoint-import` therefore cannot also supply the initialization artifact named by checkpoint 1. This does not implement the architecture's rule that no-state checkpoint 1 contain a valid task- or legacy-initialization manifest (`architecture.md:278-284`). The other mode is incomplete too: a nonempty gapless chain may begin above revision 1, invariant 6d then has no supplied “named predecessor,” and invariant 8d compares only `expected_state_revision`—not the predecessor digest the architecture requires to match existing state exactly. State plus an absent `expected_state_revision` is also accepted even though absence is defined as no-state adoption. **Suggested resolution:** pin one complete representation for both modes: provide the initialization target for revision 1; require a full chain starting at 1 or supply an authenticated predecessor target; make `expected_state_revision` present iff state is supplied; and correlate the existing state to the exact predecessor checkpoint, not only its revision number.

2. **blocker — A digest-valid manual chain may cross task boundaries.** Both the import wrapper and every checkpoint carry `task_id` (`phase-7…md:507-545`), but none of invariants 6–8 requires `chain[*].task_id === import.task_id` or even requires all checkpoint task IDs to agree (`:588-590`). An attacker can deliberately self-digest and predecessor-link checkpoints from different tasks, and the proposed validator accepts the chain. This violates REQ-26's cross-task isolation and REQ-39's conservative manual authority. **Suggested resolution:** add an ordered invariant requiring every checkpoint task ID to equal the wrapper task ID, and bind the first checkpoint to the wrapper's repository/initialization identity.

3. **blocker — `state.json` can contradict the initialization document whose digest it claims to adopt.** `TaskStateV1` duplicates `repository_identity_digest`, `config_digest`, `workflow_digest`, `constitution_digest`, and `policy_base_commit` (`phase-7…md:327-348`), but invariant 8 compares only the initialization digest and `task_id` (`:590`). A state can therefore reference the correct task- or legacy-initialization digest while asserting different pinned execution inputs. That defeats the Phase 7 slices of REQ-04 and REQ-21 and leaves the schema with two disagreeing authorities. **Suggested resolution:** for both initialization variants, pin comparisons for every field duplicated in state—task and repository identity, config/workflow/constitution digests, and policy-base commit—and add one-field-at-a-time mismatch fixtures.

4. **major — The “exact” cross-chunk TypeScript seam omits mirrors that later chunks must import, while `OutputEntry` remains a placeholder.** The exact export block (`phase-7…md:159-260`) pins only the four D21 schemas and `snapshotAccountingV1Schema`. It does not name the Zod exports required for `CanonicalTaskPaths` (chunks 5–6), `DeclaredInputRef` (7–8), or `StepStatus`, `PredecessorLink`, and `EvidenceChainEntry` (9). `outputEntryV1Schema` appears only incidentally at `:276`, outside that inventory and without a pinned `z.ZodType<OutputEntry>` signature. Separately, the exact `OutputEntry` declaration is literally `/* 14-branch union */` (`:186`); the later matrix never pins the types/minima of `previous_path`, `payload_bytes`, and `payload_digest`. Independent agents can choose incompatible export names or locally redeclare mirrors and still believe they followed the document. **Suggested resolution:** add exact exports and types for at least `canonicalTaskPathsV1Schema`, `declaredInputRefV1Schema`, `stepStatusV1Schema`, `predecessorLinkV1Schema`, `evidenceChainEntryV1Schema`, and `outputEntryV1Schema: z.ZodType<OutputEntry>`, then spell out the complete `OutputEntry` helper/leaf aliases, including required and forbidden properties in every branch.

5. **major — The claimed total `ProjectResult` function still has a strict-parameter throw path.** Rank 2 runs before phase validity. A schema-valid state may use `phase-impl-99999999999999999999` (accepted by the JSON pattern but rejected by `decodePhaseInstance`) and simultaneously have a wrong document digest. Rank 2 then attempts `STATE_INVALID{phase_instance, issue_code}`; the live strict parameter parser in `errors.ts:26,45,86` rejects that phase value and throws. Moving invariant 3 to `CONTRACT_INVALID` does not protect an earlier rank. **Suggested resolution:** make invalid error-carrier parameters an earlier precondition/invariant than every error that consumes them, or otherwise select `CONTRACT_INVALID` before rank 2 when the state's phase cannot be carried. Add the combined invalid-phase plus self-digest-mismatch fixture, not only the isolated invariant-3 fixture.

6. **major — Getter rejection and structural-error behavior contradict the validator contract and success criteria.** D12 says to read subject/document getters once and then validate the returned `value` (`phase-7…md:577`); it never descriptor-checks the subject slots or the `CanonicalDocument` shell. Reading once prevents split observation but accepts a getter-backed slot, `.value`, or `.digest`, contrary to the explicit rejection criterion at `:772`. Verification step 9 weakens that again to “cannot influence the outcome” (`:800`). Separately, D12 makes prior normative-schema validation a precondition and says input discipline throws (`:579,583`), while success criterion `:765` says unknown fields and structural predecessor failures return pinned existing error codes. Both cannot be true through this function. **Suggested resolution:** require own enumerable data descriptors for the subject slots and document `value`/`digest` before reading them, and choose one public failure contract: either distinguish structural parser throws from semantic `ProjectResult` errors in the criterion, or define the boundary that translates structural failures to exact project errors.

7. **major — The deterministic-error seam does not pin enough information for chunks 10 and 11 to agree.** No exact `issue_code` value is listed for any sub-rank; “names the sub-rank” permits many valid `SafeCode` spellings. The `INPUT_FINGERPRINT_MISMATCH` orientation is also unstated, so one agent can treat state as expected and another artifact as expected. Finally, a single `index` does not order nested or different collections such as `chain[i].phase_instance` versus `chain[i].authoritative_results[j].phase_instance`, root versus array phase IDs, or the two directions of accounting invariant 5c. Thus `(rank, sub-rank, slot, index)` is not the total candidate order the document claims, even where two candidates happen to serialize to the same error today. **Suggested resolution:** publish an exact invariant table containing each `issue_code`, code, complete parameter construction, fingerprint orientation, collection/field ordinal, and full index tuple.

8. **major — The validator promises reference-target correlations for targets it cannot receive.** The overview assigns it reference-target digest agreement (`phase-7…md:21`), and the task-state section says it correlates authoritative results, approvals, open gates, and waivers to their targets (`:357`). Yet `DurableSemanticSubject` contains only `state`, one artifact, and maintenance (`:560-564`); there are no result-manifest, decision, approval, waiver, authority-link, or evidence targets, and none of the ten invariants checks them. This leaves the claimed REQ-11/REQ-13/REQ-21/REQ-39 contribution materially weaker than stated. **Suggested resolution:** either add typed target collections with deterministic resolution invariants, or narrow the claims and assign one named later semantic authority that receives and validates those targets. Do not claim this validator performs correlations its signature cannot express.

9. **major — A cross-class rename remains structurally representable.** The design says one `path_class` governs both endpoints and therefore makes a cross-class rename impossible (`phase-7…md:297,768`). In reality both endpoints are runtime-indistinguishable `RepositoryPathClaim` strings; Phase 6's sole lexical validator cannot derive their classes (`src/contracts/path-claims.ts:31-45`), and this design explicitly defers path-template verification to Phase 9 (`phase-7…md:747`). A rename can carry endpoints from two actual classes while asserting one claimable class. **Suggested resolution:** withdraw the structural-unrepresentability claim and pin Phase 9 to classify and verify both endpoints, or add explicit endpoint-class data if the Phase 7 format must represent the distinction.

10. **major — Two chunks are oversized even if the aggregate token arithmetic fits.** The estimate of 47 files is correct, and 6,250–7,050 lines is plausible before the fixes above. But the closest shipped analogue to chunk 2a's branch structure is the nine-branch gate contract: 544 schema lines and roughly 796 lines across its schema/module/basic unit test. Scaling to 14 branches is already about 1,240 lines before the new blob identities, class partitions, exact TypeScript union, and broader matrix, which supports the design's own 1,200–1,700-line estimate—not a normal chunk. Chunk 11 must independently cover nine shapes, ten invariants, accessors, four-way error ordering, and every set permutation, and is likely another 800–1,200 lines. Thirteen delegated chunks also exceeds the skill's typical 8–12 calibration, though not by itself a blocker. **Suggested resolution:** re-estimate after fixing the missing semantic contracts; split chunk 2a's output authority from its matrix tests and split chunk 11 into structural versus cross-document corpora. If the manual-import target model adds more roots/targets, split the phase at an approved architecture boundary.

11. **minor — D1 overstates both the closure and the neutrality of the third interface conversion.** A real TypeScript 7.0.2 probe extending the repository `tsconfig.json` (including `exactOptionalPropertyTypes`) confirms that `DeclaredInputRef` and `SecretFinding` cause `TS2344` and that the planned closure compiles after those two become aliases. `GitIdentityRef` is not reachable from any durable root; it is used only through `InputFingerprintSubject`, which the criterion itself excludes. Converting an exported interface to an alias is runtime-neutral and neutral for current repository consumers, but not behavior-neutral in general because it removes declaration merging. The repository has no current merges/extends/implements of these names; all unit tests passed in a temporary converted copy. **Suggested resolution:** leave `GitIdentityRef` as an interface and remove it from the transitive criterion, or state explicitly that the conversion intentionally closes declaration merging. Describe the two required changes as runtime/current-consumer neutral rather than absolutely behavior-neutral.

## Verified non-findings

- The pinned JSON `$ref` inventory covers every implied cross-file target found in the design, and the named shipped pointers exist under their exact `$id`/`$def` names.
- The full planned durable type closure compiles under the real TypeScript 7.0.2 settings after the two necessary conversions; `exactOptionalPropertyTypes` introduces no further closure failure.
- The strict parameter key inventories are otherwise correct: `STATE_INVALID`, `SNAPSHOT_INVALID`, `TASK_INVALID`, and `CONTRACT_INVALID` include the required fields, while `INPUT_FINGERPRINT_MISMATCH` correctly excludes `issue_code`.
- The proposed architecture amendment correctly replaces the standalone `snapshot-accounting` registry entry with a `durable-primitives` schema `$def`; no other architecture amendment is justified by that representation choice.
- The document still names and advances all eight Phase 7 requirements. REQ-11 and REQ-14 were not silently dropped; the blockers above show incomplete semantics for REQ-04, REQ-13, REQ-21, REQ-26, REQ-39, and REQ-50 rather than missing requirement labels.
- No conflict was found with Phase 6's Git/pathspec gotchas, contract-to-repository import boundary, or no-new-dependency constraint.

## Triage

Triaged 2026-07-28 against the design at `phase-7-durable-state-and-artifact-schemas.md`. Every finding was reproduced against the document and the shipped source before disposition. **All eleven are accepted**; none was rejected.
