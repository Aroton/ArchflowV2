# Phase 2 Implementation Counter-Review

1. **Blocker — Opaque trust brands are not authenticated before minting qualified evidence.** `assertLinkMatches` compares only ordinary fields, and `authorityQualifier.qualifyReview` / `qualifyAdjudication` never check `authorityLinkBrand` or `verifiedReferencedEvidenceBrand`; `currentReviews` likewise never checks `qualifiedEvidenceBrand` (`src/contracts/trust.ts:143-175`). Mutually consistent plain objects can therefore be passed at the JavaScript boundary and receive the real qualified/current-set brands, violating the central rule that schema-valid or forged JSON cannot mint authority.

   **Suggested resolution:** Require exact internal brand identities and kind/assurance values at every authority consumer, use non-copyable identity-backed brands, and add runtime tests proving that mutually consistent unbranded, cast, spread-cloned, and cross-kind objects cannot qualify or enter a current review set.

2. **Blocker — Result correlation does not bind the canonical request digest.** `correlateProjectResult` checks tool, task, intent, input fingerprint, revision, and success but never compares `expectation.request_digest` (`src/contracts/mcp-tools.ts:96`). `ParsedToolCall` contains no trusted request digest to compare, so same-tool/different-request expectations can correlate successfully; the internal test factory also creates an enumerable symbol brand that survives object spread (`src/contracts/internal/test-capabilities.ts:19-20`).

   **Suggested resolution:** Bind a canonical request digest to the parsed call or pass a separately branded request identity, compare it during correlation, make authority brands non-enumerable or identity-backed, and add same-tool/different-request and spread-clone replay tests.

3. **Blocker — `archflow_gate` input parsing falsely mints the strong current-evidence type from a loose slot array.** The MCP Zod mirror accepts an unordered `array(union).min(2).max(3)` and does not enforce canonical roles, family independence, unique evidence digests, or the exact tuple (`src/contracts/mcp-tools.ts:29-34,64,68-72`). The normative MCP schema is looser still: `current_evidence` is only an object (`src/contracts/schemas/v1/mcp-tools.schema.json:270`). `parseToolCall` nevertheless returns `CurrentEvidenceSetRef`, allowing duplicate, reordered, same-family, or otherwise invalid evidence slots into the gate contract.

   **Suggested resolution:** Reuse `parseCurrentEvidenceSetRef` / `currentEvidenceSetRefSchema` in the tool parser, reference the normative evidence-slot schema from the MCP schema, and add agreement tests for role order, tuple cardinality, family relation, gate slot shape, and digest uniqueness.

4. **Major — Exact gate identity is lost between observation and current-set qualification.** A gate-counter observation binding carries `gate_id` (`src/contracts/trust.ts:43-45`), but `ServerAttestedReview` and `AuthorityLinkBase` do not (`src/contracts/review.ts:129-139`, `src/contracts/trust.ts:91-98`). `currentReviews` therefore compares role, digest, assurance, families, and common scope but cannot prove that a gate-counter review came from the `gate_id` asserted by the slot (`src/contracts/trust.ts:167-175`). Evidence from another gate with the same common scope can be substituted unless a future owner performs an unspecified out-of-band lookup.

   **Suggested resolution:** Carry the gate identity in the attestation/authority binding or require a gate-correlated authority token when constructing the current set. Pin any receipt lookup responsibility explicitly and test same-scope evidence from a different gate.

5. **Major — Server authority links are not correlated with server-attested provenance.** `assertLinkMatches` does not compare the link's `invocation_id`, `result_id`, `envelope_input_digest`, or `observed_output_digest` with the corresponding fields on server-attested evidence (`src/contracts/trust.ts:91-98,143-148`). Even after adding missing brand checks, a branded link and wrapper from different invocations/results can qualify when their outer scope and digest agree. Observation minting also does not enforce the adapter-to-family relation; a capability can label `claude-cli` as family `codex` or vice versa (`src/contracts/trust.ts:64-87`).

   **Suggested resolution:** Branch qualification by assurance and compare every duplicated provenance field, enforce the fixed adapter/family mapping at observation, and add wrong-invocation, result, envelope, output, adapter, and family substitution tests.

6. **Major — Renderers accept forged structural values as trusted projections.** `renderReviewEvidence`, `renderAdjudicationEvidence`, and `renderTriage` never verify their runtime brands (`src/contracts/renderers.ts:33-72`). The renderer unit test explicitly casts a hand-built object with `authority: {}` and successfully renders it (`test/unit/renderers.test.ts:5-9`). Consequently, raw or fabricated metadata can be displayed under trusted ArchFlow headings even though prose escaping itself is effective.

   **Suggested resolution:** Add internal runtime brand assertions to all renderers, use genuinely qualified/validated fixtures for positive tests, and add explicit raw, schema-valid-but-unqualified, cast, and spread-clone rejection cases.

7. **Major — Minted trust and context values are mutable or cloneable after minting.** Observation results are only shallow-frozen, leaving `raw_output_bytes` and nested findings/arrays mutable under fixed digests (`src/contracts/trust.ts:73-87`). `currentReviews` retains authority slots and review objects directly (`src/contracts/trust.ts:167-175`), and test capability factories shallow-copy bindings (`src/contracts/internal/test-capabilities.ts:7-20`). Separately, context brands are enumerable symbol properties; spreading a legitimate `ConnectionContext`, changing its ordinary fields, and retaining the copied brand passes `createInvocationContext`'s sole brand check (`src/contracts/contexts.ts:5-22`).

   **Suggested resolution:** Defensively copy and recursively freeze every plain-data graph, encapsulate mutable byte arrays with copy-on-read/private storage, and use WeakSet/WeakMap or non-enumerable identity brands for contexts and other capabilities. Test source mutation, returned nested mutation, byte mutation, and spread-cloned branded objects.

8. **Major — Evidence parsers bypass required semantic validation and disagree with the normative schemas.** `provenanceBase` spreads `rawReviewSchema.shape`, discarding its duplicate-finding/rule and role-to-step refinements; `parseReviewEvidence` rechecks only verdict/count (`src/contracts/review.ts:86-100,146-175`). `parseReferencedEvidence` performs no review/adjudication semantic derivation at all (`src/contracts/trust.ts:128-135`), so a wrapper containing contradictory evidence can be returned as typed evidence. There are also direct agreement gaps: the review-evidence JSON schema rejects duplicate finding IDs that Zod accepts, while Zod enforces opposite-family server reviews that the JSON schema does not.

   **Suggested resolution:** Compose evidence parsing through the complete raw semantic validators rather than `.shape`, route referenced payloads through `parseReviewEvidence` / `parseAdjudicationEvidence`, mirror every semantic rule in the normative validation path, and add negative agreement cases for duplicates, role/step, family, and contradictory aggregates.

9. **Major — Adjudication can claim compliance when mechanical evidence is absent.** `validateAdjudicationClaims` rejects suspect states only while iterating `enforced_by`; an empty array therefore permits `compliance: "pass"` (`src/contracts/adjudication.ts:108-120`). This contradicts the design requirement that missing mechanical evidence cannot be upgraded to compliance.

   **Suggested resolution:** Require at least one current, correctly subject-bound mechanism before permitting `pass` (and define the legal mixed-state rule), encode the same constraint in both schema and Zod validation, and add empty and mixed mechanical-evidence cases.

10. **Major — Gate and supplemental JSON Schema authority omits the runtime semantic contract.** `parseGateContract` runs only the discriminated structural union and never calls `validateGateDecision` (`src/contracts/gates.ts:159-187`), so ineligible waiver requests, incomplete adjudication resolutions, and mismatched restore adoption authority can parse. The normative gate schema also accepts unsorted canonical sets, `attempts < maximum_attempts`, empty commit digest sets, and non-lexical restore paths that Zod rejects. The supplemental schema independently accepts mismatched `prior_gate_id`/slot `gate_id` and invalid old/new supersession subjects that Zod rejects (`src/contracts/supplemental.ts:23-30`).

   **Suggested resolution:** Make semantic correlation mandatory in the public gate parser and normative validation path, share/customize schema constraints for ordering and cross-field equality, and add bidirectional agreement fixtures for every gate and supplemental variant.

11. **Major — MCP JSON Schema and runtime parsing diverge beyond current-evidence slots.** Gate `context` is unconstrained in the MCP schema while runtime invokes `parseGateContext`; waiver `human_provenance` is unconstrained in JSON and runtime accepts any `recorded_at` string instead of canonical UTC milliseconds (`src/contracts/mcp-tools.ts:25-27,64-70,83`). The embedded path schema uses 1,024 characters and omits C1 controls, while `TaskPathClaim` uses 1,024 UTF-8 bytes and rejects U+0080-U+009F (`src/contracts/schemas/v1/mcp-tools.schema.json:21-26`, `src/contracts/path-claims.ts:9-21`). A 600-character two-byte path is therefore schema-valid but parser-invalid.

   **Suggested resolution:** Compose/reference the authoritative gate, provenance, evidence-slot, and path schemas and reuse their Zod parsers. Add positive/negative agreement corpora for all five tool inputs/results, including multibyte and C1 path cases.

12. **Major — Error parsing treats JSON property order as authority, while the error schema is looser in other trust-bearing fields.** `parseSerializedError` compares `JSON.stringify` output to a reconstructed object (`src/contracts/errors.ts:90-97`), rejecting otherwise identical schema-valid errors whose top-level or parameter keys are reordered. Conversely, `project-error.schema.json` accepts arbitrary, unsorted 1-1,024-character `SNAPSHOT_LIMIT.offending_paths`, whereas the Zod registry requires sorted unique lexical `TaskPathClaim`s (`src/contracts/errors.ts:30,45`).

   **Suggested resolution:** Compare correlated error fields structurally and order-insensitively while preserving the original value, reuse the normative path claim plus canonical ordering validation, and agreement-test reordered objects, traversal/control paths, and unsorted offending-path sets.

13. **Major — Correlated identifiers use incompatible grammars across the phase.** Gate decisions and MCP contracts accept the broad `SafeId` grammar, including uppercase, colon, underscore, and dot (`src/contracts/gates.ts:61`, `src/contracts/mcp-tools.ts:19`), while supplemental gate/task references and trust links use a lowercase hyphen-only slug (`src/contracts/supplemental.ts:16`, `src/contracts/trust.ts:108`). A valid gate such as `Gate:1` can be decided but cannot be referenced by supplemental evidence, and the same incompatibility affects task identity across tools and evidence.

   **Suggested resolution:** Use one shared identifier primitive for each correlated identity category across TypeScript, Zod, and JSON Schema, or explicitly tighten the minting boundary everywhere to the narrowest grammar. Add cross-contract round-trip fixtures.

14. **Minor — The claimed single gate-effect authority and adversarial coverage are not implemented.** Runtime effects are hard-coded in a parallel map rather than derived or exhaustively agreement-checked against `x-archflow-effect` in `gate-contract.schema.json` (`src/contracts/gates.ts:110-112`). The phase-planned gate, supplemental, and error fixture directories are absent, and agreement tests sample only one gate, one envelope, and one error from each registry (`test/contracts/gate-error-schema-agreement.test.ts:16-37`). The review/adjudication and MCP agreement suites are similarly sparse, which is why the defects above pass all 157 tests and the full `npm run check`.

   **Suggested resolution:** Derive or exhaustively compare every runtime effect against schema annotations and add the planned positive/negative fixture corpora for every provenance, gate, supplemental, error, and tool variant, including all required substitution and non-mutation cases.

The internal test-capability factories are not re-exported by `src/contracts/index.ts`, and the temporary bundle smoke confirms their names are absent. No public-barrel leak was found; the problem is that several public consumers fail to authenticate the opaque brands they are supposed to consume.
