# Phase 3 Implementation Counter-Review

1. **Severity: major — Tool-bound project failures can be substituted across tools.** `validateProjectFailureStructure(name, value)` uses `name` only to brand the result and accepts a closed `CONTRACT_INVALID` or `RESULT_INVALID` whose diagnostic `tool` names a different tool. `createToolBoundary` then accepts the same mismatch from a handler because its failure path delegates to `validateProjectResultStructure`, which likewise does not compare an error's optional/required `tool` parameter with `call.name`. For example, an `archflow_state` handler can return a valid `CONTRACT_INVALID` naming `archflow_gate`, and the authenticated boundary emits that contradictory result instead of the required safe `INTERNAL_ERROR`. This exceeds the design's allowance for *tool-neutral* failures and leaves a detectable cross-tool substitution unhandled.

   **Suggested resolution:** Centralize failure-to-tool correlation in the structural-result owner. Permit failures without a tool binding on any known path, require every present tool binding to equal the selected/called tool, and make the boundary reduce a mismatch to correlation-only `INTERNAL_ERROR`. Add direct validator and boundary tests for both `CONTRACT_INVALID` and `RESULT_INVALID`, including matching, neutral, and cross-tool cases.

2. **Severity: major — The advertised waiver output schema accepts an unsafe integer that runtime revalidation rejects.** The projected `archflow_waiver` output inherits `mcp-tools.schema.json`'s `success.rule_version`, which specifies only `type: "integer"` and `minimum: 1`; unlike the shared rule definition and the Zod success schema, it has no `maximum: 9007199254740991`. Fresh strict Ajv therefore accepts `rule_version: 9007199254740992`, while `validateProjectResultStructure` rejects the same otherwise-valid result through `.max(Number.MAX_SAFE_INTEGER)`. The catalogue consequently advertises a structurally valid output that the authenticated boundary can never admit, violating schema/runtime agreement and the requirement not to weaken projected branches.

   **Suggested resolution:** Correct the normative waiver-success schema to reuse the shared bounded rule-version definition (updating the phase file scope first if needed), then add an agreement fixture at both safe bounds and both adjacent unsafe values. Exercise the same cases through the standalone advertised output schema and authentic runtime result validation.

3. **Severity: major — The classified corpus cannot prove the required success-output semantics and covers only a subset of removed runtime checks.** In `mcp-advertised-schema.test.ts`, every output corpus entry is sent to `validateProjectFailureStructure`; the harness therefore cannot test even one success output or any success-to-request correlation. Its self-declared semantic category list also treats one `attempts-exhausted` case as coverage for all gate-context semantics, omitting the distinct review/adjudication rule-set, waiver eligibility/scope, material-drift ordering, and commit-authorization ordering checks. It likewise omits gate-decision relations and the state, gate, and waiver success correlations enforced by `successFor`. This is why the unsafe waiver output in finding 2 passed despite the success criterion requiring the corpus to distinguish all portable structure from runtime-only semantic constraints.

   **Suggested resolution:** Give output-success corpus cases a companion authentic parsed call and validate them with `validateProjectResultStructure`; retain the failure-only validator only for failure cases. Add positive coverage for every tool's success plus differential portable-accept/runtime-reject cases for each removed validating semantic family and each call-correlated result rule. Make the expected semantic inventory derive from, or be exhaustively reconciled with, the exact eight source documents/custom-keyword behaviors instead of letting a hand-written subset certify itself.

4. **Severity: minor — The CI SDK-free check is bypassable by valid TypeScript import forms.** The workflow grep matches `from "@modelcontextprotocol/..."` and dynamic `import(...)`, but not a side-effect import such as `import "@modelcontextprotocol/server"` or a re-export such as `export * from "@modelcontextprotocol/server"`. The current production source is clean, but the added CI control does not fully enforce the Phase 3 no-SDK-import boundary it claims to enforce.

   **Suggested resolution:** For Phase 3, reject any `@modelcontextprotocol/` occurrence in production TypeScript (or use an AST-based import/re-export check), with a small mutation test covering static imports, side-effect imports, dynamic imports, and re-exports. Phase 4 can then replace the blanket rule with the exact adapter-only allowlist required by its design.

## Triage

1. **Accepted — fixed.** Project-failure parsing is now centralized in `src/contracts/mcp-tools.ts`. Both `validateProjectFailureStructure` and the failure branch of `validateProjectResultStructure` accept tool-neutral errors, require any present diagnostic `tool` to match the selected/authentic call tool, and reject cross-tool `CONTRACT_INVALID` and `RESULT_INVALID` substitutions. Boundary regression tests prove matching and neutral failures pass, mismatches invoke the handler only once, and the mismatch becomes a correlation-only `INTERNAL_ERROR` without leaking the contradictory result.

2. **Accepted — fixed.** The normative waiver-success `rule_version` now references the shared bounded rule-version schema in `src/contracts/schemas/v1/mcp-tools.schema.json`. Agreement tests exercise `1`, `Number.MAX_SAFE_INTEGER`, `0`, and `Number.MAX_SAFE_INTEGER + 1` through the normative schema, the standalone advertised output, and authentic runtime result validation.

3. **Accepted — fixed.** The catalogue corpus is now input/output-aware: failure outputs use `validateProjectFailureStructure`, successful outputs carry an authentic companion call and use `validateProjectResultStructure`, and all five tools have positive success controls. The corpus contains 46 cases, including 38 runtime-semantic differentials covering every validating `x-archflow-*` family in the exact eight-schema source set plus failure/state/gate/waiver call correlations. Its keyword inventory is collected from those eight documents and explicitly distinguishes annotation-only `x-archflow-effect`. During this fix, output differentials exposed that gate success parsed decision envelopes without applying gate-context semantics; `successFor` now calls `validateGateDecision`, with regressions for waiver eligibility, adjudication resolution order/coverage, and restore-adoption authority.

4. **Accepted — fixed.** The partial CI grep was replaced by `scripts/check-phase-3-mcp-boundary.mjs`, which rejects any `@modelcontextprotocol/` occurrence in production TypeScript and all premature Phase 4/5 paths. `scripts/test-phase-3-mcp-boundary-policy.mjs` mutation-tests aliased static, type-only, side-effect, dynamic, and re-export forms plus `src/main.ts`, the SDK adapter/barrel, and `dist`. Both checks are part of the local aggregate and both-node CI matrix.
