# Phase 13 Design Counter-Review

1. **Blocker — The Codex invocation is not tool-free, so the central reason for deferring the OS read sandbox is false.** In current Codex 0.146.0, disabling `shell_tool` and `unified_exec` only removes the shell arm. The official tool planner still registers `apply_patch` when the model supports it, always registers `view_image` when an environment exists, and separately registers collaboration tools when multi-agent is enabled (`codex-rs/core/src/tools/spec_plan.rs:698-702, 855-878, 882-968` at upstream commit `745603a5a1eb48b6f343633d622eeb72dd549d7b`). `view_image` resolves a model-supplied path and reads it through the read-only filesystem sandbox (`handlers/view_image.rs:118-175`); read-only is therefore not a read boundary. The installed feature set also has `multi_agent` enabled, but the pinned argv does not disable it, so the claim that the child cannot create descendants is also unsupported. The five text-canary prompt cannot repair this: one stochastic run that does not choose or echo a capability does not prove the capability was absent, and `codex debug prompt-input` renders input messages, not the request's `tools[]`. This misses REQ-26/REQ-32/REQ-35 and VAL-07 as written. **Suggested resolution:** while OS confinement remains deferred, mark Codex reviewer dispatch unsupported unless the exact gated CLI offers a deterministic empty tool surface. Gate compatibility on inspection/capture of the actual tool declarations for the exact invocation, not only on a behavioral answer; retain canaries as regression tests, including a real image canary, but do not let them waive an exposed filesystem-capable tool.

2. **Blocker — Claude managed policy remains an undeclared read/injection mechanism, but the design records it without gating.** The installed 2.1.220 help explicitly says `--safe-mode` leaves admin-managed policy active. Managed hooks can run shell commands independently of model tools and a `UserPromptSubmit` hook can add model context; managed instructions likewise survive user/project setting suppression. The design admits server-delivered policy is undetectable, then makes the stat-only preflight non-gating and excludes it from the probe key. That permits a normal managed environment to read or inject repository/global context despite `--tools ""`, contrary to REQ-32/VAL-07 and to architecture lines 310-312, which make managed injection unsupported unless proved absent. The stat-only attestation is also complexity with no protective effect. **Suggested resolution:** fail Claude dispatch closed unless the effective invocation proves managed hooks/instructions absent; at minimum, any detected managed-policy surface must be unsupported rather than telemetry-only. If server-delivered policy cannot be ruled out for an account/environment, do not claim that environment as supported.

3. **Blocker — The pinned Claude structured-output argv does not run.** Claude 2.1.220 defines `--json-schema <schema>` as inline JSON, not a schema-file path. Passing the proposed temp path fails locally with `--json-schema is not valid JSON: ... Unrecognized token '/'` before a model call. Claude JSON output is also a CLI wrapper whose validated value must be extracted from `structured_output`; it is not the raw strict review object that `observationSource.observeReview` accepts. The shared wording “schema handed to the CLI is `review.schema.json`” obscures the required adapter difference. **Suggested resolution:** serialize the schema document as the Claude argument, keep the file path only for Codex, and pin the Claude wrapper decoder so only the exact `structured_output` bytes/value reach the review parser/mint. Add a no-network fixture that rejects the file-path form and validates wrapper extraction.

4. **Blocker — Auth preflight checks a different environment from the child it authorizes.** The pinned `CliAdapter` exposes `preflight()` with no workspace/environment, while only `buildInvocation(envelope, route, workspace)` receives the generated home and scrubbed map. A preflight run in the parent environment can report logged in from the real home or a provider-key sentinel and then authorize a generated-home child that is logged out, cannot refresh, or selects different auth. That violates REQ-34/VAL-08's fail-before-invocation guarantee even under the settled one-bit auth policy. **Suggested resolution:** make the generated workspace/scrubbed environment an explicit input to preflight and execute `claude auth status` / `codex login status` under the exact child environment. Test parent-logged-in/generated-home-missing and parent-key-sentinel cases.

5. **Blocker — The Codex classifier uses a forbidden and unstable source for semantic failure classes.** Design line 92 says to derive classes from `--json` events “plus stderr text,” but the required contract is event-only because Codex has one failure exit. Current upstream `exec_events.rs:8-36, 90-94` emits `turn.failed` and top-level `error`, but their structured payload contains only a `message`; stderr simultaneously carries warnings and startup diagnostics. Letting stderr participate can turn an unrelated warning into `RATE_LIMITED`, `AUTH_UNAVAILABLE`, or `UNSUPPORTED_MODEL`, and the design pins no event precedence or exact fallback. **Suggested resolution:** define one JSONL decoder and precedence: classify semantic Codex failures only from the message inside valid terminal/fatal JSONL events; deduplicate a top-level `error` followed by `turn.failed`; treat stderr as diagnostic/secret-scan input only; and map a nonzero exit with no recognized valid failure event to exact `PROCESS_FAILED {adapter, exit_class}`. Record gated-version fixtures for each supported message shape and prove adversarial stderr cannot affect classification.

6. **Major — `DispatchSubject` is sufficient only for ordinary counter-review, but the proposed generic review seam permits shapes it cannot mint and accepts IDs the evidence schema rejects.** The strict raw review needs eight subject fields: `step` is required and role-correlated by `rawReviewSchema`, while `observeReview` directly compares the other seven at `trust.ts:100`. The proposed record carries those eight, so ordinary `counter-review` can mint. However, its unspecified `role` also leaves `gate-counter-review` representable, for which `ObservationBindingByKind["review"]` requires a binding-only `gate_id` that the record lacks; self-review must not enter this production seam at all. Separately, `invocation_id` and `result_id` are plain strings copied into evidence, while existing upstream identities accept broad `SafeId` values and `reviewEvidenceSchema` accepts only lowercase kebab IDs. A valid upstream `Invocation:1` or `Result_1` can therefore mint typed evidence that later fails its own durable schema. **Suggested resolution:** pin `DispatchSubject` as a discriminated counter/gate-counter union with fixed role/step and a binding-only `gate_id` on the latter, or explicitly narrow Phase 13 to ordinary counter-review. Parse/generate both provenance IDs against the evidence ID vocabulary before envelope construction/minting, and test wrong role/step, missing gate ID, and broad-SafeId inputs. Do not echo `gate_id`, `invocation_id`, or `result_id` into the strict raw model object.

7. **Major — The adapter seam is review-only even though this phase builds adjudication envelopes for Phase 14.** `DispatchEnvelope` has no result kind, `CliAdapter.buildInvocation` has no output-contract/schema input, and the design pins adapter validation to `review.schema.json`. Phase 14 therefore cannot send an adjudication envelope through these “exact adapters” with `adjudication.schema.json` without rewriting the chunk boundary. This leaves REQ-33's validated-result path uncovered at the Phase 13/14 seam. **Suggested resolution:** make the dispatch contract a discriminated `review | adjudication` shape that selects the corresponding CLI output schema and parser, while keeping review and adjudication minting separate. If Phase 13 intentionally supports reviews only, remove the adjudication builder from its claimed seam and pin the exact extension point Phase 14 owns.

8. **Major — Codex's persisted final-output channel bypasses the stated output bound.** The invocation captures JSONL on stdout and independently writes the last message through `-o <file>`. Node's `maxBuffer` bounds stdout/stderr only; it does not bound that file, and the workspace/result interfaces pin no bounded stat/read. An implementation following the design can read an arbitrarily large final response and never produce the required `OUTPUT_OVERFLOW`, missing REQ-35/VAL-08. **Suggested resolution:** treat JSONL and the `-o` file as separate bounded channels. Stat and bounded-read the final-output file before parsing, return the exact `OUTPUT_OVERFLOW {adapter, byte_count, byte_cap}` when it exceeds the cap, and cover it with a fake CLI that keeps JSONL small while overgrowing `-o`.

9. **Major — The clean-home credential branch pre-pins state import and a macOS real-`HOME` fallback that the available evidence does not justify.** On this Linux host, both current CLIs authenticate with only the credential-file symlink under an otherwise empty generated home; Claude creates its own fresh `.claude.json`, and Codex needs no copied first-run database/config. Current Codex's file backend writes refreshes by truncating `CODEX_HOME/auth.json`, so refresh follows the symlink; there is no demonstrated write-back defect to solve. Importing unspecified “minimal first-run state” from the real home risks reintroducing exactly the global/project metadata the clean home removes. The macOS fallback is also only an assumption: Keychain lookup is not necessarily controlled by `HOME`, so generated `HOME` may work without surrendering layer 2, and this Linux-only implementation session cannot prove otherwise. **Suggested resolution:** pin generated defaults only and forbid copying/symlinking real non-credential state unless an experiment identifies an exact required field. Try generated `HOME` with the macOS Keychain first; keep that platform unavailable until a recorded macOS auth, refresh-writeback, onboarding, and prompt-input run passes, and adopt real `HOME` only if that evidence proves it necessary and characterizes the resulting context leakage.

## Triage

All nine findings accepted. Findings 1 and 2 are accepted as *correct diagnoses* but resolved differently from their suggested resolutions, because they prompted a scope decision by the task owner that supersedes them.

**Owner scope decision (2026-07-30).** Isolation in this phase is **best-effort context hygiene, not an enforced or proven boundary**. The owner has run hundreds of cross-client counter-reviews by hand without a reviewer going rogue, and explicitly accepts that results may be slightly worse. Phase 13 therefore builds no machinery to enforce or verify an isolation boundary. This is a deliberate, evidence-based risk acceptance, not an oversight.
