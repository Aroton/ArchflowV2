# Phase 4 Implementation Counter-Review

1. **Severity: major — An SDK-invalid cancellation can consume a live request without aborting it, permanently suppressing its eventual response.** `src/mcp/session.ts:339-353` marks an executing record `cancelling` after checking only that `params` is plain JSON and `requestId` is safe. It does not validate the optional `reason`, even though beta.5's public `specTypeSchemas.CancelledNotification` rejects non-string reasons. `src/mcp/sdk-adapter.ts:279-305` prevalidates only list/call requests, so the malformed cancellation is handed to the SDK after the state mutation. The SDK rejects it without aborting the handler; when the handler later settles, `src/mcp/sdk-adapter.ts:385-388` calls `onRouteSettled`, which deletes the cancelling record at `src/mcp/session.ts:467-471`, and the SDK's valid eventual response is then dropped at `src/mcp/session.ts:405-408`. I reproduced this with an enabled delayed `archflow_state` handler and `reason: { invalid: true }`: the handler was not aborted, returned a valid success, and stdout contained no call response. This violates the design's rule to ignore malformed cancellation and leaves the client waiting indefinitely.

   **Suggested resolution:** Validate the complete cancellation through the pinned public SDK schema before mutating the session record (or add an SDK-free exact shape guard proven equivalent to that schema). Add a composed runtime test with a pending enabled handler showing that malformed cancellation neither aborts nor suppresses the normal response, alongside the valid-cancellation case.

2. **Severity: major — The framer applies the 10 MiB limit to an arbitrary input chunk rather than to each JSONL frame and the retained incomplete suffix.** `src/mcp/framing.ts:40-45` rejects whenever the compacted retained bytes plus the newly delivered chunk exceed `MAX_FRAME_BYTES + 2`, before it searches the chunk for line feeds. A single chunk containing more than 10 MiB total of small, independently valid JSON lines therefore produces one fatal parse error and discards every frame, while the same byte stream split into smaller `Readable` chunks succeeds. I reproduced this with repeated `{}\n` records. This violates segment-independent framing and makes protocol behavior depend on Node's arbitrary chunk partitioning. The "many lines" test at `test/unit/mcp-framing.test.ts:88-97` is too small to cross the aggregate boundary.

   **Suggested resolution:** Split/consume complete LF-delimited segments incrementally and enforce 10 MiB only on an individual frame and the genuinely unconsumed suffix. Add equivalent-byte-stream tests using different chunk partitions, including one greater-than-10-MiB chunk made entirely of short valid frames.

3. **Severity: major — The required composed runtime verification is materially incomplete, so several Phase 4 success criteria are not proven.** The adapter suite at `test/unit/mcp-sdk-adapter.test.ts:67-173` covers only inert initialization/list/call/metadata/parse-error paths; the integration suite at `test/integration/mcp-stdio.test.ts:180-289` covers basic transcripts, byte errors, signals, and a closed stdout pipe. Neither exercises an enabled asynchronous handler, valid or malformed SDK cancellation, adapter-level backpressure and input pause/resume, close while paused, initialize post-mutation projection/write failure, projection throw points, callback failure with active records, or post-close late-handler quarantine. The session tests also do not cover ID non-reuse after all of success, project/protocol error, send failure, and close, and there is no test of the `UNSUPPORTED_PROTOCOL` mapping despite the explicit four-mapping criterion. Component queue/session tests cannot prove these cross-layer behaviors; the malformed-cancellation defect above demonstrates the gap.

   **Suggested resolution:** Add controlled-stream adapter tests and live enabled-handler races for the omitted Phase 4 verification steps, including every terminal ID path and all four protocol mappings. Keep component tests, but prove the state/SDK/queue interactions at the composed boundary where ordering defects occur.

4. **Severity: major — The compatibility probe is narrower than the stop-on-drift gate specified by the design.** `scripts/probe-phase-4-mcp-compatibility.mjs:65-95` checks npm dist-tags, package metadata, and runtime existence of a few `Server` methods, but it does not check official beta/stable status or guidance, the required public TypeScript declaration signatures/two-argument handlers, the consumed Call/List/Cancelled schema surfaces, or all required `Transport` hooks. The script and CI can therefore pass after a relevant public-surface or guidance drift that the phase says must stop implementation/review.

   **Suggested resolution:** Extend the compatibility gate with compile-time public-declaration fixtures and runtime assertions for every consumed schema/hook, including cancellation. Record and enforce the immediately-before-review official-source status/guidance check (or make the documented manual portion explicit and retain its evidence) so the automated probe is not presented as the complete gate.

5. **Severity: minor — `SessionAction` is not the closed route-specific tagged union promised by the design.** The single `forward-sdk` member at `src/mcp/session.ts:57-66` makes `route`, token, IDs, and name/argument candidates independently optional, so impossible values such as a `tools-call` route without recovery candidates type-check. `src/mcp/sdk-adapter.ts:270-277` compensates with presence checks and would silently omit `forwardedCalls` state if an internal producer regressed instead of making that state unrepresentable.

   **Suggested resolution:** Split `forward-sdk` into discriminated variants for request routes, cancellation, and initialized notification, with route-specific required fields. Add compile-time negative cases for incomplete combinations.

## Triage

| Finding | Disposition | Resolution |
|---:|---|---|
| 1 | Accepted and fixed | Cancellation is now a two-step operation. `session.ts` emits a non-mutating `validate-cancellation` action; `sdk-adapter.ts` validates the complete notification with public `specTypeSchemas.CancelledNotification`; only the closed `cancellation-accepted` event changes the record to `cancelling` and rewrites the request ID. Composed delayed-handler tests prove a malformed reason is ignored and the normal response is delivered, while a valid cancellation aborts and quarantines the late result. |
| 2 | Rejected | The approved `JsonLineFramer.append(chunk): void` contract and the explicit 10 MiB retained-current-chunk bound cannot both accept an arbitrarily large delivered chunk and yield all of its frames later without retaining that oversized chunk or eagerly queueing an unbounded number of decoded frames. Either choice violates the phase's bounded-memory/backpressure contract. The implementation therefore intentionally fails closed when the current retained delivery exceeds the cap. Removing delivery-partition dependence would require a design-level streaming interface revision, such as returning consumed bytes or driving frames through a bounded callback; that scope is not inferred during implementation triage. |
| 3 | Accepted in part and fixed proportionally | Added composed enabled-handler races for malformed and valid cancellation, post-close late-result quarantine, and representative permanent ID reuse after success, project error, protocol error, and cancellation. All four protocol numeric mappings are now pinned by an exact exhaustive typed table, with live routes for `TOOL_NOT_FOUND`, `TOOL_DISABLED`, and `INITIALIZATION_REPEATED`; `UNSUPPORTED_PROTOCOL` remains a no-live-route mapping as designed. Existing controlled send-queue/session tests cover backpressure, callback failure, close cleanup, caps, and state transitions, while spawned integration tests cover EPIPE and signals. Rejected building a second exhaustive cross-product harness for already-covered component invariants because it is disproportionate to the prototype after the reproduced cross-layer defect and representative terminal paths are now covered. |
| 4 | Accepted and fixed after design review | Added runtime checks for every consumed public schema and transport/server hook, including `CancelledNotification` and `Server.oninitialized`, plus `test/types/mcp-sdk-public-surface.ts` for compile-time handler/context and transport signatures. The probe states that official status/guidance remains a dated manual gate. At `2026-07-28T00:06:53Z`, live npm metadata showed both `@modelcontextprotocol/server` and `@modelcontextprotocol/core` stable `2.0.0` published at approximately `2026-07-27T23:55Z` and moved to `latest`; the official SDK `main` README simultaneously changed to state that v2 is the stable release line. Work stopped for architecture/design review. The revised stable design was approved, exact stable pins and evidence were updated, and the strengthened probe now passes under both supported Node patches while retaining protocol `2025-11-25`. Official evidence: [SDK repository](https://github.com/modelcontextprotocol/typescript-sdk), [server package](https://www.npmjs.com/package/@modelcontextprotocol/server), and [2026-07-28 specification](https://modelcontextprotocol.io/specification/2026-07-28). |

Impossible combinations no longer type-check; compile-negative cases cover incomplete tools-call, initialized, and cancellation actions. The adapter no longer uses optional-field presence checks to reconstruct route authority. |
