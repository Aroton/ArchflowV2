# Phase 16 Design Counter-Review

1. **blocker — `task-init` rejects the supported per-task routing override.** The design requires an existing `.archflow/tasks/<task>/config.yaml` to be byte-identical to the repository template or returns `scaffold-diverged`. REQ-30 explicitly permits a human-authored per-task config to override model and effort by role and phase, while `TaskInitializationV1` pins the exact whole-file digest without requiring template equality. Implemented as written, every legitimate pre-initialization override is rejected. **Suggested resolution:** copy the template only when the task config is absent; when it exists, parse and validate it, preserve it, and digest its exact bytes. Reserve template-divergence handling for repository scaffold assets that ArchFlow actually owns.

2. **blocker — Claude registration uses effective name resolution as project-scope authority.** `claude mcp get archflow` resolves the highest-precedence entry, and Claude's documented precedence is local, then project, then user. A pre-existing local or user `archflow` therefore makes the design skip `claude mcp add --scope project`, leaving the required committed `.mcp.json` entry absent; after a project entry is added, the same masking also makes `get` an invalid timeout readback. This misses REQ-01 and the architecture's Phase 16 project-registration success criterion. [Claude Code documents the scope precedence and project `.mcp.json` behavior](https://code.claude.com/docs/en/mcp). **Suggested resolution:** determine project entry presence, command collision, and persisted timeout from the parsed project `.mcp.json`; add the project entry whenever that scope lacks it. Use `claude mcp get` only for runtime/approval diagnostics and explicitly report any higher-precedence same-name entry.

3. **blocker — Codex registration abandons required preservation for an ordinary existing project config.** Refusing every unmarked `<repo>/.codex/config.toml` and asking the human to paste a block is not idempotent init preserving unrelated Codex configuration as REQ-01 and the architecture require. Project config is a normal supported Codex layer for MCP servers, hooks, model settings, and other options, so this turns a common supported repository into a manual failure path. The correction that no project-scoped `codex mcp add` exists is valid: installed `codex-cli 0.146.0` exposes no scope option, and the open upstream request confirms that `mcp add` still writes only user config. [Official Codex config layering](https://learn.chatgpt.com/docs/config-file/config-basic), [official project-scoped MCP configuration](https://learn.chatgpt.com/docs/extend/mcp), [upstream scope request](https://github.com/openai/codex/issues/23487). **Suggested resolution:** own only the `mcp_servers.archflow` table or a delimited ArchFlow block, parse existing TOML, reject only malformed TOML or an actual conflicting `archflow` entry, and append/update the fixed table while preserving unrelated bytes and settings. A small maintained TOML parser is justified by this current requirement; no generalized format-preserving writer is needed.

4. **blocker — the Node gate accepts runtimes below the repository's supported floor.** Comparing only `process.version`'s major to `manifest.json.launch_profile.node_major` admits Node 24.0 through 24.14, while `package.json` declares `node: ^24.15.0` and the architecture names 24.15.0 as the functional minimum. Implemented as written, install reports success on explicitly unsupported runtimes and violates the phase criterion to detect unsupported runtime versions. **Suggested resolution:** put the complete machine-readable Node minimum/range in the release manifest and compare against it without requiring npm; test a same-major version below 24.15.0 in addition to a wrong major.

5. **major — installer verification omits the runtime assets that init installs and consumes.** `verify_payload` hashes only `manifest.json.artifacts[]`, but the design copies `assets/` beside the bundles and `src/init` scaffolds from those bytes. The current manifest records workflow and constitution hashes under `release_control_inputs`, not `artifacts`; the new `assets/config.template.yaml` is also absent from `DECLARED_ASSETS` unless release support is changed, which the Files and Work Breakdown sections do not require. A stale or corrupt asset tree can therefore pass installation verification and seed repositories/tasks from bytes different from the release's pinned inputs. **Suggested resolution:** add the config template to the release-declared asset set and verify every copied runtime asset against its manifest record during install (or promote the copied assets into the artifact set), including a mutation test for one scaffold asset.

6. **major — the Codex `0.145.0` floor is based on a bundled-model migration, not a demonstrated runtime incompatibility.** The `0.145.0` release notes make GPT-5.6 Sol the default for the new Bedrock path and migrate bundled/internal GPT-5.4 selections; they do not establish that `0.122.0` cannot invoke the arbitrary `gpt-5.6-sol` slug. A hard version floor also does not prove that the current account/catalog can use that model, so the proposed bump excludes potentially working installations without preventing the failure it claims to catch. [`0.145.0` release notes](https://github.com/openai/codex/releases/tag/rust-v0.145.0), [`0.122.0` release notes](https://github.com/openai/codex/releases/tag/rust-v0.122.0), [current GPT-5.6 Sol model](https://developers.openai.com/api/docs/models/gpt-5.6-sol). **Suggested resolution:** retain the established functional floor unless a direct older-client compatibility test proves a protocol/client failure, and make init check the current Codex model catalog under the same generated-home/auth environment used by dispatch so it detects actual slug availability.

## Triage

Triaged 2026-07-31. Six findings, six accepted; one accepted with a different resolution than suggested.

1. **`task-init` rejects the supported per-task routing override — ACCEPTED.** Correct and squarely against REQ-30, which permits a human- or Archforge-authored per-task `config.yaml` to override model and effort by role and phase; `TaskInitializationV1` pins the whole-file digest and never requires template equality. Chunk 6 now copies the template **only when the task config is absent**, and otherwise parses, validates, preserves, and digests the existing bytes as-is. Divergence handling is confined to the repository scaffold assets ArchFlow owns in chunk 3. Verification adds a case for an overriding pre-existing task config preserved byte-for-byte.

2. **Claude registration used effective name resolution as project-scope authority — ACCEPTED.** The precedence hazard is real: `claude mcp get` resolves local, then project, then user, so a pre-existing local or user `archflow` would have made init skip `claude mcp add --scope project` and leave the required committed entry absent, then misreport the timeout. Presence, command collision, and the persisted timeout now come from the parsed project `.mcp.json`; the project entry is written whenever that scope lacks it; `claude mcp get` is demoted to runtime/approval diagnostics and any masking higher-precedence entry is reported explicitly. Success criteria and the registration test matrix updated.

3. **Codex registration abandoned required preservation — ACCEPTED, with a different resolution.** The finding is right: refusing every unmarked `<repo>/.codex/config.toml` is not the idempotent preserving init REQ-01 requires, project config is an ordinary supported Codex layer, and the architecture explicitly says init "never replaces whole JSON/TOML files." The design now appends a **marker-delimited block**, leaving every prior byte untouched (TOML tables are order-independent), replaces only the bytes between its own markers on re-run, and refuses only on a genuine conflicting `archflow` entry or an unclassifiable file.

   The suggested TOML-parser dependency is **rejected**. `smol-toml@1.7.1` is maintained and permissively licensed, but it does not preserve formatting, so parse-and-re-serialize would rewrite the user's whole file and destroy their comments — the opposite of the preservation this finding asks for, and a wholesale rewrite besides. Detecting a conflicting entry needs a line scan for the `[mcp_servers.archflow]` header and `mcp_servers` inline/dotted forms, not a parser, and anything ambiguous fails closed to the paste path. Verification adds byte-identity assertions for an existing file with unrelated tables and comments, and for a second run.

4. **Node gate accepted runtimes below the supported floor — ACCEPTED.** A major-only compare against `launch_profile.node_major` would admit 24.0–24.14 while `package.json` declares `^24.15.0`. The gate now does a full version compare against `engines.node`, read from the checkout with `node -e` and no npm — simpler than adding a manifest field, since `package.json` is already the authority and already present at install time. Verification adds a same-major below-floor case alongside the wrong-major one.

5. **Installer verification omitted the runtime assets — ACCEPTED.** Correct: `assets/**` is recorded only under `release_control_inputs`, `assets/config.template.yaml` is not in the declared asset set at all, and init seeds every initialized repository from those bytes — so hashing `artifacts[]` alone would let a corrupt asset tree pass. Chunk 1 now adds the template to the release-declared asset set and gives copied assets a verifiable manifest record; `install.sh` verifies every file it copies; `scripts/release-support.mjs` is added to the Files table; and a mutated-scaffold-asset case is added to verification.

6. **Codex `0.145.0` floor was inference, not demonstrated incompatibility — ACCEPTED, and extended.** The reasoning applies equally to the proposed Claude `2.1.219` bump, which rested on the same kind of release-note inference. **Both floor bumps are dropped**; `CLAUDE_MINIMUM_VERSION` stays `2.1.205` (which already clears the v2.1.203 requirement for a per-server `timeout` to raise the stdio idle floor) and `CODEX_MINIMUM_VERSION` stays `0.122.0`. A version floor cannot prove catalog availability anyway. The suggested per-run model-catalog probe is **not adopted** as machinery: init already reports both observed CLI versions in its diagnostics and dispatch already classifies an unavailable slug, which is proportionate for this envelope. The implementer is directed to raise a floor only on a demonstrated failure at that version.
