# Phase 6 Design Counter-Review

Independent Git checks confirmed the narrow claims behind the proposed attribute rule: in a temporary repository, `.archflow/** -text merge=binary` produced `text: unset` and `merge: binary`; a forced modify/modify conflict left the selected JSON side parseable with zero conflict markers while both porcelain v2 and `git diff --name-only --diff-filter=U -z` still reported the path as unmerged. The live repository does not yet contain the rule, so its current output is `text: auto` / `merge: unspecified`, as expected before implementation. The findings below concern the surrounding contracts and phase fit.

1. **blocker — The phase does not fit the implementation-session budget it cites.** The skill's current calibration is roughly 8–12 delegated chunks plus end-to-phase verification, while this design has 16 chunks, several of which are themselves large multi-file subsystems (notably chunks 10, 12, 13, 14, 15, and 16). The proposed fallback to 14 still exceeds that calibration and does not address integration/rework costs from multiple fresh-context authors. **Suggested resolution:** split Phase 6 at a coherent approved architecture boundary, most naturally repository/Git/path/digest primitives versus durable schemas/semantic validation, rather than merely merging chunk labels; preserve a dedicated integration and aggregate-verification allowance in each resulting phase.

2. **blocker — Most durable chunk seams are prose, not pinned contracts.** `TaskStateV1`, `MaintenanceRecordV1`, all six artifact root shapes, and their exact properties/required fields/refs are not declared. Chunk 15 then accepts generic `PlainJsonObject` values and is expected to correlate fields whose names and shapes chunks 11–14 independently invent. The statement that shared `$defs` are pinned does not pin the root documents that consume them. **Suggested resolution:** add exact interfaces or exhaustive field/ref tables for every root shape, including discriminants and cross-document keys, and pin the semantic validator's typed inputs and correlations before delegating those chunks.

3. **blocker — Chunk 5's “exact inventory” omits live mirrors and runtime validators, so agreement can break even if every listed file is changed.** `trust.ts:157` parses `current_evidence.slots[*].gate_id` with the old `idSchema`; `gate-decision.schema.json:107-112` mirrors the `GateDecisionEnvelopeBase.gate_id` and `task_id`; and `result-expectation.schema.json:35-36` mirrors `mcp-tools.ts:128`'s `task_id` and `intent_id`. None is in the file/test inventory. The same logical gate IDs also occur in `supplemental.ts`/`supplemental-review.schema.json` and authority-link contracts, while `test/unit/trust.test.ts`, `test/unit/supplemental.test.ts`, and gate/supplemental exhaustive fixtures currently accept values such as `Gate:1` and `Task_1`. **Suggested resolution:** inventory every logical task/intent/gate ID across Zod, exported types, all normative JSON Schemas, advertised schema closure, and fixtures; explicitly decide whether the retightening is global for each logical ID; update `trust.ts`, gate-decision, result-expectation, supplemental/authority-link mirrors, and their tests atomically.

4. **major — The new ID brands stop at their parsers and cannot cross the MCP-to-repository seam.** The proposed schemas are declared as `z.ZodType<string>`, while `CommonToolInput`, `ResultIdentityPayload`, `WaiverDecisionBinding`, `GateDecisionEnvelopeBase`, `GateSupersessionRef`, and related fields remain plain `string`. Consequently, a parsed `task_id` cannot be passed to `computeTaskIdentity` or `toRepositoryPathClaim`, and parsed gate/intent IDs cannot be passed to path templates without an undocumented cast or reparse. **Suggested resolution:** pin branded Zod outputs (`z.ZodType<TaskSlug>` / `z.ZodType<PathSafeId>`) and retype every affected public interface, or define one explicit conversion boundary with an owner and compile-time tests.

5. **major — The chunk order does not typecheck as written.** Chunk 3 publishes `computeTaskIdentity(taskId: TaskSlug, ...)`, but `TaskSlug` is not created until chunk 4; the stated hard constraints mention chunk 4 before 5, not chunk 4 before 3. **Suggested resolution:** move `TaskSlug` into an earlier primitive chunk or reorder/depend chunk 3 on chunk 4, and update the advertised landing order.

6. **blocker — The pinned ProjectResult signatures lack the data needed to construct the promised existing errors.** `readIndexEntries(runner, paths)` promises `TASK_INVALID`, which requires `{task_id, issue_code}` but receives no `task_id`. `classifyMutationReadiness(status)` promises `GIT_CONFLICT`, `GIT_DIVERGED`, and `HANDOFF_REQUIRED`, whose live parameters respectively require `operation`, `{expected_digest, observed_digest}`, and `phase_instance`; `WorktreeHistoryStatus` contains none of those. Git spawn mapping has the same gap: `REPOSITORY_NOT_FOUND` requires `repository_candidate_digest`, and `IO_ERROR` requires `{operation, attempt}`, but neither `preflightGit` nor the runner carries those values. **Suggested resolution:** add a pinned boundary/error context to the relevant reader/classifier signatures (or move translation to a layer that owns it) and specify exact code/parameter construction for every failure branch.

7. **blocker — `EvidenceChainEntry` cannot `$ref` the existing evidence-slot definitions as prescribed.** `evidence-slots.schema.json`'s `self`, `counter`, and `gateCounter` objects require `producer_family`, `reviewer_family`, and `independence`, forbid extra properties, and do not contain `authority_link_digest`; the proposed `EvidenceChainEntry` omits those required fields and adds that forbidden field. Ajv/Zod agreement is therefore impossible under the stated reuse. **Suggested resolution:** either make the chain entry include/compose the full slot provenance shape plus its authority-link digest, or introduce one narrower shared correlation definition that both schemas can legally reference.

8. **blocker — Repository-relative path claims are not guaranteed by the Git APIs.** `GitRunner.cwd` may be any caller cwd, while `readIndexEntries` and `checkArchflowAttributes` receive neither `WorktreeLocation` nor a root-bound runner. Reproduction from `repo/sub` showed `git ls-files -s -- .archflow/...` returned nothing and `git check-attr ... -- .archflow/...` returned `text: auto` / `merge: unspecified`; spelling the path as `../.archflow/...` found it but emitted a path that cannot be a `RepositoryPathClaim`. **Suggested resolution:** pin a root-bound runner created after discovery, or pass the worktree root into every repository-path command; use top-anchored literal pathspecs and assert that returned paths exactly equal requested repository claims.

9. **major — The Git parsing contract is neither byte-safe nor literal.** Without `-z`, both `git ls-files -s` and `git check-attr` quote non-ASCII filenames (a reproduced `.archflow/ü space.json` became a C-quoted path), while `check-attr -z` emits NUL triplets rather than “lines.” In addition, the lexical claim schema permits Git pathspec metacharacters such as `*`, `?`, and `[]`, so one claimed path can select multiple files. **Suggested resolution:** pin `ls-files -s -z` and `check-attr -z`/`--stdin -z` parsers with exact cardinality, use `--literal-pathspecs` or `:(top,literal)`, and add Unicode-filename and metacharacter tests. Consider rejecting the remaining Windows-illegal `< > | ? *` characters as part of the claimed portability boundary.

10. **major — Not every path emitted by Git can be branded `RepositoryPathClaim`.** An otherwise valid Git repository may contain conflicted paths with a colon, trailing dot, non-NFC text, reserved device name, newline, or another spelling deliberately rejected by ArchFlow's lexical schema. `git diff --diff-filter=U -z` emits those raw paths, so `conflictedOtherPaths: RepositoryPathClaim[]` either throws while checking unrelated conflicts or requires an unsafe cast. **Suggested resolution:** introduce an untrusted/raw Git path representation (or return valid claims plus an invalid-conflict presence/count) and only mint `RepositoryPathClaim` after validation; include a conflict outside `.archflow/` whose filename is invalid under ArchFlow claims.

11. **major — The two-frame resolver cannot represent all declared path classes.** `resolveTaskPath` accepts a task-rooted `TaskPathClaim`, and `toRepositoryPathClaim(taskId, claim)` necessarily places it below `.archflow/tasks/<task>`, but `PATH_CLASSES` also includes repository-rooted `shared-workflow`, `shared-constitution`, and `repository-source`. No repository-claim resolver or exact class-to-template/parameter table is pinned. **Suggested resolution:** split task-scoped and repository-scoped resolver APIs, restrict each to an explicit class subset, and write the exact template and required identifier inputs for every `PathClass`.

12. **major — The documented `exit 128 => absent` rule is unsafe and under-specified.** Git uses 128 for dubious ownership, corrupt objects/repositories, invalid revision syntax, and other fatal conditions, not only absent refs/objects/config. The interaction of `allowExitCodes`, `absent`, `runText`, and `runNulLines` on nonzero exits is also unspecified, leaving chunks 3, 7, and 8 to invent incompatible behavior. **Suggested resolution:** make expected absence command-specific and caller-declared, classify only the exact expected exit/diagnostic for that command, and pin helper behavior for every nonzero/spawn/timeout/overflow case.

13. **major — The OutputEntry table is structurally total but not integrity-total.** For `raw-payload`, nothing requires `payload_bytes` to equal retained byte length, `payload_digest` to equal SHA-256 of those bytes, or `after.oid` to equal `gitBlobOid(bytes)`; the five listed snapshot-accounting invariants only equate `stored_bytes` with the asserted `payload_bytes`. `path_class` is also unconstrained by path/operation, so an implementation output can claim a shared/task-state class, and rename has no cross-class rule for `previous_path`. **Suggested resolution:** pin the layer that validates payload bytes/digest/blob OID and add rejection fixtures; constrain implementation-output classes and rename transitions, or explicitly define every permitted class/path combination.

14. **major — Input fingerprint canonicalization is not deterministic for logically set-valued collections.** `canonicalJsonBytes` preserves array order, but `artifact_identities`, `upstream_identities`, and `declared_inputs` have no canonical sort key, ordering precondition, or duplicate rule. Independent callers can hash the same logical inputs to different fingerprints. **Suggested resolution:** declare which collections are semantic sequences versus sets; for sets, pin ordinal sort keys and duplicate rejection before hashing, with permutation and duplicate tests.

15. **major — `parseCanonicalDocument` does not pin the byte-authority security contract consumed by later chunks.** The design does not say whether it rejects noncanonical JSON bytes, malformed UTF-8, duplicate keys, dangerous object keys, or whether `digest` covers the original bytes or a re-rendered value. Phase 5's live precedent checks raw bytes against canonical rendering, but parity tests here cover only rendering. **Suggested resolution:** specify fatal UTF-8/JSON/plain-JSON validation, duplicate/dangerous-key policy, byte-for-byte canonical equality, and digest ownership; add malformed, duplicate-key, noncanonical-whitespace/order/newline fixtures.

16. **major — The `SNAPSHOT_LIMIT.offending_paths` exception defeats the new path-frame distinction.** The design intentionally leaves it as `TaskPathClaim`, while `OutputEntry` and `SnapshotAccountingEntry` identify repository-relative declared outputs. A producer reporting those exact offending outputs must cast/reparse across frames. **Suggested resolution:** retype the diagnostic semantically as repository-relative (the wire schema may still share the same lexical authority) and update Zod/schema/tests, or explicitly redefine and prove that accounting paths are task-payload-relative instead.

17. **major — The shared-file ownership plan is not safe for fresh-context delegation.** `SCHEMA_IDS`, `SCHEMA_FILES`, and `src/contracts/index.ts` are edited by many independent chunks at the same object/export-list boundaries; “append-only in numeric order” does not prevent patch conflicts, duplicate exports, or one agent omitting another's row. The document does not enumerate exact per-chunk keys/files/exports, and even lists chunk 1 as editing registries despite not adding a schema ID. **Suggested resolution:** pin every per-chunk registry key, filename, and barrel export, and give one final integration chunk sole ownership of the shared registries/barrel after leaf modules land.

18. **major — REQ-04 and REQ-26 are advanced, not completed.** REQ-04 requires task-start recording and enforcement of immutable identity/base/workflow/constitution/config inputs; this phase defines schemas/digests but explicitly excludes state mutation, while Phase 7 still owns config-pin enforcement and also lists REQ-04. REQ-26 requires every tool to resolve the canonical root and reject scope/identity violations before reads or child dispatch; this phase supplies utilities but wires no production handlers, and later transaction/handler/dispatch/proof phases still own that behavior. **Suggested resolution:** mark both requirements as advanced and state the exact contract/mechanism slice delivered here; reserve completion for the phase that integrates and verifies the behavior through all five tools. The seven requirements already labeled advanced are honest partial contributions.

## Triage

**All 18 findings accepted; none rejected.** Findings 2–18 are verified defects with concrete resolutions. Finding 1 is accepted in principle but its resolution is a scope decision reserved for the human, and because that decision determines where the other 17 fixes land, the design revision is held until it is made.

Spot-verified directly against live code before triage: `evidence-slots.schema.json`'s `self`/`counter`/`gateCounter` do require `producer_family`, `reviewer_family`, and `independence`, are `additionalProperties: false`, and carry no `authority_link_digest` (finding 7 confirmed); `gate-decision.schema.json:107-112`, `result-expectation.schema.json:35-36`, and `trust.ts:157` all mirror task/gate/intent IDs and are absent from the chunk 5 inventory (finding 3 confirmed).
