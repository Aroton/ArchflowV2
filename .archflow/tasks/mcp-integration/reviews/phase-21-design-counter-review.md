# Phase 21 Design Counter-Review

- **Blocker — The purported opt-in suite runs automatically whenever both real CLIs are installed and logged in.** Chunk 1 defines `realHostsAvailable()` only from binary/version/auth availability, while `vitest.config.ts` includes every `test/**/*.test.ts` in ordinary `npm test`. On a developer machine like the one this phase targets, chunks 2–4 and 8 therefore run real-host work—and real model calls in chunk 3—during `npm test`, consuming subscription quota and breaking the promised hermetic/offline default. Proving skip behavior only with both binaries removed from `PATH` does not protect the common case where they are installed. **Suggested resolution:** make the shared guard require an explicit real-host opt-in before probing binaries or auth, pin that opt-in contract in the design, and verify ordinary `npm test` skips with the real CLIs still on `PATH` and the opt-in unset. Keep the benchmark behind its separate explicit opt-in.

- **Blocker — The VAL-02 benchmark can count an unrelated blocker as detection of the seeded defect and omits two required quality observations.** Chunks 5–7 define detection as any `fail` containing any blocking finding. A reviewer can miss the seed, raise an unrelated blocker, and still improve the approved detection rate. The PRD's review-quality metric also requires triage completeness and defects found after pass; neither has an execution or recorded result in the design. The later unstructured human judgement of “substantive rather than nitpick” does not bind each finding to the known seed and cannot repair the computed threshold. **Suggested resolution:** record a human disposition for every run that maps findings to the seeded defect (and classifies clean-control blockers), calculate the approval metric from those dispositions, and add explicit recorded observations for triage completeness and post-pass defect review. Retain raw verdict/blocker rates only as secondary telemetry.

- **Blocker — Chunk 8 assigns normal initialization failures to a server boundary that cannot produce them.** `archflow-mcp` can consume a staged initialization artifact through `runStateInitialization`, but repository scaffolding and artifact staging exist only as `archflow-local init` and `archflow-local task-init` (`src/local/commands.ts`). Missing and uncommitted policy-base failures occur inside `stageTaskInitialization`, before any MCP call. The statement that everything except snapshot/manual work is a server transaction therefore makes the clean/missing/uncommitted/mismatched-base scenarios either bypass the installed launchers or assert at the wrong boundary. **Suggested resolution:** pin the installed sequence and ownership: `archflow-local init` scaffolds, the test commits policy where appropriate, `archflow-local task-init` stages and owns its staging failures, and `archflow-mcp` owns successful revision-1 adoption plus artifact/commit mismatch failures.

- **Blocker — The planned “secret-bearing checkpoint rejection before Git projection” has no matching production path.** `archflow-local checkpoint` validates chain extension and writes the canonical checkpoint; it does not invoke a secret scanner, and MCP adoption of a `manual-checkpoint-import` likewise has no Git projection to scan. Secret rejection before projection exists for implementation/result projection paths, not for checkpoint bytes. Implementing the test literally either cannot reach `SECRET_DETECTED` or forces an unplanned feature into a validation-only phase. **Suggested resolution:** exercise a secret-bearing implementation output through installed `archflow-mcp` and assert rejection before projection/state advancement, or name the exact existing manual-workflow result-preparation path if that is the intended subject. Do not add checkpoint scanning merely to satisfy the mislabeled scenario.

- **Major — The shared helper and workspace override seams remain under-specified for independently implemented chunks.** The design pins only `realHostsAvailable(): boolean`; it does not pin the timeout export names/values, the real-host and benchmark opt-in helpers, or the config override field and type. “Optional config-source” also does not say whether the value is bytes, text, or a path, nor pin its application point after scaffold creation and before the policy-base commit. Chunk 6 needs both producer orientations but is not declared as a consumer of that override. **Suggested resolution:** specify the complete `test/helpers/real-host.ts` export surface and exact opt-in semantics; add an exact `TaskWorkspaceOptions` field/type with whole-byte replacement semantics at the scaffold-before-commit point; and explicitly make chunks 3 and 6 consume it.

- **Major — One scratch `HOME` cannot serve both safe installation and authenticated installed-server dispatch.** Overriding the installer's child `HOME` genuinely redirects `~/.claude/skills` and `~/.agents/skills`, so that part protects the developer's installation. But `src/dispatch/workspace.ts` also resolves the selected CLI credential file from the server process's `HOME`; launching the installed `archflow-mcp` under the empty scratch home makes real counter-review/adjudication return `AUTH_UNAVAILABLE`. Chunk 8's multi-phase server-attested evidence can therefore fail despite valid real logins. **Suggested resolution:** separate environments explicitly: run installation and unauthenticated local setup under scratch `HOME`, then invoke the absolute scratch-installed launcher (or scratch `PATH`) with the developer `HOME` only for calls that require selected-CLI authentication, while keeping `ARCHFLOW_HOME`, `ARCHFLOW_BIN`, and the repository scratch-scoped. Never run the installer with the developer home or copy credentials into the scratch home. If chunk 8 intentionally performs no dispatch, state that and assign its server-attested evidence to chunk 3 or 6.

- **Major — The design claims a VAL-17 migration journey pass without assigning the required migration evidence.** Chunk 8 covers only `archflow-local upgrade` staging followed by server initialization, and chunk 9 enumerates only two VAL-01 journeys plus the VAL-12 manual journey. No Phase 21 execution records normal-versus-manual upgrade equivalence, interruption/rerun non-duplication, completion of the current-digest pipeline and migration decisions, or the unchanged legacy source required by VAL-17. Earlier Phase 19 tests may prove component invariants, but they do not become the claimed real installed-launcher journey merely by being cited in the coverage report. **Suggested resolution:** add explicit installed-launcher normal and manual upgrade/recovery slices with interruption/rerun and source/destination assertions, or mark VAL-17 as prior fake/in-process coverage rather than a Phase 21 journey pass and adjust the success criteria accordingly.

## Triage

All seven findings accepted. Two were verified against source before triage.

- **Blocker 1 (availability-only guard runs real-host work during `npm test`) — accepted.** Correct and the most consequential finding: on this machine both CLIs are installed and logged in, so the guard as designed would have spent subscription quota on every plain `npm test`, and the stated verification (CLIs off `PATH`) deliberately exercised the case that could not fail. Chunk 1 now requires an explicit opt-in environment variable *before* any binary or auth probe, adds `realHostsEnabled()` and `benchmarkEnabled()` to the pinned export surface, and makes the chunk-1 exit condition two runs — one with the opt-in unset and both CLIs still on `PATH`, watching for model calls rather than a green result. Success criteria and verification steps updated to match.

- **Blocker 2 (detection proxy counts unrelated blockers; triage completeness and post-pass defects missing) — accepted.** The proxy was wrong in the direction that inflates the approved rate: a reviewer that misses the seed and raises an unrelated blocker would have improved it. Chunks 5–7 now compute the approval metric from a recorded human disposition per run against the manifest's per-case seeded-defect description, with a pinned disposition vocabulary; raw verdict and blocking-count rates are demoted to secondary telemetry. Chunk 6 adds triage completeness and defects-found-after-pass as explicit recorded observations, both required by the PRD's review-quality requirement. This adds a recorded field and a human step, not machinery.

- **Blocker 3 (initialization failures assigned to a boundary that cannot produce them) — accepted.** Missing and uncommitted policy-base failures occur inside `stageTaskInitialization`, before any MCP call. Chunk 8 now pins the installed sequence and ownership explicitly: `archflow-local init` scaffolds, the test commits the policy base, `archflow-local task-init` stages and owns its staging failures, and `archflow-mcp` owns revision-1 adoption plus artifact and commit-mismatch failures. The blanket "everything else is a server transaction" claim is gone.

- **Blocker 4 (secret-bearing checkpoint has no production path) — accepted, verified.** `grep SECRET_DETECTED src/` constructs it only in `src/state/snapshots.ts:583,587` (projection preparation) and `src/init/legacy-upgrade.ts:263` (legacy staging); no checkpoint path scans. Chunk 8 now names the subject as a secret-bearing **implementation output** rejected before projection and state advancement, records that the architecture's "checkpoint" wording maps to the projection path, and explicitly forbids adding checkpoint scanning to satisfy the literal phrase.

- **Major 5 (seams under-specified for independent chunks) — accepted.** Chunk 1 was rewritten as "Real-host gate and shared seams" and now pins the `real-host.ts` export surface including the two opt-in helpers and the named timeout constants, and specifies the `TaskWorkspaceOptions` addition as **whole-byte replacement** config content applied after `scaffoldRepositoryAssets` and before the policy-base commit, so the committed base and pinned digest agree. Chunks 3 and 6 are both declared consumers.

- **Major 6 (one scratch `HOME` cannot serve both safe install and authenticated dispatch) — accepted, verified.** `src/dispatch/workspace.ts:65` resolves the credential source from `process.env.HOME`, so a scratch-home server returns `AUTH_UNAVAILABLE`. Resolved by the simpler of the two suggested branches: chunk 8 now performs **no dispatch at all** and runs entirely under scratch `HOME`; all server-attested dispatch evidence is assigned to chunks 3 and 6 under the developer home. A two-home split would have added coordination for no coverage the other chunks do not already provide.

- **Major 7 (VAL-17 claimed without assigned migration evidence) — accepted.** Chunk 8 now carries explicit installed-launcher normal and manual upgrade slices with interruption/rerun non-duplication and a byte-identical legacy source, and states that Phase 19's in-process tests do not become an installed-launcher journey by being cited. If any part goes unexecuted, the coverage report marks VAL-17 partial with the reason.

No finding was rejected. No requirement, architecture phase boundary, or success criterion was changed by this triage; the revisions correct mechanism, boundary ownership, and measurement definition within the existing scope.
