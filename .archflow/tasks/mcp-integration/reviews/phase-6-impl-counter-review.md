# Phase 6 Implementation Counter-Review

1. **blocker — The digest functions inspect live caller-owned objects more than once, so excluded fields can be smuggled into a request digest and one fingerprint subject can hash differently across calls.** `computeRequestDigest` walks `operation_fields` through `Object.entries` in `src/contracts/fingerprints.ts:135-146`, then canonical hashing traverses the original object again at `:155-165`. Neither traversal first validates and materializes a stable plain-JSON snapshot. An enumerable getter can therefore return a safe object to the exclusion walk and `{ intent_id: "excluded-but-hashed" }` to canonicalization; the function returns a digest instead of throwing. `computeInputFingerprint` has the same split observation: `sortedSet` reads each key at `:95-103`, then `identityJson`/`declaredInputJson` reads the entries again at `:105-132`. A reproduced getter-backed identity made the exact same subject object return two different fingerprints on consecutive calls. This violates both the asserted-exclusion security property and the byte-stable set contract. **Suggested resolution:** validate and materialize one accessor-free, plain-data snapshot of the complete subject before checking or hashing, then perform exclusion checks, duplicate checks, sorting, and canonicalization only over that snapshot. Add regression tests for a getter that changes between traversals and repeated hashing of the same subject.

2. **major — The supposedly path-safe ID schemas accept values that the path-claim authority rejects, so valid boundary inputs cannot be used by the repository templates.** `pathSafeIdV1Schema` and `taskSlugV1Schema` in `src/contracts/evidence.ts:33-34` permit reserved Windows device names and trailing dots, while `src/contracts/path-claims.ts:23-27,40-43` rejects those values as path components. Reproductions: `parseTaskSlug("con")` and `parseTaskSlug("task.")` succeed, but `toRepositoryPathClaim(..., "config.yaml")` throws; `parsePathSafeId("CON")` and `parsePathSafeId("gate.")` succeed, but the corresponding `decisions/<gate-id>/request.json` task claims throw. The global retightening therefore still allows MCP `task_id`/gate IDs that fail only at deep repository composition, recreating the mismatch `PathSafeId` was introduced to prevent and violating the criterion that every class template is producible. **Suggested resolution:** make `TaskSlug` and `PathSafeId` enforce every single-component restriction required by the templates (at least reserved-device and trailing-dot/space rejection), update their JSON Schema mirrors and global fixtures atomically, and add composition tests for every ID-bearing template.

3. **major — The request-digest denylist cannot enforce the category-wide exclusion contract it documents.** `src/contracts/fingerprints.ts:47-79` claims timestamps, attempt counters, timeout/cancellation state, and retry metadata are excluded, but `operation_fields` is an open `PlainJsonObject` and the exact-name list omits ordinary spellings such as `started_at`, `finished_at`, `attempt_number`, `retry_reason`, and `timed_out`. Those fields pass `assertNoExcludedFields` and change the digest, so two operation callers can encode the same volatile state under different names and disagree. **Suggested resolution:** replace the open-ended denylist boundary with operation-specific closed semantic-field schemas/constructors, or define and test an explicit complete naming policy; only approved semantic fields should reach canonical hashing.

4. **minor — Correct implementation choices silently diverge from the still-pinned path and Git command contracts.** The added `rel !== ".."` guard at `src/repository/paths.ts:369-370` is necessary because `"..".startsWith("../")` is false, but the exact seven-step sequence in the phase design at line 421 still omits it. Likewise, `src/repository/index-entries.ts:88-93` correctly explains that global `--literal-pathspecs` disables the `:(top,literal)` magic it uses, and `src/repository/attributes.ts:78-80` correctly notes that `check-attr` takes pathnames rather than pathspecs; nevertheless, the design and success criteria at lines 352, 639, and 674 still require both mechanisms together. The code is safe here, but the plan no longer reflects reality. **Suggested resolution:** update the phase design to include the exact-parent containment guard and to pin `:(top,literal)` for `ls-files` while using root-bound literal pathname arguments for `check-attr`; remove the contradictory `--literal-pathspecs` requirement. No code change is needed for these points.

5. **minor — The global ID sweep appears complete in code, but the required inventory delta was absorbed without a durable reconciliation.** The mechanical sweep found no remaining target ID using a plain string, `safeId`, or the wrong JSON Schema ref. However, the diff correctly retightens additional review, adjudication, and triage Zod/types and normative schemas that are absent from the design's known-site list and Files row: `src/contracts/review.ts`, `src/contracts/adjudication.ts`, `src/contracts/triage.ts`, and their review/adjudication/triage/evidence JSON Schemas. The phase design at lines 165, 654, and 668 explicitly requires every inventory difference to be reported rather than silently absorbed, but its only current edit is the status transition. **Suggested resolution:** record the discovered inventory delta in the phase design or implementation log, update the Files table to match actual scope, and add negative agreement coverage for the newly discovered mirrors before passing the gate.

Targeted verification remained green: `npm run typecheck`, 148 focused Vitest tests across fingerprints, repository paths/index readers, primitive agreement, gate/error agreement, and MCP contract agreement, plus `git diff --check`.

## Triage

**Four findings accepted, one accepted in part.** Findings 1, 2, 4, and 5 are confirmed defects. Finding 3 identifies a real limit but its proposed resolution belongs to a later phase; the limitation is documented instead.

Findings 1 and 2 were reproduced independently before triage rather than taken on the reviewer's word:

- **Finding 1 confirmed, with one correction.** The `operation_fields` smuggling reproduces exactly: the getter is observed twice, `intent_id` reaches the hash, and `computeRequestDigest` returns a digest instead of throwing. The review's *second* claim — that a getter-backed identity makes the same subject "return two different fingerprints on consecutive calls" — did **not** reproduce; an alternating getter yields equal digests, because both calls observe the same parity. The underlying split-observation defect is real and identical in kind (the value checked is not the value hashed), so the finding stands and the fix is unchanged, but the specific consecutive-call repro is fragile and should not be cited as evidence.
- **Finding 1's suggested resolution was larger than necessary.** `assertPlainJson` **already** rejects accessor properties anywhere in a subject (`accessor properties are not JSON values at value.x`). No new snapshot subsystem was needed — validate with the existing helper, then `structuredClone`.
- **Finding 2 confirmed**, with one over-statement: `parseTaskSlug` accepts `con`, `task.`, `nul`, `com1` and `parsePathSafeId` accepts `CON`, `gate.`, `PRN.txt`, all rejected at composition. But `aux ` (trailing space) was **already** rejected — neither charset admits a space — so the trailing-space half of the finding was moot.
