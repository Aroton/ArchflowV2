# Phase 5 Implementation Counter-Review

Focused verification (`release:check`, the release contract tests, and the release offline integration tests) passes, but the implementation still has the following substantive gaps.

1. **blocker — The accepted `fast-uri` risk decision is backed only by unresolvable digest strings.** `release/legal-review.json` contains `advisory_snapshot_digest` and `reachability_evidence_digest`, but those digests occur nowhere except the source/payload copies of that receipt. The schema only checks that they look like SHA-256 values (`src/contracts/schemas/v1/release-legal-review.schema.json:127-163`), and `validateLegalCorrelation` never resolves or hashes canonical advisory-snapshot or reachability records (`scripts/release-support.mjs:516-539`). Consequently arbitrary 64-hex values can satisfy the release gate, and the tracked payload has no durable evidence for the separate prototype-risk acceptance required before implementation. **Suggested resolution:** add closed canonical advisory-snapshot, patched-artifact-availability, focused reachability, and explicit acceptance records as repository controls; reference them by path and digest from the decision; resolve and hash them in the sole semantic validator; and mutation-test missing, stale, and substituted evidence.

2. **major — Manifest input records are not required to identify the physical metafile input they claim to describe.** Validation reads each `bundle_input` from its `origin`, but never requires a repository record's `key` to equal `origin.path` or a dependency record's `key` to equal `node_modules/<package>/<package_relative_path>` (`scripts/release-support.mjs:567-575`). Metafile correlation checks key membership and `bytesInOutput`, but not `metafile.inputs[key].bytes === bundle_input.size` (`scripts/release-support.mjs:620-629`). A canonical manifest can therefore bind metafile key A to the digest of physical file B and can forge scanned-input sizes while passing `release:check`. **Suggested resolution:** enforce exact key/origin algebra and metafile input-byte equality, then add aliasing and size mutations to both semantic and integration tests.

3. **major — Dependency provenance and legal component closure are not derived as exact closed sets.** `verifyDependencyRecords` verifies only records the manifest elects to list (`scripts/release-support.mjs:431-450`), while legal correlation requires the six hard-coded embedded components but never derives the exact installed-component set from dependency-origin contributors, rejects extra ungrounded components, or requires every component to have applicable retained legal evidence (`scripts/release-support.mjs:485-514`). Embedded license files are bound only as repository bytes; they are not tied to an immutable upstream tarball/commit/package manifest for the embedded name and version. A regenerated receipt can omit installed `zod`/SDK components, add invented components, or substitute supposedly applicable embedded license text after rebinding its digest. **Suggested resolution:** derive the exact installed and mapped component sets from bundle/provenance evidence, require one closed component-to-license/provenance mapping with no omissions or extras, and bind embedded legal sources to immutable upstream package identity and exact bytes.

4. **major — Adjacent source-map discovery fails open.** For a contributing dependency `.mjs`, `collectDependencyProvenance` silently continues when the adjacent map is missing, and it records no per-prebundle expected/present/expected-absent state (`scripts/release-support.mjs:309-348`). It also ignores every source path that does not match one specific pnpm-layout regex, so a newly shaped third-party mapped root is not necessarily rejected. The current contributing `chunk-Br0eD_fh.mjs` has no adjacent map and leaves no evidence explaining why absence is expected. **Suggested resolution:** bind an explicit adjacent-map expectation for every contributing prebundle, classify every map source as reviewed first-party or recognized third-party regardless of package-manager layout, fail unknown shapes and missing expected maps, and mutation-test deletion, unexpected addition, and alternate-root syntax.

5. **major — The supposedly exact hostile launch profile is largely unchecked.** The release validator constructs raw Ajv with `strict: false`, so the project's `x-archflow-sorted-unique`/`x-archflow-unique-by` annotations are ignored there (`scripts/release-support.mjs:392-405`). Semantic validation pins only `allowed_imports`; it does not derive or compare `argv`, environment/removal sets, guard identity, canary identities, or fixture paths/digests (`scripts/release-support.mjs:640-643`). Schema-valid changes, duplicates, stale fixture digests, or a substituted guard path therefore pass `release:check`, while `reproductionProof` merely hashes whatever profile the manifest supplied. **Suggested resolution:** compile with the established custom-keyword validator and compare the entire launch profile against exact derived constants and current proof-input digests; add mutations for every launch field and ordering/uniqueness rule.

6. **major — Computed dynamic built-in loading bypasses the five-builtin policy.** The builder rejects only literal `import("node:...")`/`require("node:...")` forms with one regex (`scripts/release-support.mjs:770-775`), and payload validation checks only static metafile imports (`scripts/release-support.mjs:620-631`). Computed `require(specifier)`, `require("node:" + name)`, `import(specifier)`, `process.getBuiltinModule(...)`, and equivalent `createRequire` aliases can produce no metafile import and evade the regex, allowing undeclared `node:net`, `node:child_process`, or other built-ins through both build and independent reproduction. **Suggested resolution:** use a parser or an explicit emitted-code loader policy that rejects all residual runtime loaders except the fixed banner, and add mutations/probe sources for computed `require`, computed `import`, `getBuiltinModule`, and loader aliases.

7. **major — Exact legal source/output mapping and the generated notice are not semantically verified.** Legal correlation verifies each retained repository source against the digest in the receipt, while artifact validation independently verifies payload files against manifest digests; it never requires `dist/legal/upstream/**` bytes to equal the corresponding `release/legal/upstream/**` bytes (`scripts/release-support.mjs:500-514,602-648`). It likewise never regenerates and compares `legal/THIRD_PARTY_NOTICES.md`. A payload can contain altered license or notice bytes with correspondingly updated artifact records and still pass the read-only checker. **Suggested resolution:** byte-compare every source/output legal pair, recompute the sole notice projection from the canonical receipt, enforce its exact bytes/digest, and add payload-only license/notice substitution mutations.

8. **major — The independent `npm ci` reproduction and tracked-writer paths are absent from aggregate and CI verification.** The integration test's “independent roots” are two builds from the same checkout and existing `node_modules` (`test/integration/release-offline.test.ts:56-67`). `check:release` never calls `reproduceReleasePayload` or the writer (`package.json:22`), and CI likewise stages once from the already-installed checkout and performs only a read-only comparison (`.github/workflows/ci.yml:35-39`). Regressions in materialization, fresh install, post-install provenance checks, promotion, or rollback can therefore ship while every required check stays green. **Suggested resolution:** expose a non-promoting reproduction command that exercises materialization plus fresh `npm ci`, run it in `check:release` and both CI matrix jobs, and test tracked replacement/failure recovery against a disposable repository copy.

9. **major — Reproduction roots can overlap and mutate the validated candidate.** `reproduceReleasePayload` checks the comparison root only against the materialization root (`scripts/release-support.mjs:901-906`); `buildReleasePayload` then checks it only against the materialized repository. A `comparisonRoot` nested below `stage.stageRoot` succeeds, creates a new directory inside the already-validated candidate, and can still return a reproduction proof based on the stale candidate summary. **Suggested resolution:** canonicalize all repository, candidate, materialization, and comparison roots before work starts; reject equality or ancestor/descendant overlap across every pair; re-walk the candidate before proof issuance; and add the nested-comparison regression.

10. **major — HEAD carry-forward checks do not preserve the complete legal audit history.** If both HEAD review files are absent, `verifyHeadLegalBaseline` returns without checking for any prior `release/legal/upstream/**` or `dist/legal/**` artifacts; when reviews exist, it checks only release-to-dist upstream counterparts and ignores orphan dist files (`scripts/release-support.mjs:928-946`). It retains prior decisions byte-for-byte but does not retain prior amendments or supersessions, so the append-only correction trail can be deleted or rewritten. **Suggested resolution:** enumerate both HEAD legal namespaces first and require either complete absence or bidirectionally identical closure; carry forward decisions, amendments, and supersessions byte-identically; reject self/cyclic/conflicting supersessions; and seed tests for every one-sided/orphan/history-mutation case.

11. **major — The hostile-copy proof does not exercise the protocol fixtures it claims to bind, and its module canary is not on a real lookup path.** The manifest binds `initialize.json`, `calls.json`, and `adversarial-bytes.json`, but the release smoke reads and sends only initialization (`scripts/smoke-release-bundle.mjs:138-159`). The module canary is created under `<tmp>/module-canary/node_modules`, which is not an ancestor search path of child cwd `<tmp>/payload`; its negative control is intercepted unconditionally by the preload before Node attempts ordinary resolution (`scripts/smoke-release-bundle.mjs:112-119,133-164`; `test/fixtures/release/hostile-runtime-guard.cjs:71-76`). Thus the tracked bundle never proves call/adversarial framing or meaningful ambient module isolation. **Suggested resolution:** drive the complete byte-exact fixture sequence through both copied-payload modes, place a canary where it demonstrably resolves under the hostile ambient setup, then prove the declared scrubbed launch makes it unavailable while the guard observes rather than preempts resolution.

12. **major — Replacement of an existing `dist/` is not crash-preserving.** The writer first renames `dist` to a random backup and then renames the promotion into place (`scripts/release-support.mjs:1005-1009`). Its catch block restores ordinary JavaScript failures, but termination or power loss between the renames leaves the fixed `dist/` absent and the prior payload stranded under an undiscoverable random name; no startup recovery or fault-injection test exists. **Suggested resolution:** use a supported atomic exchange/indirection, or add a durable transaction marker and deterministic recovery before any subsequent release operation; fault-inject between each filesystem step and prove the old payload remains available or recovery is automatic.

13. **minor — The build can consult unbound ambient TypeScript configuration.** `tsconfig.json` is absent from `REQUIRED_CONTROLS` and the materialization allowlist, while esbuild is invoked without `tsconfigRaw` or another explicit mechanism disabling tsconfig discovery (`scripts/release-support.mjs:80-102,705-717,746-765`). Ordinary staging may therefore consult repository configuration that the fresh reproduction root does not contain, contradicting the claimed closed reproduction-input set even if today's settings happen not to change emitted bytes. **Suggested resolution:** either digest and materialize `tsconfig.json` as a release control or pass a complete explicit `tsconfigRaw` profile that prevents ambient discovery, with a mutation proving repository tsconfig drift cannot silently affect the release.

## Triage

1. **Accepted and fixed.** Added four closed canonical controls under `release/evidence/` for the live advisory snapshot, patched-artifact availability, focused inert reachability, and the user's explicit local-only risk acceptance. The legal decision now binds each by path and digest, and semantic validation resolves, hashes, correlates, and mutation-tests them.
2. **Accepted and fixed.** Bundle records now require exact key/origin identity and exact agreement with `metafile.inputs[key].bytes`. Alias and forged-size mutations are rejected.
3. **Accepted and fixed.** Semantic validation derives the exact installed and mapped component closure, rejects missing/extra components, and requires one component-to-provenance/legal-source mapping. Embedded components bind official npm tarball URLs/integrities and exact retained license bytes.
4. **Accepted and fixed.** Every contributing dependency prebundle now has a derived `present` or `expected-absent` adjacent-map record. Map sources are classified into reviewed first-party roots or recognized third-party components; unknown layouts, stale maps, missing expected maps, and expectation drift fail closed.
5. **Accepted and fixed.** Release validation now enforces the custom sorted/unique keywords and compares the complete launch profile with values derived from current fixtures, guard, canaries, environment policy, argv, stdio, and import policy. Launch-profile mutations are rejected.
6. **Accepted and fixed.** A TypeScript 7 token-policy pass examines emitted executable tokens, rejects computed/dynamic `require`, `import()`, `process.getBuiltinModule`, and extra `createRequire` paths, and distinguishes inert strings/comments. Direct, alias, and nested-template probes cover the bypasses.
7. **Accepted and fixed.** Every retained legal source is byte-compared with its payload counterpart, and `THIRD_PARTY_NOTICES.md` is regenerated from the canonical receipt and compared byte-for-byte. Payload-only legal and notice substitutions are rejected.
8. **Accepted and fixed.** Added the non-promoting `release:reproduce` command, which materializes the closed source set, runs fresh `npm ci`, revalidates provenance, rebuilds, and compares the 14-file payload. It is part of `check:release` and both CI matrix jobs; disposable transaction-recovery probes cover replacement recovery.
9. **Accepted and fixed.** Repository, candidate, materialization, and comparison roots are canonicalized and checked pairwise for equality or ancestor/descendant overlap before work. Candidate closure is revalidated before proof issuance, and the nested-comparison regression is rejected.
10. **Accepted and fixed.** HEAD checking now enumerates both legal namespaces bidirectionally, requires complete absence or identical closure, preserves decisions/amendments/supersessions byte-identically, validates their reference graph, and rejects orphan or conflicting history.
11. **Accepted and fixed.** Hostile smoke now drives initialization, every call, and all adversarial-byte fixtures in exact and guarded modes with byte-equal transcripts. A real `NODE_PATH` control proves the canary resolves before the hostile environment removes that path; the guard observes native resolution failure without preempting it.
12. **Accepted and fixed.** Tracked replacement now uses deterministic promotion/backup paths plus a canonical durable transaction marker. Every release operation recovers interrupted pre-install or installed states before proceeding; fault probes cover both recovery branches.
13. **Accepted and fixed.** The esbuild profile supplies complete explicit `tsconfigRaw`, preventing ambient `tsconfig.json` discovery from affecting the release.
