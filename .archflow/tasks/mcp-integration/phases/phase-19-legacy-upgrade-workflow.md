# Phase 19: Legacy Upgrade Workflow

**Status**: DESIGNED
**Task**: mcp-integration
**Goal**: Migrate selected legacy material into a distinct canonical task without changing or implicitly approving the source.
**Requirements**: REQ-02, REQ-04, REQ-09, REQ-13, REQ-15, REQ-16, REQ-17, REQ-18, REQ-19, REQ-20, REQ-21, REQ-22, REQ-23, REQ-24, REQ-25, REQ-26, REQ-38, REQ-39, REQ-40, REQ-41, REQ-50

## Context

The durable half of this phase already shipped. `legacy-import-initialization` has a JSON Schema, a TS/Zod mirror in `src/contracts/durable-legacy-import.ts`, a registry entry, an `archflow_state.artifact` union membership, and a fifteen-field strict shape whose `mapping[].disposition` cannot express `"approved"`. The no-state to initialized transition, the intent receipt, the CAS revision-0 to 1 write, live `config_digest` verification, commit resolution, and every replay and changed-input rejection are built and tested in `src/state/initialization.ts` and `src/mcp/handlers/state.ts`. The `import` path class exists end to end and is already in the projection allowlist. The `migration-audit` gate kind is fully wired through `src/contracts/gates.ts` and `src/state/gates.ts` with its context, its decision set, and its `advance` effect. The pure-manual route already parses either initialization kind in `src/local/manual-workflow.ts` and builds an `initial` import call. Phase 19 uses all of that as-is.

What is missing is everything upstream of the manifest. Nothing stages legacy bytes, nothing computes `import_digest` or `source_identity_digest`, nothing derives `mapping` or `staged_payload_refs`, nothing writes the `imports/<import-digest>/manifest.json` the architecture layout requires, and no resolver can read a legacy source under `.archflow/tasks/<legacy>/` because `REPOSITORY_CLASS_RULES` admits only `.archflow/workflow.yaml` and `.archflow/constitution/<name>.md`. `workflow_digest` and `constitution_digest` are never live-verified, so an explicit policy base means nothing unless the stager resolves both from that commit's tree — `fingerprint-readers.ts` reads them from `policy_base_commit`, so a HEAD-derived digest would fail the initialization fingerprint check. `mapping[].destination_path` is validated by nothing, and the shipped contract fixture proves it by mapping to `architecture.md`, which matches no task class rule. There is no `archflow-upgrade` skill.

Two facts about the state machine set this phase's shape, both established by review against the real code. First, a task cannot produce at a phase whose upstream documents lack retained produce results and bound `artifact-approval` approvals: `expectedProduceUpstreamBindings` names `prd.md` and `design.md` as the upstreams of every `phase-design-<n>`, `loadProduceUpstreamSubject` fails `current-upstream-produce-result-missing` without them, and `requireApprovedUpstreamDigests` throws without their approvals. Revision 1 starts with both sets empty, so a destination initialized directly at a late cursor deadlocks. Second, `nextPhase` is a strict `+1` successor and `legalMovement` admits no skip, while leaving `phase-impl-<n>` demands an authenticated commit authorization and a live committed-tree proof — so walking a legacy task's already-implemented phases is structurally impossible.

The user's settled resolution is therefore: the destination initializes at `prd` and walks `prd` and `design` for real, using the imported documents as produce artifacts and obtaining genuine human approvals, which is exactly what REQ-50 asks and which creates the upstream results, the approvals, and `planned_final_phase` that later production requires. An accepted `migration-audit` gate then authorizes one guarded jump to the resume phase design. The user also settled that this phase ships and proves the path against a fixture copied from this repository's legacy layout, and does not migrate `.archflow/tasks/mcp-integration/`, which will be finished under the legacy system.

## What We're Building

One offline staging orchestrator behind a new stdin-bearing `archflow-local upgrade` command, plus one `archflow-upgrade` skill and one guarded transition clause. The orchestrator walks an explicitly named legacy source root through a single narrow source-frame resolver, content-addresses every file it finds, copies the bytes unchanged into the destination task's `imports/<import-digest>/`, persists the canonical initialization manifest at that same path, derives the legacy-to-canonical mapping by layout convention, resolves the constitution and workflow digests from an explicitly selected policy-base commit's tree rather than HEAD, binds the import and code baselines separately, and emits the manifest and the migration-audit gate context on stdout. Apart from creating the destination task root and its `config.yaml`, it writes only under `imports/<import-digest>/` and never touches state, so an interrupted staging leaves inert unreferenced bytes and an exact rerun is idempotent. The skill hands the manifest to `archflow_state` with `expected_revision: 0`; the transition, receipt, and replay semantics are the existing server code.

The destination then runs `prd` and `design` through their current pipelines. At each produce step the skill seeds the canonical document from the staged `draft` payload and builds the ordinary document artifact from those bytes — `buildDocumentArtifact` reads whatever sits at the canonical path and requires no provenance, and the projection scores `exact` rather than `collision` because it derives from the same bytes. Nothing legacy is approval evidence; the human approves the current digests through the ordinary mandatory gates, and the design approval sets `planned_final_phase`. Only then may `migration-audit` open at `design`: a new precondition beside the two `openDurableGate` already has requires its subject to equal the current `design` produce subject, requires an `artifact-approval` bound to that subject, and requires `planned_final_phase` to be set and to cover the derived resume phase — so an accepted triage finding cannot leave a stale audit behind, and an imported design that declares too few phases or carries the open-ended marker must be revised by the human before the audit can open rather than stranding the task short of terminal completion.

Accepting the audit records an ordinary `advance` approval and leaves the cursor at `design`; the jump itself happens on the next `archflow_state` produce call, where one new clause in `legalMovement` admits a `phase-design-<n>/produce/running` target at attempt 1. `legalMovement` is a pure synchronous predicate and `TransitionPlanInput` carries no filesystem authority, so the handler resolves that authority first — selecting the `imports/*/manifest.json` whose canonical digest equals `state.initialization_digest`, which is what makes a wrong or tampered manifest unusable, deriving the resume phase from its mapping, and passing it in as a plain-JSON field beside the existing `commit_observed`. The clause additionally requires an authenticated `migration-audit` approval through `assertAuthenticatedGateApproval`, the same unforgeable WeakSet membership that already guards the `phase-impl` exit and which survives because `planStateTransition` deliberately passes approvals un-cloned. The resume phase is derived, not declared: one past the highest `phase-impl-<n>` in the mapping, so a legacy task implemented through phase 18 resumes at `phase-design-19` and one that never implemented resumes at `phase-design-1`, where the target equals the natural successor and the ordinary clause already covers it. `exclude` is the lever for a human who wants to redo the last implemented phase.

Legacy phases before the resume point are never represented as completed state — state has no such concept — but as historical imported material audited once. No migration phase instance, gate kind, MCP tool, error code, runtime dependency, durable schema field, or workflow-graph change is added. V1 requires the legacy source and the destination to live in the same repository, because `validateLiveInitialization` resolves all three commit baselines through the destination runner and a foreign import baseline would be absent from its object database; the stager rejects a cross-repository source rather than pretending otherwise.

## Work Breakdown

1. **Resolve one narrow source frame**: Add `resolveLegacySourcePath(options: { readonly sourceRoot: string; readonly claim: RepositoryPathClaim; readonly context: RepositoryOperationContext }): Promise<ProjectResult<ResolvedSourcePath>>` to `src/repository/paths.ts`, where `ResolvedSourcePath = Readonly<{ sourceRelative: RepositoryPathClaim; absolute: ResolvedTaskPath }>`. It reuses the existing `containedUnder` sequence verbatim against the passed source root and carries no `path_class`, because the source frame is deliberately unclassified read-only material and must never gain a third class-rule table. It therefore fails only with `PATH_ESCAPE` or `IO_ERROR`. The resolver never writes and is the only way the upgrade path may read outside the destination frame.

2. **Preflight and establish the destination before any write**: In `src/init/legacy-upgrade.ts`, reject a `source_root` that contains or is contained by the destination task root — otherwise the walk ingests its own output and mutates the source — and reject a source outside the destination repository. Reject a destination that already has `state.json` or any canonical document artifact, so a mistyped existing task ID stops instead of overwriting. Then create and validate the destination task root and `config.yaml` through the existing task-initialization config helper, because that root must exist before staging: `ensureRealDirectory` calls non-recursive `mkdir`, so `ensureTaskProjectionParent` fails `ENOENT` when `authority.task_root` is absent. Only then mint the staging authority through `discoverWorktree`, `preflightGit`, and `createInternalTransactionAuthority`. Config creation is EEXIST-tolerant, so an exact rerun re-reads rather than failing.

3. **Stage the source and derive the mapping in one ordered pass**: Walk the source root, resolve every regular file through the source resolver, skip and report non-regular entries, run the existing secretlint scanner over each candidate before any write, hash each with `sha256Bytes` for `staged_payload_refs` (zero-byte payloads are legal), derive `mapping` from the same file list, then compute `import_digest` as the canonical digest over the sorted staged refs and mapping, then materialize `imports/<import-digest>/` and copy. That order matters: `import_digest` covers the mapping, so the staging directory cannot be created until the mapping exists. Neither `LegacyMappingEntry` nor `StagedPayloadRef` carries `import_digest`, so the digest is well defined and not cyclic. Writes go through `createProjectionWriter().replaceRegular` with parents materialized by the shipped `ensureTaskProjectionParent`, and each target is resolved with `resolveTaskPath({ expectedClass: "import" })` — `import` is already in `PROJECTABLE` while `createExclusive` rejects it, and content addressing makes exclusive-versus-replace moot because an identical digest implies identical bytes. Persist the completed initialization manifest at `imports/<import-digest>/manifest.json`; the architecture layout requires it and chunk 6 authenticates against it. Staging writes nothing outside that directory — the `draft` documents are seeded later by the skill at produce time — which is what keeps chunk 2's preflight and the idempotent rerun consistent. Apply no byte cap: `RESULT_BYTE_CAP` and `TASK_BYTE_CAP` bound retained-result accounting that `LegacyImportInitializationV1` has no field for, `SNAPSHOT_LIMIT`'s scopes are `result` and `task`, and no requirement bounds import size.

4. **Assemble the manifest**: Export `stageLegacyUpgrade(input: StageLegacyUpgradeInput): Promise<ProjectResult<StagedLegacyUpgrade>>` from the same file. Pin `StageLegacyUpgradeInput = Readonly<{ working_directory: string; source_root: string; task_id: string; policy_base_commit: string; import_baseline_commit: string; code_baseline_commit: string; exclude?: readonly string[] }>` and `StagedLegacyUpgrade = Readonly<{ initialization: LegacyImportInitializationV1; audit_context: GateContext<"migration-audit">; manifest_path: string; resume_phase: PhaseInstanceId; draft_sources: readonly { destination_path: string; staged_path: string }[]; staged_paths: readonly string[]; unmapped: readonly string[] }>`. Selection is the whole source root minus `exclude`, which exists both so a secretlint false positive on the user's own prose has an escape that does not require editing the legacy source, and so a human can withhold the last implemented phase to redo it. The mapping is derived by layout convention — `prd.md` and `architecture.md` to `prd.md` and `design.md`, `phases/phase-<n>-<slug>.md` to `phases/<n>/design.md` with the slug dropped, `-log.md` to `phases/<n>/impl-notes.md`, and the three counter-review families to their canonical review names. `prd.md` and `design.md` are `draft` and are reported in `draft_sources` so the skill can seed them; everything else is `historical`. A file with no canonical slot stays in `staged_payload_refs`, out of `mapping`, and is reported in `unmapped`. `resume_phase` is one past the highest `phase-impl-<n>` in the mapping, or `phase-design-1` when none exists. `constitution_digest` and `workflow_digest` are resolved from the selected policy-base commit's tree; `resolvePinnedConstitution` and `detectTaskLocalConstitutionEdit` are called, and an unresolved task-local constitution edit fails `POLICY_BASE_INVALID`. `config_digest` is `computePinnedConfigDigest` over the destination `config.yaml`. `audit_context` is a `GateContext<"migration-audit">` — the shipped shape, no new type name; three of its digests come from the manifest, while `code_baseline_digest` and `policy_baseline_digest` are derived through the commit-digest shape `policyBaseInvalid` uses, which must first be exported **parameterized by `digest_kind`** — its hardcoded `"policy-base-commit"` tag would make the two identical whenever the commits are equal, destroying exactly the separation the audit binds.

5. **Enforce the manifest at the trust boundary**: In `src/state/initialization.ts`, classify every `mapping[].destination_path` as a task claim for the destination and fail `PATH_INVALID` on any that matches no rule; require every `mapping[].legacy_path` to name an entry in `staged_payload_refs`; and require each entry's `phase_instance` to agree with its `destination_path` under the canonical correspondence, because that field is what the jump guard later derives the resume phase from and a typo would silently relocate it. `classifyTaskPath` is already imported there; note `parseTaskPathClaim` throws rather than returning a result. All three checks belong on the server because the manual route hand-authors the manifest and lands in the same `runStateInitialization`. Do not re-read and re-verify staged payload bytes: the PRD places malicious-local-user protection explicitly out of scope, and these checks catch the authoring mistakes that are actually reachable. Correct the shipped contract fixture in the same change, and rebind the mapping and staged-ref paths in `test/crash/state-initialization.test.ts`, which reuses that fixture with only `task_id` and `canonical_paths` overridden and would otherwise start failing for the new reason while still passing its `ok === false` assertion.

6. **Gate and guard the jump**: Add a `migration-audit` precondition to `openDurableGate` in `src/state/gates.ts`, beside the existing `commit-authorization` and `restore-collision` ones: the gate's subject must equal the current `design` produce subject, an `artifact-approval` must already bind that subject, and `planned_final_phase` must be set and cover the resolved resume phase. Leave the decision effect as the shipped `advance`, so `nextStateForRecord` records an ordinary `ApprovalRef` and the cursor stays at `design` — routing it through the retry-effect re-entry seam would both land at the wrong phase instance and skip the approval append, making the guard below permanently unsatisfiable. Then add one clause to `legalMovement` in `src/state/transitions.ts` admitting a `phase-design-<n>/produce/running` target at attempt 1 from a succeeded `design`, legal only when an authenticated `migration-audit` approval is present and the supplied resume phase equals that target. Because `legalMovement` is a pure synchronous predicate and `planStateTransition` clones its plain-JSON inputs, `src/mcp/handlers/state.ts` resolves the authority first — selecting the `imports/*/manifest.json` whose canonical digest equals `state.initialization_digest`, failing non-advancing on none or more than one, deriving the resume phase from its mapping, and passing it through a new plain-JSON `TransitionPlanInput` field alongside the existing `commit_observed`. Guard the approval with `assertAuthenticatedGateApproval`, which survives because `planStateTransition` deliberately passes approvals un-cloned. `revise` and `abort` advance nothing.

It carries a payload and therefore must **not** join `INPUT_FREE_COMMANDS` in `src/local/main.ts`. ## Success Criteria
