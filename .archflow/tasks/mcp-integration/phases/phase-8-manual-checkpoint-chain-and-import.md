# Phase 8: Manual Checkpoint Chain and Import

**Status**: IN PROGRESS
**Task**: mcp-integration
**Goal**: Define the immutable predecessor-linked manual checkpoint chain and its import wrapper as a self-proving conservative manual authority.
**Depends on**: Phase 7 (COMPLETE)
**Requirements**: REQ-11, REQ-21, REQ-26, REQ-39, REQ-50

**This phase completes no requirement.** Like Phase 7 it defines file formats, extends one pure comparator, and wires no handler. Each requirement receives an exact slice. REQ-11 gets the checkpoint's `evidence_chain` — the shape that carries degraded-mode review provenance into the manual authority, composed over Phase 2's `evidence-slots` rather than restating it; the review schemas, assurance vocabulary, and family cross-products stay Phase 2's. REQ-21 gets the *conservative manual authority* half of the truthful state machine: the shape that stands in for `state.json` when the server is unavailable, with no reader and no writer here. REQ-26 gets the chain-to-wrapper identity binding that makes a two-task chain fail as an isolation violation. REQ-39 — which **left Phase 7 entirely** — gets the manual milestone record format and the import that returns it to the server without discarding it, **complete for chains that begin at revision 1 and knowingly incomplete for one entry path**: a task the server committed before any checkpoint existed cannot begin a manual chain in these two formats. That is stated in full in D-M and owned in Non-Goals rather than softened here. REQ-50 gets the manual-import-as-checkpoint-chain half its legacy-import manifest could not express. Completion for all five belongs to Phases 9, 14, and 17, which adopt, drive, and verify the behaviour.

## Context

Phase 7 landed seven durable schemas, eight modules, one consolidated semantic validator, and a registry at 32 entries. Six of its results bind this phase directly.

1. **The checkpoint family was cut out of Phase 7 at its design gate**, with two named defects it must fix (`phase-7-…-log.md`, and the Phase 7 Non-Goals row): (a) *the format could not prove its own initialization* — a checkpoint carried only an `initialization_digest`, `DurableSemanticSubject` admits exactly one artifact document, so an import could not also supply the initialization artifact checkpoint 1 names; the continuation mode was equally incomplete, since a gapless chain could legally begin above revision 1 and the head comparison used a revision number rather than a digest; and (b) *a digest-valid chain could cross task boundaries*, because nothing required every checkpoint's `task_id` to equal the wrapper's. Both are closed here, by D-A and D-G.
2. **Structural beats semantic, and it is measurable.** Phase 7's strongest result was that 102 of its rejection cases never reach the validator. This phase applies the same rule and says, per rule, which authority owns which half.
3. **`validateDurableSemantics` is extended in place.** `src/contracts/durable.ts` stays the phase's only cross-document authority; no second semantic module is created.
4. **`task-state.schema.json:5` pre-authorizes this phase's `$ref`s** by name, and Phase 7's D21 records that Phase 8 "authors its own mirrors then". Both are honoured literally below, and the cost is a narrowing of one Phase 7 negative assertion, pinned in chunk 8. **Phase 8 also *writes* to that shipped root** — one optional property and one `$def` — which the first draft of this design refused and the counter-review proved necessary; see D-M.
5. **`src/contracts/**` may never import `src/repository/**`** (`test/contracts/repository-boundary.test.ts:27-38`), so no path-template classification happens here.
6. **`npm run check` is unsatisfiable as an aggregate**, because `check:release` is blocked on a contradiction inside Phase 5's release-integrity model that Phase 6 diagnosed and Phase 7 inherited. This phase inherits it too and deepens its cause by two more schema files.

## What We're Building

Two versioned durable shapes — `manual-checkpoint` (a standalone file at `manual/checkpoints/<revision>-<checkpoint-digest>.json`) and `manual-checkpoint-import` (the fifth `archflow_state.artifact` union member) — each with a JSON Schema authority in `src/contracts/schemas/v1/` and a Zod mirror, because both are supplied by an agent across the MCP tool boundary (Phase 7's D2 rule, unchanged). One new module, `src/contracts/durable-checkpoint.ts`, holds both roots, both mirrors, both parsers, the self-digest, the three chain predicates, and one pure candidate-set selector. `validateDurableSemantics` gains one widened union member, eighteen sub-ranks under rank 5, four new carriers at rank 4a, and twenty-two `issue_code` literals.

One **shipped** shape is edited too: `TaskStateV1` and `task-state.schema.json` gain a single optional `adopted_checkpoint {revision, checkpoint_digest}`, without which no invariant in this phase can correlate supplied state to the exact predecessor checkpoint the architecture (`:554`, `:559`) requires. The first draft of this design rejected that edit; the counter-review showed the criterion is unsatisfiable without it and the human chose it at the review gate. D-M states the reversal in full.

Structural authority is pushed as far as it goes:

- **A revision-1 checkpoint carries the whole initialization artifact and no predecessor; a revision ≥ 2 checkpoint carries a predecessor and no initialization.** Both halves are a constraint-only `oneOf` on `revision`, mirrored by one `.superRefine`, mirrored by a two-member flat TypeScript union. A checkpoint that names an initialization it does not supply is *uninhabitable*, not rejected.
- **The wrapper's two modes are a discriminated union on `import_mode`.** `predecessor`, `expected_state_revision`, and `expected_state_digest` are present exactly in `continuation` and absent in `initial` — structurally, in all three authorities.
- **Duplicate revisions in a chain are rejected structurally** by the already-registered `x-archflow-unique-by` keyword.
- Every other declared collection is a set with a declared ordinal sort key and duplicate rejection, exactly as Phase 7 requires.

The validator is reserved for what genuinely spans documents or spans chain elements: chain-to-wrapper identity, per-checkpoint self-consistency, contiguity, predecessor-digest linkage, the initialization proof *and the embedded initialization's own identity binding* (5j, 5k), the wrapper-to-`state` correlation, the state-to-predecessor-checkpoint correlation without which "authenticated predecessor target" is only a revision number (5s), and the state-to-chain initialization binding without which a continuation import could adopt a chain built on a different initialization entirely (5t).

The phase implements **no** state mutation, adoption, revision-0→1 establishment, reconciliation, secret scanning, path classification, or `archflow-local` command, and adds **no runtime dependency**. It adds one optional field to `TaskStateV1` and writes nothing that ever sets it: the field's *format and invariant* are Phase 8's, its *lifecycle* is Phase 9's.

## Decisions

Labelled D-A … D-N to match the design record. Findings where a decision did not survive contact with the code — or, in D-H and D-M, did not survive the counter-review — are marked **FINDING** and stated in full rather than silently substituted. **D-H and D-M are reversals**: each argued a position in the first draft that the counter-review falsified and the human overruled at the review gate. Both say so in their own words rather than presenting the new answer as if it had always been the answer.

**D-A — the subject keeps exactly three slots.** `manual-checkpoint-import` becomes the **fifth** `DurableArtifact` member and occupies the existing `artifact` slot; no fourth slot is added. The architecture's requirement that "the validator's subject admits that artifact together with the chain, so an import can carry both" is satisfied because the wrapper carries both: a revision-1 checkpoint supplies the **whole** `task-initialization` or `legacy-import-initialization` artifact, not only a digest. Phase 7 pinned this direction (`durable.ts` log: "`DurableArtifact` (4 members; Phase 8 widens with `manual-checkpoint-import`)").

The consequence is load-bearing: `artifactInvalid` (`durable.ts:140-144`) dispatches on `artifact_kind` and its else-branch reads `artifact.task_id`. **The wrapper therefore carries a top-level `task_id`**, that helper needs no new branch, and rank 7b (`state.task_id === artifact.task_id`) fires correctly for an import at no cost. `artifact.snapshot_digest` is read only inside the `implementation-output` branch, so widening the union does not require the wrapper to carry one.

**D-B — rank 7 is left byte-identical, because the widening D-B proposed is provably vacuous. FINDING.** The intent was to widen rank 7's initialization resolution so ranks 7a–7h apply uniformly whether the initialization arrives directly or embedded in a revision-1 checkpoint. Against the shipped code that resolver can never fire, and the proof is short:

1. Rank 7's entire block is guarded by `state !== undefined` (`durable.ts:354`).
2. Sub-rank 5o rejects `import_mode === "initial"` together with a supplied `state`, which is exactly what architecture success criterion 2 requires ("the expected-state-revision field is present exactly when existing state is supplied and absent otherwise"). So when rank 7 runs with an import artifact, the mode is `continuation`.
3. A continuation wrapper structurally carries a `predecessor` with `revision >= 1`, and sub-ranks 5e and 5h — both at rank 5, therefore both **before** rank 7 — establish `chain[0].revision === predecessor.revision + 1 >= 2`. **This step depends on 5h rejecting a continuation `chain[0]` that carries no `predecessor` at all**, which is structurally legal (a revision-1 initial checkpoint) and which neither 5e nor 5g catches; that branch is pinned in the seam block rather than left to the implementer, precisely so this proof does not rest on unstated behaviour.
4. Only a revision-1 checkpoint may carry an `initialization`, structurally.

Therefore no initialization is reachable from an import artifact at rank 7, and a resolver would return `undefined` in every case. **What Phase 8 does instead**: the initialization-proving invariants live at rank 5, where they actually fire — 5i proves the revision-1 checkpoint's `initialization_digest` equals the canonical digest of the artifact it supplies, 5j and 5k prove that artifact is *this* task's and *this* repository's, and 5l proves every checkpoint in the chain names that same initialization. Rank 7 is not touched at all, which also satisfies D-B's own hard requirement ("behaviour for the four existing members must be byte-identical") literally rather than by inspection. The corpus asserts the vacuity structurally, in chunk 12's style: a fixture proving that `import_mode === "initial"` and a present `state` slot cannot coexist.

**D-C — rank placement, with the deviation proved rather than hidden.**

- **Every chain invariant runs before rank 7.** Rank 7a compares `state.initialization_digest` against an initialization document, and it must not trust one drawn from a chain whose own integrity is unproven. This mirrors Phase 7's "7d–7h presuppose 7a" reasoning. Placing the import family at rank 5 satisfies it with room to spare.
- **No existing rank number or sub-rank is renumbered.** The pinned 22-literal table, the corpus assertions, and Phase 7's invariant table all cite them. Rank 5 gains sub-ranks `5c`–`5t`; `5a` and `5b` keep their meaning. (The `5c`–`5t` letters themselves were renumbered *within this design* when the counter-review added 5j/5k and 5s; every table below was recounted from scratch rather than patched.)
- **A checkpoint carries a `phase_instance`, so its decodability belongs at rank 4a**, which reports `CONTRACT_INVALID{issue_code}` — an error family that carries no phase instance and therefore has no throw hazard.
- **Rank 2's "no later rank can throw" precondition is re-verified against every new carrier.** All twenty-two new failures report `TASK_INVALID{task_id: wrapper.task_id, issue_code}` through the existing `artifactInvalid`, and the four new rank-4a carriers report `CONTRACT_INVALID{issue_code}`. Neither parameter set runs `decodePhaseInstance`. `TASK_INVALID`'s `task_id` runs `taskSlugV1Schema` under `.strict()` (`errors.ts:42`; `:45` is `STATE_INVALID`, the code this bullet argues no new rank can reach), whose two `.refine()` rules are expressed **exactly** by the lookahead in `primitives.schema.json:36-39` — so a wrapper that passed its normative schema always parses, and `createProjectError` cannot throw. **No new rank can report `STATE_INVALID`**, so rank 2's precondition is untouched, not merely still satisfied.
- **Source order, and the mutual-exclusivity proof.** The import block is placed **physically before** the `if (artifact.artifact_kind === "implementation-output")` block. That is not cosmetic: 5a, 5b and 6a–6f live inside that single `if`, so placing the import block after 5b would put it after rank **6**, a rank-level inversion, whereas placing it before inverts only `(5c…5t)` against `(5a, 5b)`. The deviating pairs are mutually exclusive: `DurableArtifact` is discriminated on one `artifact_kind` literal per member (`durable.ts:30-34`) and the subject has exactly one `artifact` slot (`durable.ts:36-40`), so no subject can make both blocks candidates — an artifact is never both an implementation-output and an import. Their relative source order is therefore **unobservable**, and Phase 7's rule ("the clauses are written in exactly that order so the first failure found is that minimum") still holds. The same proof covers rank 4a, where the artifact-kind branches (`isStepped` root clause, `legacy-import-initialization.mapping`, and the new import-chain carriers) are written in source order `""`, `mapping`, `chain…` rather than the lexicographic `""`, `chain…`, `mapping`.

**D-D — the self-digest is derived, never stored.** A checkpoint carries **no** self-digest field. `checkpointSelfDigest(c) = canonicalJsonDigest(c)`. The successor's `predecessor` object carries `{revision, checkpoint_digest}`, and Phase 6's filename template `manual/checkpoints/<revision>-<checkpoint-digest>.json` (`paths.ts:94`) carries it too.

The alternative — a stored, self-excluded digest field — is rejected twice over. A stored digest over the whole document is self-referential and uncomputable. A digest that excludes itself requires the excluded field to be invisible to the hash, and a non-enumerable or accessor-backed field is exactly the hazard the Phase 7 implementation counter-review closed: `canonicalJsonBytes` serialises only enumerable properties (`canonical.ts:48-63` via `Object.keys`), so an excluded field is invisible to every digest derived from it, and `durable.ts:94-112` now requires **both** `value` and `enumerable` on every read for that reason. Deriving instead mirrors `CanonicalDocument`, which already keeps `digest` outside `value` (`canonical.ts:98-102`), and lets the validator re-derive every digest it compares, per `durable.ts:122-125`. Because `canonicalDocument` computes its digest from `canonicalJsonBytes(value)` (`:105-106`) and `parseCanonicalDocument` proves the bytes it read are already in canonical form (`:137-140`), the filename digest, the stored bytes' digest, and `checkpointSelfDigest(value)` are the same number by construction — a reader can check a checkpoint file's name against its bytes with no stored field at all.

**D-E — structural beats semantic; the wrapper's two modes are a discriminated union, and each half is pinned.** Phase 7's strongest result was that 102 of its rejection cases never reached the validator. The wrapper discriminates on `import_mode`:

- **`initial`** — no `predecessor`, no `expected_state_revision`, no `expected_state_digest`; the chain begins at revision 1; the revision-1 checkpoint carries the whole initialization artifact.
- **`continuation`** — `predecessor {revision, checkpoint_digest}`, `expected_state_revision`, and `expected_state_digest` all required; the chain begins at `predecessor.revision + 1`.

**The structural half** (JSON Schema `oneOf`, Zod `.superRefine`, and the two-member TypeScript union, all three): the three continuation-only fields are present exactly in `continuation` and absent in `initial`. Also structural, on the checkpoint itself: a revision-1 checkpoint has an `initialization` and no `predecessor`; a revision ≥ 2 checkpoint has a `predecessor` and no `initialization`. That second rule is a property of the *checkpoint file*, not of any import — architecture `:320` says initial normal and legacy checkpoints commit the corresponding manifest unconditionally — so it belongs in the checkpoint schema rather than in the wrapper's mode branch.

**The semantic half** (rank 5, and only this): the wrapper-internal revision correlation (5m, D-M), correlating the wrapper against the subject's actual `state` slot (5n, 5o), the two comparisons against a supplied state (5p, 5q), the repository-identity binding (5r), the state-to-predecessor-checkpoint correlation (5s, D-M), and the state-to-chain initialization binding (5t, D-M). These are genuinely cross-document — the wrapper's `import_mode` is a field and the presence of a `state` slot is a fact about a different document — and no schema can see both. 5m is the one exception and it is deliberate: both of its operands are wrapper fields, but JSON Schema cannot express cross-field equality and a Zod-only `.superRefine` would break the "S and Z always agree" property that `assertZodAgreement` enforces, so it is a validator sub-rank rather than a structural rule. It is also why 5m sits **before** the state clauses rather than after them: it needs no `state` slot, so ordering it after 5n would make it unreachable for the wrapper it is meant to reject.

**Structural rule used in both files.** A shape with a **literal** discriminant gets a discriminated union; a shape whose branches are separated by an **integer bound** cannot have one. `revision` is the checkpoint's separator, so both files use one idiom for consistency: a single closed root object declaring every property with `additionalProperties: false`, plus a constraint-only `oneOf` whose branches assert only the discriminant, extra `required` entries, and `not: {required: […]}` for the forbidden ones. The Zod side is one `.strict()` object plus a `.superRefine` mirroring the `oneOf` clause for clause, **cast `as unknown as z.ZodType<ManualCheckpointV1>`** (and likewise for the wrapper): a `z.object` infers an object output type and can never infer a union one, so the cast is the only way a single-object mirror can carry the two-member union type, and it is the same idiom every shipped durable root mirror already uses — `durable-document.ts:95` is `z.object({…}).strict() as unknown as z.ZodType<DocumentArtifactV1>`, and `trust.ts:140-141` and `path-claims.ts:45` do the same for branded primitives. The TypeScript side is a **flat** two-member union (each branch written out in full, never an intersection), following Phase 7's 14-flat-leaf `OutputEntry` precedent. **The reason is readability and precedent, not the compiler** — that distinction is stated because the obvious justification is false and a reader can falsify it in one probe: `CanonicalDocument<Initial | (Omit<Initial, "initialization"> & {predecessor: PredecessorLink})>` was probed under the project's exact options and **compiles**, so `PlainJsonValue`'s reachable-graph check does *not* forbid an intersection branch. What does argue for flat is that the field list is normative across four chunks that cannot see each other's file, and an `Omit`-plus-intersection branch makes the reader compute the field list rather than read it. `z.discriminatedUnion` is deliberately not used for the wrapper even though `import_mode` is literal: the JSON authority is one closed object, and a Zod discriminated union would be a structurally *different* document that must be hand-kept in sync, which is the drift `assertZodAgreement` exists to prevent.

**D-F — the chain uses `x-archflow-unique-by`, not `x-archflow-sorted-unique-by`, and reordering is a validator rank. FINDING.** The intended decision was to declare `chain` with `x-archflow-sorted-unique-by: "revision"`, so that reordering and duplicate revisions are both rejected by the already-registered keyword and the single `isSortedUniqueBy`/`tupleKey` predicate. **That keyword cannot be used on a numeric key.** `tupleKey` reads each property and `String()`-coerces it (`validators.ts:79-88`), and `isSortedUniqueBy` compares the resulting strings with `<` (`validators.ts:63-65`). The comparison is ordinal, so `String(9) < String(10)` is `false`: **a perfectly valid chain running 9 → 10 would be rejected as unsorted.** Every existing use site keys on a string (`gate_id`, `path`, `input_id`, `destination_path`, `legacy_path`, and the `(phase_instance, step)` tuple); `revision` would be the first numeric key in the repository.

The conservative substitution keeps every property D-F wanted:

- **No new Ajv keyword is registered**, so no schema fails to compile under `Ajv2020 strict:true` and `validators.ts` gains no keyword. D-F's stated win is preserved. `ajv-keywords`' `uniqueItemProperties` was evaluated as an off-the-shelf substitute and **rejected**: its semantics are per-property rather than over the tuple, it has been unmaintained since 2021, and — decisively — it cannot share its predicate with the Zod side, which is the whole point of the single-predicate discipline below. No dependency is added.
- **Duplicate revisions stay structural.** `chain` declares `x-archflow-unique-by: "revision"`, whose backing predicate `hasUniqueObjectPropertyValues` compares with `isDeepStrictEqual` (`validators.ts:37`) and is numeric-safe. The Zod mirror calls **the same function**, which is why chunk 1 exports it — one predicate, two authorities, exactly Phase 7's D11 discipline.
- **Reordering is rejected by sub-rank 5f**, which requires `chain[i].revision === chain[i-1].revision + 1`. Contiguity implies strict increase, so a reordered chain fails 5f with a stable error, satisfying architecture success criterion 4 ("reordered or duplicated revisions … fail with stable errors"), which demands a stable error rather than a structural one.

**This resolves Phase 7's "Phase 8 reintroduces the sequence case" more conservatively than Phase 7 expected, and the deviation is flagged rather than hidden.** `chain` *is* an order-significant array — `canonicalJsonBytes` preserves array order (`canonical.ts:49`) — but its order is a total function of `revision` under 5f, so two callers holding the same logical chain always produce the same canonical bytes. No order-significant-array machinery is introduced, and Phase 7's criterion "there is no sequence in this phase" is superseded for Phase 8 by a sequence whose order is derived, not chosen.

**D-G — cross-task isolation is a semantic rank, and it runs first.** Every `chain[i].task_id` must equal the wrapper's (5c) and every `chain[i].repository_identity_digest` the wrapper's (5d). These are the **first** two clauses of the import block, ahead of every linkage and digest clause, so a chain assembled from two tasks' checkpoints fails as an isolation violation (REQ-26) even when its digests all link correctly — it never reaches the point of looking valid. This closes the Phase 7 counter-review's blocker finding 2.

**D-H — "greatest valid chain" is a pure candidate-set selector, not a prefix truncation. FINDING, and a reversal.** The first draft defined the operation as `greatestValidChain(wrapper)`: the longest contiguous validly-linked *prefix of `wrapper.chain`*. **The counter-review was right that this cannot be criterion 4, and the argument is unanswerable.** `wrapper.chain` is already a caller-selected linear sequence, so a function over it accepts no candidate set, and a fork is not even representable in its input. Given `A@1` and two checkpoints `B@2` and `C@2` that both validly link to `A`, separate calls over `[A,B]` and `[A,C]` each return a full "greatest" chain and nothing anywhere reports that authority is ambiguous — while `architecture.md:261` ("pure manual authority is the greatest valid immutable checkpoint chain"), `:284`, and `:320` ("collision, chain gap, or ambiguity stops") all require exactly that stop. Deferring *filesystem enumeration* to Phase 14 was and remains right; deferring the *selection semantics* was the error, because the selection semantics are pure and are what criterion 4 names.

**What this phase exports instead.** `src/contracts/durable-checkpoint.ts` exports a pure selector that **returns its value** (Phase 6 decision 5):

- an **anchor** — what the chain must begin from — which is `{mode: "initial"}` or `{mode: "continuation", predecessor}`, plus the `task_id` and `repository_identity_digest` the candidates must all carry. Every component is known without server state: Phase 14 knows which task's `manual/checkpoints/` directory it is reading. `chainAnchor(wrapper)` derives one from a wrapper, so the validator and the selector build their head test from the same value.
- an **unordered candidate collection**, not a sequence. Order in the input is not consulted and not preserved.
- a result that is either **a chain** — possibly the empty one — or an **explicit stop**: `gap`, `fork`, or `foreign-candidate`.

**Three outcomes, and each is named by a requirement. FINDING (m7).** The first draft carried four and defended them by the shape the counter-review suggested, which is not a defence. `CLAUDE.md` asks for the simplest design that meets the current requirement, so each outcome now either names its requirement or goes:

- **`gap`** — `architecture.md:320` ("collision, chain gap, or ambiguity stops") and `:284` ("No route imports a gap, loose prepared file, or unreferenced decision"). Architecture criterion 4 names predecessor gaps directly.
- **`fork`** — `:320`'s *ambiguity*, and `:261`'s "pure manual authority is **the** greatest valid immutable checkpoint chain". The definite article is a uniqueness claim, and `fork` is the only outcome that can report its failure; reporting it is the whole reason the prefix truncation could not be criterion 4.
- **`foreign-candidate`** — REQ-26, this phase's own cross-task isolation requirement, applied to the selector by D-G. A stray checkpoint from another task or repository sitting in this task's directory must **stop**, because filtering it would let a stray file silently change which chain is greatest.
- **`no-valid-successor` is dropped, and that is the m7 decision.** No requirement names it, and it was never a stop: "no candidate advances the anchor" is the *absence of news*, not a failure — an empty `manual/checkpoints/` and a manual chain that has not moved past its predecessor are both ordinary. The selector returns `{kind: "chain", chain: []}` for it, which is literally the greatest valid chain from that anchor, and the caller stops having to distinguish a benign stop from a real one. Dropping it is only safe because steps 2 and 4 below both key on the **anchor's expected head revision**: every candidate that *claims* to advance the anchor and fails to link is a `gap`, so an empty chain means exactly "nothing at or above the head revision", never "something was there and was ignored".

**The algorithm, pinned so two chunks cannot read it differently.** Let `linked(tail)` be the candidates `c` with `checkpointSelfBreak(c) === undefined` and `checkpointLinkBreak(tail, c) === undefined`, and let the anchor's **expected head revision** be `1` in initial mode and `anchor.predecessor.revision + 1` in continuation mode — one derived value, used twice, so the two steps that decide "is something missing" cannot drift apart.

1. **Identity first, as a whole-set stop.** If any candidate's `task_id` or `repository_identity_digest` differs from the anchor's, return `foreign-candidate`. A foreign checkpoint is never *filtered out* — filtering it would let a stray file silently change which chain is "greatest", and would contradict 5c/5d, which reject the whole wrapper. This is D-G's rule applied to the selector.
2. **Heads.** The candidates `c` with `checkpointSelfBreak(c) === undefined` and `chainHeadBreak(anchor, c) === undefined`. Two or more heads: `fork`. Zero heads: build nothing, skip step 3, and let step 4 alone decide between `gap` and an empty chain.
3. **Walk.** From the current tail, take `linked(tail)`. Two or more: `fork` — this is the reviewer's `B@2`/`C@2` case, and it is also how a duplicate revision with differing bytes is caught. Exactly one: it must carry the head's `initialization_digest` or the result is `foreign-candidate` (never a filter, for the same reason as step 1); append and continue. Zero: stop walking.
4. **Completeness, keyed on the expected head revision rather than on the tail. FINDING (m5).** Any **unconsumed** candidate whose `revision` is **at or above** the expected head revision means the collection holds material that claims to advance the anchor and does not link: `gap`. Otherwise return the chain, empty or not.

   The first draft keyed this on "above the tail's revision", and that silently dropped exactly the case `:320` calls a **collision**. The witness: `A@1`, `B@2`, `B'@2` — same identity and `initialization_digest` as `B`, self-valid, but not linking to `A` — and `C@3` linked to `B`. The walk yields `[A,B,C]`; `B'` is unconsumed and *not above* the tail's revision 3, so nothing was reported, even though two distinct revision-2 checkpoint files exist. That is the collision `:320` says must stop, and step 1's own principle — a foreign checkpoint is never filtered out — forbids passing it over. Keyed on the expected head revision instead, `B'` is at 2 and the head revision is 1, so the set stops with `gap`. The same key is also what keeps ordinary **history** quiet: in continuation mode a directory holding revisions 1…R alongside an anchor expecting `R+1` leaves every older file unconsumed and *below* the key, which is correct and must not be reported.

**The self-break quantifier includes the head, and that is the earlier finding, preserved.** The obvious form — testing `checkpointSelfBreak` only on successors, on the theory that `chainHeadBreak` has already vetted the head — **diverges from the validator**. In continuation mode `chainHeadBreak` compares only the candidate's `predecessor` against the anchor's; it never checks `revision === predecessor.revision + 1`. So an anchor carrying `predecessor {revision: 3, digest: X}` with a candidate `{revision: 7, predecessor: {3, X}}` would be accepted as a head by the selector while the validator rejects the same subject at 5e. Step 2 tests `checkpointSelfBreak` on every head candidate for exactly that reason. This is the one place where the two callers of the shared predicates could disagree without either predicate being wrong.

**The prefix-truncation function is removed, not kept alongside.** It has no caller in any phase once the selector exists — Phase 14 assembles from a directory, which is a candidate set, and Phase 17 reconstructs status from the selector's result — and `CLAUDE.md`'s "simplest design that meets the current requirement" does not support shipping a second, weaker derivation whose only distinguishing property is the defect the counter-review found. Everything it was carrying moves: the quantifier finding into step 2, the truncation matrix into the selector's outcome matrix, and the "identity failures are never silently salvaged" proof into steps 1 and 3 plus chunk 7's validator half (R5).

**Three things the selector deliberately is not.** It is **not a second semantic authority**: `validateDurableSemantics` requires the *whole* supplied chain to be valid and never truncates, and the selector constructs no `ProjectError`. Its three outcome literals are deliberately **not** `issue_code`s and deliberately **not** members of `CHECKPOINT_BREAK_CODES` — a stop is a caller's decision input, not a validation error, and the pinned `CHECKPOINT_BREAK_CODES ⊆ DURABLE_ISSUE_CODES` assertion must not be widened to cover them. It **reads no file and consults no state**, which is precisely what criterion 4 asks for; enumerating `manual/checkpoints/` stays Phase 14's. And it does **not** evaluate the wrapper-revision or state correlations (5m–5t) — those need a wrapper and a state, and the selector has neither.

**D-I — `trust.ts` needs exactly one D1 conversion, and Phase 7's predicted export edit is withdrawn.** `requiredReviewSlotsSchema` (`trust.ts:158`) and `currentEvidenceSetRefSchema` (`trust.ts:159`) are **already exported**, so Phase 7's deferred "D5 export edit" is unnecessary; that deferral is recorded as closed-by-inspection and no export is added.

What *is* needed is Phase 7's D1 rule: every type transitively reachable from a durable root must be a `type` alias, never an `interface`, or `CanonicalDocument<T extends PlainJsonValue>` fails with `TS2344`. **Probed at design time under the project's exact compiler options** (`target ES2024`, `strict`, `exactOptionalPropertyTypes`, `noUncheckedIndexedAccess`, `verbatimModuleSyntax`, TypeScript from the repository's own `node_modules`), with these results:

**Exactly one conversion, and the implementation must prove minimality** the way Phase 7 proved two sufficed: `trust.ts:137`, `export interface CurrentEvidenceSetRef` → `export type CurrentEvidenceSetRef = {…}`, body unchanged. **`AuthorityLinkBase` (`trust.ts:126`) is *not* converted**, and neither is any other `trust.ts` interface: no checkpoint field is typed as an `AuthorityLink`, because Phase 2 already shaped the reference to run the other way — `DegradedAuthorityReferences` (`trust.ts:124`) is `{kind:"degraded"; checkpoint_digest; checkpoint_revision}`, a link that points **at** a checkpoint. Converting it would be cosmetic churn on a shipped module for no compile benefit, exactly the mistake Phase 7 avoided with `GitIdentityRef`. The conversion is runtime-neutral and neutral for every current consumer (`grep` shows no `extends`, `implements`, or declaration merge on the name); what it removes — the ability to declaration-merge — is the point, per the `CLAUDE.md` rule.

**D-J — compose `evidence-slots`, do not restate it.** Each evidence-chain entry carries a `current_evidence` object of `{set_digest, slots}`, where `slots` references `urn:archflow:schema:v1:evidence-slots` as a **whole root** — that schema's root is itself a 2- or 3-tuple `oneOf` (`evidence-slots.schema.json:4-7`) with no reusable object `$def` — exactly as `mcp-tools.schema.json:51` does. The Zod mirror is the **already-exported `currentEvidenceSetRefSchema`** (`trust.ts:159`), which is `z.object({set_digest, slots: requiredReviewSlotsSchema}).strict()`; no local re-declaration of either. **Nothing here restates assurance values, independence values, or the family cross-product correlations** — Phase 2 owns them in both authorities (`evidence-slots.schema.json:10-12` and `trust.ts:155-158`), and `evidence-slots.schema.json` is **not edited**.

**Two inherited facts, recorded rather than discovered later.**

1. **`currentEvidenceSetRef` is this shape's *third* declaration, and that is still the right call.** `mcp-tools.schema.json:45-53` already declares `$defs/currentEvidence` as exactly `{set_digest, slots: {$ref: "urn:archflow:schema:v1:evidence-slots"}}`, with `currentEvidenceSetRefSchema` (`trust.ts:159`) as its Zod model. Phase 8 declares a **local** `$def` rather than `$ref`ing the `mcp-tools` one, because a durable schema pointing at a legacy `https://archflow.dev/…` `$id` would bind a durable file format to the tool-contract document's identifier — strictly worse than a two-line duplicate. The duplication is recorded here because `DEF_INVENTORY` does not cover `mcp-tools` and no test catches it; a later phase that unifies the two owns the migration.
2. **The composed Zod mirror is weaker than the shipped parse entry point, and this is an inherited gap.** `currentEvidenceSetRefSchema` (`trust.ts:159`) does **not** run `validateSlots`; only `parseCurrentEvidenceSetRef` (`trust.ts:166`) does. `validateSlots` (`trust.ts:204-211`) adds cross-slot evidence-digest uniqueness (`:210`), which neither `evidence-slots.schema.json` nor the bare Zod schema expresses. Phase 8 does **not** close this: tightening `currentEvidenceSetRefSchema` changes a shipped Phase 2 export's behaviour for every existing consumer. **Owner: Phase 13**, which correlates each slot's `evidence_digest` to the evidence documents it names and is where cross-slot uniqueness becomes load-bearing; recorded in Non-Goals. What verification step 13 therefore proves is the *role-order and family-independence* composition, not digest uniqueness.

The checkpoint's own `assurance: "degraded"` const and a slot's `assurance` are at different levels and neither constrains the other. A checkpoint is always degraded because it is manual-mode authority (architecture `:320`, REQ-38–REQ-39); a counter-review slot inside it may legitimately be `server-attested`, because the work may have been done while the server was up and only checkpointed after it went away. The design states this so a later phase does not "tidy" it into a correlation.

**D-K — `$ref` the pre-authorized `task-state` `$defs`, and author the mirrors here.** `task-state.schema.json:5` says verbatim that `authoritativeResultRef`, `approvalRef`, `waiverRef`, `openGateRef`, `stepStatus`, `gateKind`, and `preparedIntentRef` are owned there and that "Phase 8 `$ref`s them from here rather than re-declaring them". Phase 7's D21 adds that Phase 8 "authors its own mirrors then". Both are honoured: this phase `$ref`s five of the seven (`preparedIntentRef` is deliberately unused — a manual checkpoint is committed by construction and has no prepared intent; `gateKind` is reached transitively inside `approvalRef` and `openGateRef` and needs no direct reference) and authors four Zod mirrors for the shapes it reaches. **A private re-declaration of any of those `$defs` is the exact drift the pinned inventory exists to prevent**, and it would pass the re-declaring chunk's own tests.

**One `$def` runs the other way, and it is not an exception to that rule.** D-M adds `adoptedCheckpointRef` *to* `task-state.schema.json`, owned there, consumed only by `task-state.adopted_checkpoint`. Its body is identical to this phase's `predecessorLink`, and it deliberately does **not** `$ref` it: a shipped Phase 7 root pointing at a Phase 8 schema would invert the phase dependency and add `manual-checkpoint` to `task-state`'s reference set at every compile site, including `durable-state.test.ts`'s two-reference validator. Two structurally identical `$def`s in two documents is the cheaper answer, and it is recorded here for the same reason D-J item 1 records the third `currentEvidenceSetRef`: a later phase that unifies them owns the migration.

**D-L — no new error code.** The five existing codes are the whole vocabulary: `STATE_INVALID{phase_instance, issue_code}`, `SNAPSHOT_INVALID{snapshot_digest, issue_code}`, `TASK_INVALID{task_id, issue_code}`, `CONTRACT_INVALID{issue_code}`, `INPUT_FINGERPRINT_MISMATCH{expected_digest, observed_digest}`. A chain has no single `phase_instance` and no `snapshot_digest`, so **every** chain failure reports `TASK_INVALID{task_id: wrapper.task_id, issue_code}` — which is precisely what `artifactInvalid` already produces once D-A gives the wrapper a `task_id`. The 52-code and 56-row error assertions must still pass unchanged. `DURABLE_ISSUE_CODES` grows from 22 to **44** literals, and **both** corpus blocks are updated to 44: the `toEqual` at `durable-semantics-corpus.test.ts:936-961` and the separate block at `:963-967`, where only the `toHaveLength(22)` literal at `:965` changes. **That block's `it` title carries no count** — it reads `"are all SafeCode, and rank 8 has none"` (`:963`) and stays byte-identical; the only stale title in this phase's shipped-test edits is `durable-agreement.test.ts`'s, pinned in chunk 8. The selector's three outcome literals (D-H) are **not** among the 44 and are not `SafeCode`-constrained; they never reach `createProjectError`.

**D-M — "authenticated predecessor target" means correlated to the exact predecessor checkpoint, and the shipped state had no field that could do it, so this phase adds one. FINDING, and a reversal.** The architecture uses the phrase without defining it, and the PRD explicitly disclaims cryptographic approver identity (`prd.md`, Out-of-Scope row "Cryptographic approver identity or malicious-local-user protection": "Manual decision files provide local traceability, not strong identity, signatures, or protection from an attacker who controls the filesystem. Tampering that affects workflow evidence must still be detected and fail closed where specified"). What it *does* define is the requirement: `architecture.md:554` says "existing state is correlated to the exact predecessor checkpoint by digest, never by revision number alone", and criterion 2 at `:559` repeats it.

**The shipped `TaskStateV1` could not express it.** `durable-state.ts:107-145` declares twenty fields — `schema_version`, `task_id`, `repository_identity_digest`, `revision`, `phase_instance`, `step`, `status`, `attempt`, `input_fingerprint`, `initialization_digest`, `config_digest`, `workflow_digest`, `constitution_digest`, `policy_base_commit`, `authoritative_results`, `approvals`, `waivers`, `open_gate?`, `prepared_intent?`, `terminal?` — and **none of them records an adopted checkpoint**.

**The first draft's answer, and why it was wrong.** This decision previously argued that two digests could do the work of the one the architecture assumed: `expected_state_digest` (proving the supplied state is the document the wrapper describes) plus `predecessor.checkpoint_digest` (proving `chain[0]` claims the predecessor the wrapper claims), with resolution of the digest to a retained file deferred to Phase 9. It listed adding a state field as *the rejected alternative*, on the grounds that it edits a shipped Phase 7 root for a fact only Phase 9 needs, and that Phase 7's D13 refuses to record a value that is a function of other authority.

**The counter-review falsified that, and the human chose the alternative at the review gate.** The witness is exact: state at revision `R` actually resulted from checkpoint **D2**; submit a continuation wrapper naming `{revision: R, checkpoint_digest: D1}`, set `expected_state_digest` to the correct canonical digest of that very state, and link `chain[0]` to D1. Every clause the first draft proposed passes — 5h compares the wrapper's claim to the chain's claim, both of which are D1; the revision clauses compare `R` to `R`; and `expected_state_digest` is *correct*, because the state bytes really are those bytes. Nothing anywhere compares the state to D1. Phase 9 resolving D1 to a retained file proves D1 **exists**, not that this state came from it. The correlation criterion 2 names was therefore unsatisfiable, and the D13 ground does not actually apply: **an adopted-checkpoint digest is not a function of anything else in state.** `revision` gives the coordinate, not the identity; two distinct checkpoints can occupy the same revision, which is exactly the case the witness constructs. D13 forbids recording a *derived* value; this one is underivable.

**What is added.** `TaskStateV1` gains a single **optional** reference, and `task-state.schema.json` gains the matching property and one `$def`:

```ts
readonly adopted_checkpoint?: {
  readonly revision: SafeInteger;      // >= 1, its own minimum per D8 — never a $ref to safeInteger
  readonly checkpoint_digest: Sha256Digest;
};
```

It is a **single optional object, never an array**, following the shipped `open_gate` and `prepared_intent` precedent exactly — both are declared as a `$def` and reached by `$ref` from the property (`task-state.schema.json:74-77`, `:78`), so `adoptedCheckpointRef` is declared as a `$def` too rather than inline. `task-state` has **no Zod mirror** (Phase 7 D2), so this is a JSON-Schema-plus-TypeScript change and nothing else; `AdoptedCheckpointRef` is declared in `durable-state.ts`, structurally identical to this phase's `PredecessorLink` and deliberately not shared with it (D-K's closing paragraph).

**The invariant it buys — 5s.** Continuation with state ⇒ `state.adopted_checkpoint` is **present**, and its `checkpoint_digest` and `revision` both equal `wrapper.predecessor`'s. Three checks in fixed order — presence, revision, digest — each with its own literal.

**Absence must fail, and that is the point rather than an edge case.** An optional field whose check silently vanishes when the field is omitted would leave open exactly the hole the human just chose to close: a wrapper asserting "you adopted checkpoint D" against a state that records adopting *no* checkpoint is precisely the ambiguity REQ-39 says must stop, and treating it as a pass would make the whole edit decorative. It gets its own literal, `import-state-adopted-checkpoint-missing`, rather than folding into the revision field the way 5h folds its absent-`predecessor` branch — 5h's branch is a structural accident of the checkpoint union, while this one is the substantive case, and it must be nameable at the gate and in the unsupported path stated next.

**What "absence fails" costs: the primary REQ-39 entry path is unrepresentable in these two formats, and this phase knowingly leaves it that way. FINDING (M2), and the one place this design does not close what it opens.**

Two rules meet here and leave no room between them. 5s requires `state.adopted_checkpoint` in continuation mode. Independently, the checkpoint shape requires every `revision >= 2` checkpoint to carry a `predecessor` naming an existing checkpoint (D-E's structural rule). A task that ran on the server to revision 7 and then lost the server has **neither**: `archflow-local checkpoint` "atomically writes the next immutable `manual/checkpoints/<revision>-<digest>.json` bound to its predecessor" (`architecture.md:320`), but there is no predecessor checkpoint to bind to, and the pre-outage `state.json` records no adopted checkpoint. Normal mode does not write a checkpoint per committed revision — the mutation flow's nine steps (`architecture.md:63-71`) never write one, and `:79` explicitly lets `archflow_state` establish revision-1 authority from a `task-initialization` adopted **directly**, so a task can reach revision 7 with no checkpoint file ever having existed. So the central REQ-39/REQ-21 scenario — **server dies mid-task, work continues manually, the chain is imported on recovery** — cannot be expressed by the two formats this phase fixes. It is complete for a chain that begins at revision 1; it is empty for a chain that must begin at revision 8 of a task the server already committed.

**The alternative was considered and declined at the gate.** Admitting a *head* checkpoint that carries a `predecessor`-shaped anchor into non-checkpoint state — a revision ≥ 2 checkpoint with no predecessor checkpoint, correlated to `state` by revision and `expected_state_digest` alone — would represent the flow, but it opens a second, weaker head form in all three authorities, needs its own head-break predicate and its own selector anchor mode, and re-litigates what "authenticated predecessor target" means one phase after this design settled it. The human's decision at the review gate was to **record it as a known unsupported path** and change neither shape. That decision is implemented literally: `manual-checkpoint` and `manual-checkpoint-import` are exactly as specified above, 5s stays strict, and nothing here is softened to make the gap smaller than it is.

**It must be resolved before Phase 17 ships**, and it is written here at full strength so no later phase discovers it as a surprise. Phase 9 owns adoption and is the only layer that ever writes `adopted_checkpoint`, so it owns the bootstrap half — how a server-committed state acquires its first one, or what stands in for it. Phase 17 owns the manual workflow that would otherwise be told, at the worst possible moment, that the outage it exists for is the case it cannot record. The Non-Goals row carries both owners.

**One related state rule, also Phase 9's.** Nothing in Phase 8 enforces `state.adopted_checkpoint.revision === state.revision`, so 5s's revision check is not redundant with 5p — that state-internal well-formedness rule has no rank here.

**The rest of the intent, unchanged from the first draft and still correct:**

- **`expected_state_digest`** — the wrapper asserts the canonical digest of the state document it expects; the validator re-derives `canonicalJsonDigest(state)` and compares (5q). Criterion 2's literal requirement: state whose revision matches but whose bytes differ **fails**. `expected_state_revision` is compared too (5p), because it is the CAS coordinate Phase 9 needs and the architecture names it; it was never sufficient on its own, and 5s is now what makes the pair complete rather than merely necessary.
- **`predecessor.checkpoint_digest`** — 5h still proves `chain[0]` claims the same predecessor the wrapper does. Resolving that digest against the retained `manual/checkpoints/<revision>-<digest>.json` file still belongs to Phase 9, which reads files. What changed is that this is no longer load-bearing for criterion 2: 5s correlates the *state* to the predecessor without reading anything.

**Two further clauses the intended definition assumed and the shipped fields do not supply. FINDING, continued.**

- **5m — `expected_state_revision === predecessor.revision`.** Without it a wrapper may declare `predecessor {revision: 3}` alongside `expected_state_revision: 57`: 5e and 5h fix `chain[0].revision === 4`, and nothing then rejects resuming a chain at revision 4 onto a state sitting at revision 57. The correlation is only meaningful because **checkpoint revisions and state revisions are one monotonic space** — `architecture.md:79`: "Both routes begin at no-state/revision-sentinel-0 and establish initialized/revision-1 authority before adopting any later checkpoint." A state at revision R is the state that adopted the checkpoint at revision R; so the state a continuation import expects to find must be at exactly `predecessor.revision`. It is a **validator sub-rank, not a Zod-only `.superRefine`**: JSON Schema cannot express cross-field equality, so a Zod-only rule would make the mirror strictly stronger than its normative authority and break the "S and Z always agree" property `assertZodAgreement` enforces. It presupposes 5h — correlating `expected_state_revision` against a `predecessor` the chain does not actually claim would report a mismatch that is not one — which is why it is ordered after it, exactly Phase 7's "7d–7h presuppose 7a" reasoning. **It is ordered immediately after 5l and before every state clause**, and that placement is load-bearing rather than cosmetic: both operands are wrapper fields, so 5m must be able to fire on a continuation wrapper carrying **no** `state` slot. Ordered after 5n instead, such a wrapper would always report `import-continuation-without-state` and stop — `ProjectResult` carries exactly one error and the first failing clause returns (`durable.ts:190-195`) — so 5m would be unreachable for the very subject it exists to reject.
- **5t — `continuation` with state ⇒ `chain[0].initialization_digest === state.initialization_digest`.** Criterion 1 is otherwise **not met in continuation mode**, and the gap is structural rather than incidental. Rank 7a fires only when `isInitialization(artifact)` (`durable.ts:355`), which is `false` for the wrapper; 5i–5k fire only in `initial` mode; 5l proves only that the chain is internally consistent about *some* initialization. So a `continuation` import whose every checkpoint names a **different** initialization than the state it is being applied to validates cleanly. `expected_state_digest` does not rescue it: that field is supplied by the same untrusted wrapper, so a correct `expected_state_digest` and a wrong chain `initialization_digest` coexist happily — the wrapper simply describes the state accurately and the chain wrongly. 5t is the binding, and it is last because it presupposes both 5l (the chain agrees with itself) and 5n (a state exists to compare against).

**5r and rank 7b split one concept, deliberately.** 5r compares `state.repository_identity_digest` to the wrapper's at rank 5; the *task* comparison is the shipped rank 7b (`state.task_id === artifact.task_id`, `durable.ts:360-362`), reporting `artifact-task-id-mismatch` at rank 7. A state mismatching on **both** therefore reports the repository-identity error and buries the more fundamental task mismatch. Rank 7b is **not** moved: D-B's whole value is that rank 7 stays byte-identical, and moving a shipped clause to satisfy a reporting preference would forfeit it. The consequence is recorded as a known reporting-precedence quirk rather than fixed — the task comparison is inherited from a shipped rank this phase deliberately does not touch, and both failures are rejections either way.

**Say plainly what this is.** This is tamper-*detection* under a trusted filesystem, not identity proof. An attacker who controls the filesystem can rewrite a checkpoint and its successors' digests together, and can rewrite `adopted_checkpoint` in the same pass. What the chain guarantees is that a *partial* or *inconsistent* tamper — one file changed, a chain spliced, a state swapped for one at the same revision — fails closed, which is exactly the standard the PRD sets. 5s is what makes the third of those cases actually fail closed; before it, a state swapped for a different state at the same revision passed every clause the design proposed.

**D-N — the revision-0 path permissiveness is inherited, and the schema is the tighter authority.** `src/repository/paths.ts:69` has `REVISION = "(?:0|[1-9][0-9]*)"`, so the `manual-checkpoint` path class admits `manual/checkpoints/0-<digest>.json`, while no valid chain begins below revision 1. The checkpoint schema declares its own minimum in both authorities — `const 1` on the initial branch, `minimum: 2` on the continuation branch, and `minimum: 1` on `PredecessorLink.revision` and `expected_state_revision` — and does **not** `$ref` `safeInteger`, per Phase 7 D8 (`safeInteger` admits `0`). The permissiveness is recorded as inherited and not fixed here: `src/contracts/**` may not import `src/repository/**` (`test/contracts/repository-boundary.test.ts:27-38`), so the schema is the only authority that can tighten it at this layer, and narrowing the path class itself belongs to Phase 10.

**How the checkpoint union narrows — `revision === 1` does not, and every consumer must know it.** `SafeInteger` is `number & { readonly [safeIntegerBrand]: true }` (`evidence.ts:24`), and `1` is a member of that type, so `if (cp.revision === 1)` narrows **nothing**: both branches remain candidates and `cp.initialization` is still an error. The working discriminator is the `in` operator on the two disjoint-presence fields:

```ts
if ("initialization" in cp) { /* cp: InitialManualCheckpointV1 */ }
if ("predecessor" in cp)    { /* cp: ContinuationManualCheckpointV1 */ }
```

`checkpointSelfBreak`, sub-ranks 5e and 5i–5k, the selector's head test, and D-B's step 4 are all written against `"initialization" in cp` / `"predecessor" in cp`, never against `revision === 1`. **Every `in` test has an else branch, and all three are pinned here rather than left to the implementer.** Narrowing on presence means each clause below has a reachable path the obvious reading skips, and D-B's vacuity proof depends on one of them:

- **`chainHeadBreak`, continuation mode, `!("predecessor" in first)`** — returns `"import-head-predecessor-revision-mismatch"`. **Guards and orderings the table compresses.**

- **Each collection-walking sub-rank is a complete separate pass over `chain`.** Sub-rank precedes index in the pinned order, so **each of 5c, 5d, 5e, 5f and 5l — the five sub-ranks that walk `chain` with index `i` — is a complete walk that finishes before the next one begins, and combining two of them into one loop is a defect** — not a stylistic choice. (5g–5k and 5t read `chain[0]` only and 5m–5s read no chain element at all, so the rule has nothing to say about them; 5g and 5h are additionally pinned to a single function each.) A single fused loop would report the *first offending element*, not the *lowest sub-rank*: a chain violating 5d at index 0 and 5c at index 1 must report `import-chain-task-id-mismatch`, and a fused loop reports `import-chain-repository-identity-mismatch`. Phase 7's precedent is explicit and is the model to copy — ranks 6c/6d and 6e/6f are written as **four separate loops** over the same two collections (`durable.ts:322-345`) for exactly this reason. Verification step 6's "one violation at a time" cannot catch a fusion, because it never presents two, which is why step 7 carries the cases separately — and it carries **five** pairs, not three. The counter-review was right that three were not enough: the first draft's c↔d, e↔f and c↔l witnesses leave a **5d+5e** fusion and a **5f+5l** fusion passing every prescribed test. In the order `c, d, e, f, l` the adjacent pairs are (c,d), (d,e), (e,f) and (f,l); the five witnesses now cover all four of those plus the non-adjacent (c,l), which is the strongest claim a witness set of this shape can support. **Why four adjacent witnesses cover every fusion, including the non-adjacent ones.** Each adjacent witness pins the relation *every check of x precedes every check of y*, and that relation is **transitive**, so the four together pin the whole order `c ≺ d ≺ e ≺ f ≺ l`. A fusion interleaves two sub-ranks by index, and no placement of the passes between them can be reconciled with that order. Fusing 5c and 5e into one loop while 5d stays a separate pass is the case that shows why the naive argument ("a non-adjacent fusion also fuses an adjacent pair") is simply false — it fuses no adjacent pair — and the transitive one still catches it: run the 5d pass **before** the fused loop and every 5c check now follows every 5d check, so the (c,d) witness reports `d`; run it **after** and every 5e check precedes it, so the (d,e) witness reports `e`. Either way a pinned witness fails.
- **Identity runs first (D-G), at every level it applies.** 5c and 5d precede every linkage and digest clause, so a chain assembled across tasks fails as an isolation violation rather than getting far enough to look valid. 5j and 5k extend the same rule one level down, to the initialization a revision-1 checkpoint *embeds*: they are ordered immediately after 5i, because 5i is what establishes that the embedded artifact is the one `initialization_digest` names, and before 5l, so a chain carrying a foreign initialization is rejected before the chain-wide consistency walk gets a chance to declare it internally consistent. Without them the whole import proves only that the chain supplies *an* initialization, not *its own* — the counter-review's first blocker, and the same class of defect as the Phase 7 counter-review blocker that created this phase.
- **What 5e and 5f together give you for free.** 5e establishes `chain[i].revision = chain[i].predecessor.revision + 1` for every continuation checkpoint and 5f establishes `chain[i].revision = chain[i-1].revision + 1`; together they imply `chain[i].predecessor.revision === chain[i-1].revision`, so no separate clause for that is needed. 5f also subsumes ordering and duplication (contiguity implies strict increase), which is what makes D-F's substitution complete.
- **What 5e and 5h together give you.** They imply `chain[0].revision === wrapper.predecessor.revision + 1` in continuation mode, so the architecture's "chain begins at `predecessor.revision + 1`" needs no clause of its own — and this is exactly step 3 of D-B's vacuity proof.
- **5n and 5o are the semantic half of criterion 2**, and 5p–5t presuppose 5n, so a continuation wrapper with no state reports 5n and stops rather than reading an absent slot. **5m is deliberately ordered ahead of all of them**: both its operands are wrapper fields, so it must fire whether or not a state was supplied, and the only way to get that is to place it before 5n. Ordered after 5n, a continuation wrapper with no state would always report `import-continuation-without-state` and return before 5m was ever evaluated (`durable.ts:190-195`).
- **The five state clauses escalate, and the order is the escalation** (D-M). 5p and 5q ask *is this the document the wrapper describes* — revision, then bytes. 5r asks *is it this repository's*. 5s asks *did it come from this predecessor*, and it is placed after 5q deliberately: comparing `adopted_checkpoint` against bytes the wrapper has not yet committed to would be comparing against the wrong document. 5t asks *is it built on this chain's initialization*, and is last because it presupposes 5l (the chain must first agree with itself about one initialization) and 5n (a state must exist to compare against).
- **5m is ordered by what it presupposes** (D-M). It presupposes 5h — `expected_state_revision` is correlated against `predecessor.revision` only once the chain is known to claim that same predecessor — and 5h is the last clause it needs, which is why it lands immediately after 5l rather than later.
- **5s's absence check is a failure, not a skip.** `state.adopted_checkpoint` is optional in the shape, so the naive reading of an optional field — "if present, compare" — would make 5s silently vacuous on exactly the subject the human's decision exists to reject: a wrapper claiming a predecessor against a state that records adopting nothing. Field ordinal 1 is the presence test and it reports its own literal (D-M).
- **5g does not apply in continuation mode and 5h does not apply in initial mode.** The two are mode-exclusive by a structural discriminant, so they can never both be candidates.
- **Every clause reads only the materialized clone.** Rank 1's discipline is unchanged: `ownDataSlot` and `ownDataField` require both `value` and `enumerable`, then `assertPlainJson` + `structuredClone`, then the caller's object is never re-read (`durable.ts:94-132`). `checkpointSelfDigest` therefore hashes the clone, never the caller's object.

Phase 8 is that phase. The order is now:

***(rank, sub-rank, slot, collection path, index, field ordinal)***, compared lexicographically, where

For every other sub-rank it is 0.

## Success Criteria

The architecture's six, refined to be observable.

- [ ] **A chain proves its own initialization — *its own* on the two identity surfaces this phase can bind, not merely *an* initialization.** "Its own" means the embedded initialization's `task_id` and `repository_identity_digest` equal the wrapper's. It deliberately does **not** extend to the initialization's `canonical_paths`, whose three task-scoped members are bare lexical path claims that nothing in Phase 7 or Phase 8 relates to the `task_id` beside them; that surface is inherited, unbound, and Phase 10's, per Non-Goals. A revision-1 checkpoint carries the complete `task-initialization` or `legacy-import-initialization` artifact **structurally** — the initial branch requires `initialization`, the continuation branch forbids it, in JSON Schema, in Zod, and in the TypeScript union — and `DurableSemanticSubject` admits that artifact alongside the chain because the wrapper carries both in the one `artifact` slot (D-A). A chain naming an initialization whose canonical digest differs from `initialization_digest` fails with `TASK_INVALID{issue_code:"import-initialization-digest-mismatch"}` (5i). **The embedded initialization's own identity is bound to the wrapper**: a schema-valid import on task/repository A that embeds a perfectly valid, correctly digested initialization for task/repository B fails with `import-initialization-task-id-mismatch` (5j) or `import-initialization-repository-identity-mismatch` (5k) — without those two clauses the criterion would prove only that the chain supplies *an* initialization, which is what the counter-review demonstrated and REQ-26 forbids. A chain whose later checkpoints name a different initialization fails with `import-chain-initialization-mismatch` (5l); and a continuation import whose chain names a different initialization than the state it is applied to fails with `import-state-initialization-mismatch` (5t), which is the clause that makes this criterion true in continuation mode as well as initial (D-M).

  **The literal wording is satisfied by a structural substitution, and that is deliberate.** "A chain that names an initialization it cannot supply" produces **no `issue_code` at all**, because D-A makes it *uninhabitable*: an initial-branch checkpoint requires `initialization`, so a document that names one without supplying it is rejected at the caller's parse boundary by `additionalProperties: false` + `required`, in all three authorities, before the validator runs. 5i, 5j, 5k and 5l detect a **wrong** initialization, not a **missing** one. No stable error literal exists for the missing case and none is added — a structural impossibility is the stronger result, and this note exists so a reviewer does not read the missing literal as an oversight.
- [ ] **Every accepted import begins at revision 1 or names an authenticated predecessor target, and supplied state is correlated to that exact predecessor by digest.** Initial mode: `chain[0].revision === 1` (5g). Continuation mode: `chain[0].predecessor` equals `wrapper.predecessor` in both fields (5h), and with 5e that gives `chain[0].revision === predecessor.revision + 1`. `expected_state_revision` and `expected_state_digest` are present exactly in continuation mode **structurally**, and the correlation to a supplied `state` slot is exactly 5n and 5o. **State whose revision matches the predecessor but whose digest does not fails**: 5p compares the revision and 5q compares `canonicalJsonDigest(state)` against `expected_state_digest`, and the corpus contains a subject that passes 5p and fails 5q. **The predecessor target is a revision coordinate, not a free-floating one**: 5m rejects a wrapper whose `expected_state_revision` does not equal `predecessor.revision`, so a chain cannot be resumed at revision 4 onto a state at revision 57 — and because 5m runs ahead of 5n it rejects such a wrapper whether or not a `state` slot was supplied. **And the state is correlated to the exact predecessor checkpoint, never by revision alone** (`architecture.md:554`): 5s requires `state.adopted_checkpoint` to be present and to equal `wrapper.predecessor` in both revision and digest, so the D1-versus-D2-at-the-same-revision substitution — state that actually came from D2, presented against a wrapper naming D1, with a correct `expected_state_digest` — **fails**, where before this revision it passed every clause the design proposed. A state recording *no* adopted checkpoint fails too, with its own literal, rather than skipping the check. **The criterion is met for every import these two formats can express, and one entry path they cannot is stated rather than smoothed over**: a task the server committed before any checkpoint existed has neither an `adopted_checkpoint` nor a predecessor to bind to, so it can begin no manual chain at all. That is a known unsupported path, owned by Phases 9 and 17, and it must be resolved before Phase 17 ships (D-M, Non-Goals).
- [ ] **Every checkpoint's task and repository identity equals the wrapper's**, checked by 5c and 5d as the **first** two clauses of the import block. A chain assembled from two tasks' checkpoints whose digests all link correctly fails with `import-chain-task-id-mismatch`, not with a linkage error and not by validating. A supplied state whose repository identity differs from the wrapper's fails with `import-state-repository-identity-mismatch` (5r), and an embedded initialization belonging to another task or repository fails at 5j/5k. Two further facts are recorded rather than fixed: 5c, 5d, 5e, 5f and 5l are **separate consecutive passes** over `chain`, so a chain violating 5d at index 0 and 5c at index 1 reports 5c; and the *task* comparison against a supplied state is the shipped rank 7b, not a rank-5 sub-rank, so a state mismatching on both task and repository identity reports 5r and buries 7b — a known precedence quirk, deliberately not fixed because rank 7 stays byte-identical (D-M).
- [ ] **Predecessor gaps, self-digest mismatches, reordered or duplicated revisions, and unknown fields fail with stable errors, and the greatest valid chain is identified without consulting server state.** Gaps and reordering: 5f (`import-chain-gap`). Self-digest: 5f's second field (`import-predecessor-digest-mismatch`), computed by re-deriving `checkpointSelfDigest` — no stored field exists to compare (D-D). Duplicated revisions: structural, `x-archflow-unique-by`. Unknown fields: structural, `additionalProperties: false` and `.strict()`, rejected at the caller's parse boundary and never inside the validator. **The greatest valid chain is `selectGreatestValidChain(anchor, candidates)`** — a pure exported selector over an *unordered candidate collection*, returning a chain (possibly empty, which is "nothing advances this anchor" and not an error) or an explicit `gap` / `fork` / `foreign-candidate` stop, reading no file and consulting no state (D-H). **Three outcomes, one per named requirement** — `:320`'s chain gap, `:320`'s ambiguity against `:261`'s definite article, and REQ-26's isolation — with `no-valid-successor` dropped as an outcome no requirement names (m7). The first draft's prefix truncation over `wrapper.chain` could not satisfy this criterion and is removed: given `A@1` with `B@2` and `C@2` both validly linking to `A`, it returned a full "greatest" chain from either input and never reported that authority was ambiguous, while `architecture.md:261`, `:284` and `:320` require exactly that stop. **Completeness is keyed on the anchor's expected head revision, not on the walk's tail**, so a second, non-linking checkpoint file at a revision the chain already occupies stops with `gap` instead of being silently left behind — the collision `:320` names (m5) — while ordinary history below the head revision stays quiet. `checkpointSelfBreak` is applied to head candidates as well as successors, which is what keeps the selector and sub-rank 5e from disagreeing (D-H). Chunk 7 proves that an identity or initialization failure is a **whole-wrapper rejection and a whole-set stop, never a truncation** — the one assertion that needs both authorities, and therefore the one chunk 4 cannot own (R5).
- [ ] **`manual-checkpoint` and `manual-checkpoint-import` pass the same Ajv/Zod agreement harness as Phase 7's union-reachable shapes**, anchored on their pinned export names in `MIRRORED`, and so do the seven `$def` mirrors this phase authors plus the one it composes — **ten new `MIRRORED` rows, 8 → 18**, each enumerated in chunk 8's transcription table. `evidence-slots.schema.json` is byte-unchanged and its Zod counterpart is composed, not restated: the mirror is the shipped `currentEvidenceSetRefSchema` (`trust.ts:159`).
- [ ] **Chain invariants live in Phase 7's consolidated semantic validator, extended in place; no second semantic authority exists.** `src/contracts/durable.ts` is the only module that constructs a `ProjectError` in this phase; `durable-checkpoint.ts` exports predicates that return a break literal or `undefined` and a selector that returns a value, never a `ProjectResult`. A runtime assertion in chunk 7's corpus — every `CHECKPOINT_BREAK_CODES` member is in `Object.values(DURABLE_ISSUE_CODES)` — makes a drifted literal a test failure, without `durable.ts` taking a value import of `durable-checkpoint.js`. The corpus also asserts the complement: **no `CHAIN_SELECTION_OUTCOMES` member is in `DURABLE_ISSUE_CODES`**, because a non-advancing selection outcome is a caller's decision input and never an error the validator returns.

Additional criteria this design commits to.

- [ ] **No new error code, and no rank can throw where it is required to return.** All twenty-two failures use `TASK_INVALID` and the four new rank-4a carriers use `CONTRACT_INVALID`; the 52-code and 56-row assertions pass unchanged. - [ ] **Sub-rank dominates index, and the implementation shape proves it.** Each of the five chain-walking sub-ranks — 5c, 5d, 5e, 5f, 5l — is a complete separate pass over `chain`. **Five witness pairs prove it, covering every adjacent pair in that order plus one non-adjacent pair.** The counter-review showed three were not enough — the first draft's set left a 5d+5e fusion and a 5f+5l fusion passing everything prescribed. The five: 5d@0 with 5c@1 → `import-chain-task-id-mismatch`; **5e@0 with 5d@1 → `import-chain-repository-identity-mismatch`**; 5f@1 with 5e@2 → `import-checkpoint-revision-not-successor`; **5l@1 with 5f@2 → `import-chain-gap`**; and 5l@1 with 5c@2 → `import-chain-task-id-mismatch`.
