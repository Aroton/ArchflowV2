## Implementation Log: Phase 14 - Constitution Adjudication, Drift, and Review Fixed Point

### Decisions Made

- `src/contracts/durable-result-manifest.ts` widens `ResultManifestV1.source_artifact` to `DocumentArtifactV1 | ImplementationOutputV1 | ReviewEvidenceArtifactV1 | TriageEvidenceArtifactV1 | AdjudicationEvidenceArtifactV1`. `src/contracts/durable.ts` treats the three evidence wrappers as a distinct persisted arm: task/phase/step/fingerprint live under `.evidence`, `artifact_digest` is `canonicalJsonDigest(source.evidence)`, and the one projection is a `review`-class regular file at mode `100644` whose payload digest is the canonical rendered bytes.
- `src/contracts/durable.ts` and `src/contracts/mcp-tools.ts` widen `DurableArtifact` / `archflow_state.artifact` from five to seven members with `review-evidence` and `triage`. Adjudication evidence is retained only through `archflow_adjudicate`; it does not enter the `archflow_state` request union. Request identity distinguishes the new `record-self-review` and `record-triage` operations.
- Evidence trust is intentionally split across the commit boundary. `createVerifiedEvidenceReference(evidence)` derives the canonical payload digest and enables brand-gated rendering before commit. `createRetainedEvidenceReference(manifest, reference)` reloads and revalidates durable result identity, while `createTransactionAuthorityLink(retained, outcome)` accepts only an authenticated committed transaction outcome and derives receipt/result/revision authority facts after commit; callers cannot supply those facts.
- `src/state/transaction.ts` binds every evidence installation to the exact consuming request. An `archflow_state` evidence installation must carry a `review-evidence` or `triage` artifact whose canonical wrapper digest equals the retained manifest source artifact; wrong tool/source/step/status/reference shapes are programmer-invariant throws, while task, repository, state, and target mismatches are classified failures. The negative suite covers every category and proves rejection writes no receipt.
- `src/state/evidence-results.ts` exports `prepareEvidenceResult(input): Promise<ProjectResult<PreparedEvidenceResult>>`, `loadRetainedEvidence(dependencies, state, phase_instance): Promise<ProjectResult<RetainedEvidenceSet>>`, `deriveCurrentEvidenceSet(retained)`, and `loadCurrentReviewSet(dependencies, authority, phase_instance)`. Preparation uses one snapshot/projection path for review, triage, and adjudication. Current-review derivation verifies exact self/counter roles, assurance/family independence, shared task/phase/subject/input/rubric/producer family, and canonical payload-digest agreement with each manifest. The loader authenticates `TransactionAuthority`, rereads canonical state, and derives the ordered verified set needed for triage without caller brands or invented receipt authority.
- `CurrentReviewSet.reviews` deliberately holds server-reconstructed verified references rather than requiring caller-authored authority links. The retained-manifest loader supplies canonical provenance and registers the assembled set in the private collection-brand registry; the alternate caller-driven `authorityQualifier.currentReviews` path continues to require `QualifiedReviewEvidence`.
- `src/state/transitions.ts` re-specifies `attempt` as the phase-instance attempt counter. Forward movement within one phase instance carries the counter, a same-step retry and a `triage|adjudicate/succeeded -> produce/running` re-entry increment it, and a new phase instance resets it to 1. Both manual-checkpoint adoption paths use the same kernel semantics.
- A succeeded evidence checkpoint must carry its matching `authoritative_results` reference. Both state-anchored continuation adoption and revision-0 initial import explicitly reject a chain that resets the phase-instance attempt counter on the next step; the initial path also proves rejection leaves state and receipts absent.
- `src/state/gates.ts` enacts the retry effects `revise`, `revise-current`, and `retry-once` as a guarded re-entry to `produce/running` at `attempt + 1`. The kernel gate seam is `resolve_gate_reentry_fingerprint(input): Promise<ProjectResult<Sha256Digest>>`: the callback derives the produce-entry fingerprint from server-owned authority, the archived gate request, and current canonical state. Gate resolution validates the exact predecessor and uses the transition planner; archive replay recognizes the already-enacted revision. `amend-upstream`, `start-base-amendment`, `revert-edit`, rejection, abort, and cancellation do not use this enactment path.
- Retry-effect archive replay validates the exact landing revision and recomputed fingerprint when the enactment revision is current; after later durable movement, the immutable request/decision binding is sufficient to return the recorded outcome. Non-enacted archived replay still requires the caller fingerprint to match durable current state.
- Phase 15 must open retry-effect `review-trigger`, `adjudication-failure`, and `material-drift` gates only at `adjudicate/succeeded`; `attempts-exhausted` may also open at `triage/succeeded`. This is a caller precondition, not a permissive fallback: an illegal placement returns `STATE_INVALID` and the decision is not archived.
- Supplemental gate-counter Markdown is a wake-up projection only. `GateLifecycleDependencies.resolve_supplemental_review({authority, request, outcome?})` supplies server-derived parsed evidence and gate identity. The gate service clones/parses it, recomputes `canonicalJsonDigest`, and verifies the exact gate/task/phase/role/subject/fingerprint/assurance/family bindings before admitting a ledger entry or reporting `SUPPLEMENTAL_REVIEW_REQUIRED`; a decline needs no resolver. Caller-authored `gate.json` entries and rendered-file digests confer no authority.
- `src/state/constitution.ts` resolves the rule registry only from `policy_base_commit` via bounded `readCommitTreeEntries`, with membership limited to `.archflow/constitution/<NN>-<name>.md`; `README.md` is excluded from the digest. `computePinnedConstitutionDigest(files)` hashes the sorted path/OID registry. Each returned `ResolvedConstitution` is registered in a private `WeakSet`; its registry, rules, nested mechanism arrays, and file list are immutable, and consumers call `assertResolvedConstitution` before accepting it as authority. Task-local edit detection combines worktree/index changes with `policy_base_commit..HEAD`; the HEAD comparison digest uses numbered-file membership and OIDs directly and does not parse the edited registry, so deleting every rule or making one unparsable still opens `constitution-edit`.
- `src/state/fingerprint-readers.ts` supplies the first production `InputFingerprintResolver`: immutable workflow and constitution readers plus current artifact, upstream, and declared-input readers. Phase 16 task initialization must use the same pinned-constitution digest function; it must not duplicate the formula.
- `src/review/envelopes.ts` adds a domain-separated, size-bounded adjudication envelope; `CliAdapter.buildInvocation(envelope, route, workspace, outputSchema)` makes the output contract explicit. Automatic same-family adjudication fails before launch; checkpoint-backed manual adjudication remains the only degraded same-family path.
- `src/review/adjudication.ts` cross-checks every active pinned rule exactly once and rejects undeclared/deprecated/version-mismatched findings. A rule with no `enforced_by` may pass with an empty list. A rule that declares mechanisms cannot pass on model-asserted evidence, so it remains uncertain and gates until a later phase supplies corroborated mechanism evidence or an exact task-lifetime waiver applies. Before dispatch, `runAdjudication` rereads canonical state, loads an authentic constitution for that state's `policy_base_commit`, and requires its digest to match state, the subject pin, and the envelope rules; caller state/registry values confer no authority. It also loads an authentic current review set and requires the envelope task/phase/subject/input/source-set facts to match it. The transaction callback checks the constitution digest again before installation. Material drift is serialized as the first material upstream in approved-digest order and re-adjudicated after resolution.
- Expected adjudication failures remain inside the `ProjectResult` contract: malformed or registry-invalid child output returns `MODEL_OUTPUT_INVALID`, and a missing durable upstream approval returns `STATE_INVALID` with `upstream-approval-missing`. Neither path mints evidence or moves the revision.
- `src/review/fixed-point.ts` exports synchronous `assessCurrentEvidence(state, retained, subject)`, `requireApprovedUpstreamDigests(approvals, digests)`, and `waiverInForce(state, rule, subjectDigest, scope)`. Triage is current only when its set digest and ordered source digests equal `deriveCurrentEvidenceSet`; adjudication is current only when its source-set digest matches that same current triage/review chain, including the clean no-gate path. `EvidenceSubject.constitution` is an authentic `ResolvedConstitution`; its digest must match durable state and retained adjudication before evidence can be current or advance, and its registry supplies every adjudication obligation. The assessment walks `selectAdjudicationGates` in constitution-failure, first-material-upstream, then review-trigger order. It skips only an obligation with its exact authenticated advancing approval or every exact live waiver and advances only after all applicable categories are satisfied. Plain `ApprovalRef` values do not suffice: `loadAuthenticatedGateApproval` rereads canonical state plus the archived request/decision and mints a WeakSet-backed capability, and assessment requires each candidate's own kind/context digest plus current self/counter/triage/adjudication evidence-set bindings to match. Material gates remain serialized and their resolution requires re-entry and fresh adjudication before another material upstream can gate. A commit/publication crash, stale approval after an input/context change, authority for a different obligation, and every non-advancing closure therefore remain non-advancing. Re-entry is authorized only by durable accepted triage or stale retained adjudication, and exhaustion is checked only at re-entry with `DEFAULT_MAX_ATTEMPTS = 3` unless `ConfigV1.max_attempts` overrides it.
- `waiverInForce` is the single waiver-admissibility predicate used by fixed-point gate satisfaction. It matches the exact rule/version/subject/operation/boundary tuple and is live only while `state.terminal === undefined`.
- `test/integration/review-fixed-point-phase14.test.ts` supplies the disk-backed restart proof for the fixed point. It uses real `runStateTransaction` calls for self-review, triage, running/rewrite boundaries, and document result installation; real `runCounterReview` and `runAdjudication`; snapshot/projection installation; retained-manifest loading; and rebuilt dependencies after restart. Version 0 and version 1 each accept findings and rewrite without adjudication; only clean version 2 adjudicates and advances. The standalone integration passes, and the post-review Phase 14 gate/fixed-point/corpus/constitution/crash run passes 64/64 tests across seven files.
- The material-drift integration consumes the real two-upstream corpus results and executes the complete serialized loop: open the first sorted upstream gate, resolve `amend-upstream`, re-adjudicate, open the second upstream gate, resolve `revise-current`, and verify server-derived re-entry at the next attempt. The `revert-edit` integration likewise proves non-advancing closure followed by the existing same-step retry.

### Deviations from Plan

- The Phase 14 design described the gate re-entry fingerprint as a recomputation through the existing transaction resolver. That resolver requires a parsed tool call and live config not retained by a gate request. Implementation instead adds the narrower `GateReentryFingerprintResolver` callback to `GateLifecycleDependencies`; Phase 15 must bind it to the canonical produce-entry inputs available to the handler.
- The design's generic retry-effect description is narrowed by the implemented decision table. Only `revise`, `revise-current`, and `retry-once` enact re-entry. `revert-edit` relies on the existing same-step retry after the human removes the edit, `amend-upstream` waits for changed upstream authority/fingerprint, and `start-base-amendment` is human-external and terminates this task through `abort`.
- The source layout differs from the original architecture sketch: canonical rendering remains in `src/contracts/renderers.ts`; Phase 14 adds `src/review/fixed-point.ts` and adds constitution, production fingerprint-reader, and evidence-result services below `src/state/`.
- Phase 14 provides direct service libraries, contracts, and fake-CLI/corpus proof. It does not register live MCP handlers, expose `archflow-local`, implement the handler-owned `resolve_supplemental_review` retained-evidence loader, persist Phase 13 managed-policy telemetry, rebuild the tracked offline bundle, or initialize a task. Those remain Phase 15/16 wiring work.
- Release-quality threshold selection was not performed from the deterministic Phase 14 corpus. Phase 21 owns real-host review-quality evaluation and explicit threshold approval.

### Patterns Established

- Persisted evidence has two identities with separate jobs: `evidence_digest` / manifest `artifact_digest` is the canonical validated JSON payload digest; projection `payload_digest` / `content_digest` is the canonical rendered-byte digest.
- Validate and render evidence before commit, but derive advancement authority only after state commits the retained result. A rendered file or pre-state snapshot is never sufficient authority.
- Kernel re-entry has two layers: `assessCurrentEvidence` establishes the semantic reason from durable evidence, while `planStateTransition` and the gate re-entry planner enforce only the predecessor/attempt/fingerprint facts visible to state authority.
- Constitution membership and identity come from immutable Git trees. Worktree and commit-range path scans are edit signals only and cannot change the pinned registry or digest.
- A declared mechanism label is not executable evidence. Until server-owned corroboration exists, model assertions about that mechanism cannot produce compliance.
- A retained adjudication result and its human obligation are one fixed-point fact. Advancement recomputes the gate from retained evidence and the pinned registry; successful result installation alone never clears a required gate.
- Disposable gate interfaces are wake-up/interaction surfaces, not supplemental authority. The service must reconstruct authority from a server-owned evidence loader and authenticate every slot binding before retaining it.

### Gotchas

- Never combine `--literal-pathspecs` with a `:(top,literal)` pathspec. Phase 14's commit-tree listing and range-diff helpers use explicit repository-owned directory arguments and bounded NUL parsing.
- Evidence wrappers deliberately keep correlation fields under `.evidence`; any persisted semantic check that assumes top-level `task_id`, `phase_instance`, `step`, `input_fingerprint`, or `snapshot_digest` will either reject valid evidence or weaken agreement.
- `renderReviewEvidence` and `renderAdjudicationEvidence` print `evidence_digest`; therefore rendered bytes cannot define that digest without a cycle.
- `scripts/smoke-temp-bundle.mjs` must expect forged renderer inputs to fail as unauthenticated evidence. Rendering accepts either an authentic verified pre-commit reference or an authentic post-commit qualified reference; the older “qualified only” error text is no longer the contract.
- `ManualCheckpointV1.attempt` now means attempts consumed in the phase instance. A chain that retries and then resets to 1 on the next step is invalid.
- One shipped constitution rule declares `enforced_by`; automatic adjudication remains fail-closed for that rule until later server-corroborated mechanism evidence exists. The exact `adjudication-failure` waiver is the current human escape.
- Adjudication evidence commits before gate publication. The fixed-point `"adjudication-gate"` action deliberately covers that crash window by recreating or resuming the deterministic obligation; never interpret a committed adjudication result alone as advancement.
- The fixed-point integration injects the Phase 15-owned dispatch and evidence-preparation callbacks, but every Phase 14 service, transaction, snapshot/result installation, retained reload, and state transition beneath those callbacks is real and disk-backed.
- The final release check still inherits the three Phase 13 failures in `test/integration/release-offline.test.ts`: the tracked bundle is stale and retains the residual `__require` loader. Phase 15 owns rebuilding the tracked release payload; Phase 14 must not disguise these as adjudication failures.
