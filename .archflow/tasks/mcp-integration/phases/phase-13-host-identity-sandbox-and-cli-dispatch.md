# Phase 13: Host Identity, Sandbox, and CLI Dispatch

**Status**: COMPLETE
**Task**: mcp-integration
**Goal**: Dispatch a fresh opposite-family counter-reviewer with a declared envelope and best-effort context hygiene.
**Requirements**: REQ-26, REQ-29, REQ-30, REQ-31, REQ-32 (counter-review only), REQ-34, REQ-35
**Implemented**: 2026-07-30

## Context

Every contract this phase fills is already frozen and unimplemented. Phase 1 froze `ConnectionContext.initialization_candidates.host` and `InvocationContext.signal`; `src/mcp/sdk-adapter.ts:270` still passes the literal `"unknown"`, and nothing in `src/` reads the field. Phase 2 froze `MODEL_FAMILIES`, `ADAPTER_IDS`, `EFFORT_VALUES`, `ServerAttestedReview`, and the `ObservationSource` trust seam — whose only minter today is `createTestObservationCapability` in `src/contracts/internal/test-capabilities.ts`. `envelope_input_digest` is a required field of every server-attested review with no producer anywhere. Phase 6 gave `src/repository/git.ts` a child-process failure taxonomy (`GitFailureKind`, 8 MiB / 30 s bounds) but no environment scrubbing — the child inherits `process.env` wholesale. Phase 12 established the shape this phase copies: build the service library, leave the tool wiring to Phase 15.

Two boundaries constrain where the code may live. `test/contracts/durable-agreement.test.ts:687` forbids `node:fs`, `node:child_process`, and `src/repository/` imports from `src/contracts/`. Separately, `scripts/release-support.mjs` limits the release bundle to five `node:` builtins, and `src/main.ts` reaches `src/mcp/**`, so anything the MCP layer imports must be pure. These are *different* checks — `node:os` and `node:path` pass the boundary test and still break `build:temp`, so `npm run build:temp` is chunk 1's real guard. `src/dispatch/**` and `src/review/**` stay out of that graph; Phase 15 inherits the problem of admitting them. `src/repository/paths.ts` has no notion of a path outside the repository, so the temp workspace is new territory and must never be modeled as a `ResolvedTaskPath`.

## What We're Building

A dispatch library under `src/dispatch/`, a counter-review envelope builder under `src/review/`, and one pure host-identity module inside `src/contracts/`. **Isolation here is best-effort context hygiene, not an enforced or proven boundary, and nothing below should be read as claiming otherwise.** Suppression flags, a generated clean home, and a temp cwd outside the repository are cheap measures that keep producer history, prior findings, repository content, and global agent instructions out of the reviewer's input — which is what review contamination actually costs us, since a reviewer that discovers the PRD, architecture, and producer notes is no longer the independent check VAL-02 exists to test. They are not a containment guarantee. Claude's `--tools ""` is a single allowlist-shaped flag and genuinely strong, but Claude managed *hooks* execute shell independently of model tools and survive `--safe-mode`. Codex has no equivalent flag at all: `codex features list` on 0.146.0 reports `multi_agent`, `browser_use`, `browser_use_full_cdp_access`, `computer_use`, `image_generation`, `apps`, `hooks`, and `in_app_browser` all stable-by-default, `view_image` resolves and reads a model-supplied path, and `apply_patch` registers when the model supports it — so the Codex suppression list is a **denylist against a registry that turns over every ~3 days with no stability policy**, the same shape this design rejects for environment variables. The surface is also not inspectable: `codex debug prompt-input` renders the model-visible input message list, not the request's `tools[]`, and there is no `codex debug tools`.

The owner has accepted that risk on the basis of extensive manual counter-review experience, explicitly allowing that results may be slightly worse, and has ruled out machinery to enforce or verify a boundary. So this phase builds the plumbing and nothing more: derive host identity and family, resolve a route, build one versioned bounded counter-review envelope and digest it, spawn a child with a scrubbed environment and classified failures, substring-scan its output for planted canaries as a regression test, and mint the first production `ObservationCapability`. There is no sandbox provider, no dispatch-gating probe, and no environment declared unsupported. **Phase 13 adds no dependency, no new error code, and no dependency-policy or notices change.**

## Work Breakdown

Interfaces that cross chunk boundaries are pinned by name so the seams stay coherent; everything else is the implementer's call.

1. **Host identity and the plug point**: `deriveHostIdentity(client: {name, version}): "claude" | "codex" | "unknown"` in `src/contracts/hosts.ts`, driven by recorded real handshakes rather than substring guessing, plus the caller-side mapping of `"unknown"` to `UNSUPPORTED_HOST` before any dispatch. Wire it at `sdk-adapter.ts:270` and run `npm run build:temp` and `npm run check:phase4-mcp-boundary` immediately — the release bundle breaking is the specific regression the purity constraint exists to prevent, and the boundary test will not catch it.

2. **Routing and family validation**: `resolveDispatchRoute(config: ConfigV1, phaseKind, role: RoutingRole, producer_family: ModelFamily): DispatchRoute` in `src/dispatch/routing.ts`, where `DispatchRoute` carries `adapter: AdapterId`, `family: ModelFamily`, `model: string`, and `effort: (typeof EFFORT_VALUES)[number]` — **not** `DeclaredEffort`, which includes `"unknown"` that `ObservationBindingBase.effort` rejects and a route from validated config can never be. Resolution is `overrides[phaseKind][role]` then `roles[role]`; every role is optional, so an absent role for a dispatched step is a classified error launching nothing. Family is derived here (`config.yaml` carries `model` + `effort` and no family) and checked with the newly exported `assertAdapterFamily`. Do not conflate the two vocabularies: `ROUTING_ROLES` says `"counter-reviewer"`, `REVIEW_ROLES` says `"counter-review"`. `EFFORT_VALUES` includes `"ultra"` which Claude does not accept, and unknown Codex effort strings pass through silently, so effort is validated against the selected adapter. Same-family counter-review is `FAMILY_MISMATCH` and launches nothing.

3. **`DispatchSubject` and the counter-review envelope**: `buildReviewEnvelope` returning `DispatchEnvelope { bytes, digest, byte_count }` over the pinned subject, with ID parsing, the `dispatch-envelope` digest, and the 1 MiB cap. Nothing about the producer session, prior findings, triage, upstream documents, repository content, or agent instructions may be representable in the envelope type — REQ-32's guarantee should be a property of the shape, not the caller's discipline. Leave the two Phase 14 extension points named in comments and build neither.

4. **Workspace, credentials, and scrubbed environment**: `createDispatchWorkspace(adapter): Promise<DispatchWorkspace>` with `{ root, home, env, dispose() }`, generated defaults plus the credential symlink only. Linux behavior is already established; the **only** experiment is macOS — record whether Claude authenticates from a generated `HOME` given a Keychain-backed store, and settle it in the implementation log rather than pre-building a fallback that would surrender the clean home. Build `env` from the pinned allowlist. This is the first environment scrubbing anywhere in `src/`.

5. **Process lifecycle, bounded channels, and the canary scan**: `runDispatchChild(spec): Promise<DispatchChildResult>` in `src/dispatch/process.ts` against the pinned bounds, treating stdout/stderr and the Codex `-o` file as separately bounded channels. Restate the small spawn-error mapping (`ENOENT`→`CLI_MISSING`, `EACCES`/`EPERM`→not-executable, maxBuffer→`OUTPUT_OVERFLOW`, killed→`TIMEOUT`) locally — `classifySpawnFailure` at `git.ts:154` is module-private, a precedent rather than an export. `scanDispatchOutput` lives here.

6. **The two adapters**: `CliAdapter { id, family, preflight(workspace), buildInvocation(envelope, route, workspace), parseOutput(result), classifyFailure(result) }` and its two-arm selection in `src/dispatch/cli.ts`, both pinned invocations side by side. `parseOutput` implements the per-adapter output contract: Claude extracts and re-encodes `structured_output` from the CLI wrapper; Codex reads the bounded `-o` file. **Codex semantic classification is event-only and is the most fragile part of the phase**: `codex exec` has exactly one failure exit (`if error_seen { exit(1) }`), so pin one JSONL decoder and this precedence — classify semantic failures *only* from the message inside a valid terminal or fatal event (`turn.failed`, top-level `error`), deduplicate a top-level `error` followed by `turn.failed`, treat stderr as diagnostic and canary-scan input only, and map a nonzero exit with no recognized failure event to `PROCESS_FAILED {adapter, exit_class}`. Otherwise an unrelated startup warning on stderr becomes `RATE_LIMITED`. On the Claude side, since 2.1.183 deprecated-model warnings go to stderr in print mode, so **non-empty stderr is not failure**; `--permission-mode default` was relabelled `manual` in 2.1.200 with both accepted. Pin full model slugs: Codex fabricates synthetic metadata for unknown slugs with only a warning and fails late at the network.

7. **The attestation mint**: `mintReviewObservation(...)` builds the `ObservationBindingByKind["review"]` from the same `DispatchSubject` the envelope used plus the observed adapter, CLI version, route, and digests, passes it to `createReviewObservationCapability`, and calls `observationSource.observeReview(capability, bytes)` on the extracted output bytes. Be precise about what the seam checks: the eight-field loop compares the **child's JSON** to the binding, so it catches a child that failed to echo the subject; `adapter`, `cli_version`, `family`, `model`, `effort`, `invocation_id`, `envelope_input_digest`, and `result_id` are copied from the binding with no cross-check (`trust.ts:104`), so route-derivation correctness is chunk 2's job and this chunk's tests.
