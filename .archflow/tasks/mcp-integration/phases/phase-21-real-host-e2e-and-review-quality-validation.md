## Context

Twenty phases proved every invariant this system has against fake CLIs, in-process services, and injected faults. About 1,681 tests across 153 files run offline in under a minute, and none of them has ever executed the real `claude` or `codex` binary, run the installed bundle, or asked a model to judge an artifact. Phase 21 is a validation phase, not a feature phase: it runs the same contracts against the actually installed hosts and a real installed bundle, measures whether opposite-family counter-review finds real defects, and produces a truthful account of which VAL IDs are proven, which are partial, and which are blocked. Phase 22 consumes that account for release packaging and the published support matrix.

The real surface has already been probed on this machine and it matches what the code expects. `claude` is 2.1.221 printing exactly `2.1.221 (Claude Code)`; `codex` is 0.146.0 printing `codex-cli 0.146.0`; both parse under the shipped anchored regexes and clear the 2.1.205 and 0.122.0 floors. `claude auth status` exits 0 with `"loggedIn": true`, `codex login status` prints `Logged in using ChatGPT`, and every argv flag either adapter builds still exists on the real CLI. A currency review confirmed both installs are exactly the current releases, that `claude-opus-5` and `gpt-5.6-sol` are current non-deprecated slugs, that `high` and `xhigh` are valid efforts, and that the `@modelcontextprotocol/server@2.0.0` pin is npm `latest`. Node is v24.18.0. The consequence is decisive: **this phase is overwhelmingly run, observe, and record — not repair.** Source changes are contingent on what the probe finds, not planned up front.

Three things remain genuinely unverified and are the probe's real job. First, whether the real CLIs accept the configured model slugs in practice — `openai/codex#35148` reports `Unknown model: gpt-5.6-sol` on codex-cli 0.145.0, one release before the installed 0.146.0, so a slug failure here is a client bug to look up rather than an invalid pin. Second, the MCP era. Protocol revision `2026-07-28` shipped on 2026-07-28 and removes the `initialize`/`notifications/initialized` handshake, moving `clientInfo` into per-request `_meta`; both installed clients carry it alongside `2025-11-25`, which this server pins. Auto-negotiation is expected to fall back to the legacy era, because the server answers a pre-`initialize` request with `-32600` and anything not positively recognized as modern falls back — but the fallback works by **spawning a short-lived sibling probe process**, so every real host connection starts the server twice and the probe child's stderr is discarded. Any PID, process-count, or startup-side-effect assertion must tolerate that second spawn, and whether `clientInfo.name` still arrives at all is now a question with a named cause rather than an open one. Third, one cheap incidental check rides along: `claude auth status` prints real PII (`email`, `orgId`, `orgName`, `subscriptionType`) on stdout, so confirm none of it reaches a persisted attempt record. The preflight reads only `loggedIn` and the attempt record carries `cli_version` and managed-policy fields rather than raw stdout, so the expected result is "already clean" — record it, build nothing for it.

## What We're Building

Three layers, deliberately different in kind. The first is an **opt-in real-CLI suite** under `test/real-host/` — the parts a machine can assert against real binaries: version and auth preflight shapes, both dispatch directions through real production services, the failure classes a real CLI produces cheaply, and machine-checkable journey slices driven through the *installed* launchers. It is inert without CLIs so `npm run check` and CI stay hermetic and offline. The second is a **review-quality benchmark**: a measurement, not an assertion. It runs real opposite-family review over a small corpus of real prose artifacts and reports detection and false-blocker rates; the human approves release thresholds from what is observed. It lives in the same opt-in suite rather than as a `scripts/*.mjs`, because `src/` uses NodeNext `.js` specifiers that Node's type stripping cannot resolve — the only established way for a plain `.mjs` to consume `src/` here is to esbuild-bundle it first, and Vitest already transpiles TypeScript natively. The third is **operator-executed journeys** — VAL-01 in both producer directions and VAL-12 server-absent manual — which require a real interactive agent session driving the real skills through real human gates. No test can stand in for that without fabricating the human. These are a written runbook plus recorded evidence: human wall-clock that delegation cannot compress, and evidence that is a recorded observation of a real run rather than a rerunnable assertion.

Explicitly not built. No new MCP tool, gate kind, error code, durable schema field, runtime dependency, or workflow-graph change. No new test framework, matrix runner, or fault-injection subsystem — and no benchmark or eval library: the computation is a count of seeded cases with at least one blocking finding over total, and the same over clean controls, which is arithmetic. No implementation of `server/discover` or the `2026-07-28` stateless era; this phase observes which era each real client negotiates and records it, and the twelve-month deprecation window leaves adoption to Phase 22 or later. No extension of `release/evidence/` or `release/legal-review.json`: that directory is a fast-uri-legal-specific instantiation whose every record is bound from `legal-review.json` through `resolveEvidence(binding, expectedPath, recordType)` against expected path constants, so unbound files dropped there risk breaking `check:release` — **all Phase 21 outputs go under `docs/validation/`, which no release or build script reads.** No OS containment or sandbox provider; VAL-07 stays partial and owner-accepted. No attempt at VAL-14, which is external and Phase 22 reports. No re-proof of what earlier phases already proved with fakes — the value here is the real binary and the installed bundle, not a second copy of an existing assertion. No per-call timeout or byte-cap override added to `src/dispatch/` merely to make a real-CLI timeout test cheap; a real `TIMEOUT` costs 300 s of a real model call, so record it as fake-only coverage. No committed assertion about which managed-policy files happen to exist on one developer's machine — Phase 20 already reasoned that class of test out of scope, because it asserts an operating-system fact that no ArchFlow change can alter. No generic secret detector, no entropy heuristic, and no CI integration of the real-CLI suite — CI installs Node only and has no credentials, by design.

## Work Breakdown

1. **Real-host gate and shared seams.** Both seams land here, fully pinned, because chunks 2, 3, 4, 6, and 8 are separate implementation units that share them and must not each invent one.

   `test/helpers/real-host.ts` exports, at minimum: `realHostsEnabled(): boolean`, `benchmarkEnabled(): boolean`, `realHostsAvailable(): boolean`, and named timeout constants with numeric separators (real model calls are far slower than the 5 s vitest default). **`realHostsAvailable()` must return `false` unless the explicit opt-in environment variable is set, and must not probe binaries or auth at all when it is unset.** Availability alone is the wrong gate: `vitest.config.ts` includes every `test/**/*.test.ts` in ordinary `npm test`, and on the developer machine this phase targets both CLIs are installed and logged in — so an availability-only guard would fire real model calls and consume subscription quota on every plain `npm test`, breaking exactly the hermetic default this phase promises. The opt-in comes first; the availability probe only decides whether an opted-in run can proceed. The benchmark sits behind its own second opt-in so `npm run test:real-host` stays short. The predicate is **synchronous** (`execFileSync`, its own version and auth probes, not the async `preflightAdapter`, which requires a `DispatchWorkspace`), captured once at module scope and passed to `describe.skipIf(...)` in the established style (`test/unit/repository-git.test.ts:45`). An async predicate returns a Promise, which is always truthy, silently making every real-host suite either always-skip or never-skip.

Chunks 3 and 6 both consume it; the shipped template carries only the Claude-producer orientation, so without it neither can construct the Codex-producer direction.

5. **The real-artifact corpus.** Build a small corpus under `test/fixtures/corpus/artifacts/`: roughly three documents each carrying one seeded *substantive* defect that should require producer action — a requirement contradicted later in the same document, a stated error path with no handling, an assumption that violates a stated constraint — and roughly three clean controls that are genuinely good, plus a manifest. These are real prose artifacts a reviewer must judge, deliberately unlike Phase 14's canned reviewer outputs, where the "seeded defect" is the literal token `DEFECT-SEED` in a pre-written verdict. That choice removes the anchor a script could match on. **The approval metric is therefore computed from a recorded human disposition per run, not from verdict shape.** A machine cannot match a model's free-text finding against a free-text defect description, and counting "any `fail` with any blocking finding" as detection is actively wrong: a reviewer that misses the seed entirely and raises an unrelated blocker would *improve* the approved detection rate. The manifest pins, per case, the seeded defect in prose for the human to match against, and the disposition vocabulary each run is classified under — at minimum seed-detected, unrelated-blocker, and missed for seeded cases, and clean-pass versus false-blocker for controls. Raw verdict and blocking-count rates are retained as secondary telemetry only. Keep the corpus small: a human dispositions every run, so this is a benchmark, not a dataset.

6. **The benchmark run.** `test/real-host/review-benchmark.test.ts` runs each case through real opposite-family counter-review in both directions with a small repeat count, recording per run the verdict, blocking-finding count, and the findings themselves. It writes `docs/validation/review-benchmark.json` with a disposition slot per run left unset, and asserts no threshold. It consumes chunk 1's config override, since both producer directions are required. It is a Vitest file rather than a `scripts/*.mjs` because the counter-review path is TypeScript under `src/` behind NodeNext `.js` specifiers that Node cannot resolve directly, and bundling it with esbuild first would add a build step for no gain. Gate it behind its own opt-in; `bench:review` is the script that runs it. Budget the wall-clock explicitly: every dispatch goes through the one process-wide FIFO in `serializeDispatch`, so cases × directions × repeats is the serial call count and each call is a real model turn.

   The PRD's review-quality requirement names four measures, and two of them are observations rather than rates: **triage completeness** — that an actual run dispositions every current finding exactly once — and **defects found after pass**, which here is the count of seeded cases a passing review missed, derivable from the same dispositions. Record both explicitly; a benchmark reporting only detection and false-blocker rates does not satisfy the requirement. Depends on chunks 1 and 5.

## Verification Steps

Run `npm run typecheck`. Then confirm `npm test` and `npm run check` pass **unchanged** with the real-host suites skipping. Run this check twice, because the two failure modes are different: once with the opt-in unset and **both CLIs still installed and logged in** — the ordinary developer case, where an availability-only guard would silently spend subscription quota — and once with both binaries off `PATH`. Watch for model calls, not just a green result. Then run `npm run test:real-host` with the opt-in set, and `npm run bench:review` as a separate, long, second-opt-in measurement.

Wall-clock is the dominant risk. Every dispatch is serialized through one process-wide FIFO and each is a real model turn, so the benchmark is by far the longest thing in this phase and must be started well before it is needed. The 5 s vitest default timeout will fail any real-host test that omits an explicit timeout — there is no global `testTimeout` in `vitest.config.ts`, so every real-host test sets its own.

Real dispatch consumes the developer's own subscription quota. **Scratch installs must override `HOME` in the child environment, not only `ARCHFLOW_HOME` and `ARCHFLOW_BIN`** — `install.sh:8-9` derives its skill targets from `$HOME` and `install_skills` deletes stale manifest entries before copying, so overriding only the two `ARCHFLOW_*` variables destroys the developer's real `~/.claude/skills` and `~/.agents/skills`. Verify those two directories are unchanged after any run that invokes the installer. Journey scratch repositories must live outside this repository so its own `.archflow/` is never polluted. Do not run `forced_login_method` or anything else that would rewrite the developer's `auth.json`.

## Amendment 1: Review-Rubric Recalibration (2026-08-04)

**Trigger.** The chunk-6 benchmark (observation digest `61f6b56b0ac92c587c5312f12c3c7babcfd29d1925206d14fa07b81f7c221eea`) measured perfect detection — all six seeded defects caught in both directions, zero defects found after a pass — but an 83.3% human-confirmed false-blocker rate on clean controls. The user rejected thresholds per chunk 7's escalation rule, blocking VAL-02 and reopening the automation premise. The user has now approved this recalibration as the revised review approach; the alternative — demoting counter-review to advisory-only evidence — was considered and deferred, not chosen.

**Diagnosis.** Every observed false blocker cites a stated acceptance criterion from the artifact — citation is not what separates them from the seeds. What separates them is *how the violation is derived*: each false blocker reaches its contradiction only by importing an assumption the artifact never states (an assumed sweeper/commit interleaving, an assumed validator pointer behavior for structural keywords, a demanded coverage boundary outside the artifact's stated scope), while every seeded defect follows from the artifact's own text alone — the document contradicts itself, drops a handling path its own contract names, or violates its own stated constraint. The current rubrics give the reviewer no burden of proof distinguishing those derivations, no statement that a clean pass is the expected outcome for sound work, and no non-blocking outlet, so debatable readings inflate into blockers. The production rubrics embedded in the four skills carry the same defect in stronger form — every criterion is blocking, and wording like "integration boundaries are explicit" invites completeness demands. Detection does not need repair; blocking calibration does.

**Decision.** Recalibrate the rubric criterion bytes and re-measure. No schema, envelope, server, corpus, or dispatch change of any kind: `RubricV1` already carries per-criterion `blocking` and free text, which is the entire surface this fix needs. The calibration reaches the reviewer inside existing criterion text (optionally including an added `blocking: false` advisory criterion); exact wording is the implementer's call subject to the content requirements below.

**Calibration content requirements.** Every recalibrated rubric must convey, in whatever wording fits its criteria:

1. A blocking finding must cite the specific artifact statement it contradicts or the stated requirement it leaves unmet — necessary, but not sufficient on its own.
2. The violation must follow from the artifact's own text without importing an assumed implementation behavior, ordering, or environment the artifact does not specify. A contradiction that only materializes under such an imported assumption, or a debatable reading of whether stated text satisfies a stated criterion, is at most advisory.
3. Absent handling for a condition the artifact does not claim to cover is not a defect unless a stated requirement demands that coverage. Local edge-case handling belongs to the implementer, not the reviewer.
4. A sound artifact yields zero blocking findings; that is the expected outcome for good work, not an under-performed review.
5. Non-blocking findings are the outlet for completeness suggestions, debatable readings, and observations, so they are not inflated into blockers for lack of anywhere else to go.

**Scope.** Modify the benchmark rubric in `test/real-host/review-benchmark.test.ts` and the four production rubrics embedded in `skills/archflow-prd/SKILL.md`, `skills/archflow-design/SKILL.md`, `skills/archflow-phase-design/SKILL.md`, and `skills/archflow-phase-impl/SKILL.md`. The benchmark rubric and the production rubrics must carry the same calibration language so the measurement transfers to production behavior; the duplication between a TypeScript literal and four markdown documents is accepted for this prototype and noted in the log. The skill contract test requires each skill's rubric to remain a single-line JSON block, so the recalibrated production rubrics stay one-line literals.

**Re-measure protocol.** Same corpus bytes (artifact digests unchanged), same 12-run matrix and serialized budget as chunk 6. The new observation payload replaces `docs/validation/review-benchmark.json`; the failed measurement is preserved by git history and the implementation log, and its digest recorded above. Human dispositions bind to the new observation digest, and thresholds are recorded only on explicit approval exactly per chunk 7. The VAL-02 row in `docs/release-validation.md` — currently blocked and bound to the superseded digest — is rewritten from the new dispositioned result, whichever way it lands (passed with approved thresholds, or escalated-blocked), so the coverage report Phase 22 consumes never cites a digest the benchmark file no longer carries. **Stopping rule:** if the re-measured false-blocker rate is still unacceptable to the human, that second measurement is decisive for this phase — it is escalated as the premise decision (advisory demotion or another user-chosen direction), never answered with a third wording iteration inside Phase 21.
