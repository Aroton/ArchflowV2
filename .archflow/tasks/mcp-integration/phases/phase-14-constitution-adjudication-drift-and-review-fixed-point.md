# Phase 14: Constitution Adjudication, Drift, and Review Fixed Point

**Status**: COMPLETE
**Implementation Date**: 2026-07-30
**Task**: mcp-integration
**Goal**: Turn validated reviewer output and pinned policy/upstream inputs into current-digest advancement evidence.
**Requirements**: REQ-10, REQ-11, REQ-12, REQ-13, REQ-15, REQ-16, REQ-17, REQ-18, REQ-19, REQ-20, REQ-32, REQ-33

## Context

Phase 2 froze every semantic contract this phase consumes and Phase 14 re-models none of them. `parseAndDeriveReview` already recomputes `verdict`/`blocking_count` and refuses server-attested self-review; `validateAdjudicationClaims` already folds `fail > uncertain > pass` and `material > incidental > aligned` and already forces `drift_findings` to cover `approved_upstream_digests` exactly — **separate compliance/drift verdicts are contract facts, not new work**. `validateTriage` already enforces exact once-only coverage against a server-minted `CurrentReviewSet`. `observationSource.observeAdjudication` is fully implemented and has never been called. Phase 12 froze the gate lifecycle including the exact `attempts-exhausted`, `constitution-edit`, `material-drift`, and `adjudication-failure` contexts and decisions; Phase 14 decides *when* to open which gate and re-implements no gate mechanics. Phase 13 built dispatch for counter-review only and left two named extension points in `src/review/envelopes.ts`.

Five gaps make this phase load-bearing rather than assembly. **Nothing computes `constitution_digest`** and nothing resolves rules from `policy_base_commit`. **`createInternalInputFingerprintResolver` has no production readers**, so no real transaction can run today. **Evidence results cannot be retained**: `ResultManifestV1.source_artifact` admits only `DocumentArtifactV1 | ImplementationOutputV1`, `durable.ts:583-593` forces a document-backed manifest's single output to `path_class === "document"`, and `transaction.ts:531-546` throws unless the call is `archflow_state` + `step: "produce"` + `status: "succeeded"`. **Self-review and triage have no route into the server at all**: `archflow_state.artifact` is a closed five-member union with no evidence member, so nothing they produce can survive a restart. And **no gate this phase opens can be enacted**: `legalMovement` (`transitions.ts:81-98`) permits only same-step `running`→`succeeded|failed`, same-step `failed`→`running`, and `succeeded`→ the next step at `attempt === 1` — no rewind and no `adjudicate → produce` — while gate closure (`gates.ts:497-509`) clears `open_gate` without touching step or status and appends an `ApprovalRef` only on `advance`, so every retry decision leaves state byte-identical modulo revision and re-gates forever.

## What We're Building

A service library, following Phases 12 and 13: plain exported functions taking an authenticated `TransactionAuthority` and pre-parsed input. **Phase 15 wires the MCP tools and `archflow-local`; Phase 14 settles the contracts it wires.** Five pieces: the trust constructors, artifact-union members, and kernel transitions that make the rest callable and durable at all; a pinned-constitution resolver reading rule blobs from the immutable policy-base commit and detecting task-local edits; the first production `InputFingerprintResolver` readers; an evidence-result retention route that reuses the Phase 11 snapshot spine by widening one union; and the orchestration that turns validated reviewer output into advancement evidence.

**Scope note on the prior-phase contract changes (owner decision, 2026-07-30).** Chunks 1-2 change shapes and rules established in Phases 2, 7, 9, and 12. Earlier drafts of this design treated those as frozen and wrapped each change in recorded-amendment ceremony; the owner has ruled that framing out. These are ordinary code changes: make the change the need actually requires, keep `architecture.md` and `prd.md` accurate afterwards because the plan must reflect reality, and do not treat a prior phase's shape as an obstacle to route around. The amendment table below is therefore a **record of what changed and why**, useful to the next reader — not a set of permissions to be sought. Where a listed change turns out to be unnecessary once the code is in front of you, drop it and say so in the implementation log.

The `review_trigger`/`enforced_by` evaluation is deliberately shallow **and deliberately fail-closed**. Both fields are free-form prose; there is no predicate language and Phase 14 does not build one, nor does it execute the shipped mechanism labels — they name test suites, and running them from the adjudication path is a subsystem no requirement asks for. What it does instead is refuse to let the adjudicator author the evidence its own pass depends on: a rule that declares `enforced_by` cannot reach `pass` on a model-asserted `current` state the server cannot corroborate, and a rule that declares none passes on an **empty** list rather than a synthesized one. **Phase 14 adds no dependency and no error code.**

## Pinned Decisions and Architecture Amendments

| Retention route | **Widen `ResultManifestV1.source_artifact` to admit the three evidence artifacts below.** Their payload schemas (`review-evidence`, `triage`, `adjudication-evidence`) are already registered, so `result-manifest.schema.json` gains `$def`s that `$ref` them and **no schema file is added** — `SCHEMA_IDS` stays at 40. The decisive reason to widen rather than add a second persisted root is that **`TaskStateV1.authoritative_results` is the only durable pointer to a retained result and `task-state.schema.json` is a frozen persisted root** (`durable-state.ts:44-51, :149`): a second root would need a second pointer inside a frozen schema. |
| Evidence artifacts and the widened tool union | The frozen evidence payloads carry no `artifact_kind`, so each is wrapped in a thin tagged artifact: `{schema_version:"1", artifact_kind:"review-evidence"\|"triage"\|"adjudication-evidence", evidence:<frozen payload>}`. **`DurableArtifact` gains `review-evidence` and `triage`**, taking `archflow_state.artifact` from five members to seven — adjudication arrives through `archflow_adjudicate` and joins only the manifest union. This resolves self-review and triage transport **in this phase rather than deferring it**: REQ-08 and REQ-11 bind every durable step artifact through `archflow_state`, and REQ-13/21/22 require restart-survivable current-evidence decisions, so caller-supplied branded values could never demonstrate this phase's own headline criterion. Consequences, none of which is "unchanged": **`durable.ts:533-554` gets an explicit evidence arm** — the four correlation checks at `:540`, `:543`, `:546`, `:549` read top-level `task_id`/`phase_instance`/`step`/`input_fingerprint` that exist on the payload but not on the wrapper, so each would read `undefined` and fail every evidence manifest at `transaction.ts:136` and `snapshots.ts:256`; the arm reads all four through `.evidence` and compares `artifact_digest` to `canonicalJsonDigest(source.evidence)` rather than to the wrapper, which is a **deliberate, stated deviation** from the generic `:537` rule and the one that keeps `evidence_digest === artifact_digest`. `artifactMatches` (`transitions.ts:102-120`) gains arms reading through `.evidence`, restoring the task check evidence installations would otherwise lose. `operationFor` yields `record-self-review` and `record-triage`; `IntentReceiptV1.operation` is an unconstrained `SafeCode`, **but the request digest is not** — `StateArtifactOperation` (`fingerprints.ts:46-51`) is a closed five-member union and both `operationForKind` (`fingerprints.ts:199-208`) and the `satisfies` map in `src/state/request.ts:27-33` are exhaustive over `artifact_kind`, so all three fail to compile until the two operations are added, and the resume-list distinguishability this design depends on is only real once `computeRequestDigest` admits them. Nothing about self-review authority is synthesized: a real retained manifest supplies a real `result_id` and `result_digest` in their own frozen domain. |
| Evidence identity | **`evidence_digest = canonicalJsonDigest(<validated evidence payload>)`** — the value `AuthorityLinkBase.evidence_digest`, `ReferencedEvidence.evidence_digest`, and `ReviewEvidenceSlot.evidence_digest` already carry, and equal to the manifest's `artifact_digest` *because the evidence arm digests the payload rather than the wrapper*. **The rendered-bytes digest is not the identity**: `renderReviewEvidence` prints `value.evidence_digest` into its own output (`renderers.ts:39`, `:69` for adjudication), so `evidence_digest = sha256(render(value))` has no solution; and rendering requires a qualified value, which `assertLinkMatches` (`trust.ts:191`) refuses to mint unless the digest already matches. The rendered bytes are the projection `payload_digest` / `content_digest`. |
| Gate-counter digest rule | **Decided here, not deferred.** `gates.ts:304-328` authenticates a supplemental review by comparing a rendered file's bytes to its slot `evidence_digest`, and `gate-wait.ts:84` returns a caller-supplied digest without proving completeness — two meanings of one field that, because the renderer embeds the digest in its own bytes, are *permanently* incompatible. Pinned: **file appearance and completeness are wake-up signals only; supplemental authority comes from parsed and validated JSON, or from a retained manifest whose `artifact_digest` is the canonical evidence digest.** `gates.ts:304-328` and `gate-wait.ts:72-90` move together as one guard site. |
| Trust constructors | The branded seams mint only through the raw factories in `src/contracts/internal/test-capabilities.ts`, which `test/contracts/schema-registry.test.ts:83-91` keeps out of the public barrel. **Phase 14 does not add production counterparts to those raw factories.** A clone-and-brand `createVerifiedEvidence` or `createEvidenceAuthorityLink` could authenticate a mismatched payload or invented result/receipt/revision facts — `parseReferencedReviewEvidence` accepts `evidence_digest` independently of the payload, and `assertLinkMatches` cross-checks provenance only for `server-attested` — so barrel absence protects nobody and a "minting discipline" is unenforceable prose. Instead: **owner-specific constructors that derive rather than accept.** One computes `canonicalJsonDigest` internally from the parsed evidence and returns the verified reference; one reloads and re-validates a retained manifest and returns the verified reference plus its result identity; the authority-link constructor derives result/receipt/revision fields from an authenticated transaction outcome and accepts none from a caller. `createAdjudicationObservationCapability` joins `createReviewObservationCapability` unchanged, its binding already fully derived. |
| Gate closure enacts retry effects | A retry-effect decision writes **nothing**: `nextStateForRecord` (`gates.ts:497-509`) appends an `ApprovalRef` only on `advance`, so `revise`, `revise-current`, and `retry-once` (`gates.ts:115`) leave state identical modulo revision, still satisfy the bound, and reopen the same gate forever. There is no durable trace to read afterwards — `TaskStateV1` has no decision slot, `RetainedEvidenceSet` holds manifests only, retained evidence cannot distinguish a `revise` from a `reject`, and the archived record's gate id derives from the original intent and is unreachable after a restart. **Pinned: resolution of any retry-effect decision on the gates this phase opens enacts the authorized transition itself**, closing to `produce`/`running` at `attempt + 1` in the same phase instance. This makes each grant inherently one-shot — the immutable closure record resolves once, the next re-entry re-checks the higher attempt, and a crash between archival and re-entry replays onto state that is already there. **It also removes the need for any decision index**: nothing downstream has to reconstruct a human decision, because the decision has already moved the state. **Two Phase 12 extensions, both recorded as guard sites**: `nextStateForRecord` becomes a step/status mover, and `openDurableGate`'s replay arms (`gates.ts:351-371`) gain one recognizing "archived retry-effect record with `current.revision > request.opened_at_revision`" — without it a completed enactment returns `INTENT_NOT_CURRENT`, since `open_gate` was cleared at `:509`, `earnsReceipt` is false for a retry effect so no receipt exists, `committed_intent` was stripped, and the outcome is not `cancelled`. The narrower archived-but-unwritten window already replays correctly via `:605`. **Fingerprint pin**: the enactment recomputes through `resolve_input_fingerprint` (already on `GateLifecycleDependencies`) and writes the produce-entry value, so it agrees byte-for-byte with what `planStateTransition` writes on the other route into the same logical move. |
| Redirect and base-amendment outcomes are **not** enacted | `amend-upstream` authorizes work in a **different phase instance** (the upstream document's own produce step), so enacting `produce`/`running` here would be premature. It is non-enacting: the upstream is amended through its own pipeline, which moves `upstream_identities` and therefore `input_fingerprint`, and the current phase re-enters later through the ordinary `legalMovement` branch on **evidence staleness alone** — a fact `assessCurrentEvidence` can compute from its own inputs with no decision trace. **`start-base-amendment` is dropped from the enactable set entirely** and documented as human-external. It cannot terminate inside this task: `detectTaskLocalConstitutionEdit` diffs `policy_base_commit..HEAD`, and both `policy_base_commit` and `constitution_digest` are frozen for the task's life by `assertPreserved` (`transaction.ts:265-266`), which this phase deliberately does not touch — so an enacted re-entry would walk the pipeline and reopen the identical gate forever. REQ-16 already describes the correct path: complete base-branch amendment review, then start a new task or use the REQ-50 upgrade flow. The task ends via `abort`. |
| Where `constitution-edit` opens, and `revert-edit` | The gate opens at **`adjudicate`/`running`**, before dispatch, since an unresolved task-local edit must block adjudication rather than be adjudicated against. That placement makes `revert-edit` need **no new machinery**: from a `running` state the existing same-step retry (`running → failed → running` at `attempt + 1`) is already legal, so the human reverts the edit and the caller retries adjudication. This is the one retry-effect decision gate closure does **not** enact. |
| Re-entry transition | One **sixth `legalMovement` branch**, inserted before the `target.attempt !== 1` test at `transitions.ts:89`: `current.status === "succeeded"` with `current.step` in `{triage, adjudicate}`, same phase instance, target `produce`/`running`, `target.attempt === current.attempt + 1`. **Those are exactly the conditions the kernel can see.** `TransitionPlanInput` is `{current, target, recomputed_input_fingerprint, artifact?, result_reference?}` — no triage payload, no finding counts on `AuthoritativeResultRef`, a pure synchronous planner, and `resultReferenceMatches` (`transitions.ts:129`) requires `reference === undefined` at this target. So **the semantic precondition lives in `assessCurrentEvidence`**, and after the two rows above both of its cases are computable from durable inputs: an accepted finding (`ValidatedTriage.accepted_count`) from `triage`, or evidence gone stale against the recomputed fingerprint from `adjudicate`. `artifactMatches` already returns true for a non-succeeded target (`transitions.ts:105`). |
| Attempt counter and the exhaustion check point | **`attempt` becomes the phase-instance attempt counter**: it resets to 1 only when the phase instance changes, carries forward across steps within a phase instance, and increments on a same-step retry and on re-entry. Today `transitions.ts:89` resets it on every forward move, which is exactly why no rewrite cycle is representable. **The exhaustion check fires only at re-entry points**, so an authorized retry is not immediately re-gated by the forward moves that follow it. No `TaskStateV1` schema change, **but this is not confined to `src/`**: both adoption planners replay every manual checkpoint through `planStateTransition` with `attempt: checkpoint.attempt` (`checkpoints.ts:112-128`, `initialization.ts:155-168`), so **`ManualCheckpointV1.attempt` now means attempts consumed in the phase instance** and a human-authored chain that retries before advancing must carry the number forward. A chain such as `produce/running a1 → produce/failed a1 → produce/running a2 → produce/succeeded a2 → self_review/running a1` is legal today and becomes `TRANSITION_INVALID`; every chain fixture sits at `attempt: 1`, which is why the suite as it stands would not catch it. |
| Result-installation guard | `transaction.ts:531-546` keeps an **exact tool → step → source-kind mapping**. The WeakMap capability (`transaction.ts:507-513`) authenticates installation *facts*, not which request may consume them, and standalone manifest semantics correlate a source to its manifest but never a manifest to current state — so without the mapping an evidence installation could ride an artifact-less `archflow_state` call or a same-phase manifest prepared for another task. The predicate is: the call's tool and step match the mapping (`archflow_state` → `produce`/`self_review`/`triage`; `archflow_counter_review` → `counter_review`; `archflow_adjudicate` → `adjudicate`), the target status is `succeeded`, the embedded source kind is legal for that step, **and** the manifest's `task_id`, `repository_identity_digest`, and resolved targets bind the authenticated task root. **Throws versus classified failures, decided once**: violations reachable only from a defective trusted callback — wrong slot shape, wrong source kind for the tool, a reference the prepared plan does not name — remain `TypeError` throws, matching live `buildPlan`. Caller-data mismatches — task identity, repository identity, fingerprint, path targets — are classified `ProjectResult` failures. Tests assert each in its own category. `transitions.ts:127` is relaxed to permit a result reference at any succeeded evidence step whose `(phase_instance, step)` and fingerprint match; `transitions.ts:105` is unaffected; the receipt-resume list at `transaction.ts:723-724` gains `counter-review`, `adjudicate`, `record-self-review`, and `record-triage`. |
| Pinned constitution | `resolvePinnedConstitution` reads rule blobs from the **`policy_base_commit` tree**, never the worktree. `readCommitTreeBlob` resolves one exact path and throws on more than one entry (`git.ts:354-377`), and no tree-listing helper exists in `src/repository/` — `index-entries.ts` reads the *index*. So Phase 14 adds a bounded `readCommitTreeEntries(runner, commit, directory)` to `src/repository/git.ts`: `git ls-tree -z <commit> -- <dir>/`, its own `SafeCode` operation, NUL-field parsing mirroring `readCommitTreeBlob`, an entry-count bound, and **never `--literal-pathspecs`**. Discovering the file list from the worktree is forbidden — it would falsify "a worktree edit does not change the digest" and let a worktree deletion silently shrink the registry. Registry membership is `.archflow/constitution/<NN>-<name>.md`; `README.md` belongs to neither registry nor digest. `constitution_digest = canonicalJsonDigest({schema_version:"1", digest_kind:"pinned-constitution", files:[{path, oid}, …] sorted by path})`, in `src/contracts/fingerprints.ts` (pure); the reading lives in `src/state/constitution.ts` (`durable-agreement.test.ts:687` forbids `src/repository/` from `src/contracts/*.ts`). **Phase 16's initialization writer must call the same function.** |
| Task-local constitution edit | `readChangedGitPaths` runs `git status --porcelain=v1` (`git.ts:304-306`) — working tree and index versus HEAD only — and `.archflow/` is tracked during development, so a **committed** task-branch edit is invisible to it, while REQ-16 says "any task-branch diff touching `.archflow/constitution/`", i.e. a diff against the policy base. Two detectors: `readChangedGitPaths` for uncommitted changes and a new bounded `git diff --name-only -z <policy_base_commit>..HEAD -- .archflow/constitution/` for committed ones, both narrowed through `resolveRepositoryPath({expectedClass: "task-branch-constitution"})`. `current_constitution_digest` is **the same formula over the HEAD tree** — the formula is a commit-tree digest by construction, so an uncommitted edit is reported by the path scan with the HEAD-tree digest and the gate opens either way. |
| Mechanical evidence and the pass rule | `validateAdjudicationClaims` checks a `current` entry only for `subject_digest` (`adjudication.ts:112-123`); nothing authenticates `state` or `evidence_digest`. So **the adjudicator must not author the evidence its own pass depends on.** Two pins, and both *remove* machinery. **(1) The `adjudicator-judgement` fallback is deleted** — it presented the pinned policy digest as mechanical evidence of artifact compliance purely to satisfy a frozen non-empty check, a fabrication this design invented. The frozen rule is amended so `compliance: "pass"` is legal with an **empty** `enforced_by` list, with "empty **iff** the rule declares none" moved to the registry-aware `crossCheckRuleFindings`. It has **four** encodings that must change together: Zod (`adjudication.ts:114`), the shared Ajv `x-archflow-adjudication-semantics` implementation (`validators.ts:134`), `adjudication.schema.json:19`, and — easily missed and the one on the **persisted** path — `adjudication-evidence.schema.json:11`, which redeclares its own byte-identical `$defs.ruleFinding` instead of `$ref`-ing the other file. Three tests assert the current behaviour: `test/unit/adjudication.test.ts:10` and `:11`, and `test/contracts/review-schema-agreement.test.ts:74`. **(2) A rule that *does* declare `enforced_by` cannot reach `pass`.** The server cannot corroborate a model-asserted `current`, and REQ-15 ("missing, stale, unknown, or failed evidence is not compliance") with REQ-17 make an uncorroborated claim inadmissible. The envelope instructs such rules to return `uncertain` with `state: "unknown"`, which the frozen fold turns into `constitution: "uncertain"` and therefore gates; a returned `pass` fails as `MODEL_OUTPUT_INVALID`. The surviving `state !== "current" && compliance === "pass"` clause remains as a correct backstop, and no dishonest `pass` path is left. **Stated limitation**: exactly one of the four shipped rules declares `enforced_by`, so that rule gates on every adjudication until a later phase supplies corroborated mechanism evidence — fail-closed and human-resolvable, since `adjudication-failure` is a `WaivableOperation` and the scoped waiver requires an explicit human decision. |
| Attempt bound | `ConfigV1` gains one optional top-level `max_attempts` (positive safe integer) — REQ-13 bounds attempts *by configuration*, and `ConfigV1` is `.strict()`, so the Zod schema, `config.schema.json`, and its agreement test all change. Absence means `DEFAULT_MAX_ATTEMPTS = 3` and stays legal, so existing whole-file config pins are unaffected. |
| Exhaustion is not an error code | The registry stays at **53**. Exhaustion opens the frozen `attempts-exhausted` gate whose decisions are the outcome. Every retryable dispatch code says `retry-unchanged-attempt`, which would be a lie here. Drift and compliance verdicts are data and ride on `AdjudicateSuccess`. |
| Material drift serialization | `material-drift` carries exactly one `affected_upstream` (`gates.ts:34, :88`) while adjudication can return several material `drift_findings`. **Serialize deterministically rather than widen the frozen context**: gate the first material upstream in `approved_upstream_digests` order, and require re-adjudication after its resolution so the next still-material upstream opens its own gate. Resolving one upstream usually changes the fingerprint and can change the others' verdicts, so re-adjudicating is not bookkeeping — it is the only way the second gate's context is true when it opens. |
| Upstream reopening | Approved upstream digests are derived from `state.approvals` plus `authoritative_results`, never asserted by the caller. `InputFingerprintSubject.upstream_identities` already feeds `input_fingerprint`, so an amended upstream moves the fingerprint, makes downstream evidence stale, and is what authorizes re-entry. The refusal is stated against what durable state records — `ApprovalRef` carries `subject_digest` and no upstream identity or fingerprint (`durable-state.ts:53-60`): for each declared upstream, resolve its current canonical document digest and require an `artifact-approval` `ApprovalRef` whose `subject_digest` equals it; absence means the upstream is unapproved or changed since approval, and advancement stops non-advancing. **No new durable field.** |
| Stale evidence | Evidence references are **not removed** from `authoritative_results` on rewrite. `(phase_instance, step)` is the set key, so a rerun overwrites naturally, and comparing `(subject_digest, input_fingerprint)` decides currency — which is also what makes post-redirect re-entry computable. |
| Adjudication envelope | `DispatchEnvelope` gains `result_kind: "review" \| "adjudication"`. `buildAdjudicationEnvelope` carries artifact bytes, the active pinned rules (id, version, text, `review_trigger?`, declared `enforced_by` labels, and the instruction that a declared-mechanism rule returns `uncertain`/`unknown`), approved upstream bytes with digests, `source_evidence_set_digest`, and the `AdjudicationSubject` — nothing else. Same 1 MiB cap, `schema_version` first in child-visible bytes, same over-cap `CONTRACT_INVALID {issue_code:"envelope-byte-cap"}`. Digest kind `"adjudication-envelope"`, the eleventh domain separator. Note for the implementer: the child **cannot** see `envelope_input_digest` — `envelopes.ts:143-155` hands it `JSON.stringify({schema_version, artifact, rubric, subject}, null, 2)` while the digest covers a different object through an encoder the child lacks, and `cli.ts:348, :420` pass only `envelope.bytes`. No instruction may require the child to echo it. |
| Adapter output schema | `CliAdapter.buildInvocation` takes a fourth parameter, the output-schema document. Claude inlines it (a path fails before the model call), Codex writes it to the workspace. Source is `review.schema.json` or the registered `adjudication.schema.json`. **The `x-archflow-*` keywords ship verbatim, unchanged from Phase 13**; strip only if a CLI ever rejects an unknown keyword. The 3-arg call at `test/integration/dispatch-plumbing.test.ts:55-107` is the exact site that changes. |
| Adjudication routing | **Automatic same-family adjudication is refused**, as `FAMILY_MISMATCH` before launch. `observeAdjudication` always returns `ServerAttestedAdjudication` (`trust.ts:107-118`), while `DegradedAdjudication` is a different assurance arm whose `DegradedAuthorityReferences {checkpoint_digest, checkpoint_revision}` an automatic CLI dispatch does not have — so "permitted but labelled degraded" is unrepresentable without fabricating checkpoint provenance, which is precisely the boundary the assurance arms exist to hold. Degraded adjudication remains available on the existing checkpoint-backed manual path. |
| Waiver expiry | One rule: `expires: "task-complete"` means a `WaiverRef` is in force while `state.terminal === undefined`, and it authorizes suppressing exactly its `(rule_id, rule_version, subject_digest, scope)` tuple. One predicate, checked where `review-trigger` and `adjudication-failure` admissibility is decided — which is also the escape path for the declared-mechanism rule that now always gates. |
| Corpus ownership | Phase 14 owns a **deterministic fake-CLI-driven corpus and harness** under `test/fixtures/corpus/`, selected by the existing `scenario` / `plumbing-scenario` file mechanism so the Phase 13 harness needs zero change. Phase 21 owns real-host review-quality validation and threshold approval. Phase 14 records no threshold. |
