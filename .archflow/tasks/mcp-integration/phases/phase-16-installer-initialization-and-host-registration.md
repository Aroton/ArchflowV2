# Phase 16: Installer, Initialization, and Host Registration

**Status**: DESIGNED
**Task**: mcp-integration
**Goal**: Install the offline bundle and initialize supported repositories repeatedly without damaging host or project configuration.
**Requirements**: REQ-01, REQ-02, REQ-28, REQ-29, REQ-34, REQ-37, REQ-40

## Context

Nothing installs the Phase 15 payload today. `install.sh` (58 lines) copies `skills/` into `~/.claude/skills` and `~/.agents/skills` and deletes a hard-coded `STALE_SKILLS=("archflow-phase")` array; `cp -R "$SKILLS_SOURCE_DIR/."` merges and never removes a file dropped from a still-existing skill directory. `dist/` holds `archflow-mcp.mjs` and `archflow-local.mjs` with **no shebang and no launcher wrapper**, so the PATH-resolved `archflow-mcp` that both host registrations must name does not exist. `src/init/` does not exist. Nothing in `src/` constructs a `TaskInitializationV1` — only fixtures do.

Live verification today against the installed CLIs (`claude 2.1.220`, `codex-cli 0.146.0`) **corrects two architecture assumptions, and both corrections belong in `architecture.md`**. (a) Claude Code *does* support a persistent per-server `timeout` in `.mcp.json` (milliseconds; overrides `MCP_TOOL_TIMEOUT` for that server; values under 1000 ignored; on v2.1.203+ it also raises that server's stdio idle window, whose default is 1800000 ms and is the real limiter on a blocking gate — the repo's existing `CLAUDE_MINIMUM_VERSION = "2.1.205"` already clears that floor). The architecture's `export MCP_TOOL_TIMEOUT=3600000` shell-profile branch and its "a newly started host proves inheritance" check are conditioned on Claude *lacking* such a field, so **neither is built**; success criterion 4 is replaced by the per-server field and its readback. (b) **There is no official Codex project registration command.** `codex mcp add` writes only the global `~/.codex/config.toml`, has no scope flag (openai/codex#23487 open since 2026-05-19), cannot set `tool_timeout_sec` (default **60 s**, fatal to REQ-37), and re-running it **replaces the whole `[mcp_servers.<name>]` table**, silently dropping anything patched in. Codex *reads* a project `<repo>/.codex/config.toml` in trusted projects — verified overriding the global entry. So ArchFlow writes that repo-owned file itself, is its only writer, and adds **no TOML dependency** (no current Node TOML library is simultaneously maintained, permissive, and format-preserving). Both hosts then end at a human trust boundary init must report and never claim past: a project `.mcp.json` server sits at `⏸ Pending approval` and since v2.1.196 a cloned repo cannot approve its own servers, and Codex project config is honored only while the project is trusted, which only Codex's own interactive prompt should grant.

## What We're Building

`install.sh` stays Bash and gains three jobs: verify the tracked payload against `dist/manifest.json` with a dependency-free re-hash, copy `dist/` plus `assets/` into a single install directory, and write two `exec node` launcher shims onto PATH. Skill installation becomes manifest-driven — an ArchFlow-owned path list per target dir replaces both `STALE_SKILLS` and the `cp -R` non-removal gap. A new `skills/archflow-init/SKILL.md` is a thin wrapper that runs a new taskless `archflow-local init` and relays its report; the logic lives in `src/init/`, which scaffolds `.archflow/` assets, registers both hosts, patches only the one field each official command cannot express, and returns a diagnostics and limitations report.

Everything init writes is idempotent and byte-stable, and init never clobbers a human edit: a scaffolded asset whose bytes diverge from the shipped asset is reported, not overwritten. Preservation is byte-level for every file ArchFlow owns, and **parse-level for `.mcp.json`**, because `claude mcp add` owns that file's formatting and — verified empirically — silently deletes unrelated *top-level* keys while preserving other servers' fields. Init therefore refuses up front when `.mcp.json` carries any top-level key besides `mcpServers`, printing the exact block to paste. `archflow-init` creates no task state and no commit; the human commits the scaffolded assets, and a second taskless command stages a `TaskInitializationV1` that refuses unless the workflow and constitution resolve from an approved immutable commit.

## Pinned Decisions

| Item | Pinned definition |
|------|-------------------|
| Install root | One directory, `${ARCHFLOW_HOME:-$HOME/.archflow}/bundle/`, replaced wholesale on every install. **Not digest-named**: `manifest.json.bundle_digest` is only the `mcp-stdio` entry digest (`scripts/release-support.mjs:1215`), so a `src/init`/`src/local`-only change leaves it unchanged and two different payloads would collide on one directory name. One replaced directory also removes the never-pruned accumulation a versioned layout would create. It holds a copy of `dist/` plus a copy of `assets/`. |
| Payload verification | `install.sh` re-hashes with `node -e` using `node:crypto` and compares `digest` and `size` for **every file it copies** — each `dist/manifest.json` `artifacts[]` entry *and* each runtime asset. The assets are the point: init scaffolds repositories from those exact bytes, and today `assets/**` is recorded only under `release_control_inputs`, so hashing `artifacts[]` alone would let a stale or corrupt asset tree pass verification and seed a repository from bytes the release never pinned. Chunk 1 adds `assets/config.template.yaml` to the release-declared asset set and gives the copied assets a verifiable manifest record. **Do not call `npm run check:release`**: `scripts/release-support.mjs:33` statically imports `esbuild`, a devDependency, so every leg of that script fails at import time in the clean checkout this phase's first success criterion names — and `checkReleasePayload` writes into the checkout via `recoverTrackedRelease`. `check:release` remains the maintainer-side gate, run from the test suite and CI, never by an end user's install. |
| Launchers | `${ARCHFLOW_BIN:-$HOME/.local/bin}/archflow-mcp` and `/archflow-local`, each `#!/bin/sh` + `exec node "${ARCHFLOW_HOME}/bundle/archflow-<x>.mjs" "$@"` with the resolved absolute path baked in. `node` resolves from PATH at runtime so nvm-style switches keep working; the bundle path is absolute and pinned. When the bin dir is not on PATH, print the exact `export PATH=...` line and the profile guidance, and fail — registration names a PATH command and is meaningless without it. |
| Node gate | `command -v node` plus a **full** version compare against the `engines.node` range in the checkout's `package.json` (currently `^24.15.0`), read with `node -e` and no npm. A major-only compare against `launch_profile.node_major` would admit Node 24.0–24.14, which the repository declares unsupported, and report success on a runtime the phase is meant to reject. Failure prints the observed and required versions. |
| Owned install manifest | `<skill target>/.archflow-installed` — a sorted, newline-delimited list of ArchFlow-owned paths relative to that target dir. Plain text, not JSON, **because `install.sh` is Bash and must not acquire a `jq` dependency**; it is a path list, not a digest ledger. Install = read previous list, delete listed paths no longer shipped, copy the new tree, write the new list. A path absent from the previous list is never deleted. Absent manifest (first install or pre-Phase-16 target) falls back to deleting only the legacy `archflow-phase` directory, then proceeds. |
| Claude registration | **Presence, command collision, and the persisted timeout are all determined from the parsed project `.mcp.json`, never from `claude mcp get`.** `claude mcp get` resolves the *highest-precedence* entry — local, then project, then user — so a pre-existing local or user `archflow` would mask the project scope, make init skip `claude mcp add --scope project` and leave the required committed entry absent, and then make the timeout readback report the wrong entry. Run `claude mcp add --scope project archflow -- archflow-mcp` whenever that scope lacks the entry (a duplicate name exits 1, so do not run this under naive `set -e`). Then parse `.mcp.json`, set `mcpServers.archflow.timeout`, and rewrite with two-space JSON and a trailing newline — init's own stable format, adopted once, byte-stable thereafter (`claude mcp add` writes two-space JSON with **no** trailing newline, so the byte-stability test compares re-runs against init's output, never against what `claude mcp add` produced). `claude mcp get` is used only for runtime and approval diagnostics (`⏸ Pending approval`, `Timeout: …ms`), and any higher-precedence same-name entry it reveals is **reported explicitly** as masking the project registration. It has no `--json`, so that read is a text match and is never the authority for what was written. |
| Codex registration | Init owns a **marker-delimited block appended to** `<repo>/.codex/config.toml`, never the whole file — project config is an ordinary supported Codex layer for MCP servers, hooks, and model settings, and replacing or refusing it would turn a common repository into a manual failure path instead of the idempotent preserving init REQ-01 requires. The block contains `[mcp_servers.archflow]` with `command = "archflow-mcp"`, empty `args`, `startup_timeout_sec`, `tool_timeout_sec`, wrapped in begin/end comment markers. Absent file: create it with just that block. Existing file without the block: **append**, leaving every prior byte untouched — TOML tables are order-independent, so appending a table is valid. Existing file with the block: replace only the bytes between the markers. Refuse, with the exact block to paste, only on a genuine conflict — an `archflow` MCP entry outside the markers — or when the file cannot be confidently classified. **No TOML dependency and no parse-and-restringify.** Detecting a conflicting entry needs a line scan for the `[mcp_servers.archflow]` header and for `mcp_servers` inline/dotted forms, not a parser; anything ambiguous fails closed to the paste path. A round-trip through `smol-toml@1.7.1` (2026-07-26, BSD-3-Clause, maintained, 26.5M weekly downloads) would parse fine but re-serialize the user's whole file, destroying their comments and formatting — strictly worse than appending. (`@ltd/j-toml` is LGPL-3.0 and must not be adopted.) Nothing in this phase *parses* TOML: verification delegates to `codex mcp get archflow --json`. `codex mcp add` is never called. Trust is probed by running that command with cwd at the repo; if the project entry does not resolve, the project is untrusted and that is **reported, never fixed** — init never writes `trust_level`. |
| Timeout constants | `CLAUDE_MCP_TIMEOUT_MS = 3600000`, `CODEX_TOOL_TIMEOUT_SEC = 3600`, `CODEX_STARTUP_TIMEOUT_SEC = 30`, declared once in `src/init/registration.ts`. One hour on both hosts. This bounds one tool call, not the decision: a gate is durable and resumable, so a host timeout leaves the gate pending (REQ-37). Note for the user-facing report: on Claude ≥ 2.1.212 a call still running after two minutes moves to a background task; gates are resumable, so this is a UX note, not a blocker. |
| Config template | Shipped `assets/config.template.yaml`, scaffolded to **`.archflow/config.yaml`** — outside the constitution digest regex and not `.archflow/workflow.yaml`, so it disturbs no pinning. Task creation copies it to `.archflow/tasks/<task>/config.yaml`, whose exact bytes are then digested by `computePinnedConfigDigest` for the task's whole life. The file carries a header comment saying so and that changing routing requires a new task. Active block: producer `claude-opus-5` / `high`, self-reviewer `claude-opus-5` / `high`, counter-reviewer `gpt-5.6-sol` / `xhigh`, adjudicator `gpt-5.6-sol` / `xhigh`. A commented Codex-producer block with the families swapped follows, since `roles` holds one route per role and the opposite-family constraint is directional. All four slugs and both efforts were live-verified against `claude 2.1.220` and `codex-cli 0.146.0` on 2026-07-31. **`gpt-5-codex` and the whole `-codex` model line are retired** — Codex's own `[notice.model_migrations]` maps it to `gpt-5.2-codex`, and both return HTTP 400 "not supported when using Codex with a ChatGPT account". No `ultra` on any `claude-*` route: the Claude CLI does not reject it, it warns and silently falls back to the default effort, which is why the existing guard at `src/dispatch/cli.ts:367` is load-bearing rather than belt-and-braces. **Implementer: re-confirm both slugs are current before writing the file** — a wrong slug is byte-pinned into every task created before the fix. |
| CLI version floors | **Unchanged — do not bump either.** An earlier revision proposed raising `CLAUDE_MINIMUM_VERSION` to `2.1.219` and `CODEX_MINIMUM_VERSION` to `0.145.0` on the theory that older clients cannot run the pinned model slugs. That is inference from release notes, not a demonstrated runtime failure: model slugs pass through to the provider, and a version floor cannot prove the account's catalog includes a model anyway, so the bump would exclude working installations without catching the failure it claims to. The design's other Claude-side dependency, a per-server `timeout` raising the stdio idle floor, needs v2.1.203+ and the existing `2.1.205` already clears it. Init already reports both observed CLI versions in its diagnostics, and dispatch already classifies the failure if a slug is unavailable. If the implementer can cheaply run a direct compatibility check at each floor version, do it and raise a floor only on a demonstrated failure. |
| Error codes | **None added.** `CLI_MISSING {adapter}`, `CLI_VERSION_UNSUPPORTED {adapter, version}`, `AUTH_UNAVAILABLE {adapter}`, `RUNTIME_VERSION_UNSUPPORTED {component, version}`, `CONFIG_INVALID {issue_code}` with issue codes `mcp-json-foreign-keys`, `codex-config-foreign`, `scaffold-diverged`, `server-command-collision`, `POLICY_BASE_INVALID`, and `IO_ERROR {operation, attempt}` cover every failure. Adding a code is a four-place edit plus the registry count assertion; do not. Untrusted Codex project, pending Claude approval, and managed-policy presence are **report fields, not errors**. `install.sh` is outside the `ProjectError` projection entirely and signals by exit status. |
| Preflight reuse | Init runs Phase 13's real version and auth probes under the same generated home and scrubbed environment dispatch uses, so the answer init reports is the answer dispatch will get (REQ-34). Two seams must open first, because the current surface does not support this call: (1) `preflight` is module-private with a nine-argument signature (`src/dispatch/cli.ts:207`) and both adapters are module-private consts (`:340`, `:422`), while the only export, `selectCliAdapter` (`:495`), deliberately returns the *opposite*-family adapter and throws `CONFIG_FAMILY_UNSUPPORTED` for the Claude one — so add an exported `preflightAdapter(adapterId, workspace)` (or export the two adapters) and call that. (2) `preflight` **throws on the first failure**, at `:223` for an unsupported version before the auth probe and at `:241` for logged-out before `existingPaths(policyPaths)` at `:243`, so a single call can never produce the combined report this phase promises. `collectInitDiagnostics` therefore catches `CliAdapterError`, maps its `project_error` into a report field, and reads the managed-policy tables directly — exporting `CLAUDE_MANAGED_POLICY_PATHS` (`:34`) and `CODEX_MANAGED_POLICY_PATHS` (`:43`); there is no `MANAGED_POLICY_PATHS`. This is the one place "reimplement nothing" bends: the version and auth probes are still reused verbatim, only fact-collection order is init's own. |

## Work Breakdown

Names below are pinned so separately-implemented chunks stay coherent; everything inside them is the implementer's call.

1. **Asset delivery — resolved, build it this way.** `src/init/` must emit the exact bytes of `assets/workflow.yaml`, the five constitution files, and `config.template.yaml`. The design's earlier open question is now closed by inspection: assets are **not** embedded and nothing in `src/` reads them (`grep 'assets/' src/**/*.ts` is empty); `declared_content` merely references repository paths (`scripts/release-support.mjs:1222-1226`) and `createControlRecords` (`:1017-1031`) digests `assets/**` as control inputs only. Schemas are embedded, but by `import … with { type: "json" }`, which does not extend to `.yaml`/`.md` without adding a `loader` entry to `RELEASE_BUILD_PROFILE` (`:54-70`, currently none) and shifting seven files from control records into `bundle_inputs`/`contributing_inputs`, changing the dependency inventory digest and both entry digests. **So do not embed.** `install.sh` copies `assets/` into the install directory and `src/init/` resolves it relative to `import.meta.url`. Because those bytes seed every initialized repository, this chunk also adds `assets/config.template.yaml` to the release-declared asset set and gives each copied asset a manifest record the installer verifies against — otherwise `assets/**` remains a `release_control_inputs`-only entry with no install-time check, and a corrupt asset tree would pass verification. Init is inherently machine-local and nothing machine-specific enters `.mcp.json` or task state either way. Relatedly, the feared builtin restriction does not exist: the only import rule is `assertReviewedExternalImport` (`:152-157`), which permits any Node builtin, and `node:child_process` is already in the `local-cli` `allowed_imports`; `entry_provenance` and `launch_profile.allowed_imports` derive from the metafile and self-update.

2. **`install.sh`**: `verify_payload` (dependency-free re-hash of `manifest.json` `artifacts[]`), Node major gate, bundle plus `assets/` copy into `${ARCHFLOW_HOME}/bundle/`, launcher shims, PATH check with exact guidance, and manifest-driven skill install replacing `STALE_SKILLS` and the bare `cp -R`. Preserve the existing `--claude` / `--codex` / `--help` flag surface and add `archflow-init` to the trailing command list.

3. **Scaffolding**: `scaffoldRepositoryAssets(input): Promise<ProjectResult<AssetScaffoldReport>>` in `src/init/assets.ts`. Write only what is missing; on a divergent existing file report `CONFIG_INVALID {issue_code: "scaffold-diverged"}` with the path and do not write. `.gitattributes` is a human file: append the required line only if absent, never rewrite. The line to append is the one-line `ARCHFLOW_GITATTRIBUTES_LINE` (`test/helpers/temp-repository.ts:28-31`), used as a reference value and not imported — **not** `ARCHFLOW_GITATTRIBUTES`, which is the whole two-line file and would inject `* text=auto` into a user's `.gitattributes`. `.archflow/config.yaml` is deliberately outside every path class in `src/repository/paths.ts` (`classifyRepositoryPath` at `:302-311` admits only `.archflow/workflow.yaml` and `.archflow/constitution/<name>.md`), so init writes it with plain `fs` and no later phase should plan to read it through the sanctioned resolver.

4. **Registration**: `registerClaudeProject(input)` and `registerCodexProject(input)`, each returning `Promise<ProjectResult<HostRegistrationReport>>`, per the pinned table. A pre-existing `archflow` entry whose command is not `archflow-mcp` is `CONFIG_INVALID {issue_code: "server-command-collision"}` — reported, never overwritten. On the Claude side, read the project `.mcp.json` for every decision and use `claude mcp get` only for diagnostics; on the Codex side, append or replace only the marker-delimited block and never rewrite the file.

5. **Diagnostics and limitations**: `collectInitDiagnostics(input): Promise<InitDiagnostics>` and `runInit(input): Promise<ProjectResult<InitReport>>`. The report enumerates: Node and both CLI versions, auth state, managed-policy presence and paths, Codex project trust, Claude pending-approval state with `claude mcp reset-project-choices` as the reset path, collisions, and recovery guidance (which step to re-run after each failure; re-running init in full is always safe). It must state plainly that Phase 13's context hygiene is **best-effort, not an enforced isolation boundary**, and must not claim success past either host's human approval step.

6. **Task-initialization staging**: `stageTaskInitialization(input: { working_directory, task_id }): Promise<ProjectResult<TaskInitializationV1>>`. **This chunk owns creating `.archflow/tasks/<task>/config.yaml`** — copy it from `.archflow/config.yaml` **only when absent**. When it already exists, parse and validate it with `parseConfigYaml`, preserve it untouched, and digest its exact bytes. A pre-existing task config that differs from the repository template is the supported case, not an error: REQ-30 explicitly permits a human- or Archforge-authored per-task config to override model and effort by role and phase, and `TaskInitializationV1` pins the whole-file digest without requiring template equality. Divergence handling belongs only to the repository scaffold assets ArchFlow actually owns (chunk 3), never here. Nothing else in this phase or Phase 17 creates this file, and this chunk digests it. Then resolve repository identity (`resolveRepositoryIdentity`, `src/repository/identity.ts:249`), the approved policy-base commit, the constitution and workflow digests **from that commit tree** (`resolvePinnedConstitution`, `readCommitTreeBlob`, `PINNED_WORKFLOW_PATH`), and the config digest by `computePinnedConfigDigest` over those bytes. Emit all nine required fields with `canonical_paths` matching what `validateLiveInitialization` hard-codes (`src/state/initialization.ts:75-89`). Refuse with `POLICY_BASE_INVALID` when the assets do not resolve from an approved immutable commit — `resolvePinnedConstitution` already returns that failure with the required `expected_digest` (`src/state/constitution.ts:109-120`), so propagate it. Note plainly in the code and the report that at init time `policy_base_commit` and `code_baseline_commit` both resolve to HEAD: the human's commit of the scaffolded assets *is* the approval, and the architecture's separation of the two exists in the artifact but is unexercised here. Creates no state, no commit, no `archflow_state` call — Phase 17 wires it into the skill pipeline.

7. **The `archflow-init` skill and CLI seam**: `skills/archflow-init/SKILL.md` plus the two `LOCAL_COMMANDS` entries and the `INPUT_FREE_COMMANDS` classification. Both new commands are input-free and **must not read stdin** — a launcher's parent commonly keeps stdin open, and waiting for EOF hangs.
