# Phase 18: Manual and Degraded Recovery Workflow

**Status**: COMPLETE (2026-08-03)
**Task**: mcp-integration
**Goal**: Complete and recover the workflow conservatively when individual MCP tools or the server are unavailable.
**Requirements**: REQ-08, REQ-09, REQ-11, REQ-12, REQ-13, REQ-14, REQ-18, REQ-20, REQ-21, REQ-22, REQ-23, REQ-24, REQ-25, REQ-36, REQ-37, REQ-38, REQ-39, REQ-40, REQ-41

## Context

Phase 17 completed the normal-mode workflow: the skills follow one server-derived next action, authoritative outputs live in retained result snapshots, gates have complete terminal interfaces, and status reconciles durable state before recommending work. Earlier phases also supplied the manual checkpoint/import schemas, state-anchored first successors, greatest-chain selection, atomic checkpoint storage, decision archives, snapshot restore, and divergence handoff primitives. Those contracts are the authority for this phase; the checkpoint family is not redesigned.

The remaining gap is composition. The helper exposes low-level checkpoint, import, decision, snapshot, and restore commands, but callers must still hand-author authenticated milestone state, result references, and import calls. Status does not validate a unique greatest manual chain, skills prohibit rather than execute fallback, and no common path makes manual gate/supplemental-review behavior or retained results match normal mode. The repository context documents are stamped at `fccf3fb`, behind current HEAD `72023f74937cadc094fb5d714c4f9cacbf7d2bbf`; current code and the Phase 17 implementation log therefore govern where those seams now live.

## What We're Building

Add one narrow manual-workflow composition layer behind `archflow-local`. It classifies authority as `normal`, `degraded`, or `repair-required`, authenticates the unique reachable checkpoint head, returns exactly one safe next action, derives rather than accepts checkpoint authority fields, and emits the exact fallback artifact or prompt for whichever of the five MCP capabilities is unavailable. It also prepares archive-authenticated checkpoint imports and exposes the existing one-writer handoff protocol without inventing a second recovery model.

The normal and manual paths will share retained-result preparation and gate projections, while a manual installer mints authority only after immutable result bytes and collision-safe projections are installed. An initial manual checkpoint embeds the complete task or legacy initialization; the first checkpoint after ordinary server state binds that exact canonical state revision and digest; every later checkpoint links to its predecessor. Only results, projections, reviews, decisions, waivers, and snapshots reachable from the selected head can authorize a degraded milestone. A gap, fork, foreign/corrupt inventory, collision, or divergent writer stops with one precise repair action and never advances. If the helper itself cannot run, the skills use static reinstall/repair guidance and create no purported status or milestone.

## Work Breakdown

1. **Classify durable authority**: Implement `loadManualAuthority(input: LoadManualAuthorityInput): Promise<ProjectResult<ManualAuthority>>` and `classifyManualWorkflowStatus(input: ManualWorkflowStatusInput): Promise<ProjectResult<ManualWorkflowStatus>>` in `src/local/manual-workflow.ts`. `ManualAuthority` is an opaque capability minted only by the loader after it authenticates exactly one of `initial` (canonical task/legacy initialization), `state-anchored` (canonical current state), or `continuation` (the unique greatest validated checkpoint chain). Its private facts include the unique reachable result manifests and `retained_task_bytes`, excluding only an exact result selected for idempotent reuse. `ManualWorkflowStatus["mode"]` is exactly `"normal" | "degraded" | "repair-required"` and every successful result contains one `next_action: ManualWorkflowNextAction`; gaps, forks, foreign/corrupt candidates, unreadable authority, and a merely highest-numbered file remain repair-required. Helper-unavailable guidance remains static in the skills because an unavailable executable cannot classify itself.

2. **Derive manual checkpoints**: Add `buildNextManualCheckpoint(input: NextManualCheckpointInput): Promise<ProjectResult<ManualCheckpointV1>>` in `src/state/manual-checkpoints.ts`. Pin `NextManualCheckpointInput` to `{ authority: ManualAuthority; milestone: ManualMilestone; results: readonly InstalledManualResult[]; gate_facts?: AuthenticatedManualGateFacts }`, where `ManualMilestone` is the closed union `{kind:"step", phase_instance, step, status}`, `{kind:"gate-open", request}`, `{kind:"gate-resolved", decision}`, or `{kind:"terminal", terminal}`. `ManualAuthority`, `InstalledManualResult`, and `AuthenticatedManualGateFacts` are opaque same-process capabilities minted only by their filesystem loaders/installers; no raw result reference, projection digest, attempt, anchor, approval, waiver, evidence set, or gate digest appears in this input. The builder validates the legal milestone transition and derives all those fields plus the appropriate embedded initialization, exact state anchor, or predecessor link. Installation remains digest-addressed and append-only through `writeManualCheckpoint`.

3. **Share retained-result authority**: Extract `prepareRetainedStateResult(input: PrepareRetainedStateResultInput): Promise<ProjectResult<PreparedStateResult>>` as the common normal/manual preparation seam, with an opaque `RetainedTaskAccounting` minted from either current state or `ManualAuthority`. Manual accounting sums each unique head-reachable manifest once, rejects an unreadable or disagreeing manifest, ignores stale normal state behind the selected checkpoint, and excludes only the exact reused result. Keep normal mode's existing one-shot `InternalResultInstallation` transaction capability; add `installManualRetainedResult(input: InstallManualRetainedResultInput): Promise<ProjectResult<InstalledManualResult>>`, whose opaque result is minted only after `installSnapshot` and the collision-safe projection plan both succeed and is bound in a private capability registry to the authenticated task, manifest, reference, and observed projections. `buildNextManualCheckpoint` resolves those private facts rather than inspecting caller JSON. A retry revalidates and reuses identical retained bytes, remints the capability, and attempts the checkpoint again; presence alone never authenticates a result. Document, implementation, and evidence paths use the same manifest builders, caps, secret checks, immutable result locations, and collision decisions as normal `archflow_state`; unreferenced prepared receipts, manifests, payloads, or projections remain non-authoritative.

4. **Emit exact fallback material**: Implement `buildManualFallback(input: ManualFallbackInput): Promise<ProjectResult<ManualFallbackOutput>>`, discriminated by `tool: "archflow_state" | "archflow_counter_review" | "archflow_adjudicate" | "archflow_gate" | "archflow_waiver"`. State unavailability yields a derived checkpoint action; counter-review yields a self-contained configured opposite-family prompt and stops for schema-valid evidence; adjudication yields an explicitly degraded pinned-input prompt whose failure or uncertainty opens a human gate; gate and waiver yield complete request/decision templates and stop until an atomic schema-valid decision is archived. The whole-server branch composes these same outputs rather than defining a sixth path, and every output includes the exact resume action.

5. **Adopt closed manual milestones without caller-authored authority**: Add `loadManualImportEvidence(input: ManualImportEvidenceInput): Promise<ProjectResult<AuthenticatedManualImportEvidence>>` and `reduceAuthenticatedManualChain(input: AuthenticatedManualChainInput): ProjectResult<ManualChainReduction>` in `src/state/manual-import.ts`. The MCP state handler loads the opaque evidence before routing an import and passes it to both mature-state `planCheckpointAdoption` and missing-state `runStateInitialization`; direct task/legacy initialization remains unchanged. The loader resolves every head-reachable result manifest, request/decision pair, waiver, and implementation output, verifies exact checkpoint bindings, and observes the committed target tree for implementation completion. The shared reducer may reuse `planStateTransition` for ordinary step movement, but it applies gate closure/retry effects only from authenticated archives and supplies the existing authenticated commit-authorization plus committed-tree proof for non-final advancement or final completion. Neither entry path copies approval, waiver, terminal, or gate facts from checkpoint JSON alone. An unresolved `open_gate` is not importable: compressed adoption cannot preserve its immutable `opened_at_revision`, so status returns the single action to finish, cancel, or supersede that interaction through the manual request/decision flow; only the resulting closed checkpoint chain may import. `buildCheckpointImportStateCall` derives the initial, state-anchored, or continuation wrapper, intent, CAS revision, fingerprint, and request digest through the same identification code as the handler. Restore remains limited to authenticated head-reachable results and the existing collision plan.

6. **Compose manual gates and supplemental review**: Add `advanceManualGate(input: ManualGateLifecycleInput): Promise<ProjectResult<ManualGateLifecycleResult>>` in `src/state/gates.ts`, and mint `AuthenticatedManualGateFacts` only by reloading the immutable request/decision/supplemental records, validating their exact bindings through `importGateDecisions` and the existing supplemental contracts, and associating them with the loaded `ManualAuthority`. Reuse `GateRequestV1`, `GateDecisionRecordV1`, `buildGateDecisionTemplates`, and `createManualGateFile` so request publication, optional counter-review ingestion, rejection/resume, accepted-change supersession, explicit decline, decision, waiver grant/denial, cancellation, and restart have the same milestone meaning as normal mode. The active files remain disposable interfaces; the non-colliding `decisions/<gate-id>/` archive and a checkpoint that reaches the opaque facts are authority.

7. **Expose the existing one-writer handoff protocol**: Add `inspectManualHandoff(input: ManualHandoffInput): Promise<ProjectResult<ManualHandoffResult>>` without changing `HandoffRecordV1`. Routine normal or pure-manual handoff is the documented human protocol: commit the authenticated checkpoint, push it, cleanly pull the selected branch in the next writer, then rerun `manual-status` and require Git head plus the selected state/checkpoint authority to agree before mutation. No routine handoff record is fabricated. Actual divergence continues to use `observeDivergentHeads` and the existing record; pure-manual repair preserves both heads and defers final record creation until server recovery adopts the selected checkpoint into state. Skills never merge, commit, push, or choose a successor.

8. **Wire helper and skills**: Extend `archflow-local` with exactly three helper-facing operations: input-free `manual-status`, input-bearing `manual-next`, and input-bearing `manual-handoff`. Only plain JSON selectors and source artifacts cross stdin. `manual-next` is the single orchestration boundary: in one process it loads `ManualAuthority`, prepares and installs or revalidates retained outputs, reloads and authenticates gate/evidence records when applicable, mints every opaque capability, calls `buildNextManualCheckpoint`, and installs the checkpoint before returning serializable paths/digests/status. `manual-handoff` likewise loads and consumes authority internally. No capability is emitted in CLI JSON or accepted from a later invocation; after interruption, a new invocation remints it from authenticated files and repeats only idempotent preparation before checkpointing. Rewrite the five workflow skills plus status so every unavailable MCP capability uses these emitted fallbacks verbatim, records every outcome before advancing, and reports both server-and-helper failure as repair-required with no manual inference. Do not add a sixth MCP tool, runtime dependency, error code, durable schema family, gate kind, or generalized recovery framework unless an existing contract proves unable to represent an acceptance path.

9. **Prove the complete recovery path and publish it**: Add focused unit, integration, and skill-contract coverage, then drive a fixture-backed multi-phase terminal workflow with each MCP capability missing in turn and with the server absent throughout. Leave exhaustive fault, path, file-kind, and adversarial matrices to Phase 20 and real-host evaluation to Phase 21. Rebuild both tracked bundles because shared runtime inputs change. After the final MCP digest is known, stop at a mandatory human gate: the existing `fast-uri@3.1.0` acceptance names `bundle-change` as an invalidator, so release evidence may be updated and reproduction may pass only if the user explicitly re-accepts the unchanged local-only exposure for that exact bundle. A decline or no decision leaves release staging blocked. Write the required implementation log and propose any durable task-independent conventions for the repository policy files without changing them before user approval.
