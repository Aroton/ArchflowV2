# Phase 12: Durable Gates, Waivers, and Manual Decisions

**Status**: DESIGNED
**Task**: mcp-integration
**Goal**: Persist every human authority boundary independently of a live MCP request.
**Requirements**: REQ-09, REQ-13, REQ-18, REQ-20, REQ-21, REQ-22, REQ-23, REQ-24, REQ-36, REQ-37, REQ-38, REQ-39, REQ-40, REQ-41, REQ-50

## Context

Phase 2 froze the gate vocabulary — nine kinds, per-kind contexts and decision payloads, cross-field validation in `validateGateDecision`, the `GateDecisionEnvelope`, `WaiverOriginRef`, `SupplementalReviewOutcome`, and the six `GATE_*`/`SUPPLEMENTAL_*`/`RESTORE_COLLISION` error codes. Phase 7 froze the state shape: `open_gate` is a single optional object so a nested gate is unrepresentable, `approvals`/`waivers` are sorted-unique sets, and it deliberately deferred *when* those may change. Phase 9's kernel freezes movement whenever `open_gate` is set (`transitions.ts:82`) and writes receipts for successful outcomes only. Phase 10 added `runStateInitialization`, the precedent for a sibling locked entry point that shares `TransactionDependencies`, authority, lock, atomic writer, and `validateDurableSemantics` without going through `runStateTransaction`. Phase 11 embedded the exact source artifact in `ResultManifestV1` so commit authorization can be bound to a retained `diff_digest` without request-lifetime memory, and left `ProjectionPlan.collision_choices` as a declared vocabulary with no applier.

Nothing in `src/` reads or writes `gate.json`, `gate.decision`, or `decisions/`; `atomic.ts`'s three class allowlists exclude both classes; `reconciliation.ts` compares `active_heads.gate` to `state.open_gate` but has no producer. The binding constraint is `lock.ts`: a 250 ms acquisition deadline, no liveness record, and an `AsyncLocalStorage` re-entrancy guard. A gate wait can be an hour long, so it must sit entirely outside `runExclusive` and must not be nested inside any locked section.

## What We're Building

A durable gate service in `src/state/gates.ts` that owns the whole lifecycle as **two locked bodies with an unlocked wait between them**. The open body CASes on the caller's `expected_revision`, derives the gate ID, and first asks whether this gate is already finished — a present closure record or a `committed_intent` naming this intent re-drives or replays instead of waiting, which is the branch `runStateTransaction` gets for free and this service must implement itself. Otherwise it verifies admissibility, writes the immutable `decisions/<gate-id>/request.json`, binds any interface bytes a crashed predecessor left behind, publishes `gate.json`, and commits a state revision carrying `open_gate` — so a caller-known deterministic gate ID exists before the call blocks. The wait then runs with no lock held and returns only a *signal*: it never carries decision bytes across the lock boundary. The resolve body reacquires the lock, re-reads both the archived request and the current `gate.decision`, validates and binds the decision against the request, derives the supplemental ledger from artifacts it can actually observe, archives an immutable closure record, writes the receipt, commits whatever authority that decision's effect actually grants, and only then clears the interface files. Restart, host timeout, cancellation, and disconnect all leave exactly the durable state the open body committed, so resume is the same code path as the first call.

Gate lifecycle is the *only* writer of `open_gate`, `approvals`, and `waivers`. Because it bypasses `runStateTransaction` entirely, the kernel gains a flat prohibition rather than a second privileged-planner escape hatch: `assertPreserved` starts rejecting any change to those three fields unless an authentic checkpoint-adoption plan is presented. Manual mode reuses the same archive: the helper library creates `decisions/<gate-id>/decision.json` with `archflow-local` provenance, the returning server resolves the live gate *from that record* before anything else, and only then may recovery import the remaining decisions into a manual checkpoint that the existing `planCheckpointAdoption` adopts.

## Gate Identity and File Contracts

| Item | Pinned definition |
|------|-------------------|
| `gate_id` | `` `g-${canonicalJsonDigest({schema_version:"1", digest_kind:"gate-identity", task_identity_digest, intent_id, request_digest})}` `` — 66 chars, a valid `PathSafeId`. New `computeGateId` in `src/contracts/fingerprints.ts` beside `computeRequestDigest`. Caller-computable before the blocking call. The waiver gate ID uses the identical formula over the `archflow_waiver` call's own intent and request digest. |
| `context_digest` | `canonicalJsonDigest({schema_version:"1", digest_kind:"gate-context", kind, context})`; for a waiver gate, over `{digest_kind:"waiver-context", origin, rationale}`. Written into `request.json`, `gate.json`, and `open_gate`; the MCP correlation layer never checks it, so **the resolve body is the sole binder**. |
| `decisions/<gate-id>/request.json` | New persisted root `GateRequestV1` (schema-only, no Zod mirror — server-internal). Immutable, `createExclusive`. Records gate ID, **`intent_id` and `request_digest`**, task/phase/kind, subject and context digests, the exact context, `current_evidence`, optional `supersedes`, allowed decisions, and `opened_at_revision`. Reuse is keyed on the identity fields, not whole-byte equality: `opened_at_revision` records the *first* archive and is never rewritten, so a crash between this write and the state commit followed by an unrelated transition does not turn a legitimate resume into a conflict. This follows Phase 11's rule that creation-time accounting is not restated when a later revision moves. The two identity fields are what let the open body tell "same intent, changed inputs" from "different intent". |
| `decisions/<gate-id>/decision.json` | New persisted root `GateDecisionRecordV1`, a closed four-arm union: `{outcome:"decided", envelope}`, `{outcome:"waiver-decided", granted, scope, origin, notes, human_provenance}`, `{outcome:"cancelled", reason, human_provenance}`, `{outcome:"superseded", supersession}`. Every arm also carries the `supplemental` ledger *derived under the resolve lock* — never copied from mutable `gate.json` — so triage survives the interface that displayed it without inheriting its trust level. Immutable, `createExclusive` — this is what makes "resolves exactly once" a filesystem property, and what makes the waiver's `granted`/`scope`/`notes`/provenance reconstructible after a crash. Cancellation, supersession, and the waiver decision live here rather than in the envelope because `GateDecisionEnvelope` is a nine-way union over `GateKind` with no arm for any of them. Needs a Zod mirror: it is parsed from untrusted file bytes. |
| `gate.json` | New `ActiveGateV1`; mutable, `replace`; exists only while a gate is open. Projection of the request plus the fill-in template and the supplemental ledger (ingested/triaged/declined evidence digests). An interface, never authority — losing it re-raises `SUPPLEMENTAL_REVIEW_REQUIRED`, which is the safe direction. |
| `gate.decision` | Canonical JSON bytes written by the human or helper via atomic rename, carrying either a `GateDecisionEnvelope`, the waiver grant/deny shape, or the explicit-cancellation shape — cancellation is a human act, so its producer is this file and not a tool argument. Because it is a *replaceable* interface a human may correct or cancel at any time, it is authoritative only as read under the resolve lock; bytes observed by the wait are a signal, never the archived decision. **No fourth renderer**: these bytes must be parsed and digested byte-exactly, so a Markdown form would need a parser back; `gate.json` carries the human-readable field list instead. |
| `open_gate` for a waiver | `OpenGateRef` gains optional `waiver_origin_gate_id`. Its presence is what marks the waiver gate; `gate_kind` carries the origin operation (`WaivableOperation ⊂ GateKind`). Tradeoff: one optional field on the Phase 7 schema (as Phases 8 and 10 both did) versus a `gate_kind` that cannot distinguish a waiver gate from an ordinary gate of the same kind. |
| `WaiverRef.scope` | Added. `WaiverRef` already duplicates rule id/version and subject digest from the archive; scope is the missing member of the same tuple, and "a grant resumes only the recorded rule/scope" is unenforceable without it. Written only after deep-equalling the archived decision's scope. `expires` stays the existing const `"task-complete"`, so writing it is mechanical and enforcing it belongs to the Phase 14 consumer. |
| Supplemental triage channel | New optional `GateInput.supplemental_outcome?: SupplementalReviewOutcome`, deliberately **excluded** from `RequestDigestSubject`'s closed `operation_fields` pick so a triage retry keeps the same `request_digest` and therefore the same gate ID. For the same reason `current_evidence` — which *is* in that pick — must be byte-identical across a supplemental retry; ingesting a review by adding its slot there would silently mint a new gate. Being caller-supplied and outside the digest, this field is an **assertion, not evidence**: an `ingest` or `triage-no-change` entry is admitted only if its evidence digest binds to a gate-counter artifact actually present for this exact gate, phase instance, and subject. A `decline` names no artifact by REQ-41 and is recorded explicitly as a caller assertion, so the closure record never implies a review occurred. |

## Work Breakdown

1. **Unblock the contract types, then pin the three gate roots**: Convert the ten `interface` declarations named in the Files table to `type` aliases and confirm `CanonicalDocument<GateDecisionRecordV1>` compiles *before* writing any schema against them. Then walk the persisted-root recipe for `GateRequestV1`, `GateDecisionRecordV1`, and `ActiveGateV1`, add the two `fingerprints.ts` derivations and the optional `GateInput` field, and close the `restore-collision` path-schema hole. `validateDurableSemantics` correlates a supplied request/decision pair: same gate ID, task, phase instance, kind, subject digest, and context digest, and a decision payload that survives `validateGateDecision` against the *archived* context — except the `waiver-decided` arm, which takes the parallel origin-binding check pinned in chunk 6 because a waiver context is not a `GateContext<K>`.

2. **Amend the state shape and close the kernel**: Add `OpenGateRef.waiver_origin_gate_id?` and `WaiverRef.scope` across the JSON Schema, the type, and the checkpoint Zod mirrors. Then make `assertPreserved` reject any difference in `open_gate`, `approvals`, or `waivers` unless the existing checkpoint-adoption authenticity check passes. Add the missing test for the `transitions.ts` open-gate movement freeze, which today has none.

3. **Add the two storage primitives**: `createExclusive` admits `decision`; `replace` admits `gate-interface`; a new narrow removal accepts `gate-interface` only. `ensureDecisionDirectory` mirrors `ensureIntentDirectory`'s lstat plus `O_NOFOLLOW|O_DIRECTORY` verification for the one caller-named `decisions/<gate-id>/` child.

4. **Open body, including the replay branch**: Under `runExclusive`, re-read state, verify repository identity and the caller's `expected_revision`, and derive the gate ID. Before anything else, read `decisions/<gate-id>/decision.json` and the intent receipt. A present closure record is resolved against current state by this four-case matrix, which exists because a closure legitimately outlives the state that opened it:

   - matching live `open_gate` — finish resolution from the record;
   - `committed_intent` naming this intent — authenticate and replay the recorded outcome;
   - state advanced past it — `INTENT_NOT_CURRENT`, touching neither state nor whatever gate it now names;
   - no live gate at all, i.e. a fully manual request/decision pair — hand to chunk 8's authenticated adoption path, never resolve silently here.

   With no closure record, classify against `open_gate`, reading the request archived for the gate `open_gate` **actually names** rather than the newly derived path — changed inputs derive a different gate ID and therefore a different directory, so the derived path cannot find the older request. If that archived request carries the caller's `intent_id` under a different `request_digest`, return `INTENT_MISMATCH`/`create-fresh-intent`; only a genuinely different intent is `GATE_ACTIVE`; the same gate ID goes straight to the wait. **Documented limitation**: when a prior gate closed without a success receipt (cancelled or superseded), neither `open_gate` nor a receipt survives to locate its request, so changed reuse of that `intent_id` opens a fresh gate instead of returning `INTENT_MISMATCH`. Closing that gap needs an intent-to-gate index nothing else in this system wants; no approval is fabricated and the fresh gate still demands its own human decision, so the residual gap is REQ-23 classification hygiene rather than a trust-boundary failure.

   Then verify kind-specific admissibility — for `commit-authorization`, the context's `diff_digest`, artifact digests, and parent-document digests must match the retained `ResultManifestV1` for the current authoritative produce result, loaded from its embedded source artifact. Write `request.json` (`createExclusive`); **bind rather than delete** any `gate.decision` a crashed predecessor left behind — bytes that bind to this gate's archived request *are* this gate's decision and resolve from there, and only bytes proven to belong to another or already-closed gate are removed, because blind removal would destroy a decision a human validly wrote in the window after `gate.json` was published but before state named it. Publish `gate.json`, then commit state carrying `open_gate`.

   Pin that this revision writes **no intent receipt and clears `committed_intent`**. Phase 9 pins receipts to successful outcomes only and a pending gate is not one, while retaining the old binding would make `durable.ts`'s rank-8b whole-state deep-equal fail for the rest of the gate's life — turning every `reconcileCurrentAuthority` call into a false `receipt-invalid` and every replay of the previous intent into `STATE_INVALID`. Clearing it instead degrades that replay to `INTENT_NOT_CURRENT`, which is both true and safe.

5. **Wait**: `waitForGateInterface(input): Promise<GateWaitOutcome>` in `gate-wait.ts`, where `GateWaitOutcome` is `{kind:"interface"}` | `{kind:"supplemental", evidence_digest}` | `{kind:"aborted"}`. It returns a **signal, not bytes**: `gate.decision` is replaceable, so a human may correct or cancel between the poll observing it and the resolve body acquiring the lock, and two waiters could otherwise carry different generations. Having resolve do the authoritative read under the lock removes that whole class of question and is less machinery than passing bytes across the boundary. **Poll-only**, at a named 500 ms constant, with an explicit `once` abort listener and no deadline of its own — the host owns the timeout. At 500 ms the response is imperceptible to a human walking to a second terminal, and polling is the only mechanism that works uniformly across native Linux, macOS, and WSL2 `/mnt/c` where inotify does not propagate; a watcher would have been a latency optimization guarded by a fallback that had to exist anyway. The wait signals on a complete projection; canonical parsing and `GATE_DECISION_INVALID` belong to the resolve body, which leaves the gate pending on a parse failure so a fixable file never strands it. A gate-counter review is surfaced only when its evidence digest is absent from `gate.json`'s ledger — that projection is a de-duplication filter here, not authority, and resolve re-derives the ledger regardless.

6. **Resolve, cancel, supersede**: Reacquire the lock and CAS **on gate identity rather than `expected_revision`** — `open_gate` freezes every other transition, so the revision cannot move under an open gate except through this service. Re-read both `request.json` and the current `gate.decision` from disk and discriminate there; the wait's signal is never trusted as content. A decision envelope is bound to the archived request on all of gate ID, task, phase instance, kind, subject digest, context digest, and human provenance, then checked by `validateGateDecision` against the archived context. A waiver decision takes the parallel waiver-specific binding step instead — rule, subject, evidence-set digest, and scope must deep-equal the archived `WaiverOriginRef` — because the waiver context is not a `GateContext<K>` and `parseGateContext` inside `validateGateDecision` would throw on it. A cancellation shape archives `{outcome:"cancelled"}` and returns `GATE_CANCELLED`; abort or disconnect writes nothing at all, leaves the gate pending, and returns dispatch `CANCELLED`.

   **What a decision grants is `gateDecisionEffect`'s answer, not this service's.** Reuse that existing classifier rather than restating the vocabulary: `advance` is the only effect that appends an `ApprovalRef` — or, for a grant, a `WaiverRef` — and earns a success receipt. `retry`, `redirect-waiver`, `redirect-upstream`, and `non-advancing` archive their closure and clear `open_gate` without touching `approvals` or `waivers`, and return a non-success outcome. Every explicit outcome is archived; only outcomes that actually grant authority reach those two sets, because recording a `revise`, `reject`, or `abort` as an approval would corrupt durable authority. Cancellation and supersession are not `archflow_gate` success payloads at all.

   Order is archive → receipt where the effect earns one → state → remove `gate.json` and `gate.decision`. Archiving strictly first means a crash can leave a record that commits nothing, but never a commit whose approval names a missing record. The archived closure carries the ledger **derived in this body** from artifacts it can observe, never copied from mutable `gate.json`.

   `GateInput.supplemental_outcome` carries the triage verdict into this body, and it is a caller assertion outside the request digest, so it is admitted only against what this body can observe: `ingest` and `triage-no-change` require their evidence digest to bind a gate-counter artifact actually present for this exact gate, phase instance, and subject — a claim naming absent or non-binding evidence fails rather than suppressing the re-raise. `decline` names no artifact by REQ-41 and is recorded as an explicit caller assertion. All three append to the derived ledger, leave the gate pending, and resume the wait so the same evidence never re-raises. `supersede` archives `{outcome:"superseded"}`, clears `open_gate`, and records no approval, requiring a fresh intent and therefore a fresh gate ID for the new subject. If the structured source behind the rendered `reviews/<phase-instance>.gate-counter.<gate-id>.md` projection is not server-readable until Phase 15 wires the local helper, say so where the seam is pinned and verify the projection's own digest binding rather than implying more.

7. **Waiver sequencing and restore-collision application**: A `waiver-requested` decision is non-advancing: it resolves and archives the origin gate and clears `open_gate` before `archflow_waiver` opens the sole waiver gate through the same two bodies, so no nested gate is representable. A grant appends a `WaiverRef` whose rule, subject, and scope deep-equal the archived origin; a denial appends the same record with `granted: false` and advances nothing. For `restore-collision`, apply on top of Phase 11 rather than around it: `discard-and-restore` re-runs `prepareProjectionPlan` over exactly the gated declared paths with the now-observed image as the authenticated before — which classifies the entry `restore-ready` instead of `collision`, so the refusal at the top of `applyProjectionPlan` is never reached — requires that re-observation to still hash to the context's `current_generation_digest`, and then applies. `adopt-as-new-generation` performs no worktree write at all: the candidate is minted at open only when the caller's changed fingerprint differs from the recorded generation's, `validateGateDecision` already forces the payload to deep-equal it, and the new generation is created by the caller's next producing transition under that changed fingerprint. `abort` writes nothing and closes the gate non-advancing. Phase 12 constructs every plan itself inside the locked body, so `ProjectionPlan` stays unbranded — a brand would guard a value that never crosses a trust boundary.

8. **Manual decisions, import, and the reconciliation head**: Library functions (Phase 15 wires the CLI) that create `decisions/<gate-id>/{request,decision}.json` with `archflow-local` provenance under the same no-clobber create, so repetition is impossible and multiple non-colliding gate IDs coexist. Ordering is load-bearing: `planCheckpointAdoption` drives every checkpoint through `planStateTransition`, which refuses to move while `open_gate` is set, so the returning server must first resolve the live gate through chunk 4's archive branch. `importGateDecisions` is therefore scoped to gates with no live `open_gate`; it takes caller-supplied validated records plus current state and returns only the approvals and waivers whose records are complete, whose digests bind their request, and whose gate IDs are absent from state — absence is never agreement, and adoption itself remains `planCheckpointAdoption`. Finally supply `active_heads.gate` for `reconcileCurrentAuthority` from `gate.json` plus the archived request, extend its comparison to `context_digest`, and make it treat an absent `committed_intent` above revision 1 as the normal open-gate condition rather than an anomaly.

9. **Prove the boundaries**: Contract tests for the three roots, registry and Zod-agreement coverage, and every rejection class. Unit and integration tests for admissibility, binding, exactly-once resolution, waiver sequencing, the three restore decisions, and **every arm of the decision vocabulary against the effect matrix** — no non-advancing outcome may reach `approvals` or `waivers`. Cover the four-case closure matrix, an unbound supplemental claim failing rather than suppressing, and a decision replaced between the wait's signal and the resolve lock. Two-process tests for conflicting opens and resolves on one task and independent waits on two tasks; state the expected contender outcome honestly rather than assuming `STATE_CONFLICT` — see the note in Verification Steps. Abort-driven and real process-kill resume fixtures.

## Success Criteria

- [ ] A call blocks until a schema-valid exact decision or an explicit cancellation/failure, and never returns pending as success; killing the process or aborting mid-wait leaves exactly one pending gate that a later call with the same intent resumes.
- [ ] Partial, malformed, non-canonical, stale, wrong-task, wrong-phase, wrong-gate-ID, wrong-subject-digest, wrong-context-digest, duplicated, and approval-shaped constitution-edit decisions all fail to resolve or advance the gate; one valid decision resolves it exactly once, a replayed call returns the recorded outcome instead of re-opening, and no second `ApprovalRef` for one gate ID is ever appended.
- [ ] Two processes cannot open or resolve conflicting gates or waivers on one task; the loser writes nothing and receives a classified non-advancing failure; two tasks wait concurrently with neither holding a lock.
- [ ] No non-advancing decision reaches `approvals` or `waivers`: every arm of the decision vocabulary lands where `gateDecisionEffect` says it does, and a `revise`, `reject`, or `abort` archives a closure without granting authority.
- [ ] A decision a human writes into a live `gate.json` window that state does not yet name survives the retry instead of being deleted as stale, and a decision replaced between the wait's signal and the resolve lock is archived as the human last left it.
- [ ] Manual files record several non-colliding gates, one waiver, supplemental review and decline, and commit authorization; a server-opened gate is resolved from its manual `decision.json` before adoption, and import then adopts only complete records, skips gate IDs already in state, and is idempotent across repeated runs.
- [ ] A `SUPPLEMENTAL_REVIEW_REQUIRED` retry after an intervening transition reuses the same intent and request digest with a refreshed `expected_revision` and unchanged `current_evidence`, and resolves the same gate ID; an accepted-change supersession closes the old gate, records no approval, and forces a fresh intent and gate ID.
- [ ] `waiver-requested` advances nothing and archives its origin gate before the sole waiver gate opens; a grant resumes only the recorded rule and scope, a denial advances nothing, and no state is reachable in which two gates are open. `restore-collision` exposes only `discard-and-restore`, `adopt-as-new-generation` with changed inputs and a rationale, and `abort`.
- [ ] An aborted invocation standing in for a host timeout leaves one pending gate, and a later in-process invocation resumes and resolves it exactly once — timeout-then-resume is the tested normal path, with real-host timing proved in Phase 21.
